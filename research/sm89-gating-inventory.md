## Notes on interpretation (explicitly my analysis, not quotes)

1. **sm89 is not "no FP8".** It has FP8 tensor cores and a usable per-tensor/per-channel FP8 W8A8 path in vLLM (`cutlass_2x_gemm<arch::Sm89, …>`) and SGLang (`cutlass_fp8_supported()` returns true for `(8,9)` on CUDA ≥ 12.4).
2. **The real sm89 tombstone lines are:**
   - **block-scaled FP8 (MXFP8 / per-32 `ue8m0`) — HARD OUT.** PTX gates warp-level `kind::mxf8f6f4.block_scale` to `sm_120a`; PTX gates the datacenter `tcgen05.mma` form to `sm_100a/sm_101a`. vLLM's `cutlass_scaled_mm_supports_block_fp8` returns false below CC 9.0; TensorRT-LLM's matrix marks Ada FP8(block scaling) as "."; SGLang's `cutlass_fp8` MoE asserts SM90/SM100/SM120.
   - **`wgmma` — HARD OUT** (`Requires sm_90a`, on every wgmma section).
   - **TMA / `cp.async.bulk` / thread-block clusters / DSMEM / cluster barriers — HARD OUT** (all "Requires sm_90 or higher" or "Compute Capability 9.0 introduces…"). `cp.async.ca/.cg` (sm_80+) *is* available, which is why Ampere-style pipelines still work on Ada.
   - **FP4/FP6 MMA — HARD OUT** (`.e3m2/.e2m3/.e2m1` warp MMA requires `sm_120a`; `tcgen05` is `sm_100a`).
   - **FA3 — HARD OUT** (Hopper-only; vLLM falls back to FA2 on sm89).
   - **CUTLASS 3.x collectives — not implemented for sm89** (no `sm89_*` builder); Ada FP8 goes through the CUTLASS **2.x** API and needs **CUDA ≥ 12.4**.
3. **Two sm89-specific performance deltas that are easy to miss:**
   - FP8 with **FP32 accumulate** runs at half the FP16-accumulate rate (330.3 vs 660.6 TFLOPS dense), per the Ada whitepaper Appendix A footnote 4.
   - CUTLASS needs a distinct `OpMultiplyAddFastAccum` tag for sm89 FP8 ("staged accumulation is not to be used … valid only for SM89 FP8 kernels"), which is why the FP8 accumulation code path differs.
4. **Careful with "block scaling" wording.** CUTLASS's `94_ada_fp8_blockwise` example is an sm89 kernel with `BlockSize = 128` and `ElementScale = float` applied around the MMA via the 2.x API. That is *not* the hardware per-32 `ue8m0` block-scale (`kind::mxf8f6f4`, `scale_vec::1X`). Do not cite it as evidence of MXFP8 on Ada.
5. **On 2× 4090, no NVLink and no PCIe P2P.** The measured `p2pBandwidthLatencyTest` off-diagonal of ~30.9 GB/s in the P2P-disabled matrix is roughly the PCIe Gen4 x16 per-direction ceiling (32 GB/s), consistent with a memcpy pattern that reads from GPU0 and writes to GPU1 over two independent links. Treat ~30.9 GB/s as the measured, driver-disabled number and note that the test labels the matrix "Bidirectional". I am **not** claiming a precise host-staging halving factor from this test alone; the authoritative staging statement is NCCL's `NCCL_SHM_DISABLE` text ("host memory is used").
