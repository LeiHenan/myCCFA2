## 三、一等判据（新增，全部在花 GPU 之前）

### 判据 1：S3b 已解决性核查（跨引擎 × 跨社区）
判据正文见 `pipeline/gates.json` 的 `S3b`；视图命令：
```bash
python pipeline/gate.py S3b --dir candidates/<slug>     # 判据 + 勾选 + 阻塞
python pipeline/solved_scan.py --keywords "…" --repos …  # 生成待查清单（manual/api/offline）
```
**硬要求**：判定矩阵 ≥5 行、覆盖 ≥3 个引擎/实现 + ≥2 个研究社区、每行带 URL 与**查证深度**；
**任一对象已 ship 或已发表同一问题类的同等解法且差异轴讲不出条件性区别 ⇒ 杀**；
矩阵不足或未读正文 ⇒ **禁止进入 S4（不许开 GPU）**。

### 判据 2：差异轴必须是**条件性**的（不是程度性）
写"我们更自适应 / 更快 / 更省"**不算**。必须写成：
> 「最近邻做了 X，在**条件 C** 下它覆盖不到 Y；我们做 Y，因此**当 C 成立时**结论不同。」

**若写不出 C，或 C 在本机不可复现 ⇒ 杀。**

### 判据 3：收益必须过**整机账**（本轮新增，来自 `sglang-draft-corpus` 的教训）
任何"可回收性"主张，除热路径的干预前后对照外，还必须给出**含获取成本的总账**：
```
T_baseline(n) = n · t_base
T_intervention(n) = C_setup + n · t_int
盈亏平衡 n* = C_setup / (t_base − t_int)
```
**判据**：必须在**目标部署形态的 n** 上 `T_intervention < T_baseline`，并把这个 n 的**依据**写出来
（副本寿命 × 请求率）。**若收益只存在于"引擎自带机制已经覆盖的区间" ⇒ 判为工程配置，杀。**

### 判据 4：可持续性（"业界会不会在 12 个月内自己解决"）
对每个候选问一句：**这条约束/负载正在以什么速度变化？已 ship 的解法会不会在 12 个月内自然失效？**
- 若答案是"会"（例如上游 roadmap 已在推进、且该方向只有 1–2 个 PR 的距离）⇒ **降低优先级**；
- 若答案是"不会"（**结构上**难，例如需要跨系统语义、需要新的度量、或与现有抽象冲突）⇒ **提高优先级**。
- 依据必须落到**可核事实**（PR 距离、抽象冲突点、roadmap 条目），不是印象。
