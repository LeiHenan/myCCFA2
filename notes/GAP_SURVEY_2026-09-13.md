## 二、唯一仍可细分的区域：#4 测量方法学 —— 但要打对靶子

|---|---|---|

## 四、本工作区已有的四条**可复现**的度量伪影（自有证据，逐条可重跑）

| # | 伪影 | 本工作区实证 | 影响 |
|---|---|---|---|
| A1 | **`--dataset-name random` ⇒ 接受率恒为 1.00** | `#6` T0 期间的实测记录（decision #47–#50 段）；随机 token 必然被接受 ⇒ 投机解码"看起来免费" | 接受长度与吞吐被**根本性高估**；用它做的对比全部失真 |
| A2 | **暖机爬升随配置变化 ⇒ "N 次均值"系统性偏置赢家** | A1 网格 120 格逐次数据：bs=1 时 d5 爬 **11–13%**、d1/d3 只爬 6–7%；改稳态口径后差距从 25.6–32.6% 变 **26.3–31.8%**（decision #66） | 报告值被系统性压低，**且偏置方向与配置相关** ⇒ 排序会被扭曲 |
| A3 | **冷/热双峰 ⇒ 重复次数少时均值无意义** | A3 对照：同格三次重复 661/669/**1389**、750/757/**1941**（2–2.6×）（decision #65） | 3 reps 的结论不可靠 |
| A4 | **`mean_itl_ms` 是"每步"而非"每 token" ⇒ 每步代价被误算 accept_len 倍** | 18/18 格实测 `tpot ≈ itl/accept_len`；初版分析器就写错了这一步，**自测当场抓到**（decision #67） | "每步代价"是深度/长度权衡分析的核心量，误算会得出相反结论 |

**这四条的共同点**：它们都在**引擎给出的默认工具链口径内**，不需要特殊硬件，任何人按官方示例都会踩到；而且**每一条都能单独把结论带偏**。

## 五、选定方向

> **`specbench-methodology`** —— 投机解码/MTP 服务评测的方法学：把「接受长度 / 每步代价 / 暖机状态 / 服务端可观测性」这组量的度量口径系统化，量化它们的伪影，并给出可直接采用的正确口径与检测方法。

**为什么选它**：
1. 地图上**唯一未被同靶子占据**的区域（2605 打客户端、2608 打行为副作用、Illusion 打宏观趋势）；
2. 有**独立的实践侧疼痛证据**（论坛两帖 + 官方 doc PR + 服务端缺指标）；
3. 本工作区已有**四条可复现伪影**作为起点（不是从零猜痛点）；
4. **单卡可做**：不需要多机、不需要训练、不需要专有 trace，96 GB 卡足以；
5. **有 MLSys 先例**：*Performance or Illusion?* 是 MLSys'26 **oral** ⇒ 这个 venue 认这类工作。

**风险（写下来，供 S2/S4 打）**：
- ⚠️ 形态⑥「本质是个工程配置/文档问题」：若结论只是"用真实文本 + 多跑几次"，则退化为 best-practice 清单 ⇒ 必须给出**机制性解释**与**可迁移的检测方法**（例如"如何在不看源码的情况下判断一个报告的接受长度是否可信"）。
- ⚠️ 形态⑤「上界」：必须算出「伪影能把结论带偏多少」的**上界**（≥8% 才做）。
- ⚠️ 与 2605.24217 的重叠：必须在 S3 读其正文，逐条划清靶子边界。

## 七、测绘第 2 轮计划（2026-09-13 追加）：**换对象，而不是换题目**

### 第 1 轮 + 两个候选的实测教训（都是钱和时间换来的）

| 教训 | 证据 |
|---|---|
| **LLM 服务引擎这一层已饱和** | 8 区域里 7 个被占；hybrid state 被 4 天前的 RFC 占住（decision #73） |
| **"找引擎的 bug/不自洽"是低产策略** | 我们造了自检器去查 vLLM 0.29 的投机指标 ⇒ **0/24 违规，引擎数值自洽**（decision #76）；两条"违规"全是**我自己的仪器 bug** |
| **评测方法学层也被占** | 2605.24217（客户端 21%/50% 伪影）、2608.04714、Performance or Illusion |
| **闸门很有效** | 三个"看起来能写"的方向（hybrid-state / specbench / P1 暖机口径）全在花大钱前被杀，**总 GPU 花费 <0.5 GPU·h** |

**⇒ 结论：问题不在于"还没找到那个题目"，而在于"这一层已经被高强度维护与占领"。**
继续在 LLM 服务引擎里找痛点 = 与一个每周都在发 PR 的社区赛跑。

### 第 2 轮策略：**换研究对象（object），保持同一套判据**

不再问"LLM 服务的哪里疼"，改问"**哪些 ML 系统负载的系统研究密度显著低于 LLM 服务，但负载本身正在快速变大**"。候选对象（按"系统关注度低 × 负载增长快"排序）：

| # | 对象 | 为什么可能仍空 | 单卡/多卡可做性 |
|---|---|---|---|
| 1 | **扩散 / 视频生成服务**（DiT、步数缓存、CFG 批处理、并行采样） | 系统研究远少于 LLM；视频生成负载正在爆炸式增长 | 96 GB 单卡可跑 SD3/Flux 级；多卡可上视频模型 |
| 2 | **多阶段 RAG / 多模态流水线联合调度**（retriever+reranker+generator 的端到端调度） | 各段有优化，**端到端联合调度**少人做 | 单卡 + CPU 检索可做 |
| 3 | **推荐系统推理**（超大 embedding 表、稀疏+稠密混合、多阶段级联） | 经典方向，但系统论文多在公司内部；公开研究密度低 | embedding 表可 CPU/GPU 混合 |
| 4 | **语音 / 实时流式推理**（ASR/TTS 的流式延迟与批处理） | 实时约束与 LLM 服务不同（有硬 deadline） | 单卡足够 |
| 5 | **向量检索服务**（ANN 索引与更新、召回-延迟权衡） | 与 RAG 强相关且被部分覆盖 | 单卡可做 |
| 6 | **训练侧非 RL 瓶颈**（长上下文/多模态训练的 I/O 与显存） | RL 交界已饱和，但**预训练数据管道/检查点**未被同等关注 | 需多卡，成本高 |
| 7 | **端侧 / 异构推理**（量化、NPU、内存墙） | 硬件依赖强，我们只有 NVIDIA | 可做但受限 |

**第 2 轮执行规则（继承第 1 轮的教训）**：
1. **占位快扫与痛点收集同时做**（decision #73 的规则）；
2. 每个对象先回答三问：**谁在疼（有数字吗）？引擎/框架里已 ship 了什么？若被占，降级成什么？**
3. **不碰已被占的靶子**：LLM 服务引擎内部、客户端评测方法学、RL rollout 交界、agent 会话调度；
4. 通过 S3 的候选才做 S4 上界（**上界 <8% 直接杀**）；
5. 单卡可做优先（成本可控），多卡只在必要时用。

**成功判据（与 goal 一致）**：产出 1 个通过 S0–S5 全部闸门、并在服务器上验证过的候选；若第 2 轮仍全部被否，则输出一份"哪些对象层仍空/已满"的完整地图作为结论。

## 八、测绘第 2 轮结果（2026-09-13 执行）：**16 个对象全部有占位者；"找未被治的痛点"这一策略已系统性失效**

### 第 2 轮对象逐个核查（每个都命中 2026 年的占位者）

| 对象 | 占位者（2026） | 判定 |
|---|---|---|
| 扩散 / 视频生成服务 | **BlockServe**（block-grained continuous batching for diffusion LLM serving）、**GenServe**（异构扩散负载共服务）、**Sol**（视频生成全栈加速） | 🔴 被占 |
| 多阶段 RAG / 流水线运行时 | **OpRAG**（资源确定性运行时）、**Scepsy**（agentic workflow 的 aggregate LLM pipelines）、**CrossPool**（**跨模型**批调度 + KV/权重解聚）、**RAGPerf**（端到端 RAG 基准） | 🔴 被占（4 篇） |
| 推荐系统推理 | Latency-Bounded **Embedding Table Partitioning** Across Heterogeneous Accelerators；**ServerlessRec**（解聚内存） | 🔴 被占 |
| 语音 / 流式推理 | **VoxServe**（统一流式推理）、**PACE**（全双工语音的 playback-aligned context engine） | 🔴 被占 |
| 向量检索服务 | **AdaptIndex**（自适应索引选择）、**Puffin-Backed Vector Indexes**（计算解聚查询引擎） | 🔴 被占 |
| 多模态 / Omni 流水线 | **LiveServe**（交互感知的实时 omni-modal 服务）、**FlashRT**（实时多模态 agent harness） | 🔴 被占 |
| 训练侧（非 RL） | **InfiniPipe**（变长语料的弹性流水线并行 + chunk 级自适应梯度检查点） | 🔴 被占 |

### 更关键的发现：连"审计/反证"这一体裁也已被占

我评估了三条替代策略，并逐条做了占位核查 —— **三条都撞墙**：

| 策略 | 想打的靶子 | 撞到了谁 |
|---|---|---|
| **(A) 审计一个"承重假设"** | "prefix caching 什么时候**不**划算"（break-even 边界） | **The Economics of Context Caching — Cost Models and Break-Even**（Zenodo）；**agentic-kv-cache**（在 **68k 真实请求 / 393 个 Claude Code 会话**上复现 KV 淘汰策略主张，结论是"**LRU 比论文说的更难打败**"）；**Same Request, Different Answer**（缓存导致的分歧） |
| **(B) 抢先刻画"已 ship 但无人研究"的新特性** | vLLM 0.29 的 `use_replayssm` / `replayssm_buffer_len` / `use_kda_recoverssm` | 特性本身极窄（仅 Mamba2 / Kimi-K3），**影响力天花板低**；且其所在区域刚被 RFC #55697 占住（decision #73） |
| **(C) 组装现有部件 + 强评估** | 面向 agent 的多轮 KV 生命周期管理 | **Continuum**（KV TTL 调度）、**Scepsy**、**SkillRouter**、**SpecNet-Agent** 已占；新颖性风险最高 |

### 战略结论（本轮最重要的产出）

> **在本工作区可触及的范围（LLM/多模态/推荐/语音/检索/训练系统）内，"找一个别人还没治的真痛点"这一策略已经系统性失效。**

证据链：两轮共 **16 个对象**、**每条痛点都命中 2026 年的 1–4 篇占位者**，其中多篇是**最近 1–3 个月**的；连"审计别人"的体裁也被 agentic-kv-cache（68k 真实 trace 复现）与若干测量论文占据。原因不是我们搜得不够，而是：**ML 系统的发表密度已经超过"可被一天文献调研发现的痛点"的消耗速度**。

**这不等于"没有课题可做"，而等于"课题的定义必须换"**：

| 换法 | 含义 | 风险/成本 |
|---|---|---|
| **① 换痛点来源：从"文献里的疼"改为"你自己环境里的疼"** | 唯一可能真正未被占据的来源是**你实际踩过、且文献里查不到的疼**（本工作区的 E1/D3 就是这么来的，虽然最后判了无 headroom，但**它们是真实的、无人做过的**） | 低（几乎零成本），但**必须由用户提供输入** |
| **② 接受"正常科学"：有人在做，我们在某差异轴上更强** | 需要真正的系统实现能力与更强基线，执行风险高 | 中–高 |
| **③ 换领域**（非 LLM 系统：科学计算、数据库、图、时序…） | 系统研究密度确实更低，但我们**没有积累**，且需重新建立环境 | 高（学习曲线） |

**推荐 ①** —— 它同时满足用户最硬的两条要求（"真实的待解决问题"+"真的可以做"），且是本工作区**唯一验证过能产出真实、无人做过结论的路径**（E1 的 `R_byte` p95 = 0.072% 与 D3 的 1.0053 都是文献里没有的数字）。
