Purpose

Under speculative decoding, _gqa_sparse_decode_kernel launches one program per
(query token, top-k chunk). A verify step carries decode_query_len (dnum) query rows per
request, so each request's selected KV blocks are re-streamed dnum times — once per draft row —
even though adjacent draft rows sit within one 128-token page of each other and select heavily
overlapping blocks.

Reported in #47763. This is an RFC / draft: the kernel is correct and I have measurements, but
it is not a win everywhere yet and I would like input on two design questions before polishing.

This adds _gqa_sparse_verify_decode_kernel, which keeps the request on the grid axis instead
of the query token, loads each selected block once, and sweeps all dnum rows against it with one
tl.dot. Two properties make that work:

  • Exactness. Top-k is chosen per query token, so rows of a request do not in general agree. The
    kernel iterates the union of the rows' block lists and carries a per-block row bitmask,
    applying membership alongside the causal bound — row r attends to exactly the blocks it
    selected. This is the same computation the existing kernel performs, not an approximation.
  • Occupancy. Q-tiling collapses the grid from total_q to num_reqs, which starves a large GPU
    at serving batch sizes. Split-K over the union restores it, cut over the runtime union size so a
    request whose rows overlap heavily does not leave most of its chunks empty. Without this the
    kernel is slowest exactly when the underlying idea works best.

The union is built by a fused Triton kernel (one program per (head, request), O(MAXB²)
first-occurrence test in registers). A torch.sort + scatter_reduce formulation cost ~190 µs
against a ~15 µs attend — it runs once per sparse layer, so it dominated completely and made the
whole change a 5–6× regression. Worth flagging for anyone attempting the same thing.

Test Plan

Two tests added to tests/kernels/attention/test_minimax_m3.py:

  • test_verify_decode_matches_per_token_decode — parity against
    minimax_m3_sparse_attn_decode over seq_lens_list ∈ {(130,257),(129,200,384)},
    decode_query_len ∈ {1,2,4}, num_padded_reqs ∈ {0,2}, num_chunks ∈ {1,4}. Reuses the existing
    _build_decode_inputs, which randomises each row's top-k independently — the adversarial case for
    the union path, since rows share almost nothing.
  • test_verify_block_lists_union_and_mask — the union is exactly the distinct ids and bit r is
    set iff row r selected that block, including a padded -1 slot that must be dropped rather than
    used to index the block table.
pytest tests/kernels/attention/test_minimax_m3.py -k "verify_decode or verify_block_lists"

Standalone parity + benchmark against the shipped kernel at MiniMax-M3's per-rank serving shape
(1 KV head, GQA 8, head_dim 128, topk 16, 80K context, dnum 8), CUDA-graph timed.

Test Result

Correctness — H100, vLLM 0.25.1, 6/6 shapes match the existing decode kernel:

batch dnum kv chunks padded max rel diff
13 8 fp8 8 0 7.4e-3
16 8 fp8 8 0 6.8e-3
30 8 fp8 8 0 6.0e-3
16 4 bf16 4 0 3.4e-3
8 2 fp8 1 0 7.3e-3
16 8 fp8 8 2 6.7e-3

(Residual is fp8 rounding; the bf16 case is 3.4e-3.)

Performance — fp8 KV, dnum=8, 80K context. ρ is the fraction of top-k entries the draft rows
share, swept because the real value is unmeasured and the exact contract's win is exactly that
overlap:

batch ρ=0.0 ρ=0.5 ρ=0.75 ρ=1.0
13 0.33× 0.47× 0.62× 0.76×
16 0.35× 0.38× 0.57× 0.76×
30 0.46× 0.59× 0.68× 1.29×
64 0.58× 0.80× 1.03× 1.48×

With the union prebuilt outside the timed region (i.e. the attend alone), the same kernel reaches
2.4× at batch 16 and 3.5× at batch 30 at ρ=1.0 — so the attend itself is doing what it
should, and the remaining gap is the union build, which is itself occupancy-starved at
num_reqs × num_kv_heads = 16 CTAs.

Separately, measured on the shipped kernel: the duplicate loads cost no HBM bandwidth — at
batch 64/bf16 the shared-top-k case would require 6.11 TB/s on a 3.35 TB/s part, so L2 is absorbing
them. At fp8 the attend is not bandwidth-bound at all (~50% of peak either way); it is gather- and
issue-bound, which is why removing issued loads helps where removing bytes does not.

Open questions

  1. Is the exact contract the right one? A shared per-request selection needs no union at all and
    would be a guaranteed dnum-fold reduction, but row 0 sits at an already-accepted position, so
    its attended blocks would depend on what later speculative rows wanted — speculative decoding
    would stop being output-equivalent to non-speculative decoding. I have deliberately not done
    that; it seems like a decision for maintainers rather than a kernel author.
  2. What is the real ρ? Everything above turns on how much adjacent draft rows' top-k sets
    actually overlap, which nobody has measured. At ρ ≥ ~0.75 this is a win at batch ≥ 30 today.
    If someone has an M3 spec-decode deployment, instrumenting topk_indices_buffer for one verify
    step would settle it.

Not done

  • Not wired into MiniMaxM3SparseImpl; this is the kernel plus tests only.
  • CUDA-graph capture not yet validated with the union-build launch in the graph.
  • fp8 k_scale/v_scale (present in the main decode kernel signature) are not applied.
  • num_chunks uses a simple heuristic; it wants tuning against the union size.

Update: end-to-end results on H100 and GB200 — the kernel is not a general win

I wired this into MiniMaxM3SparseImpl behind a flag and A/B'd it on live MiniMax-M3
NVFP4 servers with EAGLE3 (num_speculative_tokens=3, so dnum=4), only the flag differing
between arms. Steady-state decode ITL p50 (each request's prefill-contended first half discarded).

8×H100, TP8, fp8 KV — wins at high batch:

ISL conc stock q-tiled Δ
20,000 44 35.90 ms 34.77 ms −3.1%
10,000 88 47.34 ms 44.62 ms −5.7%
80,000 1–8 9.4–17.1 ms 10.8–17.1 ms +12 to +15%

GB200 NVL72, TP4, fp8 KV — loses everywhere, n=3 per point:

ISL conc working set vs 136 MB L2 stock q-tiled Δ t
80,000 40 84 MB fits 197.12 ±2.65 216.36 ±2.09 +9.8% 9.9
40,000 76 159 MB over 191.81 ±1.01 197.90 ±3.41 +3.2% 3.0
20,000 150 315 MB over 178.65 ±0.97 182.67 ±2.64 +2.3% 2.5

Measurement noise on this metric is sd 2.2% (established from four runs that were
unknowingly stock-vs-stock), so all three GB200 deltas are real, including the two
above the L2 crossing where the mechanism was supposed to help.

Why it flips

The benefit is bytes removed; the cost is architecture-independent overhead.

  • GB200 moves the removable bytes 2.4× faster (HBM ~8 TB/s vs 3.35), so the same
    saved traffic is worth far less time.
  • Its L2 is 2.6× larger (136 MB vs 52 MB), so more of the duplicates were already
    being absorbed. At 80K the max concurrency the KV pool allows (~40) has a working set
    of 84 MB, which fits in L2 — the bandwidth mechanism cannot fire there at all.
  • The kernel's costs do not shrink: a union-build launch per sparse layer (57 per step),
    split-K partials, and the merge pass.

Separately confirmed on the shipped kernel: the duplicate loads cost no HBM bandwidth
when L2 absorbs them — at batch 64/bf16 the shared-top-k case would require 6.11 TB/s on a
3.35 TB/s part. At fp8 the attend is not bandwidth-bound in either configuration (~50% of
peak); it is gather- and issue-bound.

Where that leaves this PR

I do not think it should be merged as-is. It is a narrow win on Hopper at high batch and a
regression on Blackwell, which is the direction the deployments are going. Keeping it open as
an RFC because the diagnosis in #47763 stands — the dnum-fold re-read is real and
structural — but this implementation is not the answer, and the honest conclusion is that
the redundancy is much cheaper than the issue implies on modern parts.

The two things that would change the verdict, for anyone picking this up:

  1. Kill the per-layer union build. It is the largest architecture-independent cost.
    Folding the union into the attend kernel's prologue, or reusing selection across layers if
    that is ever valid, removes it.
  2. Measure the real top-k overlap. Everything here uses synthetic overlap. If adjacent
    draft rows genuinely share most of their top-16, the shared-selection contract becomes a
    guaranteed dnum-fold reduction with no union build at all — but it ends output
    equivalence between speculative and non-speculative decoding, which is a maintainer call.

Correction: I measured the real top-k overlap, and my diagnosis above was wrong

Point 2 of my previous comment asked for the real overlap because everything up to
then used synthetic values. I have now measured it on a live GB200 MiniMax-M3 NVFP4
server, and it changes the explanation — though not the verdict.

The real overlap is high: rho = 0.874

160 samples, taken on the production indexer's own topk_idx during serving
(dnum=4, topk=16):

quantity measured
|union| 22.1 of a possible 64
rho 0.874
bytes vs stock 0.345x

Draft rows 2-4 each add only ~2 blocks beyond row 1's 16, which is what you would
expect: four consecutive draft tokens have nearly identical relevance profiles.

So the premise of this PR holds. The q-tiled kernel really does read a third of
what the shipped kernel reads. My earlier speculation that the union might degenerate
to dnum*topk was wrong.

(Method note, since it nearly fooled me: sampling the first N verify calls measures
the profile run and CUDA-graph capture, not serving — 57 sparse layers per step
consume the budget before the server is healthy. Those samples report |union| = 1
and an impossible rho = 1.31 from all-zero dummy topk_idx, which reads as
near-perfect overlap if you don't range-check it. Real samples must satisfy
topk <= |union| <= dnum*topk.)

Why it is still slower, and why my L2 explanation was wrong

I attributed the Blackwell regression to L2 absorbing the duplicate loads. That
only ever covered the 80K/conc-40 row, whose 84 MB working set fits in 136 MB of L2.
At 20K/conc-150 the working set is 315 MB and cannot fit, yet it still regressed.
I extended a one-row argument across the whole table; that was not supported.

The actual mechanism is work inflation. This kernel computes every draft row
against every union block and masks afterward:

  • shipped: topk * dnum = 16*4 = 64 (block, row) products
  • q-tiled: |union| * dnum = 22*4 = 88

It trades 0.34x bytes for 1.375x work. And on this part neither kernel is
HBM-bound — at batch 150 the shipped kernel achieves 2.42 TB/s and this one
804 GB/s against ~8 TB/s of peak (30% and 10%). The bytes were never the binding
constraint, so removing them buys little while the extra work costs directly.

Sweeping rho on GB200 (CUDA-graph timed, output parity checked against the shipped
kernel at rel err 3-5e-3; the shipped kernel's own time stays flat at 127.8-131.5 us
across the sweep, as it must, since it never sees the union):

rho |union| work bytes batch 40 batch 150
1.000 16 1.00x 0.25x 1.273x 1.189x
0.874 22 1.375x 0.34x 1.162x 0.903x
0.750 28 1.75x 0.44x 1.033x 0.811x
0.500 40 2.50x 0.63x 0.735x 0.617x

Time tracks the work column, not the bytes column. Break-even is
rho = 0.722 at batch 40 and rho = 0.917 at batch 150. The real rho of 0.874
falls between them — which is exactly why this wins on H100 at batch 44-88 and loses
on GB200 at batch 76-150. It is not a Blackwell property; GB200 simply runs the
higher-batch, less bandwidth-starved end where break-even exceeds the real overlap.

Correcting my "what would change the verdict" list

  1. The per-layer union build is not the largest cost. I asserted it was. Measured,
    it is 8.4-9.7 us against 60-130 us for the attend. Removing it entirely at batch 150
    leaves 0.968x — still a regression. The cost is in the attend.
  2. Measuring the overlap did not favour the shared-selection contract. At rho=0.874
    the exact contract already captures most of the available bytes; abandoning output
    equivalence would buy the remaining 0.345x -> 0.25x, not a clean dnum-fold. That
    weakens the case for changing the serving guarantee, which is the opposite of what
    I implied.

The fix this points to

Ideal work for the exact contract is sum over blocks of (rows needing that block),
which is exactly topk * dnum = 64 for any rho — every row needs precisely topk
blocks. This kernel pays 88 only because it computes all dnum rows per union block
and masks. Skipping rows a block is not needed by restores work parity while keeping
the byte saving. The rho=1.0 row above is the empirical bound on what that buys, since
it already has work parity: 1.189x at batch 150, versus 0.903x today.

The caveats are real: branch divergence when rows disagree, and tl.dot needs M>=16,
so with dnum=4 and 16 q-heads per KV head the skip granularity is one draft row
(16 of 64 M-rows). It would not generalise to smaller GQA ratios.

I have not implemented this. Leaving the PR as an RFC with the corrected diagnosis;
the measured numbers say the approach is sound and this implementation is not, which
is a narrower and more fixable claim than the one I made above.

Limitations: the sweep is synthetic topk_idx at the measured rho with uniform
context, TP4 shapes, one KV head per rank. The rho measurement itself is from real
serving; batches sampled ranged 2-46.

Follow-up: I implemented the row-skipping fix. It works, and it still doesn't ship.

My previous comment identified the cost as work inflation — this kernel computes
every draft row against every union block and masks afterward, doing |union|*dnum = 88
block-row products where the shipped kernel does topk*dnum = 64 — and proposed removing
it. I've now built that and measured it on both machines.

The identity

sum over blocks of (rows needing that block)
  == sum over rows of (blocks that row needs)
  == topk * dnum                                 for ANY rho

Every row needs exactly topk blocks, so a kernel that never computes a row against a
block that row did not select does exactly the shipped kernel's work while still
reading only |union| blocks.

Implementation

Partition each request's union by row pattern in the builder (same launch that already
dedupes it), then one pass per segment with a uniform tile — no row-membership mask
anywhere:

pass blocks tile
A selected by all dnum rows [dnum*QH, D]
B everything else, one row at a time [QH, D]

A block wanted by exactly k rows is visited k times in pass B — its exact share. Both
passes write disjoint slots of the same split-K partial buffer, so the existing LSE merge
combines them unchanged and output stays bit-comparable.

Verified on device: work per request is exactly 64 at every rho (rho=1 -> 16+0, 0.874 ->
14+8, 0.5 -> 8+32, 0 -> 0+64), the builder matches a pure-Python reference elementwise
including blocks belonging to exactly 2 or 3 of 4 rows, and all 20 parity checks against
the shipped kernel match the existing kernel's error identically.

Measured — the two machines want different kernels

Best chunk config per point, CUDA-graph timed, ctx 20000, dnum 4:

machine gqa rho batch stock this PR row-skip winner
GB200 16 0.874 76 62.8 us 0.856 0.942 row-skip
GB200 16 0.874 150 130.3 0.897 1.027 row-skip
GB200 16 0.500 150 131.8 0.613 0.948 row-skip
H100 16 0.874 44 75.1 1.500 1.444 this PR
H100 16 0.874 88 131.1 1.700 1.526 this PR
H100 8 0.874 88 122.8 1.654 1.480 this PR

Row-skip wins 8/12 GB200 points — every one where this PR loses — and loses 6/8 on H100.

Why

Which resource binds differs by machine:

stock achieved BW of peak this PR at rho=0.874
H100 1.41 TB/s 42% of 3.35 1.70x — bytes pay
GB200 2.42 TB/s 30% of ~8 0.90x — bytes buy nothing

H100 is bandwidth-sensitive, so this PR already captures the whole benefit, and both
variants read the same bytes — the work reduction is irrelevant there and the row-skip
overhead is pure cost. GB200 is not bandwidth-bound, so work is what binds and row-skip
helps.

Correcting my own projection

I projected ~1.19x at batch 150 by reading the rho=1.0 row of the sweep. That was the
wrong bound — rho=1.0 has work parity and a denser tile structure, so it flatters any
variant. Actual result at the real rho is 1.027x. The shortfall splits into:

  1. ~3% fixed two-pass overhead — visible at rho=1.0 where segment B is empty yet
    row-skip (1.145) still trails this PR (1.176): an extra launch with zero work, a
    larger partial buffer, a wider merge.
  2. Tile efficiency — pass B runs M=16 tiles against pass A's M=64. Arithmetic
    work is 64 either way, but small-M tiles don't reach the same tensor-core throughput,
    so work parity doesn't become time parity. At gqa=8 (TP8) it's worse still, since
    tl.dot needs M>=16 and pass B pads, wasting half its lanes.

Where that leaves things

Row-skip converts a 10% GB200 regression into a 2.7% win that is inside the 2.2% e2e
noise floor, while giving up ~10% of a solid H100 win. Shipping it would need
machine-dependent dispatch — real maintenance cost for a benefit unmeasurable on one
side. So my recommendation is unchanged: don't merge this PR as-is. The narrower
claim I can now support is that the approach is sound on bandwidth-limited parts and the
implementation is not the problem — the redundancy simply isn't the bottleneck on parts
with Blackwell's bandwidth.

Anyone picking this up: the row-skip variant is worth having if a workload shows low
overlap (at rho=0.5 it recovers 0.613 -> 0.948), but MiniMax-M3's real rho is 0.874, so
that regime does not arise here.
