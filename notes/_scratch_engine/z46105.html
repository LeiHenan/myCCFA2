High-level tracking issue for DFlash deployments. There's a lot of complexity and additions we need to fully support the current and upcoming DFlash model ecosystem.

Models to support

  • "Standard" DFlash: non-causal attention, all full attention layers. e.g. Qwen3-8B-DFlash.
  • "Hybrid" DFlash: hybrid of causal SWA attention and non-causal full attention. e.g. Gemma4 DFlash
  • "MiMo-style" DFlash: all sliding-window layers, presumably requires non-causal+SWA support. PR
  • "Speculators-style" DFlash: all sliding-window layers, all causal attention.

Challenges

Attention backend support

Generalizing DFlash to multiple attention backends and KV cache dtypes requires many changes to attention backends to support non-causal decode-style attention.

  • TRTLLM is pending decode-optimized kernels. Until then, it is possible to use the TRTLLM-gen causal prefill kernel to improve support and efficiency on Blackwell. See Non-Causal TRTLLM-Gen support for Decode flashinfer-ai/flashinfer#3570
  • CuteDSL (via FlashInfer) supports optimized spec-decode-friendly non-causal attention but is not plugged into vLLM. See: https://github.com/flashinfer-ai/flashinfer/blob/main/flashinfer/cute_dsl/attention/wrappers/batch_decode.py#L564. Contribution welcome
  • XQA (via FlashInfer) has optimized spec-decode kernels for Hopper that do not seem to be integrated into vLLM. These support fully custom masks for non-causal, diffusion, and tree attention. https://github.com/flashinfer-ai/flashinfer/blob/9c5ed7c194e7412780862491742fc655daaad6ac/flashinfer/decode.py#L3001. Contribution welcome
  • FlashInfer (default cutlass backend, not TRTLLM backend) supports non-causal prefills, so it is possible to use this for non-causal DFlash queries. Support added in [SpecDecode] Support DFlash with FlashInfer  #43081 (merged). This enables FP8-KV Cache + DFlash for many use-cases.

Supporting Sliding Window

Both causal and non-causal sliding-window attention modes require some changes to vLLM's KV cache management, attention backend implementations, and attention metadata preparation for draft models.

  • Fixes for FlashInfer attention: The PRs [Spec Decode] Add FlashInfer metadata grouping for DFlash SWA #43200 and [Spec Decode] Support DFlash FlashInfer backend with SWA and FP8 KV cache #39995 attempt to patch FlashInfer: "FlashInfer metadata builders cannot be shared across layers with different attention parameters". I don't fully understand the precise requirements, and review help is needed to assess exactly what changes are needed.
  • Fixes for scheduler & KV management: the PR [Spec Decode] Add Sliding Window Attention support to DFlash drafter #40898 extends the implementation of "EAGLE cache drop" to exclude DFlash. It's not clear to me why this is needed, or what the purpose is. help needed to parse the needs of the scheduler, when it is and isn't safe or necessary to drop prefix cache blocks when DFlash is / isn't in SWA mode.
  • Model Code Support: [Spec Decode] Support SWA + DFlash for MiMo #46104 adds SWA support to the DFlash model with generic configurable settings that should work for most combinations of swa/hybrid and causality. Also enables MiMo-style DFlash. Ready for review.

Supporting Hybrid Drafters

Supporting "hybrid" drafters with some SWA and some full attention layers is new to vllm (since Gemma4MTP, which is a special case since it does not have its own KV). This leads to many issues in the KV cache manager and attention metadata preparation for hybrid-style drafters. This will require special care as our final design should also be extensible e.g. to hybrid/linear standalone draft models.

  • [Spec Decode] Add Sliding Window Attention support to DFlash drafter #40898 adds many patches to get hybrid DFlash working in MRV1. This PR is stale and needs to be rewritten in MRV2. @benchislett is leading the rework of this PR for MRV2, with review help wanted (once an initial implementation lands), and until then review of [Spec Decode] Add Sliding Window Attention support to DFlash drafter #40898 is encouraged to understand the current set of changes, e.g. https://github.com/vllm-project/vllm/pull/40898/changes#diff-fb2b41380ca86adbba904aff40b18a0815beb73c1198818912e71723383ab604R1305. See also [Tracking][Spec Decode] DFlash Bring-Up Tracker #46105, a MRV1 reference

Performance Opportunities

Beyond new attention backends, there are a few performance tuning features that can be further explored:

Draft quantization support.

To date, no FP8 DFlash checkpoints are in widespread use. However, vLLM supports online FP8 quantization. We could enable speculator-specific quantization configuration to unlock online FP8 DFlash with any quantization of the target model. This can improve throughput at medium-concurrency, and enables longer sequence lengths by expanding available KV cache memory. Contribution welcome

Quantized checkpoints are largely expected to work OOTB, but some issues may arise (such as in DFlash's cross-layer inlined+fused KV precomputation).

Fusions and graphs

DFlash's KV precomputation and model implementation both do not leverage aggressive kernel fusion, and can be accelerated in the min-latency regime with custom (e.g. triton) kernels or tuned GEMMs. This will be especially important if FP8 quantization is enabled. Contribution welcome
