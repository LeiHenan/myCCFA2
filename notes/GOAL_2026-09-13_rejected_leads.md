## 一、三条线索的终局（每条都有真实实验，不是文献推断）

### 线索 1：投机解码下的前缀复用生效时延（`candidates/prefix-reuse-lag/`）

| 项 | 内容 |
|---|---|
| **现象（稳固）** | 同一 serve 会话、同一批 prompt、同一并发下，**投机关时第 2 次即命中、投机开时要到第 3 次**。四格复现：投机关 bs1/bs32 onset=2；投机开 bs1/bs32 onset=3。代价 **2.09×（投机关）/ 2.63×（投机开）** 吞吐，TTFT 差 **−57.5%~−90.8%**；噪声 ≤2%（同格逐次极差）。 |
| **机制（已定位到边界）** | 投机把 KV 缓存拆成 **9 组**（target 注意力 KV + drafter 多类状态）。第 2 次时 **组 0–7 全部已有该块**（逐组探测 `111111110`），查找仍返回 `computed=0`；第 3 次探测状态**完全相同**却返回 4080 ⇒ **拒绝复用的决策在缓存查找之后**（调度器/分配器侧，投机路径特有）。 |
| **被否原因** | **修复半径**：三次干预（绕过其他组 / 关 EAGLE 丢块 / 对齐覆盖）**均未撼动 onset** ⇒ 预登记降级条件触发。要修需在调度器层实现"按组独立 computed 长度"，属 3–4 周引擎手术，超出决策级半径。 |
| **已排除的假设（8 条）** | ① 非填充侧（两边都缓存到 256 块）；② 非 `skip_reading_prefix_cache` 闸门；③ **非驱逐**（`evictions=0`）；④ 非 EAGLE 丢块（`use_eagle=False` 无变化）；⑤ 非对齐取整（`alignment_tokens=16`）；⑥ 非链断（第 2 次前 10 块全命中）；⑦ 非"全组一致归零"（组 0–7 已齐备）；⑧ 非草案语料状态。 |
| **复活条件** | 允许动调度器（3–4 周）时：实现按组独立 computed 长度，或修正投机下的复用决策。**现象与机制记录已足够支撑一篇"测量/刻画"论文或一次系统改造。** |

### 线索 2：跨引擎指标语义不等价（`candidates/engine-metric-conformance/`，S0–S8 全过）

| 项 | 内容 |
|---|---|
| **现象** | vLLM 0.29 vs SGLang 0.5.19，同模型/同负载/同客户端：**接受长度差 −32.6%**（1.479 vs 2.194 @bs32）；同名延迟指标 `itl/tpot` = **1.07× vs 1.98×**。 |
| **机制（源码级）** | `mean_itl_ms` 记在**每个流式 chunk**（`endpoint_request_func.py:241`），`mean_tpot_ms` 是**每 token**（`serve.py:616`）⇒ `itl/tpot ≈ 每个 chunk 携带的 token 数`，该数随引擎/方法变化。 |
| **被否原因** | **贡献类型不符**：这是「让别人报告可信」的**测量/一致性**课题，不是「解决一个真问题」的优化课题；且反证明确（计数类指标完全一致 0.00%、吞吐口径仅差 4%）⇒ 不能写成"跨引擎比较普遍失真"。 |
| **可交接价值** | 判据 C1–C4 + 可运行检查器 + 实测差异表；体裁有先例（*Performance or Illusion?* MLSys'26 oral）。若接受测量类课题，这是现成的。 |

### 线索 3：草案语料（NGRAM）的跨会话收益（`probes/p11-ngram-corpus/`）

| 项 | 内容 |
|---|---|
| **现象** | SGLang + NGRAM **自己就会在会话内累积**：基线吞吐 544 → 1434/1624/1561/1673（第 2 次起 ~2.6–3×），accept 1.97 → 2.65（p09）。 |
| **关键判断** | **收益是引擎自带的** ⇒ "预置语料"只是**现成原语**，不构成创新（会被判工程配置）；**真问题是跨会话/跨副本的语料生命周期**（预热后共享/选择/淘汰/跨租户复用），量级指标 = **冷启动罚金**。 |
| **被否原因** | 未能在本轮跑通干预（连续 4 个约束），且**创新点未确立**。 |
| **已定位的 4 个约束（配方可直接用）** | ① 必须 JSONL（不是纯文本）；② 必须同时给 `--speculative-ngram-external-sam-budget`；③ 该值 **≤ `num_draft_tokens − 1`**（是**每请求预算**，语料容量用 `--speculative-ngram-external-corpus-max-tokens`）；④ **每行必须是 JSON 字符串**（`expected a JSON string`），不是对象/数组。另：接受率是 **gauge**，必须**运行中轮询**采集（跑完归零）。 |

## 二、下一轮测绘结论（这三条否掉之后，应该往哪走）

1. **"解半径"必须成为选题的一等筛选条件** —— 本轮最大的教训：线索 1 的现象与机制都成立，但**修复点在引擎调度器内部**，决策级半径（≤1 GPU·h/轮）根本够不到。下一轮测绘时，**每个候选必须先回答"改动落在哪一层、需要几周"**，落在调度器/内核层的候选**要么直接放弃、要么先申请更长半径**。
2. **"引擎自带的收益"不能当创新点** —— 线索 3 的教训：如果一个增益引擎默认就会产生（会话内累积），那相关工作的创新必须落在**它不覆盖的维度**（跨会话/跨副本/跨租户），否则会被判工程配置。
3. **测量类课题要早判类型** —— 线索 2 有完整判据、检查器与实测差异，但它是"证明别人的数字不可信"，与"解决真问题"不符。**下一轮应在 S1 就标注课题类型（优化 / 测量 / 刻画），并在用户的判据下先过滤**。
4. **可以考虑的下一步方向**（均需先过"半径"筛）：
   - **跨副本/跨会话的草案语料生命周期**（线索 3 的精炼形态，半径 = 应用层，较小）；
   - **调度器级"按组独立 computed 长度"**（线索 1 的复活形态，半径 = 3–4 周引擎手术，需更高预算）；
   - 回到 `notes/GAP_SURVEY_2026-09-13.md` 的"仍空"区域，但**先做半径评估**再进 S1。
