## §3 Any surviving slice(s)

I could not construct a slice that clears all four criteria. Two candidates survived longest; each is stated in the required form, with its exact failure mode. **S-B is the stronger of the two**; S-A is the only *policy* axis I could not find occupied but its magnitude is genuinely in doubt.

### S-A (policy, thin): memory/VRAM-state-aware K on 24 GB-class GPUs

> **Nearest neighbour X does A:** vLLM's shipped controller (#47808, `adaptive_verification.py`) and SGLang's EMA tier controller both pick the verification budget by an *execution-time* objective — vLLM: `draft_budget = int(np.argmax(num_tokens_to_estimated_accepted_tokens / costs))` — **verified by me at `vllm/v1/worker/gpu/spec_decode/adaptive_verification.py:342`** — with `costs` assembled from two profiled curves keyed on `num_reqs` and `num_target_tokens`; SGLang: `target_steps ≈ clamp(round(ema_accept_len) + 1, …)` per batch-size slot.
> **Under condition C:** a 24 GB-class card where the binding resource is *memory*, not step time — the capture set, the KV block pool and the weights must share 24 GB — and where a K-switching policy must therefore buy graphs, not just time.
> **X does not cover B:** X never reads memory state. At a *fixed* batch size and a fixed acceptance EMA, halving free VRAM (longer context, more LoRA/offload, larger capture set) leaves every shipped policy's K unchanged, because none of the six/seven signals tabled in #54749, nor #47808's cost curves, nor SGLang's tiers, nor TRT-LLM's EMA monitor is a memory signal. **We would do B:** choose K (and the captured graph set) by maximising the same goodput objective *subject to* a VRAM budget — i.e. make the constraint that #56626 shows is real (6.57 GiB of varlen FULL decode graphs; static k=5 needs ~1.1 GiB) an explicit term in the decision instead of assuming FULL graph capture.

- **Magnitude:** **estimated, weak.** Upper bound borrowed from upstream *measured* numbers: fixed-K speculation costs 24–33 % of throughput/capacity-under-SLA at saturation (vLLM #47808: *"at c=256, fixed 7-token is 33% below no-spec"*; #48202 comment thread on one A100-40GB: throughput 0.76×, SLA-bounded capacity 16.4 → 12.4 qps = −24 %, +135 % p99 TTFT — caveat: that run used `--no-async-scheduling` and shared the node). The memory *term* is measured once but on the wrong hardware: 6.57 GiB capture for the adaptive path vs ~1.1 GiB static on a B300 (#56626). I have **no** measurement of how much of that survives on a 4B-model/24 GB configuration, and the KV-slot term is plausibly ≤1 block/request. So: do not believe a number here until the zero-GPU bound below says the term is non-trivial.
- **Zero-GPU first experiment (CPU only, ~1 h, no GPU allocation):** with vLLM v0.26.0 source in hand (already fetched) — (i) parse `CompilationConfig`/cudagraph capture-size computation for a target config (Qwen3-4B + EAGLE-1 draft, `max_num_seqs=64`, `max_model_len=8192`) and count *captured graphs as a function of the K-set in the dynamic schedule*; (ii) replay a synthetic arrival trace through the block-manager arithmetic as 0.26.0 actually does it — note `self.num_lookahead_tokens = self.num_spec_tokens` (max K) is set unconditionally (`scheduler.py:251-263`) and passed to allocation (`:567`, `:910-940`), while the schedule may select K=0 at the same instant (`:1134-1135`) — and tabulate {graphs captured, max resident requests, preemptions} per K ∈ {0,1,3,7}. **Kill criterion:** if max resident requests varies < 3 % across that K-set at 8 k context, S-A is immaterial on our box and should be dropped.
- **Why it is thin:** #56626's reporter explicitly left the remaining 6.57 GiB open — *"If I can pin it down to something actionable I'll file it separately with data"* — so requirement 2 ("not currently being built") is one GitHub issue away from failing, and the honest reading is that the memory angle is *warm*, not cold.

### S-B (measurement/mechanism, more defensible unoccupied-ness): matched-control decomposition of the "pays / does-not-pay" surface

> **Nearest neighbour X does A:** every occupier treats the optimum as a function of one or two *separable* signals — batch (#32374/#47808/#38038), context (#48944), entropy (#54082), marginal gain (LibraSpec), expert cost (EcoSpec), step efficiency (SparseSpec-L), learned payoff (HVD), sequence length (#54801) — and assumes a cost form of `K* = argmax_K E_accept(K) / (F(ctx) + K·M(bs))`.
> **Under condition C:** the regime #54749 measured on one H100 NVL (and #54691 measured with the *opposite sign* on B300/TP8/DCP-8 with Kimi-K3+DFlash) where the pays/does-not-pay region is **non-separable across batch and context** — #54749 spells it out: *"(2k, B=8) pays, so neither rule fires there; (32k, B=8) does not pay, so the context rule must fire at 32k; but then (32k, B=1) would be switched off, and it pays."*
> **X does not cover B:** no occupier *decomposes* that surface.
