### 1.1 DSD（动态投机调度）的 **K=0 档代价** ｜ 本轮 **实测** ｜ 0.55 GPU·h

**现象数字**（p20 v3，Qwen3-4B / sm120 / 并发 8 / 前缀缓存开启 / 每臂先跑 1 趟预热丢弃 + 3 次测量）：
暖态 p50 吞吐 = 不投机 **646.18** ｜ 静态 K=3 **959.24（+48.5%）** ｜ 静态 K=1 **718.68（+11.2%）** ｜ 表全 K=0 **441.42（−31.7%）** ｜ 跳变表 **437.97（−32.2%）** ｜ 表常量 K=3 **954.38（+47.7%）** tok/s。
暖态 ITL：不投机 **11.90 ms** ｜ 表全 K=0 **17.42 ms** ｜ 静态 K=3 **18.04 ms**。
`num_drafts`：静态 K=3 **4954** ｜ 表全 K=0 **0** ｜ 跳变表 **31**。
重复性：暖态极差 **0.36%–3.63%**（未触发 E1）。

**预登记判定**：**P1a 否证原假设 H1** —— K 匹配对照（`A2 静态K=3 无表` vs `A6 表常量K=3`，**K 完全相同、唯一变量是有没有表**）测得 **−0.51%，噪声 3.63%** ⇒ **表的存在本身零代价**。
**P1b 成立**：零草稿表比完全不投机慢 **31.69%**（噪声 1.73%，效应 ≈18× 噪声）。P3 通过（A4 的 `num_drafts` 精确为 **0**）。P5 实质通过（A5 仅 31 草稿 = A2 的 0.63%，证明表的档位选择真的在生效）。

**复现命令**：
```bash
cd /root/myCCFA && MODE=full WARMUP=1 bash probes/p20-dsd/run_dsd_grid.sh
/root/ccfa_venv/bin/python probes/p20-dsd/analyze_dsd.py --dir /root/ccfa_results/<date>/p20_dsd_v3
```

**机制到源码行（我的测量 + 上游命名）**：K=0 档的 ITL（17.42 ms）**≈ 真投机档（18.04 ms）≫ 不投机（11.90 ms）**
⇒ **K=0 并没有回到普通解码路径**，而是照付投机路径的每步代价、每步只吐 1 个 token。
上游 PR #53426 的标题即此机制的命名：*"Opt-in skip of the **K=0 draft sync forward**"*。

**被否的确切原因（S3b 三问：②有未关闭同类报告 ✔ ③上游正在修 ✔ ⇒ 🔴）**：
| artifact | 状态 |

| vLLM issue **#49548** *"catastrophic aggregate-throughput collapse under concurrency at the batch-size threshold"*（含报告者自建 `VLLM_DSD_K0_DIAG=1`） | **OPEN** |
| vLLM issue **#48494** *"12–25% throughput penalty … even with an all-K=0 table"* | **OPEN** |
| vLLM **PR #47737**（K=0 的 cudagraph 捕获 ZeroDivisionError） | **OPEN** |

**证据路径**：`results/p20-dsd/2026-09-14/summary.md`、`notes/prereg/p20-dsd-concurrency.md`（含采数前修订 #1）、决策 #123。
**复活条件**：若上述 PR 全部落地**且**有人报告 K=0 档仍有残余开销 ⇒ 可重开"残余开销归因"（但我方负载上届时应先重测确认残余存在）。

**本条的方法学产出（比结论更有价值）**：**用 K 匹配对照纠正了上游的因果措辞。**
#48494 写 *"**The presence of the batch-size table is the trigger**; K=0 tiers are not required."* —— 我的 K 匹配对照测得"表的存在本身 −0.51%"
⇒ 正确表述是 *"把 K 设成 0 仍要付投机路径的每步代价"*（即 #53426 自己的标题）。**"花费落在哪个变量上必须用匹配对照钉死，不能沿用上游措辞"** 可复用。

### 1.2 DFlash/DSpark × **前缀缓存**（"命中仍要重算"）｜ 本轮 **实测** ｜ 0.15 GPU·h

**现象数字**（p21，8 个 4096-token prompt，同顺序，三段对照：A 冷 / B 热 / C 再热；`vllm:request_prefill_kv_computed_tokens` 官方定义 = *"new KV tokens computed during prefill (excluding cached tokens)"*）：

| 臂 | 阶段 B 命中 / 查询 | 阶段 B 每请求**重算** | 阶段 C 命中 |
|---|---|---|---|
| `nospec` | 32,640 / 32,768 | **16**（1 个 block） | 32,640 |
| `eagle3_k3` | 32,512 / 32,768 | **32**（2 个 block） | 32,512 |
| `ngram7` | 32,640 / 32,768 | **16** | 32,640 |
| **`dflash2_k3`** | **0 / 32,768** | **4096 = 100%** | **32,512（第三遍才命中）** |

⇒ **同一操作白算的 prefill 相差 256×**；服务日志自报累计命中率与此吻合（dflash **33.1%** ≈ 1/3，nospec **57.7%**）。
**副作用**：它同时解释了 p20 网格 v2 里"投机臂第 3 遍才暖"的异常（v2 的"热 p50"因此是冷热不匹配的伪比较，v3 用预热趟修正）。

**复现命令**：
```bash
# 服务（前缀缓存保持默认开启）
/root/ccfa_venv/bin/python -m vllm.entrypoints.openai.api_server --model /root/autodl-tmp/models/Qwen3-4B \
  --served-model-name q3 --port 32090 --max-model-len 8192 --max-num-seqs 32 \
  --gpu-memory-utilization 0.55 --enforce-eager \
  --speculative-config '{"method":"dflash","model":"/root/autodl-tmp/models/dflash2","num_speculative_tokens":3}'
/root/ccfa_venv/bin/python probes/p21-prefix-hit-recompute/probe_prefix_hit.py \
  --base-url http://127.0.0.1:32090 --prompts /root/autodl-tmp/prompts/prompts_4096.jsonl \
  --n-prompts 8 --max-tokens 32 --logprobs 1 --out /root/ccfa_results/.../S_dflash2_k3
```

**机制到源码行（上游原文，与我实测完全一致）**：PR #47926 ——
*"DFlash/DSpark drafters build their context KV from the target's auxiliary hidden states … Tokens whose KV is restored at request (re)admission — **automatic prefix caching hits** … **never run through the target, so their draft context KV slots are never written** … so it reads uninitialized/stale KV for the whole restored region … while **MTP/EAGLE-style drafters on the same workload are unaffected**."*
**我的实测独立复现了这条分野**：`eagle3` 正常、`dflash2` 全失效 —— 与"eagle 从最后一个 decode 隐藏状态起草、不建 context KV"一致。

**被否确切原因（② ✔ ③ ✔ ⇒ 🔴）**：
| artifact | 状态 |
|---|---|
| vLLM issue **#47930**（标题即我的结论：*"DFlash/DSpark draft acceptance collapses with automatic prefix caching enabled"*） | **OPEN** |
| vLLM **PR #47926**（机制原文见上） | **OPEN/Draft** |
| vLLM **PR #54163** *"DFlash/DSpark no longer drop the last prefix-cache block"*（*"the whole context was recomputed on every reply"*） | **OPEN** |
| vLLM issue **#54094**（1.04M prompt zero reuse；环境栏正是 **RTX PRO 6000 Blackwell**，"Resolved attention/Mamba block size: **1,648 tokens**"） | **OPEN** |

**证据路径**：`results/p21-prefix-hit/2026-09-14/summary.md`、`probes/p21-prefix-hit-recompute/{probe_prefix_hit.py,run_hit_grid.sh}`（`--selftest` 通过）、决策 #124。
**复活条件**：**无**（这条没有可做的残余）—— #47926 的机制说明已经给出了修法方向（把命中恢复的 token 从 draft attention 里屏蔽）。

**本条的方法学产出**：**"投机解码破坏前缀缓存"是错的，必须按 drafter 类别分别陈述。** 地图把 "EAGLE/MTP" 合写成一类，实测**只有 dflash 系失效**。

### 1.8 B112 级联崩塌 / C44 / C109 / C110 —— **理由失效但机制上不可达** ｜ 纯检索 + 源码线索 ｜ 0 GPU·h

**但读全 C109 的理由会看到真正的根因**（引 #42948 线程上 @stecasta 的 block-pool 插桩）：
> *"the real bug is **131% pool overflow from the homogeneous `lcm=256` physical block layout vs DSv4-Flash's `{256, 64, 4, 8}`-block-size KV groups**."*

### 1.9 B112（并发下命中率崩塌）—— **机制上不可达 + 匹配对照** ｜ 本轮 **实测** ｜ 0.2 GPU·h

**为什么它值得一次实验**：这是三张地图里**唯一**我此前只能用关键词（`hybrid`）判"够不着"、给不出机制的高价值格。
上游的因果断言（C109 关闭理由，引 #42948 上 @stecasta 的插桩）：
*"the real bug is **131% pool overflow from the homogeneous `lcm=256` physical block layout vs DSv4-Flash's `{256, 64, 4, 8}`-block-size KV groups**"*。

**匹配对照**：dense Qwen3-4B 逐层 page size 均匀 ⇒ lcm = page size ⇒ 不溢出 ⇒ 预测无崩塌。2×2（池压力 × 并发）：

| 配置 | KV 池 | 并发 | 冷命中率 | 热命中率 | 热态每请求重算 |
|---|---|---|---|---|---|
| loose_c1 | 319,328 | 1 | 0.0000 | **0.9981** | 8 |
| loose_c8 | 319,328 | **8** | 0.0000 | **0.9981** | 8 |
| tight_c1 | 146,448 | 1 | 0.0000 | **0.9981** | 8 |
| tight_c8 | 146,448 | **8**（占用 ~90%） | 0.0000 | **0.9981** | 8 |

**四格逐位相同，无崩塌** ⇒ 上游归因**得到支持**；报告者的一般性机制假设（"自由块与已缓存条目混为一谈"）在本压力区间**不成立**。

### 1.15 n-gram 提议器的 1 线程上限 —— **同样死于量级（但这次是零 GPU 拿到的）** ｜ 0 GPU·h
