## Candidate 2 — "Crossover-aware optimization selection"

### 1. VERDICT

**PARTIALLY OCCUPIED.**

No artifact I found does the *specific* mechanism: a runtime that reads its position in **(batch, context)** space relative to a **measured** bandwidth→compute crossover and uses that position to select **between the byte-reduction family (quantization / sparsity / offload) and the FLOP-reduction family** for the same model and workload.

But the neighbourhood is dense enough that this is **not** an open field. Three separate lines each take one of the two halves:

* **Bottleneck-informed selection of a reduction technique** — done (PMPD, HAQ, DP-LLM, 2602.10377).
* **Runtime roofline model driving a live resource decision** — done (DuetServe 2511.04791, QEIL v2 2602.06057).
* **Byte-reduction × FLOP-reduction composition** — done (BitSkip 2510.23766).

What none of them does is make the **crossover location itself** the selector, and none of them crosses the **family** boundary at runtime.

### 1a. Single strongest occupying artifact (Candidate 2)

**PMPD — "Progressive Mixed-Precision Decoding for Efficient LLM Inference"**
URL: https://arxiv.org/abs/2410.13461 · https://arxiv.org/html/2410.13461

**State verified by fetching:** arXiv preprint (abs page fetched by me: `raw/arxiv_2410.13461.html`, 44,258 bytes, title read back ✓ — renders exactly `[2410.13461] Progressive Mixed-Precision Decoding for Efficient LLM Inference`). Full HTML body fetched by me: `raw/html_2410.13461.html` (273,956 bytes). No venue/DOI printed on the abs page. This is a **preprint**.

**Verbatim quote #1** — file `raw/html_2410.13461.html`, exact string:

> `By considering the distinct redundancy, sensitivity to approximations, and arithmetic intensity of the prefill and decoding phases, our scheme tailors the arithmetic precision to each phase’s characteristics.`

**Verbatim quote #2** — same file, exact string:

> `Computationally, the prefill phase is known to be compute-bound, while the decoding stage is memory-bound`

**How close it is:** PMPD is the closest single artifact to Candidate 2's *first half*. It explicitly (i) names the compute-bound/memory-bound phase asymmetry, (ii) names **arithmetic intensity** as the reason, and (iii) **acts on it** by allocating different arithmetic precision per phase and then progressively lowering precision deeper into the decode sequence ("precision-switching schedulers"). That is bottleneck-driven selection of a byte-reduction policy — genuinely the same *family of reasoning*.

**What it misses (the distinguishing condition):**
1. **No crossover variable.** PMPD's decision variable is *phase* (prefill vs decode) and *decode depth* (token index). It never measures, models, or thresholds a **batch-size / context-length crossover**. There is no point at which the policy re-decides because *n* or *L* moved. I grepped the saved HTML: `roofline` occurs **0** times; `arithmetic intensity` occurs **1** time (the sentence above); `batch` never appears as a decision axis.
2. **No family crossing.** PMPD only ever changes **bit-width** — pure byte-reduction. It never selects a FLOP-reduction technique. The word "pruning"/"FLOP-reduction" is not a policy option in it.

So PMPD does *A* = "pick a reduction policy from the compute/memory character of where you are"; under condition *C* = "the operating point moves along the (batch, context) axis *within* the decode phase, e.g. n=1 → n=64 at fixed model", PMPD misses *B* = "re-decide, and cross the family boundary, from the measured crossover"; we do *B*. See §3.

### 3. Candidate 2 — the required "nearest neighbour" sentence

> **Nearest neighbour:** PMPD (arXiv 2410.13461) does **A** = picks the arithmetic-precision policy from the *phase's* compute-bound vs memory-bound character, explicitly reasoning from **arithmetic intensity**. **Under condition C** = the operating point moves along the **(batch, context)** axis *inside a single phase* on a fixed model and workload — precisely this box's decode at n=1 (7.31 ms, bandwidth-shaped) versus n=64 (18.85 ms, compute-shaped), crossover at **n ≈ 28** — PMPD **misses B**, because its decision variables are *phase* and *decode depth* and it never re-decides from a measured crossover; and it has no FLOP-reduction technique in its action set at all. **We do B** = select *between* the byte-reduction family and the FLOP-reduction family using the measured crossover location. **Therefore, when C holds** — i.e. once n is at or beyond the measured crossover — **the conclusion differs**: byte-reduction stops being the paying move and the policy should cross to FLOP-reduction, which is a transition PMPD's action space cannot express.

A second, complementary framing (needed because PMPD alone only covers half): **nearest neighbour** 2602.10377 does **A** = derive *different optimal technique settings* for the **prefill** regime (compute/ξ_F-constrained) and the **decode** regime (bytes/ξ^dec_W-constrained) from the FLOPs-to-bytes ratio. **Under condition C** = the card is *fixed* and the model is *fixed* (this box: one RTX PRO 6000, one Qwen3-4B bf16), so prefill-vs-decode is the wrong axis — the axis that actually moves is (batch, context). **It misses B** = a runtime selector; it is design-time architecture co-design on Jetson Orin. **We do B** = a runtime selector keyed on the (batch, context) crossover. **Therefore when C holds the conclusion differs**: with the architecture frozen, the only remaining lever is *which family to run at the current operating point*, and that lever is set by the crossover, not by the phase label.

### 3a. What would kill Candidate 2

Any **one** of these makes it non-novel or vacuous — I would treat each as a kill:

1. **A serving engine that already dispatches optimization *family* on a batch/context axis.** A vLLM/SGLang/TensorRT-LLM code path or config that switches between a quantized path and a sparsity/early-exit/offload path as a function of `num_tokens`/batch/context would occupy it outright. I looked for this and did not find it, but I could not read vLLM 0.29.0 source in this session (see §4), so this is the highest-value unchecked surface.
2. **A paper presenting a crossover-conditioned policy over {quantization, pruning/sparsity, offload}** evaluated on one model + one workload with measured speedups. None found; BitSkip (2510.23766) is the closest and is single-model composition, not a policy.
3. **Evidence the crossover is not a usable decision boundary** — e.g. that it moves faster than any control loop can track, that it is smeared by kernel-level non-linearities (different quantization kernels have different roofline knees, so there is no single crossover *line* in (batch, context) space), or that the two families' cost curves cross *each other* rather than crossing the roofline. If byte-reduction and FLOP-reduction have their own internal crossovers, the "measured crossover" is not one number and the mechanism loses its crispness. A paper arguing this would kill Candidate 2 as stated — and **I did not find one either** (see the negative-direction note, §4).
4. **The trivialising case:** if the winning policy at n > 28 is simply "turn speculative decoding off", then the mechanism collapses into an existing, already-measured scheduling knob (the box's own spec-decode decay 2.96× → 1.11×). Candidate 2 only survives if the byte-vs-FLOP family choice is a *distinct* decision from that knob.

## Candidate 3 — "Prefill/decode partition as a first-class decision"

### 1. VERDICT

**OCCUPIED.**

The mechanism is done, with experiments, **twice over**, on both granularities — and the crux version (derive the split *from* the compute/bandwidth asymmetry via a roofline model) is done too. I tried to find a gap and could not: the split is a live decision variable, recomputed from the live mix, in at least two published systems, one of which explicitly builds an **attention-aware roofline model** to set it.

> `an attention-aware roofline model to forecast iteration latency`

**How close it is:** **This is the mechanism.** Enumerating Candidate 3's conditions against DuetServe:

| Candidate 3 condition | DuetServe |
|---|---|
| The split between prefill and decode work is a **decision variable** | ✅ — "selects the optimal SM split" |
| …decided **at runtime**, not fixed | ✅ — "operates in aggregated mode by default and **dynamically activates** SM-level GPU spatial multiplexing" |
| …derived from the **live mix**, not a static ratio | ✅ — gated on **predicted TBT degradation**, i.e. live iteration latency |

The **only** residual difference from the literal candidate text is granularity of the resource being split: DuetServe splits **SMs** (spatial multiplexing) rather than repartitioning a **token budget**. But Candidate 3's own definition explicitly contrasts itself against "a fixed chunked-prefill token budget (e.g. vLLM's `max_num_batched_tokens`)" and against "a fixed prefill:decode GPU ratio" — and SM split is squarely in the second category, decided live. The token budget is a *proxy* for the GPU-time split; DuetServe controls the thing itself. I therefore call this **OCCUPIED**, not partially.
