🐛 Describe the bug

The batch invariance docs
state the feature makes output "deterministic and independent of the batch size or the
order of requests in a batch." With VLLM_BATCH_INVARIANT=1 this holds on a single
GPU, but breaks under tensor parallelism: repeating a byte-identical workload
against the same unchanged engine returns non-identical logprobs (and, on near-ties,
different tokens) once tensor_parallel_size > 1. This is worse than running without
batch invariance, where the same workload is token-stable.

I bisected it to a single compilation pass. Disabling only fuse_allreduce_rms (with
torch.compile and cudagraphs otherwise untouched) fully restores determinism. That
pass installs a FlashInfer fused all-reduce + RMSNorm kernel (Enabled custom fusions: allreduce_rms, Auto-selected flashinfer allreduce backend: trtllm/mnnvl).

This is not the custom-all-reduce issue #50136 — the engine reports
disable_custom_all_reduce=True, so that path is already off under batch invariance.

Reproduction

Same config run 8 times in one process (fresh engine, warm cache, nothing changes
between repeats), then all-pairs compared as exact doubles. The
if __name__ == "__main__": guard is required — TP>1 uses spawn, which re-imports the
module.

import os, itertools
os.environ["VLLM_BATCH_INVARIANT"] = "1"
from vllm import LLM, SamplingParams

def main():
    # tensor_parallel_size=1 is bit-stable; =4 is not. Add
    #   compilation_config={"pass_config": {"fuse_allreduce_rms": False}}
    # to see determinism restored with TP=4.
    llm = LLM(model="Qwen/Qwen2.5-7B-Instruct", tensor_parallel_size=4,
              gpu_memory_utilization=0.9, enable_prefix_caching=True)
    sp = SamplingParams(temperature=0.0, max_tokens=1, logprobs=20)
    prompts = [f"{'the quick brown fox ' * 50} item {i}:" for i in range(2000)]

    runs = []
    for _ in range(8):
        out = llm.generate(prompts, sp, use_tqdm=False)
        runs.append([(o.outputs[0].token_ids[0],
                      o.outputs[0].logprobs[0][o.outputs[0].token_ids[0]].logprob)
                     for o in out])
    groups = []
    for i, r in enumerate(runs):
        if not any(runs[g[0]] == r and g.append(i) is None for g in groups):
            groups.append([i])
    print(f"{len(groups)} distinct bit-exact outputs over {len(runs)} identical runs")

if __name__ == "__main__":
    main()

Results (Qwen2.5-7B-Instruct, H100, vLLM 0.25.1):

config distinct bit-exact outputs / 8 verdict
tensor_parallel_size=1 1 deterministic
tensor_parallel_size=4 8 non-deterministic
tensor_parallel_size=4, fuse_allreduce_rms=False 1 deterministic (the fix)

Ruled out

  • Not custom all-reduce ([Bug] should_custom_ar()'s size threshold makes all-reduce kernel selection batch-dependent, which is why custom all-reduce can't simply be re-enabled under VLLM_BATCH_INVARIANT #50136): disable_custom_all_reduce=True in every TP run.
  • Not concurrency ([Bug]: VLLM_BATCH_INVARIANT=1 returns non-identical logprobs across repeats of a byte-identical concurrent workload at ~44 co-resident sequences #51187): --max-num-seqs 8 does not fix it under TP; TP=1 stays
    deterministic even at --max-num-seqs 256.
  • Not the MoE reduce_scatterv path ([Bugfix] Deterministic MoE combine (reduce_scatterv) under VLLM_BATCH_INVARIANT #45683): this is a dense model on the
    all-reduce path.
  • Not version-specific: reproduces on 0.20.2 and 0.25.1.
  • Not model-specific: also reproduces on Llama-3.1-70B (dense, TP=4).
  • enforce_eager=True largely mitigates (small residual); disabling only
    fuse_allreduce_rms is the clean fix.

Likely mechanism

The fused all-reduce + RMSNorm kernel appears to reduce in an order that isn't stable
run-to-run under TP. I could only narrow this from outside the engine.

Suggested fix

Disable fuse_allreduce_rms when VLLM_BATCH_INVARIANT is set, mirroring the existing
disable_custom_all_reduce guard in ParallelConfig. Happy to open a PR (I have the
change and a validated repro).
