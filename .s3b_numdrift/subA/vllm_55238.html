Update (2026-09-08): scope corrected, three claims below retracted

This reproduces only on compute capability 10.x (B200, B300). On 9.0 (H200), 12.0 (RTX PRO 6000) and 8.0 (A100, measured by @spa5k) the two execution paths are bit-identical. A clean result on those boxes is the expected outcome, not a failed reproduction. Hardware is the variable this report originally missed, and it is the reason the thread stalled.

Please use the single-variable repro in this comment rather than the script below. Three statements in the original text are wrong, and I am retracting them:

  1. The repro below is not single-variable. enforce_eager switches off torch.compile and CUDA graphs together, so it does not isolate graph replay. Holding torch.compile off in both arms and changing only cudagraph_mode, the failure still reproduces on a B300: worst logprob delta 6.773 nats, argmax moves at 3/13 positions, next token 992 → 9079.

  2. "The CUDA-graph path is not self-consistent between runs" is wrong. Each arm is bit-identical when run twice, on every box tested. The 7/12 and 8.27 figures came from re-running both arms together, which cannot attribute the movement to either one. Thanks to @sinanezhadian for catching the measurement gap.

  3. "VLLM_BATCH_INVARIANT=1 reduces this but does not fix it" is wrong. That measurement inherited the same conflation. With graph replay as the only variable, the flag makes the output bit-identical at every prompt length tested.

The headline 6/12 and 7.4689 figures also came from the conflated comparison. Part of that gap is custom_ops substitution, which is a separate and smaller effect. The control table below still stands, and the dense Gemma 4 siblings added in the comment strengthen it.

🐛 Describe the bug

Greedy decoding on google/gemma-4-26B-A4B-it returns a different token depending
on whether CUDA graphs are enabled. This is not a small numerical wobble: the
sampled token changes, and the argmax over the prompt differs at half the
positions, with logprob deltas up to ~7.5 nats.
Two other models tested identically do not move at all, so this does not look
like ordinary bf16 nondeterminism.

Reproduction

Self-contained; runs itself twice and prints the comparison.

import json, subprocess, sys
MODEL = "google/gemma-4-26B-A4B-it"
PROMPT = "The capital of France is Paris, and the capital of Japan is"
def capture(mode):
    from vllm import LLM, SamplingParams
    llm = LLM(model=MODEL, enforce_eager=(mode == "eager"),
              max_model_len=2048, gpu_memory_utilization=0.85)
    out = llm.generate([PROMPT], SamplingParams(
        temperature=0.0, max_tokens=1, logprobs=20, prompt_logprobs=20))[0]
    json.dump({"next_token": int(out.outputs[0].token_ids[0]),
               "prompt_logprobs": [None if p is None else
                                   {int(k): float(v.logprob) for k, v in p.items()}
                                   for p in (out.prompt_logprobs or [])]},
              open(f"/tmp/repro_{mode}.json", "w"))
def compare():
    a = json.load(open("/tmp/repro_eager.json"))
    b = json.load(open("/tmp/repro_graph.json"))
    print(f"next token eager={a['next_token']} cudagraphs={b['next_token']}")
    flips = worst = n = 0
    for pa, pb in zip(a["prompt_logprobs"], b["prompt_logprobs"]):
        if pa is None or pb is None:
            continue
        n += 1
        flips += max(pa, key=pa.get) != max(pb, key=pb.get)
        worst = max(worst, max(abs(pa[k] - pb[k]) for k in set(pa) & set(pb)))
    print(f"argmax differs at {flips}/{n} positions; worst logprob delta {worst:.4f}")
if __name__ == "__main__":
    if len(sys.argv) > 1:
        capture(sys.argv[1])
    else:
        for m in ("eager", "graph"):
            subprocess.run([sys.executable, __file__, m], check=True)
        compare()

Result

next token eager=992 cudagraphs=9079
argmax differs at 6/12 positions; worst logprob delta 7.4689

Expected: the same greedy token from both, and prompt logprobs agreeing to
within bf16 rounding.
A second run of the same script gave 7/12 flips and a worst delta of 8.27, so
the CUDA-graph path is not self-consistent between runs either.

Controls

The same script against two other models, unchanged apart from the repo id:

model next token argmax flips worst logprob delta
google/gemma-4-26B-A4B-it 992 vs 9079 6/12 7.47
Qwen/Qwen2.5-7B-Instruct (dense) same 0/12 1.66
Qwen/Qwen3-30B-A3B (MoE) same 0/12 0.58

Both controls hold their argmax at every position, so this is not MoE routing
sensitivity in general.

Additional data: VLLM_BATCH_INVARIANT=1 reduces this but does not fix it

Running the same script with VLLM_BATCH_INVARIANT=1:

next token eager=992 cudagraphs=992
argmax differs at 1/12 positions; worst logprob delta 2.3930

The sampled token now agrees, but the prompt distribution still does not. One
position still flips its argmax (position 8, token 563 vs 573) and the worst
logprob delta is still 2.39 nats.
For scale, that is worse than either control model gets in default mode:

run argmax flips worst logprob delta
gemma-4-26B, default 6/12 7.47
gemma-4-26B, VLLM_BATCH_INVARIANT=1 1/12 2.39
Qwen2.5-7B-Instruct, default 0/12 1.66
Qwen3-30B-A3B, default 0/12 0.58

So batch invariance removes most of the gap but leaves this model further from
self-consistency than two other models are without it. That it helps at all
points at batch-shape-dependent kernel selection as a contributing cause, but it
does not account for the whole divergence, and it is not a usable workaround —
it costs throughput and still changes the prompt logprobs.
