Your current environment

  • vLLM main @ 7470082 (2026-09-10), Python sources with the v0.29.0 precompiled kernels (VLLM_USE_PRECOMPILED=1); also reproduced with the v0.29.0 wheel
  • torch 2.13.0+cu130, triton 3.7.1, NCCL 2.27.3
  • 4x NVIDIA RTX PRO 6000 Blackwell (sm_120, 96 GB), PCIe only (no NVLink), driver 580.159.04
  • Model: Qwen/Qwen3-1.7B (bf16), attention backend TRITON_ATTN

🐛 Describe the bug

VLLM_BATCH_INVARIANT=1 is supposed to make outputs independent of the batch composition. With tensor parallelism it holds as long as sequence parallelism is off, but as soon as pass_config.enable_sp=True is set (or fuse_gemm_comms=True, which implies it), the same request produces different logprobs — and with greedy sampling different tokens — depending on how many other requests are in the batch.

Nothing in the config guards against this combination: enable_sp / fuse_gemm_comms are never checked against VLLM_BATCH_INVARIANT (compare the existing guards for cascade attention and the fused allreduce+RMSNorm path in vllm/config/vllm.py). docs/features/batch_invariance.md also does not mention SP / async TP.

Measurement. 64 prompts, greedy (temperature=0, max_tokens=24, logprobs=1, ignore_eos=True), seed=0, max_model_len=512, max_num_seqs=64, gpu_memory_utilization=0.5, default compilation (SP forces full-graph + cudagraph_mode=FULL). Each prompt is generated once alone (bs=1) and once with all 64 prompts in a single generate() call (bs=64); token ids and sampled-token logprobs are compared bitwise. sp_min_token_num is set explicitly because the SP threshold heuristic returns None on sm_120 (it only has SM90/SM100 buckets); on H100/B200 the heuristic enables SP automatically once enable_sp=True, so the same paths are hit there.

TP enable_sp sp_min_token_num tokens with different logprob prompts whose greedy output changed max abs logprob diff
4 False – 0 / 1536 0 / 64 0
4 True 64 1522 / 1536 17 / 64 2.98
4 True 1 (SP on every compile range) 1527 / 1536 15 / 64 2.04
2 True 64 1239 / 1536 6 / 64 2.13
2 True 1 4 / 1536 0 / 64 3.1e-6

So:

  1. Batch invariance under TP=4 is clean without SP (row 1), so this is not a general TP problem.
  2. With SP it is broken both when batches straddle the SP threshold (rows 2, 4: below the threshold the graph keeps all_reduce, above it the SequenceParallelismPass rewrites all_reduce + rms_norm into reduce_scatter + rms_norm + all_gather) and when SP is applied to every compile range (row 3). The SP path itself is not batch-invariant.
  3. TP=2 with SP everywhere is almost invariant (row 5), TP=4 is not (row 3). That is what you get if the reduction order of the reduce-scatter depends on which rank owns a token's output chunk: with 2 ranks a+b is commutative, with 4 ranks the ring order starting at the owner rank changes as the batch composition changes. (reduce_scatterv already has a deterministic root-0 reduce+scatter branch for the MoE combine under batch invariance, added in [Bugfix] Deterministic MoE combine (reduce_scatterv) under VLLM_BATCH_INVARIANT #45683 for exactly this class of problem; the plain reduce_scatter used by the SP pass has no such branch.)

Reproduction

bi_sp_probe.py (run with VLLM_BATCH_INVARIANT=1 VLLM_ATTENTION_BACKEND=TRITON_ATTN python bi_sp_probe.py <tp> <off|threshold>) 
import sys, json
from vllm import LLM, SamplingParams

tp = int(sys.argv[1]); sp = sys.argv[2]           # sp: "off" or an int threshold
N = 64
pass_config = {"enable_sp": False} if sp == "off" else {"enable_sp": True, "sp_min_token_num": int(sp)}
llm = LLM(model="Qwen/Qwen3-1.7B", tensor_parallel_size=tp, max_model_len=512, max_num_seqs=N,
          gpu_memory_utilization=0.5, compilation_config={"pass_config": pass_config}, seed=0)
cc = llm.llm_engine.vllm_config.compilation_config
print("enable_sp =", cc.pass_config.enable_sp, "sp_min_token_num =", cc.pass_config.sp_min_token_num)

base = ["The capital of France is", "def fibonacci(n):", "秋天的风", "In 1969, humans first", "The derivative of x^2 is",
        "Once upon a time in a small village", "SELECT name FROM users WHERE", "The mitochondria is", "Explain quantum entanglement briefly:",
        "import numpy as np\n", "The recipe calls for two cups of", "Dear hiring manager,", "翻译成英文：今天天气很好", "1, 1, 2, 3, 5, 8,",
        "The theory of relativity states", "To be or not to be,"]
prompts = [f"{base[i % len(base)]} ({i})" for i in range(N)]
sp_params = SamplingParams(temperature=0.0, max_tokens=24, logprobs=1, ignore_eos=True)

def run(batch):
    out = []
    for o in llm.generate(batch, sp_params, use_tqdm=False):
        toks = list(o.outputs[0].token_ids)
        lps = [float(d[t].logprob) for t, d in zip(toks, o.outputs[0].logprobs)]
        out.append((toks, lps))
    return out

single = [run([p])[0] for p in prompts]   # bs=1, one request at a time
batched = run(prompts)                    # bs=64, all requests together
tok_mismatch = sum(a[0] != b[0] for a, b in zip(single, batched))
lp_mismatch = sum(x != y for (_, la), (_, lb) in zip(single, batched) for x, y in zip(la, lb))
maxd = max((abs(x - y) for (_, la), (_, lb) in zip(single, batched) for x, y in zip(la, lb)), default=0.0)
print(json.dumps(dict(tp=tp, sp=sp, tokens=sum(len(l) for _, l in single), logprob_mismatch_tokens=lp_mismatch,
                      prompts_with_different_tokens=tok_mismatch, max_abs_logprob_diff=maxd)))

Expected: logprob_mismatch_tokens == 0 for every row, as it is for sp=off.

Proposed fix

  1. Short term: when VLLM_BATCH_INVARIANT=1, force pass_config.enable_sp = pass_config.fuse_gemm_comms = False with a warning_once, next to the existing batch-invariance guards in vllm/config/vllm.py, and add a multi-GPU regression test (TP=4, prompts on both sides of sp_min_token_num) to tests/v1/determinism/. Document the limitation in docs/features/batch_invariance.md.
  2. Longer term: keep SP under batch invariance by giving the SP pass's reduce-scatter a fixed, owner-independent reduction order (e.g. the root-0 reduce + scatter path that reduce_scatterv already uses for the MoE combine), then re-enable it.

I'm happy to send the PR for (1) with the test. @mosafariuk since #50505 is about custom allreduce under batch invariance and mentions AG/RS guards as a follow-up: does that follow-up already cover the SP reduce-scatter path, or should this be handled separately?
