Purpose

This PR is based on PR #24799 aiming to implement GPU version of ngram speculative decoding and make it compatible with Async Scheduler.

Test Plan

  • Async Scheduler + NGram + Qwen3-1.7B
    Test config:
# dataset is CMU-DoG, which is an input-grounded dataset.
python3.12 -u -m vllm.entrypoints.openai.api_server \
--host 0.0.0.0 \
--port 8000 \
--max-num-seqs 128 \
--max-model-len 2048 \
--model Qwen/Qwen3-1.7B \
--tensor-parallel-size 1 \
--trust-remote-code \
--dtype bfloat16  \
--enable-chunked-prefill \
--disable-log-requests \
--async-scheduling \
--speculative_config '{"method": "ngram_gpu", "num_speculative_tokens": 3, "prompt_lookup_max": 2,"prompt_lookup_min": 2}'

Test Device: NVIDIA H20

@zzaebok

Thanks for the question — this was intentional.

The main reason is that the effective batch dimension on this path is dynamic: the number of active requests can change from step to step, and the proposer also needs to handle reordering / incremental updates of the active rows. That makes CUDA graph capture less natural here unless we add extra staging or fixed input buffers to make the inputs capture-safe.

In practice, that extra complexity did not look worthwhile for this kernel. The current torch.compile + Triton fused-kernel path already gives us most of the benefit we need, and the end-to-end execution time of this operator is only around ~100 us. So even if CUDA graphs remove some launch overhead, the absolute gain is likely quite small compared with the engineering cost of adapting the input-buffering path.

So for now I kept cudagraph_mode=CUDAGraphMode.NONE for simplicity. If later profiling shows this becomes a meaningful bottleneck, I’m happy to revisit it.
