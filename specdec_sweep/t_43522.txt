Purpose

DFlash generates multiple speculative tokens in parallel within one step. This can substantially increase the speculative length, leading to longer accepted lengths and better performance. However, a longer verification length also puts computing pressure on the target model. Compared with methods such as MTP, DFlash have a lower acceptance rate, meaning many verified speculative tokens are eventually discarded.

This PR adds a simple dynamic verification mechanism for DFlash. Instead of always verifying the full preconfigured speculative length, we can truncate speculative tokens early based on draft-token confidence. The motivation is that low-confidence draft tokens are unlikely to be accepted, so removing them before target-model verification can reduce wasted compute.

This is especially useful under high-concurrency workloads, where target-model verification is more likely to become compute-bound. In low-concurrency settings, the extra computation, copying and shorter accepted length can hurt performance. For details, please see the test result.

Main changes:

Add dynamic_verifying to SpeculativeConfig .

None : disabled.

float in (0, 1) : confidence threshold.

"auto" : adaptive per-request threshold = clamp(mean(conf), 0.1, 0.8) .

Add dynamic_verifying_min_length to avoid over-truncating every request.

Compute DFlash draft-token confidence from greedy draft logits.

Truncate DFlash speculative tokens once confidence drops below the configured threshold.

Propagate the valid draft-token counts back to the scheduler so speculative decoding stats use the actually verified draft length.

Document the new DFlash speculative config options.

AI assistance was used in preparing this PR. I reviewed the changed lines and am responsible for the implementation, behavior, and tests.

Author 

I think this is a duplicate of this PR: #35301 For which I have some reservations. I expect the same concerns will apply to this PR, see my comments.

Thanks for your feedback!

I took a look at #35301 . I agree that both PRs share a similar idea around confidence-based truncation, but I think the goals and implementations are quite different:

[speculative decoding] Add dynamic speculation length with confidence-threshold early exit #35301 implements per-step dynamic k for autoregressive speculative decoding by using more spec steps with early stopping. This does not directly apply to DFlash parallel drafting.

Simply 0-padding low-confidence tokens does not reduce verification compute of target model.

The main goal of this PR is per-request dynamic verification length, so that the target model verifies fewer draft tokens for batched requests whose draft tokens are unlikely to be accepted.

That said, I do think these two PRs could potentially be unified at the config, runner, and scheduler layers, while still using method-specific dynamic strategies for different spec decoding methods.

Following your comments in #35301 , I will add more comparisons, including:

Qwen3-8B without speculative decoding

DFlash with k=7 

EAGLE3 with k=2 or 3 

MATH500 results

The current results also do show that this approach does not provide speedup at lower batch sizes.

I also looked at #32374 . That PR goes deeper into dynamically allocating k in scheduler, which is also something I would like to explore next. More specifically, I am considering a scheduler policy based on batched_tokens * context_len , combined with confidence-based truncation. Similar to #35301 , I think #32374 could also be complementary to this PR.

Regarding the CUDA graph concern, I guess it may depend on specific operators? In the Qwen3-8B experiments, shorter dynamic verification length does improve performance, but this may not hold for other operators such as linear attn or moe. I will test more situations to better understand this. In addition, the case of high concurrency, for example 64, batched_token = 64*16 = 1024 is already greater than the general max_graph_size = 512, and cudagraph_mode becomes None. However, I am not sure whether there are other optimizations for uniform_decode besides CUDA graph. If there are, please point them out and I will further study them.

Thanks for the summary! A few things to watch out for:

Some attention backends may rely on having a fixed number of spec tokens in the batch to dispatch an optimized kernel when the requests are all verification requests. If we vary the number of verification tokens per step, we need to ensure that we're still issuing the optimized kernel pathway. This is largely optimized for server-class Blackwell GPUs and may not be visible on others. https://github.com/vllm-project/vllm/blob/main/vllm/v1/attention/backends/flashinfer.py#L662C14-L662C43 

This is a particular challenge for FULL CUDA graph compatibility: I believe we currently record graphs across batch sizes with a uniform verification size equal to 1 + num_spec_tokens . If we replay the wrong graph we might hit a wrong attention kernel and corrupt the outputs.

Synchronization overhead is nontrivial. We have worked hard to ensure that there are no blocking synchronization points in our main model runner loop. By deciding the verification size based on some heuristic derived from previous-step acceptance rates, we introduce a data dependence between GPU data and the CPU decision-making, forcing a synchronization between the steps. This is costly as the GPU must go idle between the synchronization point and the next issued work, and if the CPU cannot issue work fast enough then we might waste a lot of time. This is especially critical in the fastest workloads, e.g. NVFP4 on B200/B300.

Author 

Thanks for the summary! A few things to watch out for:

Some attention backends may rely on having a fixed number of spec tokens in the batch to dispatch an optimized kernel when the requests are all verification requests. If we vary the number of verification tokens per step, we need to ensure that we're still issuing the optimized kernel pathway. This is largely optimized for server-class Blackwell GPUs and may not be visible on others. https://github.com/vllm-project/vllm/blob/main/vllm/v1/attention/backends/flashinfer.py#L662C14-L662C43 

This is a particular challenge for FULL CUDA graph compatibility: I believe we currently record graphs across batch sizes with a uniform verification size equal to 1 + num_spec_tokens . If we replay the wrong graph we might hit a wrong attention kernel and corrupt the outputs.

Synchronization overhead is nontrivial. We have worked hard to ensure that there are no blocking synchronization points in our main model runner loop. By deciding the verification size based on some heuristic derived from previous-step acceptance rates, we introduce a data dependence between GPU data and the CPU decision-making, forcing a synchronization between the steps. This is costly as the GPU must go idle between the synchronization point and the next issued work, and if the CPU cannot issue work fast enough then we might waste a lot of time. This is especially critical in the fastest workloads, e.g. NVFP4 on B200/B300.

Thanks for pointing these out. These are all important concerns.

Unfortunately, I do not have access to Blackwell GPUs, so I cannot directly validate the server-class Blackwell path. From the code, it looks like TRTLLM decode requires uniform query lengths per request. In that case, this dynamic verification feature may need to be disabled for that backend/path.

For the Qwen3-8B setup I tested most, I found that even without dynamic verification length, where the query length is still fixed at 1 + num_spec_tokens , desc.uniform is already False , and CUDA graph mode is mixed prefill-decode, FULL . In that case, whether the verification query length is uniform does not seem to change the graph path. For Qwen3.5-35B, however, I observed a different behavior: CUDA graph is FULL when the verification size is uniform, but falls back to PIECEWISE when it becomes non-uniform. This does cause a performance regression with dynamic verification. I need to spend more time understanding this path. In the worst case, models/backends that rely on the uniform verification path may simply not be a good fit for this dynamic verification feature.

Synchronization is another important issue. I think this is one reason why this feature gets a worse performance at low batch sizes. However, synchronization seems unavoidable here. This is similar to the ngram_gpu path in [Core] NGram GPU Implementation compatible with Async Scheduler #29184 (MRV2 [ModelRunner V2] Speculative Decoding NGram GPU Implementations #40704 ): the async copy and synchronize are necessary; otherwise, as we also tested, the acceptance drops. That said, I agree the current implementation can likely be improved. A better approach may be to share the synchronization point with the existing draft_token_id copy synchronization, similar to MRV2, instead of using an independent synchronization stream. The current implementation reuses the ngram_gpu valid-length synchronization path mainly for simplicity. I will try to change it to share the existing synchronization and see whether that improves performance.

Thanks again for the detailed suggestions!
