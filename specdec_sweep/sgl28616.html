Motivation

NGRAM speculative decoding was hard-blocked when DP attention was enabled — _handle_ngram raised ValueError("Currently ngram speculative decoding does not support dp attention."). This PR enables --speculative-algorithm NGRAM together with --enable-dp-attention.

Modifications

  • Drop the guard in arg_groups/speculative_hook.py.
  • NGRAMWorker — handle an idle DP rank (a rank with no local requests), mirroring how EAGLE handles it:
    • On a global verify step — gated on the DP-gathered is_extend_in_batch flag (which is populated even with the overlap scheduler off, unlike global_forward_mode) — attach a zero-row NgramVerifyInput so ForwardBatch.init_new applies the draft-token coefficient and global_num_tokens scaling agrees across ranks.
    • Keep the idle batch in IDLE mode (do not convert it to TARGET_VERIFY): an idle batch stays collective-aligned through init_new's idle path, which skips attention; a bs=0 TARGET_VERIFY forward would instead launch the attention kernel with degenerate args. An explicit idle branch in forward_batch_generation runs a collective-aligned forward and returns an empty result.
  • NgramVerifyInput — add create_idle_input; expose kv_indptr/kv_indices as None so the decode/idle attention-metadata path builds plain metadata from seq_lens. (num_tokens_per_req is no longer part of this PR — [Spec] Single-source num_tokens_per_req derivation and access #31013 landed it upstream.)
  • forward_batch_info — NGRAM captures no hidden states, so an idle DP rank carrying a zero-row NgramVerifyInput reaches the extend/idle slice with hidden_states None; guard it. This mirrors the identical guard Multiple flexibility fixes for DP attention #33537 added on the sibling target_verify branch of the same function.
  • Tests — unit test for the guard removal; e2e GSM8K test (tp2/dp2).

Accuracy Tests

Validated on 2× H20. GSM8K (200q / 5-shot / temp 0) parity vs the dp-on non-spec baseline:

backend baseline-dp ngram-dp
triton 0.930 0.930
flashinfer (1000q) 0.914 0.915

At 1000 questions on flashinfer, correctness flips are balanced (C→W = 7 / W→C = 8, McNemar p ≈ 1.0) — i.e. lossless up to floating-point. dp-off regression (NGRAM without DP): 0.935. The new e2e test passes on a Qwen3-30B-A3B-class target: GSM8K 0.935.

Speed Tests and Profiling

NGRAM acceptance length is ~10 on repetitive workloads and is unaffected by DP (dp-triton 10.65, no-dp-triton 12.43, dp-flashinfer 10.65) — DP attention does not degrade speculation. On GSM8K (math reasoning, less repetitive) accept length is ~1.8.

Note: pre-existing DP issue with qwen2.py models (out of scope)

The default NGRAM CI target (Qwen2.5-Coder-7B, qwen2.py) has an unrelated, pre-existing DP-attention bug that reproduces with no speculative decoding: under --enable-dp-attention the attention emits KV heads split by tp_size while the DP KV pool holds the full head count, so the KV store fails (view / store_cache mismatch) at warmup. The e2e test therefore uses the DP-attention-capable Qwen3-30B-A3B target (the same model as the EAGLE DP test). Filed separately as #28615.

Skip NGRAM verify on global extend batches

When DP attention mixes work across ranks (for example one DP rank is prefill/extend while this rank has decode requests), batch.is_extend_in_batch is true. EAGLE handles that case as a plain target step (eagle_worker_v2.py:963 checks forward_mode.is_extend() or batch.is_extend_in_batch), but this code only checks the local forward_mode and still converts decode ranks to TARGET_VERIFY with spec_info; ForwardBatch.init_new then multiplies the gathered global_num_tokens by draft_token_num only on those ranks while the extend ranks leave the counts unscaled, so the MLP-sync collective sizes disagree and the step can hang or crash. Please return without speculation whenever batch.is_extend_in_batch is true.

Thanks for the catch — I traced this carefully:

In the default config the spec + dp-attention MLP-sync block (scheduler.py:2562) defers a decode rank to an idle batch whenever any rank prefills: prepare_mlp_sync_batch_raw creates a get_idle_batch() when max(global_num_tokens) > 0 (dp_attn.py:237-242). So a locally-decode rank never coexists with is_extend_in_batch=True — it arrives as an idle batch, which the idle branch already gates on the flag. (The scheduler.py:2558 comment states this intent: prefill and decode aren't mixed under spec + dp-attn.)

But under --speculative-skip-dp-mlp-sync that prevention block is skipped, and the mismatch you describe is exactly right: the decode rank scales global_num_tokens by draft_token_num while the extending rank doesn't, so the MLP-sync collective shapes disagree.

Fixed in f5221318cf by gating the decode path the same way EAGLE does (eagle_worker_v2.py:963):

if not batch.forward_mode.is_decode() or batch.is_extend_in_batch:
    return

This is a no-op in the default config (every all-decode step has is_extend_in_batch=False, so it never disables speculation) and prevents the desync under the skip flag. Thanks again!

Thanks @bandham-manikanta — this is exactly the second data point I was after. All my numbers are from 2× H20, so an Ampere confirmation on (1) and (2) is the part I couldn't produce myself.

On (3): that assertion is expected, and I'd rather leave it alone in this PR. Writing out the reasoning, since "just allow NGRAM too" was my first instinct as well.

It's a pre-existing guard, not something this PR narrows. arg_groups/speculative_hook.py:133 landed together with the flag in #24177, at a point where _handle_ngram still hard-rejected DP attention outright ("Currently ngram speculative decoding does not support dp attention." — the check this PR removes). So the assert was really restating "only EAGLE supports DP attention at all" rather than making an independent claim about this flag.

Safety isn't what's blocking it. The desync this flag can cause under NGRAM is the one flagged in the review thread above, and it's already fixed here: _prepare_for_speculative_decoding returns early on batch.is_extend_in_batch (ngram_worker.py:331), mirroring eagle_worker_v2.py:1108. Relaxing the assert would not be unsafe.

But today it buys NGRAM nothing. The flag's only effect is skipping the pre-merge sync at scheduler.py:3114, which is what keeps prefill and decode from co-occurring across DP ranks. On the mixed steps that then become possible:

  • that same is_extend_in_batch gate turns speculation off for the decode rank, and
  • is_ngram_supported in runner/decode_cuda_graph_runner.py:715 requires bs * captured_req_width == input_ids.numel(), and captured_req_width is draft_token_num under spec (model_runner.py:785), so a width-1 plain decode batch also falls back to eager.

Net: one all-gather per step saved, in exchange for mixed steps running with neither speculation nor a CUDA graph. EAGLE takes a different route on those steps (full target-prefill + draft-extend at eagle_worker_v2.py:1108), so its trade-off isn't the same one. I don't have a benchmark showing this is a win for NGRAM, and enabling the flag without one mostly hands users a silent slowdown.

And the assert is too narrow in ways unrelated to NGRAM. It's a literal == "EAGLE", so EAGLE3 is rejected too (alias resolution maps NEXTN→EAGLE but leaves EAGLE3 as-is). And dspark_components/dspark_planner.py:178 already reads speculative_skip_dp_mlp_sync as a disqualifier for its DP-tier gather, which this assert makes unreachable. That points at a per-algorithm capability rather than one more string in the comparison — a separate PR with its own mixed-traffic validation, not scope stacked on this one. Happy to take it once this lands.

If you're up for one more run, the highest-value one left is accuracy rather than throughput: GSM8K with NGRAM + --enable-dp-attention at tp2/dp2, against a DP-on non-speculative baseline on the same node. Speculation must be output-neutral, so any accuracy delta there is a real bug — and that's the one claim I can only support with my own hardware right now. Reported accept length alongside it would be a bonus.
