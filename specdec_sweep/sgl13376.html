Motivation

Speculative Decode often works well for relatively smaller batch sizes. When the batch size is large, we want to run regular decode. Similar feature is also supported in vllm: vllm-project/vllm#4592.

From the benchmark, at large batch size, we can reduce 50% of the latency. See benchmark result down below.

I also implemented this feature for EAGLE3. However, because of the required draft extend step after each decode, the latency increases by a lot even after merging them into a single CUDA graph. See: Dynamic SpecDecode in SGLang

We are going to support overlap scheduler batch for ngram in a following PR to further reduce the overhead.

Modifications

This pull request introduces a dynamic mechanism for enabling or disabling speculative decoding (spec decode) on a per-batch basis, based on batch size thresholds and runtime conditions. It also refactors the codebase to consistently check this new flag rather than relying solely on the speculative algorithm type, and adds logic to handle transitions between speculative and regular decoding. Several minor refactorings and bug fixes are included to support these changes.

Dynamic Speculative Decoding Enablement:

  • Added an is_spec_enabled_for_batch flag to ScheduleBatch to dynamically enable or disable speculative decoding per batch, with logic to update this flag based on a configurable batch size threshold in Scheduler.update_running_batch. Also introduced a turning_off_specdecode flag to handle transitions. [1] [2] [3]
  • Updated prepare_for_decode in ScheduleBatch to merge output IDs appropriately when turning off speculative decoding mid-batch, ensuring correct token handling during the transition. [1] [2]

Consistent Use of Speculative Decoding Flag:

  • Refactored all speculative decoding logic in scheduler, output processor, and metrics mixins to use the new is_spec_enabled_for_batch flag instead of checking the algorithm type, ensuring correct behavior when speculative decoding is dynamically toggled. [1] [2] [3] [4] [5] [6]

Speculative Algorithm Handling and Refactoring:

  • Updated various checks and code paths to use new or refactored methods like is_none_or_ngram() for clarity and correctness in handling speculative algorithms, and ensured correct propagation of the speculative algorithm reference in model executor and scheduler classes. [1] [2] [3] [4] [5] [6] [7] [8]

Speculative Decoding Metrics and State Reporting:

  • Improved metrics and internal state reporting to account for batches where speculative decoding is disabled, preventing division by zero and reporting correct averages. [1] [2]

Minor Fixes and Cleanups:

  • Minor bug fixes, code cleanups, and imports (such as adding accumulate from itertools), and improved comments/documentation throughout the affected files. [1] [2] [3]

These changes collectively make speculative decoding more robust and adaptable to runtime conditions, improving both correctness and flexibility.

Unit Test added, ngram unit test passed.

Summary of Changes

Hello @yubofredwang, I'm Gemini Code Assist1! I'm currently reviewing this pull request and will post my feedback shortly. In the meantime, here's a summary to help you and other reviewers quickly get up to speed!

This pull request enhances the system's speculative decoding capabilities by introducing a dynamic mechanism that intelligently switches between speculative and regular decoding based on batch size. For NGRAM speculative decoding, if the batch size exceeds a predefined threshold, the system will gracefully fall back to regular decoding. This change aims to optimize performance by leveraging speculative decoding for smaller, more efficient batches while avoiding its potential overhead for larger ones, ultimately making the decoding process more robust and adaptable to varying runtime conditions.

Highlights

  • Dynamic Speculative Decoding: Introduced a dynamic mechanism to enable or disable speculative decoding (specifically NGRAM) on a per-batch basis, controlled by a configurable batch size threshold. This allows the system to fall back to regular decoding for larger batches where speculative decoding might be less efficient.
  • Refactored Speculative Decoding Logic: Updated the scheduler, output processor, and metrics mixins to consistently use a new is_spec_enabled_for_batch flag instead of solely relying on the speculative algorithm type. This ensures correct behavior when speculative decoding is dynamically toggled.
  • Transition Handling: Added logic in ScheduleBatch.prepare_for_decode to correctly merge output IDs when transitioning from speculative to regular decoding mid-batch, ensuring token handling remains accurate.
  • Dedicated Decode CUDA Graph Runner: Implemented a new NgramDecodeCudaGraphRunner to manage CUDA graphs specifically for decode batches when speculative decoding is turned off, optimizing performance for these scenarios.
  • Improved Metrics and State Reporting: Adjusted speculative decoding metrics and internal state reporting to prevent division by zero errors and accurately reflect performance when speculative decoding is disabled for certain batches.
  • New Server Argument and Validation: Added a new server argument --speculative-batch-size-threshold to configure the dynamic behavior, along with validation to ensure this feature is only used with NGRAM speculative decoding.
  • Unit and Batch Generation Tests: Included new unit tests and a batch generation test case that simulates ramp-up scenarios to verify the dynamic speculative decoding mechanism works as expected.
