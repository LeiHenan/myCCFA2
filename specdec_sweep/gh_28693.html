Purpose

We implemented Elastic Speculation, an adaptive control layer for EAGLE speculative decoding that delivers double-digit latency improvements over fixed-length speculation while reducing KV-cache DRAM traffic.

Two independent features:

  1. Adaptive Draft Length: Dynamically adjusts speculation depth based on acceptance rates
  2. Confidence-Based Early Exit: Gates KV writes for low-confidence draft tokens

Summary

Adaptive Draft Length

Captures multiple draft lengths as CUDA graphs (default: [5, 10, 15]), tracks
acceptance rate via EWMA, selects based on thresholds:

70% acceptance → d = high (maximize benefit)
50-70% → d = med (balanced)
30-50% → d = low (conservative)
<30% → d = very low (minimize waste)

Confidence-Based Early Exit

When draft token confidence drops below threshold, set slot_mapping = -1. CUDA
kernel early-returns, skipping KV write:

In reshape_and_cache kernel:

if (slot_idx < 0) return;  // No DRAM write

Implementation

Core implemntation:

  • vllm/config/speculative.py - Config options
  • vllm/v1/cudagraph_dispatcher.py - Multi-draft-length graph support
  • vllm/v1/spec_decode/eagle.py - Adaptive + early exit logic
  • vllm/v1/spec_decode/metrics.py - EWMA tracking, draft selection

Environment variables:

VLLM_SPEC_ADAPTIVE_DRAFT_LENGTH = 0,1
VLLM_SPEC_CONFIDENCE_THRESHOLD = [0,1]

Config options:

SpeculativeConfig(
  draft_length_options = [d_1 ... d_n],  # None = auto-compute
  draft_confidence_threshold = c,    # 0.0 = disabled
)

Testing and Results

Implementation was tested across draft lengths (5, 10, 15), early exit thresholds (0.3, 0.5, 0.7), and two Llama target + draft model pairs and evaluated on four benchmark datasets to simulate diverse inference workloads (Alpaca, SQuAD, BigCodeBench, and CNN DailyMail).

We observe a ~20-50% reduction in latency depending on the task and configuration and confirm a threshold-proportional reduction in KV writes (~50% at 0.5 at 1-3% latency cost). In production, where as much as 70% of memory can be KV cache and as up as 50% of attention cycles stall on bandwidth constraints, this could potentially translate to latency savings as well.

Our blog post with background, methodology, and full results can be found here: https://iluvatarlabs.com/blog/2025/11/elastic-speculation/

We're excited to PR this to vLLM and happy to address any feedback!

Include draft length in CUDAGraph batch descriptor

Adaptive draft lengths are added to the set of CUDA graph keys, but the BatchDescriptor used for dispatch is still created without a draft_length value. This means every decode step uses the same key regardless of the current draft length and will replay the first captured graph. Once the adaptive controller switches from the initial draft length to another option, the dispatcher will attempt to reuse a graph recorded with different tensor shapes, causing CUDA graph replay failures or corrupted outputs. The descriptor passed to dispatch() needs to reflect the selected draft length so that each length is captured and replayed with the correct shapes.

Author

First off, happy new year and thanks everyone for the thoughtful review and comments! Apologies for the very belated response, I was offline for most of the holidays and finally catching up on everything.

@MatthewBonanni Really appreciate the detailed comments in your review, Matthew. We're preparing an update we'll push shortly.

Regarding the envs, we've switched over using the standard args in --speculative-config.

For the model_executor scripts, it was something was mirrored from llama.py (it's already in deepseek_eagle.py and minicpm_eagle.py) because vLLM doesn't like the mismatch that occurs when quantized models are loaded from HF if they have bias params.

Great call on using masked_fill_, now modifies tensor in place.

On the extra CPU-GPU sync, It's a great call out since the whole point of this is for efficiency while minimizing unnecessary overhead. I'll have to think a little more about how we can avoid this and switch everything downstream to GPU tensors. In terms of low hanging fruit, we can reduce the # of syncs to just 1 for early exit if we move it outside the loop (and skip it entirely if not using early exit and just do seq_lens_cpu += draft_length).

Finally, for the tunable threshold, we should absolutely make it configurable. We zeroed in on 0.7 as a default based on our tests but users should be able to select a threshold that meets their speed vs quality calculus.

@fluctlux Thanks for sharing those links! I wasn't aware of them previously so I'll take some time this week to compare those proposed methods with how we implemented this approach. At a quick glance, these appear more similar to the adaptive draft length component rather than the confidence-based early exit.

Terrific questions. I do believe these are valuable features to integrate as the savings to both latency and memory bandwidth can be quite substantial depending on the workload. Though I don't have hard evidence of this, it is plausible that frontier labs are already using similar techniques in their proprietary stacks given their current emphasis on latency tricks for serving.

IMO the biggest obstacle is determining when to use elastic speculation in practice. While confidence-based early exit is pretty much universally beneficial in bandwidth-constrained settings, adaptive draft length has a small amount overhead so the cost-benefit depends on the target-draft model pair and accept rate. It's worth noting that in our benchmarking, we found that adaptive draft length even WITHOUT graph capture was faster than fixed draft length WITH it. Speaking of graph capture...

@Fsanic This is another terrific question. We actually only need to capture a single graph per batch size as multiple draft lengths produce duplicate graphs. The num_tokens dimension already differentiates CUDA graphs based on actual tensor shapes. So in practice, no additional memory overhead.

Your question actually reminded me of some dead code that snuck into this PR that we're going to clean up. We did try a couple approaches to optimize multiple draft length graph capture (behind enable_draft_length_cudagraph_specialization), which is how we found doing so to be redundant and just wastes memory.

[CLEANUP] Remove redundant draft_length CUDA graph specialization
9ae68ff 
The enable_draft_length_cudagraph_specialization feature was removed because
draft_length in BatchDescriptor was only used as a Python dictionary key for
CUDA graph lookup, not as an input to GPU computation. CUDA graphs with the
same num_tokens but different draft_length captured identical GPU operations,
wasting 3-4x memory for no benefit.

Removed:
- enable_draft_length_cudagraph_specialization field from SpeculativeConfig
- draft_length field from BatchDescriptor
- _resolve_draft_length_for_cudagraph method
- draft_length handling in CUDA graph capture/dispatch

Preserved (runtime adaptive draft length still works):
- draft_length_options in SpeculativeConfig
- compute_optimal_draft_length() in SpecDecodingStats
- draft_length parameter in propose()

[PERF] Reduce GPU-CPU sync points in early-exit drafting loop
95bc755 
The early-exit feature introduced a per-iteration GPU-CPU sync
(active_mask.cpu()) to keep seq_lens_cpu updated. However, FlashAttention
does not read seq_lens_cpu during build_for_drafting — it uses the GPU
seq_lens tensor directly. This commit defers the CPU sync to after the
loop for FlashAttention, reducing N GPU-CPU synchronizations to 1.

Other backends (FlashInfer, ROCm AITER FA, FlexAttention, etc.) read
seq_lens_cpu inside build(), so they retain the per-iteration sync via
a runtime isinstance check on the attention metadata type.

Signed-off-by: yuz207 <ben@iluvatarlabs.com>

[BUGFIX] Update acceptance EWMA in async scheduling path
ee7c557 
The spec decode stats (observe_draft + update_acceptance_ewma) were only
called inside the `if not self.use_async_scheduling:` branch. With async
scheduling enabled, the EWMA stayed permanently at the 0.5 bootstrap
value, causing compute_optimal_draft_length to always select the shortest
draft length.

Hook into the existing per-request acceptance counting in _update_states,
which already computes num_accepted from valid_sampled_token_count for the
async path. Accumulate batch-level stats and update EWMA immediately after

[BUGFIX] Fix auto-computed draft_length_options exceeding proposer cap
f8c5a03 
The old formula [max(2,n//2), n, min(8,n*2)] produced a third option
greater than num_speculative_tokens for any n<8. Since propose() caps
draft_length at num_speculative_tokens, the third option was silently
clamped to n at runtime — identical to the second option. This collapsed
the three-tier adaptive system to two tiers (or one for n=2).

Use thirds of n instead: [n//3, 2*n//3, n]. All values are <= n so none
are capped by propose(). For n=15 this produces [5,10,15], matching the
benchmarked configuration.
