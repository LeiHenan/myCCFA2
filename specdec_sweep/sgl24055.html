Motivation

PR #21599 introduced adaptive speculative decoding that dynamically adjusts speculative_num_steps based on EMA of accept lengths.

This PR extends the adaptive controller to maintain per-batch-size independent state, where each BS range has its own EMA tracker, candidate steps, and hysteresis thresholds.

Modifications

Architecture

The AdaptiveController maintains a bs_params dict keyed by BS lower bounds, matched via bisect_right - 1, here's the default value:

AdaptiveController
├── bs_params: Dict[int, AdaptiveSpeculativeParams]
│   ├── BS [1, 64):   steps=[1,3,7], hysteresis=(up=0.0, dn=-0.25)
│   ├── BS [64, 128):  steps=[1,2,5], hysteresis=(up=0.0, dn=0.0)
│   └── BS [128, ∞):   steps=[1,2,6], hysteresis=(up=-0.1, dn=0.25)
└── _states: Dict[int, SpecRuntimeState]  (shared, indexed by step count)

Each BS range has its own:

  • EMA tracker — observations from small bs don't pollute the large bs signal
  • current_step seperated for different bs — small bs can run at step 7 while large bs runs at step 5
  • different bs can take different sets of candidate_params — small bs candidates default to take [1,3,7] vs large bs candidates default to [1,2,6]
  • Hysteresis parameters — can be tuned per BS range

SpecRuntimeState objects are shared across BS ranges (keyed by step count, not by BS), since CUDA graphs and attention backends depend only on step count.

Per-BS Config File Format

Example:

{
  "1":   {"steps": [1, 3, 7], "up_hysteresis": 0.0, "down_hysteresis": -0.25},
  "8":   {"steps": [1, 3, 7], "up_hysteresis": 0.0, "down_hysteresis": -0.25},
  "32":   {"steps": [1, 3, 7], "up_hysteresis": 0.0, "down_hysteresis": -0.25},
  "64":  {"steps": [1, 2, 5], "up_hysteresis": 0.0,  "down_hysteresis": 0.0},
  "128": {"steps": [1, 2, 6], "up_hysteresis": -0.1, "down_hysteresis": 0.25}
}

Config keys are lower bounds matched via bisect_right - 1. In the above example, BS=16 uses the "8" slot; BS=100 uses the "64" slot; BS=200 uses the "128" slot. This flat format is backward-compatible with the original adaptive config from PR #21599.

Backward Compatibility

To get behavior identical to PR #21599 (disable bs-aware), use a config with a single BS=1 entry:

{
  "1": {"steps": [1, 3, 7], "up_hysteresis": 0.0, "down_hysteresis": -0.25}
}

With a single BS=1 entry, all batch sizes map to the same slot, producing identical EMA tracking, step selection, and activation timing as the global EMA-only baseline.

Without --speculative-adaptive-config, the built-in defaults (per-BS steps and hysteresis) are used automatically.

Speed Tests and Profiling

Setup

  • Model: GLM-4.7-FP8 on 8×GPU (TP=8), EAGLE speculative decoding with topk=1
  • Workload: transition (alternating low/high acceptance phases: low_1 → high_1 → low_2 → high_2)
  • Benchmark tool: bench_adaptive_speculative.py
  • Metrics: 3-run average throughput (tok/s), per-phase throughput
  • CUDA graph BS: [1, 2, 4, 8, 16, 32, 64, 128], --mem-fraction-static 0.65
  • Configs compared: No-bs-aware (ema_only_config.json, single BS=1 slot with [1,3,7]) vs BS-aware (default config, with lower num_steps candidate when bs>=64)

Comprehensive Results: SpecV1 and SpecV2

Both SpecV1 (synchronous scheduler) and SpecV2 (overlap scheduler) support bs-aware adaptive spec. The table below shows 3-run average output throughput across all batch sizes.

Usage

# Per-BS adaptive with built-in defaults
python3 -m sglang.launch_server \
  --model-path /path/to/model \
  --speculative-algorithm EAGLE \
  --speculative-num-steps 3 --speculative-num-draft-tokens 4 \
  --speculative-eagle-topk 1 \
  --speculative-adaptive

# Per-BS adaptive with custom config file
python3 -m sglang.launch_server \
  --model-path /path/to/model \
  --speculative-algorithm EAGLE \
  --speculative-num-steps 3 --speculative-num-draft-tokens 4 \
  --speculative-eagle-topk 1 \
  --speculative-adaptive \
  --speculative-adaptive-config /path/to/per_bs_config.json

# Fallback to EMA-only (identical to PR #21599)
# Use a config with a single BS=1 entry:
python3 -m sglang.launch_server \
  --model-path /path/to/model \
  --speculative-algorithm EAGLE \
  --speculative-num-steps 3 --speculative-num-draft-tokens 4 \
  --speculative-eagle-topk 1 \
  --speculative-adaptive \
  --speculative-adaptive-config ema_only_config.json

Where ema_only_config.json contains:

{
  "1": {"steps": [1, 3, 7], "up_hysteresis": 0.0, "down_hysteresis": -0.25}

I found that when different batch sizes correspond to different sets of speculative steps, the CUDA graph capture logic currently iterates over the union of speculative steps across all batch sizes, and captures the full set of CUDA graphs for every batch size. However, in practice, some batch sizes will never enter certain steps.

For example:

"1":   {"steps": [1, 3, 7], "up_hysteresis": 0.0, "down_hysteresis": -0.25},
"64":  {"steps": [1, 3, 5], "up_hysteresis": 1.75, "down_hysteresis": -0.25}

When capturing the CUDA graph for steps = 5, we should not capture the graph for bs = 1, because bs = 1 only drafts with steps [1, 3, 7].

This may lead to unnecessary GPU memory usage, especially in scenarios where each batch size corresponds to only one step and the step distribution is relatively wide, maybe in DFlash.

Perhaps this could be addressed in build_adaptive_runtime_state before calling init_cuda_graphs(): temporarily override server_args.cuda_graph_bs with the batch-size range that the current step can actually serve. The _override_worker_state context manager has already been implemented in eagle_worker.py:395, so extending it should be enough.

This way, all three runners would naturally receive the pruned list. It would be very helpful for me if this issue could be resolved.

Did a quick investigation of performance degradation across different batch sizes for three cases: LLaMA, Qwen3.6, and DSV4:

Thanks for the investigation! I've tested several additional models and here are the results:

Models tested: Qwen3-235B-A22B (EAGLE3, 8xH20), MiniMax-M2.5 (EAGLE3, 4xH20, FP8), GLM-4.7-FP8 (EAGLE, 8xH20)

Key finding: The no-spec crossing point varies dramatically by model

Model Draft Quality Crossing BS (LOW) Crossing BS (HIGH) Crossing BS (OVERALL)
GLM-4.7-FP8 Strong (AL ~2.3/6.9) BS≥64 Never Never
Qwen3-235B-A22B Uniformly good (AL ~4.2/4.6) BS≥64 Never Never
MiniMax-M2.5 Weak (AL ~2.5/2.8) BS≥8 BS≥8 BS≥32

This matches the observation across LLaMA/Qwen3.6/DSV4 — the crossing point depends on multiple factors: draft model quality is the dominant one, but sequence length, TP size, and hardware (e.g., H20 vs H100 memory bandwidth ratio) also shift the breakeven. Models with weak drafts (MiniMax, DSV4) cross the no-spec line at much lower batch sizes, while strong drafts (GLM, Qwen3, LLaMA high-accept) can sustain speculation to higher BS. The EMA ceiling rule (below) coudl be applied as a safe lower bound that prevents fundamental degradation from over-speculation — regardless of which factor is causing the low accept rate, the ceiling responds to the observed accept rate at runtime and caps the step count accordingly.

Per-BS throughput delta vs no-spec

EMA Ceiling Rule Design

The key insight from multi-model testing is that the crossing point depends on draft model quality — but we don't want users to have to figure out model-specific configs. Instead, here's a possible design -- an EMA ceiling rule that provides a safe lower bound automatically for all models:

max_step ≤ ceil(ema_accept_len * 1.67)

where ema_accept_len tracks correct_drafts (no bonus token), applied at BS > 8.

How it works:

  • When workload is easy (ema ~4.0): ceiling = ceil(4.0 * 1.67) = 7 → no restriction, full speculation
  • When workload is hard (ema ~0.5): ceiling = ceil(0.5 * 1.67) = 1 → caps at step=1, minimal overhead
  • When workload is moderate (ema ~2.0): ceiling = ceil(2.0 * 1.67) = 4 → allows profitable steps only

Why 1.67? It corresponds to a ~60% accept_rate breakeven threshold (1/0.6 ≈ 1.67). When accept_rate drops below 60%, the draft cost outweighs the benefit at high BS.

  • Restrictions: Currently Do not cover no-spec fallback. For models with extreme heavy workload where even step=1 loses to no-spec at high BS (like MiniMax at BS≥16 and Llama-3.1-8B at BS≥8), the ceiling rule alone isn't enough, and no-spec fallback mode should be applied.
