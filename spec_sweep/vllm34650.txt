 Bug: Speculative Decoding (MTP) Causes </think> Detection Failure in Structured Output + Reasoning Mode #34650 
 #44993 
 Copy link 
 Labels
 bug Something isn't working Something isn't working 
 Description
 cicirori 
 opened on Feb 16, 2026 
 Issue body actions 
 Summary
 When using MTP speculative decoding together with a reasoning parser and structured output ( response_format={"type": "json_schema"} ), the </think> token can be silently missed by the StructuredOutputManager.should_advance() method. This causes reasoning_ended to never become True , so JSON schema constraints are never enforced after the thinking phase ends.
 Root Cause
 In vllm/v1/structured_output/__init__.py:324-328 , should_advance() computes the delta tokens to check for the </think> token:
 delta_from = request . num_computed_tokens - request . num_output_placeholders 
 all_token_ids = request . all_token_ids 
 if self . reasoner . is_reasoning_end_streaming (
 all_token_ids , all_token_ids [ delta_from :]
):
 structured_req . reasoning_ended = True 
 The problem is a timing mismatch between num_computed_tokens and all_token_ids in the speculative decoding path:
 _update_after_schedule() ( scheduler.py:943 ) increments num_computed_tokens by all scheduled tokens, including speculative tokens, before the model runs.
 After model execution, _update_request_with_output() ( scheduler.py:1352 ) appends the generated tokens (accepted spec tokens + bonus token) to all_token_ids .
 Then should_advance() is called ( scheduler.py:1385 ), where delta_from = num_computed_tokens already accounts for the speculative tokens.
 Concrete Example
 With num_speculative_tokens=1 , prompt length P , and G previously generated tokens:
 Step 
 num_computed_tokens 
 len(all_token_ids) 
 delta = all_token_ids[delta_from:] 
 Before scheduling 
 P+G 
 P+G 
 — 
 After _update_after_schedule 
 P+G+2 (1 main + 1 spec) 
 P+G (unchanged) 
 — 
 Spec token accepted, output=[T1,T2] appended 
 P+G+2 (unchanged) 
 P+G+2 
 all_token_ids[P+G+2:] = [] (empty!) 
 Spec token rejected, output=[T1] appended 
 P+G+2-1 = P+G+1 
 P+G+1 
 all_token_ids[P+G+1:] = [] (also empty!) 
 The delta is always empty regardless of whether the speculative token is accepted or rejected. The is_reasoning_end_streaming() check ( end_token_id in delta_ids ) never finds </think> , so reasoning_ended is never set to True .
 Resulting Behavior
 As a result:
 should_fill_bitmask() keeps returning False (no JSON grammar constraint applied)
 should_advance() keeps returning False (grammar FSM never advances)
 The model output is completely unconstrained after </think> 
 How to Reproduce
 python -m vllm.entrypoints.openai.api_server \
 --model Qwen/Qwen3.5-397B-A17B \
 --reasoning-parser deepseek_r1 \
 --speculative-config ' {"method": "mtp", "num_speculative_tokens": 1} ' 
 Send a request with:
 {
 "response_format" : { "type" : " json_schema " , "..." : " ... " },
 "enable_thinking" : true 
}
 The output after </think> will not be constrained to the JSON schema.
 Disabling either speculative decoding or thinking ( "enable_thinking": false ) works around the issue.
 Suggested Fix
 The delta calculation in should_advance() should not rely on num_computed_tokens (which is pre-incremented for scheduling). Instead, it should use the actual new token IDs that were just appended in the current step.
 One approach:
 def should_advance ( self , request : "Request" ) -> bool :
 ...
 structured_req = request . structured_output_request 
 if structured_req . reasoning_ended :
 return True 
 # Use the actual new tokens instead of deriving delta from num_computed_tokens 
 new_token_ids = new_token_ids # passed from update_from_output 
 if self . reasoner . is_reasoning_end_streaming (
 request . all_token_ids , new_token_ids 
 ):
 structured_req . reasoning_ended = True 
 return False 
 Alternatively, pass new_token_ids from scheduler.py:1385 directly into should_advance() so the method doesn't need to recompute the delta.
 Affected Versions
 Any version of vLLM V1 with speculative decoding + reasoning parser + structured output.
