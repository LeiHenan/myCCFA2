 [Bug] DeepSeek-V4.1-Flash + Engram: profiled SPS table (compact ragged verify) dies in CUDA-graph capture with "engram target-verify expects one equal block per request" #39173 
 Copy link 
 Description

 opened on Sep 12, 2026 
 Issue body actions 
 Checklist
 I searched related issues but found no solution.
 The bug persists in the latest version.
 Issues without environment info and a minimal reproducible demo are hard to resolve and may receive no feedback.
 If this is not a bug report but a general question, please start a discussion at https://github.com/sgl-project/sglang/discussions . Otherwise, it will be closed.
 Please use English. Otherwise, it will be closed.
 Describe the bug
 On DeepSeek-V4.1-Flash (an Engram model), enabling DSpark compact ragged verify via a profiled SPS cost table makes the engine die deterministically during CUDA-graph capture, on every rank :
 AssertionError: engram target-verify expects one equal block per request, got 42 tokens for 8 requests of 6
 Removing the table (so the planner stays on the verify-all / static schedule) boots and serves fine, so weights, TP4/EP4, FP8 KV cache and the RDMA transport are all healthy.
 Suspected root cause. The capture batch seems to get the wrong slot count. DecodeCudaGraphRunner._ragged_capture_slots() returns min(num_tokens, self.max_bs) ( model_executor/runner/decode_cuda_graph_runner.py:667-670 ), while the per-tier token bucket is bs * captured_req_width ( _build_ragged_verify_token_buckets , same file, line 569). For the tier num_tokens = 42 (bs=7, width=6) with max_bs = 8 this selects 8 slots , so build_capture_verify_lens(num_tokens=42, num_slots=8, num_draft_tokens=6) returns [6,6,5,5,5,5,5,5] — 8 rows of unequal length summing to 42. EngramHasher.forward() 's target-verify branch ( srt/layers/engram.py:291-298 ) requires one equal block per request ( num_tokens == bs * block → 42 != 8*6 ), so the capture batch is rejected. Only the largest tier (bs == max_bs → 48 tokens / 8 slots) survives; every smaller tier aborts. Dense-layout consumers elsewhere handle ragged layouts through RaggedVerifyLayout.padded_to_bucket(padded_bs, cap) , but the Engram hasher reads the raw input_ids.shape[0] / req_pool_indices.shape[0] pair before any padding.
 The test escape hatch SGLANG_TEST_RAGGED_VERIFY_FORCE_UNIFORM_CAPTURE=1 avoids the capture assertion but then dies on the first request (second traceback below), so compact ragged verify currently appears unusable for this model.
 Reproduction
