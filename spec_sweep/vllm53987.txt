 Purpose
 This PR adds FLy ( arXiv:2511.22972 ) (Accepted by ICLR 2026), an opt-in verification policy for draft-model speculative decoding, developed and evaluated at AMD .
 Standard rejection sampling stops at the first rejected draft token, so a single ambiguous position truncates the whole draft and discards the tokens the target has already verified. FLy observes that when the following acceptance decisions all still agree, an isolated rejection at a genuinely ambiguous position is usually not worth a full truncation. At such a position, FLy defers to the draft token instead of rejecting, which lets the rest of the window be accepted.
 Evaluated over 40 model–dataset configurations, covering four target/draft pairs across ten benchmarks. The pairs include a 405B FP8 model and a 235B MoE reasoning model, and an independent NVIDIA validation is included as well. FLy is faster than standard speculative decoding in every configuration.
 Executive Summary
 We completed an end-to-end evaluation of FLy against target-only decoding and standard speculative decoding (Standard SD). The AMD MI355X evaluation is the primary result set and covers four target/draft model pairs across 10 benchmarks, for a total of 40 model–dataset configurations.
 Consistent acceleration on AMD: FLy is faster than Standard SD in all 40 primary configurations, with speedups from 1.067x to 1.938x . The typical improvement is about 1.23x .
 Quality preservation on AMD: among the 29 configurations for which a quality-retention ratio is reported, the minimum retention is 97.9% . 23 configurations exceed 99%. Low-correct-count AIME/HLE cases report the three raw correct counts instead of a ratio.
 Mechanistic improvement: draft acceptance and mean accepted tokens per verification round ( tau ) increase in every AMD primary row. The tau improvement ranges from 1.03x to 1.83x .
 Surpass the state-of-the-art method: on the MI300x, FLy surpasses DFlash by over 1.09x on the Kimi-K2.5-1T model with 8k/1k input/output sequence length while keeping 99.7% of the GSM8k accuracy.
 Cross-platform validation: on the NVIDIA B300 evaluation, FLy improves over Standard SD on all 7 listed workloads, by 1.07x to 1.43x .
 Sampling-path coverage: Supplementary experiments on AMD and NVIDIA further validate FLy beyond the default temperature-0 setting, covering non-zero-temperature decoding under two speculative sampling policies: greedy drafting with target-only verification, and probabilistic drafting with standard p/q rejection sampling.
 Mechanism
 FLy lives entirely in the verification/sampling stage. After the target model has produced logits for the drafted positions, RejectionSampler.rejection_sample() normally runs one of two native acceptance kernels; FLy inserts a single pre-pass in front of them that can flip individual rejections into acceptances at high-entropy positions, after which the native kernels run unmodified. Nothing in drafting, scheduling, KV cache, attention, or the model runner is touched, and no extra checkpoint or confidence head is required.
 draft model proposes K tokens
 │
target model forward ──► target_logits for the K drafted positions
 │
 ▼
 RejectionSampler.rejection_sample() ← the only place FLy touches
 │
 ├── [FLy pre-pass] top-3 target entropy, then at gated positions only:
 │ greedy path : target_argmax[i] <- draft_token_ids[i]
 │ random path : uniform_probs[i] <- 0
 │
 └── native rejection_{greedy,random}_sample_kernel (unmodified)
 │
 ▼
 accepted tokens + bonus token
 The pre-pass does not re-implement acceptance; it rewrites the inputs the native kernels read, so the unchanged native logic emits the deferred decision. Overwriting the target argmax makes the native equality test pass on the greedy path, and setting the uniform sample to 0 makes the native p/q >= u test pass on the random path once p > 0 and q > 0 are checked. Per-position accounting and acceptance metrics therefore stay on the existing code path.
 A native rejection at position i is overridden only if all of the following hold:
 Gate condition 
 Purpose 
 target top-3 entropy at i >= fly_entropy_threshold 
 the target is genuinely uncertain here, not confidently disagreeing 
 the next fly_window_size positions would all be accepted natively 
 the draft has re-synchronised, so the deferral is local 
 the draft token has non-zero target probability 
 never emit a token the target assigns zero mass 
 i + fly_window_size < num_draft_tokens 
 a full window must fit in the remaining draft 
 The entropy is computed from the target scores after temperature, top-k, and top-p processing, so the gate reflects the distribution actually being sampled from. When FLy is disabled, no entropy is computed, neither pre-pass kernel is launched, and the code path is exactly the pre-existing one.
 Because the pre-pass reads only target_logits and the proposed token IDs, FLy is independent of how the draft was produced. It is therefore enabled both for draft_model drafting and for the hidden-state drafting methods ( eagle , eagle3 , mtp , dflash , dspark ), including their parallel drafting: a parallel drafter still proposes a linear token sequence, and the target logits at each position are still conditioned on the proposed token before it. FLy composes with those methods rather than competing with them.
 Usage
 llm = LLM (
 model = "Qwen/Qwen3-8B" ,
 speculative_config = {
 "method" : "draft_model" ,
 "model" : "Qwen/Qwen3-0.6B" ,
 "num_speculative_tokens" : 8 ,
 "rejection_sample_method" : "fly" ,
 "fly_window_size" : 6 , # default 6, must be < num_speculative_tokens 
 "fly_entropy_threshold" : 0.3 , # default 0.3 
 },
)
 FLy is disabled by default. Config validation rejects unsupported combinations up front: it requires a trained drafter ( draft_model or one of the hidden-state methods above), a shared target/draft vocabulary, and fly_window_size < num_speculative_tokens . It works with both the default target-only acceptance and draft_sample_method="probabilistic" .
 The pre-pass is implemented in the V1 model runner's rejection sampler, so FLy is V1-only for now: configurations that merely default to V2 fall back to V1 with a warning when FLy is enabled, and configurations that require V2 are rejected with an explicit error rather than silently ignoring the flag. See Limitations .

 Limitations
 FLy is an approximate verification policy. It does not preserve the target distribution exactly, so it is opt-in and nothing changes unless rejection_sample_method="fly" is set. Across the 40 configurations above the measured cost is small: retention is at least 97.9% wherever a ratio is reported.
 Three of the eleven raw-count configurations where FLy is below both Target and Standard SD. All three are benchmarks on which even the target model answers very few questions correctly, so a difference of one to three questions dominates2:

 V1 model runner only, for now. FLy is implemented in the V1 rejection sampler. The evaluation above uses draft-model speculative decoding with a separate draft and target model, which the V2 model runner does not support, so V1 is the runner for this setup in any case. For hidden-state drafting, enabling FLy makes the engine fall back to V1 with a warning; configurations that require V2, such as dspark , are rejected rather than silently ignoring the flag. Adapting FLy to the V2 sampler is planned as follow-up work.
 Why this is not a duplicate
 Several concurrent PRs touch the verification step, but they change how many draft tokens are verified, while FLy changes the accept/reject decision itself :
 #47808 (DSpark confidence-scheduled verification) and #47131 (D-Cut) size or prune the verification budget from draft confidence before verification and leave the acceptance test intact. FLy leaves the budget alone and overrides individual rejections instead, so the two are complementary.
 #50246 proposes DFly , which despite the similar name is a drafting method rather than a verification policy.
 As of this submission, I found no other PR that modifies the acceptance decision itself in rejection_sampler.py .
 Drive-by doc fix
 The rejection_sample_method row in the speculative decoding docs was stale: it listed a non-existent strict default, omitted block , and listed probabilistic , which belongs to draft_sample_method . This PR corrects that row and adds the missing draft_sample_method row, which use_heterogeneous_vocab right below it already referenced.

 The new cases cover the greedy and random deferral paths, the entropy gate, window boundary conditions, the accepted drafting methods, and rejection of invalid configs; the full rejection-sampler suite (81 tests) passes unchanged.
