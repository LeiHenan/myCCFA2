 Contributor 
 Motivation
 Fix the conflict in adaptive speculative decoding for Qwen3.5 and Qwen3-Next.
related issue: #23330 
adaptive speculative decoding: #21599 
 Summary of Issues
 AttributeError: 'RadixLinearAttention' object has no attribute 'is_cross_attention' 
 The MTP draft model mutates hf_config during construction, but get_config() is cached by lru_cache , so the draft and target models share the same object. This pollutes the target's full_attention_layer_ids , causing linear-attn layers to be misrouted to the full-attn backend. Fix: deepcopy(config) in the MTP constructor to isolate the mutation; additionally, rewrite _is_full_attn to dispatch via isinstance(layer, RadixLinearAttention) so routing no longer depends on the easily-polluted ID list.
 GDN kernel stride-calculation conflict causes accuracy anomalies in adaptive mode
 The GDN Triton kernel computes the per-request stride of intermediate_states_buffer using the runtime cache_steps , but the buffer is allocated once against the maximum candidate steps — its true stride is determined by the physical dimension. In static mode the two values happen to match, masking the bug; in adaptive mode the stride is wrong, so requests overwrite each other's intermediate states and the output shows repeated fragments. Fix: In the Python wrapper, derive the stride from intermediate_states_buffer.shape[1] so it always matches the physical layout.
 Mamba intermediate buffer overflow causes CUDA illegal memory access in adaptive mode
 The pool allocates intermediate_ssm based on the initial speculative_num_draft_tokens , but adaptive mode may switch to a larger candidate at runtime (default [1, 3, 7] ), so the actual draft-token count exceeds the allocated dimension and crashes out of bounds. Fix: Add effective_max_speculative_num_draft_tokens() returning the max across all candidates, and use it for pool allocation ; keep the original value for memory estimation and padding to avoid shrinking max_running_requests / capture_bs 
 Modifications
 qwen3_5_mtp.py / qwen3_next_mtp.py 
 copy.deepcopy(config) at the entry point so every mutation lands on the copy and never pollutes the target's shared config.
 hybrid_linear_attn_backend.py 
Rewrite _is_full_attn to "prefer isinstance type dispatch, fall back to the ID list only when the layer object is unavailable"; call sites uniformly forward kwargs.get("layer_id") . Acts as a second line of defense against config pollution.
 fla/fused_sigmoid_gating_recurrent.py 
The cache_steps passed to the Triton kernel is now derived from intermediate_states_buffer.shape[1] ; the original parameter is kept for API compatibility.
 server_args.py 
Add effective_max_speculative_num_draft_tokens() , which reports the max draft-token count across all candidate states — used as the single source of truth for one-shot buffer allocation.
 model_runner_kv_cache_mixin.py 
Both pools now pass effective_max_...() as speculative_num_draft_tokens ; memory estimation and extra_max_context_len padding keep the original value.
 adaptive_spec_params.py 
The default candidates [1, 3, 7] are demoted to a module-private immutable tuple; only resolve_candidate_steps(config) (default-fallback + dedup + sort) is exposed externally, and both AdaptiveSpeculativeParams and server_args go through it.

 Fix hybrid linear attention misrouting linear layers to full backend 
 … 
 4445a7a 
 HybridLinearAttnBackend._is_full_attn classified any RadixAttention
instance as a full-attention layer:
 if isinstance(layer, RadixLinearAttention):
 return False
 if isinstance(layer, RadixAttention):
 return True # <- wrong for models using RadixAttention for linear layers
This works when linear layers are RadixLinearAttention (e.g. Qwen3.5
hybrid GDN, the model #23331 targeted), but Bailing/Ring models build
their linear-attention layers with a plain RadixAttention
(bailing_moe_linear.py). Those linear layers therefore matched the
RadixAttention branch and were routed to the full-attention (MLA)
backend, which on CUDA-graph capture calls set_kv_buffer/set_mla_kv_buffer
on the HybridLinearKVPool with a non-full layer id and crashes:
 ValueError: layer_id=0 not in full attention layers:
 dict_keys([7, 15, 23, 31, 39, 47, 55, 63, 71, 79])
Drop the isinstance(layer, RadixAttention) -> True shortcut and fall
through to the authoritative 'layer_id in self.full_attn_layers' check.
RadixLinearAttention layers are still short-circuited to linear; all
other layers are classified by id, which is correct for both
RadixLinearAttention-based hybrids and plain-RadixAttention hybrids.
Reproduced and verified the fix on an 8x B300 host with a reduced
bailing_hybrid config (dummy weights): before, capture crashed at the
first linear layer; after, layer 0 routes to the linear backend and
capture proceeds.
Fixes the Ring-2.5-1T (inclusionAI/Ring-2.5-1T) nightly TP8 crash.
