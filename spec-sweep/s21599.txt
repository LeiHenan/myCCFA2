 Motivation
 One of the core parameters of speculative decoding is speculative_num_steps , which controls how many autoregressive draft-model steps are executed in each round. It directly determines the amount of computation in the draft stage, and also affects speculative_num_draft_tokens (the number of tokens verified by the target model), which in turn determines the shape used in the verify stage.
 In real workloads, accept length often changes over time, so a static num_steps cannot consistently deliver optimal throughput:
 If num_steps is too small : the draft model could have produced more accepted tokens, but the limited number of steps caps each round to only a small number of accepted tokens, leaving draft-model capacity underutilized.

 The goal of this feature is to build a low-level adaptive speculative decoding mechanism:
 Pre-build multiple runtime states (attention backends and CUDA graphs) for different speculative_num_steps / speculative_num_draft_tokens pairs.
 During draft decoding:
 Track the accept length of recent batches with an EMA-based policy.
 Dynamically switch speculative_num_steps and the corresponding runtime state.
 Runtime switching does not require online graph recapture or backend reconstruction.
 Modifications
 Architecture
 The overall design centers on AdaptiveController , with three lower-level components: AdaptiveSpeculativeParams (policy), SpecRuntimeState (runtime state), and AdaptiveSpecWorker (worker).
 AdaptiveController 
 At startup, it drives the worker to pre-build a SpecRuntimeState for each candidate tier and stores them in a state pool. After each verify step at runtime, it receives the accept length and delegates the EMA decision to the policy. If the tier changes, it fetches the corresponding state from the pool and asks the worker to perform an atomic switch.
 Policy - AdaptiveSpeculativeParams 
 It maintains an EMA of accept length and decides when to move up or down across discrete candidate tiers (default: [1, 3, 7] ). It supports warmup (skip the first N batches), update interval (evaluate every K batches), and hysteresis (asymmetric rise/drop thresholds to suppress oscillation). Decision formula: target_steps = clamp(round(ema) + 1, min, max) , which probes one extra step beyond the observed accept length.
 Runtime State - SpecRuntimeState 
 This is a @dataclass that encapsulates all execution resources required by the three stages for a given num_steps tier. CudaGraphRunner is tightly bound to (num_steps, num_draft_tokens) because its static shape depends on them, so each tier must own an independent graph instance.

 Worker - AdaptiveSpecWorker Protocol 
 This protocol defines the two interfaces a worker must implement:
 build_adaptive_runtime_state() captures the CUDA graph and attention backend under a temporary server-args override.
 apply_runtime_state() assigns the resources stored in the state back onto the worker one by one, completing a zero-overhead reference swap.
 This is currently implemented by EAGLEWorker ; support for EAGLEWorkerV2 is left as a follow-up TODO.

 Accuracy Tests
 Model: GLM-4.7-FP8 , EAGLE, topk=1, TP=8, --mem-fraction-static 0.55 , --hicache-size 60 .
 The benchmark defines three workloads to cover different accept-length distributions:
 low - Stable low acceptance. Prompts such as creative writing or long-list generation make draft prediction difficult, so accept length remains low. In this scenario, a large num_steps wastes computation.
 high - Stable high acceptance. Highly repetitive outputs (for example, printing the same content line by line) let the draft model predict almost perfectly, so accept length stays high. In this scenario, a large num_steps brings clear benefits.
 transition - Alternating phases. Requests are sent in four phases, low_1 -> high_1 -> low_2 -> high_2 , to simulate real workloads whose characteristics change over time. This is the core evaluation scenario for the adaptive mechanism.
 The results below use the transition workload, with 16 requests per phase, concurrency 8, and max-tokens 256 .
