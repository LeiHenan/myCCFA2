# [RFC]: Cache-affinity-aware request ordering for the V1 scheduler

## Summary

A `CacheAffinityScheduler` plugin loadable via `--scheduler-cls` that reorders the V1 waiting queue by cached-prefix length before each scheduling iteration. In-engine equivalent of sglang's RadixAttention scheduling, on top of vLLM's existing block-hash prefix cache. No token-level radix tree, no KV cache manager surgery, no request-schema changes.

## Motivation

vLLM has block-level prefix caching ([docs](https://docs.vllm.ai/en/stable/design/prefix_caching/)), but the V1 scheduler admits waiting requests in priority + FCFS order. A waiting request with thousands of cached prefix tokens is treated identically to a request with no cached prefix — the prefill savings are left on the table when the cache-warm request waits behind a cache-cold one.

Issue [#7883](https://github.com/vllm-project/vllm/issues/7883) (open since Aug 2024) identified the budget-calculation half of this problem; the in-flight `[1/n]` series fixes `can_allocate` to consider cached blocks. **Waiting-queue ordering is the other half** and is not addressed by that series — confirmed by reading the merged commits.

External evidence the gap is felt:

- sglang's [RadixAttention scheduling](https://www.lmsys.org/blog/2024-01-17-sglang/) reports 10–30% throughput uplift on multi-turn / RAG / agentic workloads by reordering requests so those with longer cached prefixes execute first.
- Multiple comparison articles ([Runpod sglang vs vLLM KV cache](https://www.runpod.io/blog/sglang-vs-vllm-kv-cache), [Particula sglang vs vLLM](https://particula.tech/blog/sglang-vs-vllm-inference-engine-comparison)) cite this as the reason teams pick sglang over vLLM for those workloads.
- vLLM forums thread "[Is FCFS Scheduling Holding Back vLLM's Performance in Production?](https://discuss.vllm.ai/t/is-fcfs-scheduling-holding-back-vllms-performance-in-production/1584)" repeatedly returns to this.

## Proposed approach

Add `CacheAffinityScheduler` as a plugin loadable via `--scheduler-cls vllm.v1.core.sched.cache_affinity_scheduler.CacheAffinityScheduler`. The class subclasses the in-tree `Scheduler` (not the `SchedulerInterface` ABC, which the engine flags as not-public) and replaces `self.waiting` with a custom `CacheAffinityRequestQueue` that owns a composite sort.

At each `schedule()` call, the policy:

1. Iterates the sortable portion of the waiting queue (preempted requests are kept in a sticky-front sub-deque and not re-sorted).
2. For each request, calls `kv_cache_manager.get_computed_blocks(req)` to get `num_cached_tokens`. The score is `num_cached_tokens // block_size`. Requests below `cache_affinity_min_blocks` (default 2) score 0.
3. Requests waiting longer than `cache_affinity_max_wait_s` (default 0.2) get a starvation-override slot at the absolute front.
4. Sorts by composite key:
   - PRIORITY mode: `(priority, -bucketed_score, arrival_time, request_id)`
   - FCFS mode: `(-bucketed_score, arrival_time, request_id)`
5. Calls `super().schedule()` against the now-reordered queue. Everything downstream (chunked prefill, allocation, preemption ladder, KV connector) stays unchanged.

Score bucketing (default edges `(4, 16, 64, 256)`) prevents per-iteration thrash on small score deltas. Sticky-front semantics preserve the V1 invariant that preempted requests are scheduled first in their preemption order.

## Design details

### Sort-key composition with priority

Cache affinity is a tiebreaker **within** a priority class, never across. A high-priority cache-cold request always beats a low-priority cache-warm request. Tested in unit test `test_priority_overrides_cache`.

### Sticky-front for preempted requests

`CacheAffinityRequestQueue` maintains two internal deques: `_sticky` (for `prepend_request` calls — preempted requests) and `_sortable` (for `add_request` — new arrivals). `pop_request` drains `_sticky` first. The reorder pass only sorts `_sortable`. Preserves the existing invariant that preempted requests retain their preemption order. Composes correctly with the new capacity-triggered preemption path in PR #40087 (verified — the new path uses the same `prepend_request` mechanism).

### Anti-starvation

`cache_affinity_max_wait_s` deadline. Catches the pathological case where a request with no cached prefix is forever deprioritized under bursty cached traffic.

### Min-blocks threshold

`cache_affinity_min_blocks` (default 2). Requests with fewer cached blocks score 0. Avoids reordering thrash from one-block hits.

### What we explicitly do NOT do in v1

- **No token-level radix tree.** vLLM is committed to block-level prefix hashing; reproducing sglang's radix tree would require KV-manager surgery and clash with the existing design. Operating at block boundaries captures the bulk of the realistic benefit (system prompts, RAG contexts are typically block-aligned).
- **No request-schema changes.** No new fields on `Request`. Config lives entirely on `SchedulerConfig`.
- **No thrash-eviction guard.** Ship the metric `vllm:cache_affinity_thrash_evictions_total` to detect thrashing; add a guard in a follow-up PR if benchmarks show it firing. Ship simple, collect evidence, iterate.

## Compatibility

- **Mutually exclusive** at engine-load time with EWSJF (PR [#33392](https://github.com/vllm-project/vllm/pull/33392)) — different `--scheduler-cls` values, users pick one. Both are reference policies on the pluggable substrate. Future composite is possible (EWSJF's partition tag as outer key, cache-affinity as inner) but out of scope for v1.
- **Independent of and composable with** the `[1/n]` series under issue #7883. That series fixes `can_allocate` budget calculation; this RFC reorders the queue. Different layers.
- **Compatible with** priority scheduling ([PR #5958](https://github.com/vllm-project/vllm/pull/5958), [PR #19057](https://github.com/vllm-project/vllm/pull/19057)) — composes via the sort-key tiebreaker.
- **Compatible with** chunked prefill (chunk-size selection unchanged at `scheduler.py:677-692`).
- **Compatible with** PR [#40087](https://github.com/vllm-project/vllm/pull/40087) (sts07142, capacity-triggered preemption) — verified via 3-way speculative merge: clean, no overlapping changes.
- **No effect** when `--scheduler-cls` points elsewhere (the policy is opt-in plugin-loaded).

## Implementation plan

Reference implementation is drafted on a feature branch: 3 commits, ~250 LOC core + 26 LOC config + ~600 LOC tests, all 13 new unit tests + 117 baseline V1 scheduler tests passing.

```
vllm/v1/core/sched/cache_affinity_scheduler.py    # NEW, ~309 lines
vllm/config/scheduler.py                          # +26 lines (4 new optional fields)
tests/v1/core/test_cache_affinity_scheduler.py    # NEW, ~576 lines
```

No other source files touched.

After this RFC, plan to open `[WIP]` draft PR within 2 weeks of feedback close, including:
- Unit tests (already passing)
- Benchmark scripts: synthetic same-prefix bursts, RAG with shared system prompt, ShareGPT multi-turn, adversarial unique-prompt regression
- Benchmark numbers from a single H100 / L40S run (Llama-3.1-8B), with multi-seed variance

## Roadmap (out of scope for v1)

Possible follow-up PRs once this lands and the substrate is validated:

1. **Thrash-eviction guard** — once metric data shows whether it's needed.
2. **SLA-tier schema** — revival of [RFC #30256](https://github.com/vllm-project/vllm/issues/30256) (closed as not planned, schema designed but never implemented). Cache-affinity sort key naturally extends to SLA-tier as primary key.
3. **Goodput-driven adaptive controller** — research-grade extension. Composes with sidikbro's EWSJF (PR #33392) — EWSJF's partition tag as outer key, cache-affinity as inner.
4. **Cross-instance cache-aware routing hooks** — exposure of cache score for use by external routers (production-stack, llm-d).

These are not part of this proposal. They are listed only to clarify that v1's small scope is intentional.

## Alternatives considered

**Token-level radix tree (sglang's approach).** Rejected: clashes with vLLM's committed block-level cache design. Would require KV manager refactor outside any reasonable PR scope. Block-level captures most of the realistic benefit on production traces (shared prefixes are typically block-aligned).

**Modify default `Scheduler` directly with a feature flag.** Rejected: violates the pluggable scheduler pattern that PR #14466 introduced. Plugin form is cleaner, opt-in, and stays out of the default code path.

**In-engine cross-instance routing.** Rejected: cross-instance routing is the gateway / production-stack layer's responsibility. This RFC is in-engine waiting-queue ordering only.

**Wait for [RFC #24484](https://github.com/vllm-project/vllm/issues/24484) (workload-aware adaptive policy) to land first.** Considered but not blocking. EWSJF (PR #33392) is the reference implementation for that RFC, scoped to throughput optimization on mixed workloads (SJF + Bayesian meta-optimizer). It does not cover cache-affinity reordering. The two contributions are orthogonal in objective and complementary in deployment.

## Open questions for the community

1. **Default bucket edges** — `(4, 16, 64, 256)` chosen by intuition. Synthetic sweeps in our benchmark harness can tune these before merge if reviewers want a specific methodology.
2. **Thrash detection** — currently shipped as a metric only, with the actual guard deferred to a follow-up. Reviewers who want the guard in v1 can flag it; we'll fold it in if there's appetite.
3. **In-tree vs `vllm-contrib`** — the implementation is small enough to live in-tree under `vllm/v1/core/sched/`. If maintainers prefer reference policies live elsewhere (analogous to how some adapters live out of tree), happy to relocate.

Software engineer at Meta in production ML serving infrastructure (large-scale ranking and inference systems for ad delivery serving hundreds of billions of daily requests). Cache-aware request scheduling is the analog problem in that domain.

Targeting feedback period of 2 weeks per vLLM convention, then opening a `[WIP]` draft PR.

2. **SLA-tier schema** — revival of [RFC #30256](https://github.com/vllm-project/vllm/issues/30256) (closed as not planned, schema designed but never implemented). Cache-affinity sort key naturally extends to SLA-tier as primary key.
3. **Goodput-driven adaptive controller** — research-grade extension. Composes with sidikbro's EWSJF (PR #33392) — EWSJF's partition tag as outer key, cache-affinity as inner.
4. **Cross-instance cache-aware routing hooks** — exposure of cache score for use by external routers (production-stack, llm-d).

These are not part of this proposal. They are listed only to clarify that v1's small scope is intentional.

## Alternatives considered

**Token-level radix tree (sglang's approach).** Rejected: clashes with vLLM's committed block-level cache design. Would require KV manager refactor outside any reasonable PR scope. Block-level captures most of the realistic benefit on production traces (shared prefixes are typically block-aligned).

**Modify default `Scheduler` directly with a feature flag.** Rejected: violates the pluggable scheduler pattern that PR #14466 introduced. Plugin form is cleaner, opt-in, and stays out of the default code path.

**In-engine cross-instance routing.** Rejected: cross-instance routing is the gateway / production-stack layer's responsibility. This RFC is in-engine waiting-queue ordering only.

**Wait for [RFC #24484](https://github.com/vllm-project/vllm/issues/24484) (workload-aware adaptive policy) to land first.** Considered but not blocking. EWSJF (PR #33392) is the reference implementation for that RFC, scoped to throughput optimization on mixed workloads (SJF + Bayesian meta-optimizer). It does not cover cache-affinity reordering. The two contributions are orthogonal in objective and complementary in deployment.

1. **Default bucket edges** — `(4, 16, 64, 256)` chosen by intuition. Synthetic sweeps in our benchmark harness can tune these before merge if reviewers want a specific methodology.
2. **Thrash detection** — currently shipped as a metric only, with the actual guard deferred to a follow-up. Reviewers who want the guard in v1 can flag it; we'll fold it in if there's appetite.
3. **In-tree vs `vllm-contrib`** — the implementation is small enough to live in-tree under `vllm/v1/core/sched/`. If maintainers prefer reference policies live elsewhere (analogous to how some adapters live out of tree), happy to relocate.

<h1 dir="auto">[RFC]: Cache-affinity-aware request ordering for the V1 scheduler</h1>
<h2 dir="auto">Summary</h2>
<p dir="auto">A <code class="notranslate">CacheAffinityScheduler</code> plugin loadable via <code class="notranslate">--scheduler-cls</code> that reorders the V1 waiting queue by cached-prefix length before each scheduling iteration. In-engine equivalent of sglang's RadixAttention scheduling, on top of vLLM's existing block-hash prefix cache. No token-level radix tree, no KV cache manager surgery, no request-schema changes.</p>
<h2 dir="auto">Motivation</h2>
<p dir="auto">vLLM has block-level prefix caching (<a href="https://docs.vllm.ai/en/stable/design/prefix_caching/" rel="nofollow">docs</a>), but the V1 scheduler admits waiting requests in priority + FCFS order. A waiting request with thousands of cached prefix tokens is treated identically to a request with no cached prefix — the prefill savings are left on the table when the cache-warm request waits behind a cache-cold one.</p>
<p dir="auto">Issue <a href="https://github.com/vllm-project/vllm/issues/7883" data-hovercard-type="issue" data-hovercard-url="/vllm-project/vllm/issues/7883/hovercard">#7883</a> (open since Aug 2024) identified the budget-calculation half of this problem; the in-flight <code class="notranslate">[1/n]</code> series fixes <code class="notranslate">can_allocate</code> to consider cached blocks. <strong>Waiting-queue ordering is the other half</strong> and is not addressed by that series — confirmed by reading the merged commits.</p>
<p dir="auto">External evidence the gap is felt:</p>
<ul dir="auto">
<li>sglang's <a href="https://www.lmsys.org/blog/2024-01-17-sglang/" rel="nofollow">RadixAttention scheduling</a> reports 10–30% throughput uplift on multi-turn / RAG / agentic workloads by reordering requests so those with longer cached prefixes execute first.</li>
<li>Multiple comparison articles (<a href="https://www.runpod.io/blog/sglang-vs-vllm-kv-cache" rel="nofollow">Runpod sglang vs vLLM KV cache</a>, <a href="https://particula.tech/blog/sglang-vs-vllm-inference-engine-comparison" rel="nofollow">Particula sglang vs vLLM</a>) cite this as the reason teams pick sglang over vLLM for those workloads.</li>
<li>vLLM forums thread "<a href="https://discuss.vllm.ai/t/is-fcfs-scheduling-holding-back-vllms-performance-in-production/1584" rel="nofollow">Is FCFS Scheduling Holding Back vLLM's Performance in Production?</a>" repeatedly returns to this.</li>
</ul>
<h2 dir="auto">Proposed approach</h2>
<p dir="auto">Add <code class="notranslate">CacheAffinityScheduler</code> as a plugin loadable via <code class="notranslate">--scheduler-cls vllm.v1.core.sched.cache_affinity_scheduler.CacheAffinityScheduler</code>. The class subclasses the in-tree <code class="notranslate">Scheduler</code> (not the <code class="notranslate">SchedulerInterface</code> ABC, which the engine flags as not-public) and replaces <code class="notranslate">self.waiting</code> with a custom <code class="notranslate">CacheAffinityRequestQueue</code> that owns a composite sort.</p>
<p dir="auto">At each <code class="notranslate">schedule()</code> call, the policy:</p>
<ol dir="auto">
<li>Iterates the sortable portion of the waiting queue (preempted requests are kept in a sticky-front sub-deque and not re-sorted).</li>
<li>For each request, calls <code class="notranslate">kv_cache_manager.get_computed_blocks(req)</code> to get <code class="notranslate">num_cached_tokens</code>. The score is <code class="notranslate">num_cached_tokens // block_size</code>. Requests below <code class="notranslate">cache_affinity_min_blocks</code> (default 2) score 0.</li>
<li>Requests waiting longer than <code class="notranslate">cache_affinity_max_wait_s</code> (default 0.2) get a starvation-override slot at the absolute front.</li>
<li>Sorts by composite key:
<ul dir="auto">
<li>PRIORITY mode: <code class="notranslate">(priority, -bucketed_score, arrival_time, request_id)</code></li>
<li>FCFS mode: <code class="notranslate">(-bucketed_score, arrival_time, request_id)</code></li>
</ul>
</li>
<li>Calls <code class="notranslate">super().schedule()</code> against the now-reordered queue. Everything downstream (chunked prefill, allocation, preemption ladder, KV connector) stays unchanged.</li>
</ol>
<p dir="auto">Score bucketing (default edges <code class="notranslate">(4, 16, 64, 256)</code>) prevents per-iteration thrash on small score deltas. Sticky-front semantics preserve the V1 invariant that preempted requests are scheduled first in their preemption order.</p>
<h2 dir="auto">Design details</h2>
<h3 dir="auto">Sort-key composition with priority</h3>
<p dir="auto">Cache affinity is a tiebreaker <strong>within</strong> a priority class, never across. A high-priority cache-cold request always beats a low-priority cache-warm request. Tested in unit test <code class="notranslate">test_priority_overrides_cache</code>.</p>
<h3 dir="auto">Sticky-front for preempted requests</h3>
<p dir="auto"><code class="notranslate">CacheAffinityRequestQueue</code> maintains two internal deques: <code class="notranslate">_sticky</code> (for <code class="notranslate">prepend_request</code> calls — preempted requests) and <code class="notranslate">_sortable</code> (for <code class="notranslate">add_request</code> — new arrivals). <code class="notranslate">pop_request</code> drains <code class="notranslate">_sticky</code> first. The reorder pass only sorts <code class="notranslate">_sortable</code>. Preserves the existing invariant that preempted requests retain their preemption order. Composes correctly with the new capacity-triggered preemption path in PR <a class="issue-link js-issue-link" data-error-text="Failed to load title" data-id="4279906029" data-permission-text="Title is private" data-url="https://github.com/vllm-project/vllm/issues/40087" data-hovercard-type="pull_request" data-hovercard-url="/vllm-project/vllm/pull/40087/hovercard" href="https://github.com/vllm-project/vllm/pull/40087">#40087</a> (verified — the new path uses the same <code class="notranslate">prepend_request</code> mechanism).</p>
<h3 dir="auto">Anti-starvation</h3>
<p dir="auto"><code class="notranslate">cache_affinity_max_wait_s</code> deadline. Catches the pathological case where a request with no cached prefix is forever deprioritized under bursty cached traffic.</p>
<h3 dir="auto">Min-blocks threshold</h3>
<p dir="auto"><code class="notranslate">cache_affinity_min_blocks</code> (default 2). Requests with fewer cached blocks score 0. Avoids reordering thrash from one-block hits.</p>
<h3 dir="auto">What we explicitly do NOT do in v1</h3>
<ul dir="auto">
<li><strong>No token-level radix tree.</strong> vLLM is committed to block-level prefix hashing; reproducing sglang's radix tree would require KV-manager surgery and clash with the existing design. Operating at block boundaries captures the bulk of the realistic benefit (system prompts, RAG contexts are typically block-aligned).</li>
<li><strong>No request-schema changes.</strong> No new fields on <code class="notranslate">Request</code>. Config lives entirely on <code class="notranslate">SchedulerConfig</code>.</li>
<li><strong>No thrash-eviction guard.</strong> Ship the metric <code class="notranslate">vllm:cache_affinity_thrash_evictions_total</code> to detect thrashing; add a guard in a follow-up PR if benchmarks show it firing. Ship simple, collect evidence, iterate.</li>
</ul>

# Closing Post-Mortem: CacheAffinityScheduler (Brief 04c)

**RFC:** #42185
**Decision:** Dropping PR — RAG improvement below threshold, no measurable benefit on correct async baseline.

---

## Summary of Results

All benchmarks: Qwen2.5-7B-Instruct, L40S, vLLM V1 async pipeline.

### v10 (final — async base, window_k=32)

| Workload | Seed | CA throughput | Stock throughput | Delta |
|---|---|---|---|---|
| RAG | 42 | 1.4311 req/s | 1.4305 req/s | **+0.04%** |
| RAG | 137 | 1.4265 req/s | 1.4213 req/s | **+0.36%** |
| ShareGPT | 42 | mean_lat 2.335s | 2.337s | **−0.09%** |
| ShareGPT | 137 | mean_lat 2.503s | 2.484s | **+0.75%** |

RAG mean delta: **+0.2%** (noise). Decision threshold: ≥+5%.

---

## Experiment History

| Version | Base class | window_k | RAG delta | ShareGPT delta | Notes |
|---|---|---|---|---|---|
| v2 | Scheduler (sync) | — | +7.4% | +78% regression | Initial prototype |
| v8 | AsyncScheduler | 8 | +0.95% | 0% | Post sync→async fix |
| v9 | AsyncScheduler | 0 (all) | +1.0% | 0% | Full-queue scoring |
| **v10** | **AsyncScheduler** | **32** | **+0.2%** | **0%** | **Option B (bounded scoring)** |

---

## Root Cause Analysis

### Why the original +7.4% RAG result was wrong

`CacheAffinityScheduler` initially extended synchronous `Scheduler` instead of `AsyncScheduler`. The stock scheduler in vLLM V1 (`get_scheduler_cls()`) returns `AsyncScheduler` when no `--scheduler-cls` is specified. The async scheduler overlaps scheduling with GPU execution via a batch queue (depth 2), yielding ~10–15% higher throughput than the sync path.

The v2 benchmark compared a sync CA scheduler against a sync stock scheduler (both degraded equally), so the +7.4% RAG number appeared real but was actually measuring something else — likely GPU utilization differences under the sync scheduling path at high queue depth.

After fixing the base class to `AsyncScheduler`, the CA and stock schedulers run on identical async pipelines. The true reordering benefit is +0.2%.

### Why reordering doesn't help RAG

The RAG workload uses a 4096-token shared system prompt (same for all 500 queries). After the very first request, this prefix is cached by vLLM's prefix cache — **regardless of scheduling order**. Any subsequent request in FCFS order gets a 91%+ prefix cache hit rate with zero scheduler intervention.

Cache-affinity reordering only provides uplift when:
1. Multiple *distinct* long prefixes compete for a finite cache, AND
2. Scheduling order determines which prefixes stay warm vs. get evicted

Neither condition holds for a single-shared-prefix RAG workload. FCFS already achieves near-optimal cache utilization.

### Why Option B (bounded scoring) didn't recover gain

The hypothesis was that O(N) `get_computed_blocks` calls per iteration (N ≈ 300–400 at peak queue depth) caused ~10ms scoring overhead per scheduling step, stalling the async pipeline. Bounding to K=32 was expected to eliminate this overhead and recover the RAG improvement.

The results show no recovery. Two likely explanations:
1. `get_computed_blocks` is fast (hash lookup, no GPU) — the overhead was not the bottleneck.
2. Even if the overhead existed, the reordering signal was so weak (single shared prefix cached after request #1) that removing the overhead only unmasks a ~0% true benefit.

### ShareGPT result

ShareGPT is correctly neutral (±0.75%, within noise band). The +78% regression from v2 was fully explained by the sync-vs-async base class mismatch and is gone. The reordering does not harm multi-turn workloads.

---

## What Was Built

The implementation is complete and correct:

- `CacheAffinityRequestQueue` extends `FCFSRequestQueue` (C-level deque, O(1) add/pop)
- `CacheAffinityScheduler` extends `AsyncScheduler` (correct async pipeline)
- Anti-starvation: requests waiting > `max_wait_s` promoted to head
- Priority-aware: cache affinity is a tiebreaker within priority class, never across
- Bounded scoring: `window_k=32` limits O(N) scoring to O(K)
- Bucketed scores: reduces sort thrash across iterations
- All 16 unit tests pass

The design is sound. The problem is the workloads it was designed for (RAG shared-prefix, ShareGPT multi-turn) don't exhibit the cache contention pattern that would make reordering beneficial.

---

## When This Would Help

Cache-affinity scheduling would show measurable gains under:
- **Multi-tenant RAG** with N distinct system prompts where N > KV cache capacity / prompt_blocks — forcing eviction competition between tenant prefixes
- **Code assistants** with long per-repo contexts that don't all fit in cache simultaneously
- **Document QA** with many distinct large documents, bursty per-document traffic

None of these were in scope for the current benchmark suite.

---

## Recommendation

Do not merge as a general-purpose scheduler improvement. If the above high-contention workloads are prioritized in a future RFC, the implementation can be revived with benchmarks targeting those scenarios.

Close RFC #42185.

<h2 dir="auto">Root Cause Analysis</h2>
<h3 dir="auto">Why the original +7.4% RAG result was wrong</h3>
<p dir="auto"><code class="notranslate">CacheAffinityScheduler</code> initially extended synchronous <code class="notranslate">Scheduler</code> instead of <code class="notranslate">AsyncScheduler</code>. The stock scheduler in vLLM V1 (<code class="notranslate">get_scheduler_cls()</code>) returns <code class="notranslate">AsyncScheduler</code> when no <code class="notranslate">--scheduler-cls</code> is specified. The async scheduler overlaps scheduling with GPU execution via a batch queue (depth 2), yielding ~10–15% higher throughput than the sync path.</p>
<p dir="auto">The v2 benchmark compared a sync CA scheduler against a sync stock scheduler (both degraded equally), so the +7.4% RAG number appeared real but was actually measuring something else — likely GPU utilization differences under the sync scheduling path at high queue depth.</p>
<p dir="auto">After fixing the base class to <code class="notranslate">AsyncScheduler</code>, the CA and stock schedulers run on identical async pipelines. The true reordering benefit is +0.2%.</p>
<h3 dir="auto">Why reordering doesn't help RAG</h3>
<p dir="auto">The RAG workload uses a 4096-token shared system prompt (same for all 500 queries). After the very first request, this prefix is cached by vLLM's prefix cache — <strong>regardless of scheduling order</strong>. Any subsequent request in FCFS order gets a 91%+ prefix cache hit rate with zero scheduler intervention.</p>
<p dir="auto">Cache-affinity reordering only provides uplift when:</p>
<ol dir="auto">
<li>Multiple <em>distinct</em> long prefixes compete for a finite cache, AND</li>
<li>Scheduling order determines which prefixes stay warm vs. get evicted</li>
</ol>
<p dir="auto">Neither condition holds for a single-shared-prefix RAG workload. FCFS already achieves near-optimal cache utilization.</p>
<h3 dir="auto">Why Option B (bounded scoring) didn't recover gain</h3>
<p dir="auto">The hypothesis was that O(N) <code class="notranslate">get_computed_blocks</code> calls per iteration (N ≈ 300–400 at peak queue depth) caused ~10ms scoring overhead per scheduling step, stalling the async pipeline. Bounding to K=32 was expected to eliminate this overhead and recover the RAG improvement.</p>
<p dir="auto">The results show no recovery. Two likely explanations:</p>
<ol dir="auto">
<li><code class="notranslate">get_computed_blocks</code> is fast (hash lookup, no GPU) — the overhead was not the bottleneck.</li>
<li>Even if the overhead existed, the reordering signal was so weak (single shared prefix cached after request <span class="reference"><svg data-component="Octicon" class="octicon octicon-git-merge merged color-fg-done mr-1" title="Merged" viewBox="0 0 16 16" version="1.1" width="16" height="16" aria-hidden="true"><path d="M5.45 5.154A4.25 4.25 0 0 0 9.25 7.5h1.378a2.251 2.251 0 1 1 0 1.5H9.25A5.734 5.734 0 0 1 5 7.123v3.505a2.25 2.25 0 1 1-1.5 0V5.372a2.25 2.25 0 1 1 1.95-.218ZM4.25 13.5a.75.75 0 1 0 0-1.5.75.75 0 0 0 0 1.5Zm8.5-4.5a.75.75 0 1 0 0-1.5.75.75 0 0 0 0 1.5ZM5 3.25a.75.75 0 1 0 0 .005V3.25Z"></path></svg><a class="issue-link js-issue-link" data-error-text="Failed to load title" data-id="1599440968" data-permission-text="Title is private" data-url="https://github.com/vllm-project/vllm/issues/1" data-hovercard-type="pull_request" data-hovercard-url="/vllm-project/vllm/pull/1/hovercard" href="https://github.com/vllm-project/vllm/pull/1">Fix a bug in tying OPT embeddings<span class="issue-shorthand"> #1</span></a></span>) that removing the overhead only unmasks a ~0% true benefit.</li>
</ol>
<h3 dir="auto">ShareGPT result</h3>
<p dir="auto">ShareGPT is correctly neutral (±0.75%, within noise band). The +78% regression from v2 was fully explained by the sync-vs-async base class mismatch and is gone. The reordering does not harm multi-turn workloads.</p>
<hr>
<h2 dir="auto">What Was Built</h2>
<p dir="auto">The implementation is complete and correct:</p>
<ul dir="auto">
<li><code class="notranslate">CacheAffinityRequestQueue</code> extends <code class="notranslate">FCFSRequestQueue</code> (C-level deque, O(1) add/pop)</li>
<li><code class="notranslate">CacheAffinityScheduler</code> extends <code class="notranslate">AsyncScheduler</code> (correct async pipeline)</li>
<li>Anti-starvation: requests waiting &gt; <code class="notranslate">max_wait_s</code> promoted to head</li>
<li>Priority-aware: cache affinity is a tiebreaker within priority class, never across</li>
<li>Bounded scoring: <code class="notranslate">window_k=32</code> limits O(N) scoring to O(K)</li>
<li>Bucketed scores: reduces sort thrash across iterations</li>
<li>All 16 unit tests pass</li>
</ul>
<p dir="auto">The design is sound. The problem is the workloads it was designed for (RAG shared-prefix, ShareGPT multi-turn) don't exhibit the cache contention pattern that would make reordering beneficial.</p>
<hr>
<h2 dir="auto">When This Would Help</h2>
<p dir="auto">Cache-affinity scheduling would show measurable gains under:</p>
<ul dir="auto">
<li><strong>Multi-tenant RAG</strong> with N distinct system prompts where N &gt; KV cache capacity / prompt_blocks — forcing eviction competition between tenant prefixes</li>
<li><strong>Code assistants</strong> with long per-repo contexts that don't all fit in cache simultaneously</li>
<li><strong>Document QA</strong> with many distinct large documents, bursty per-document traffic</li>
</ul>
<p dir="auto">None of these were in scope for the current benchmark suite.</p>
<hr>
<h2 dir="auto">Recommendation</h2>
<p dir="auto">Do not merge as a general-purpose scheduler improvement. If the above high-contention workloads are prioritized in a future RFC, the implementation can be revived with benchmarks targeting those scenarios.</p>

AsyncScheduler (not Scheduler) to match the default async pipeline.

                                [RFC]: Cache-affinity-aware request ordering for the V1 scheduler     #42185               New issue               Copy link              New issue               Copy link                Closed as not planned                 Closed as not planned      [RFC]: Cache-affinity-aware request ordering for the V1 scheduler   #42185                  Copy link          Labels       stale    Over 90 days of inactivity   Over 90 days of inactivity                       Description             kliukovkin    opened    on May 9, 2026                  Issue body actions          [RFC]: Cache-affinity-aware request ordering for the V1 scheduler 
 Summary 
 A  CacheAffinityScheduler  plugin loadable via  --scheduler-cls  that reorders the V1 waiting queue by cached-prefix length before each scheduling iteration. In-engine equivalent of sglang's RadixAttention scheduling, on top of vLLM's existing block-hash prefix cache. No token-level radix tree, no KV cache manager surgery, no request-schema changes. 
 Motivation 
 vLLM has block-level prefix caching ( docs ), but the V1 scheduler admits waiting requests in priority + FCFS order. A waiting request with thousands of cached prefix tokens is treated identically to a request with no cached prefix — the prefill savings are left on the table when the cache-warm request waits behind a cache-cold one. 
 Issue  #7883  (open since Aug 2024) identified the budget-calculation half of this problem; the in-flight  [1/n]  series fixes  can_allocate  to consider cached blocks.  Waiting-queue ordering is the other half  and is not addressed by that series — confirmed by reading the merged commits. 
 External evidence the gap is felt: 
 
 sglang's  RadixAttention scheduling  reports 10–30% throughput uplift on multi-turn / RAG / agentic workloads by reordering requests so those with longer cached prefixes execute first. 
 Multiple comparison articles ( Runpod sglang vs vLLM KV cache ,  Particula sglang vs vLLM ) cite this as the reason teams pick sglang over vLLM for those workloads. 
 vLLM forums thread " Is FCFS Scheduling Holding Back vLLM's Performance in Production? " repeatedly returns to this. 
 
 Proposed approach 
 Add  CacheAffinityScheduler  as a plugin loadable via  --scheduler-cls vllm.v1.core.sched.cache_affinity_scheduler.CacheAffinityScheduler . The class subclasses the in-tree  Scheduler  (not the  SchedulerInterface  ABC, which the engine flags as not-public) and replaces  self.waiting  with a custom  CacheAffinityRequestQueue  that owns a composite sort. 
 At each  schedule()  call, the policy: 
 
 Iterates the sortable portion of the waiting queue (preempted requests are kept in a sticky-front sub-deque and not re-sorted). 
 For each request, calls  kv_cache_manager.get_computed_blocks(req)  to get  num_cached_tokens . The score is  num_cached_tokens // block_size . Requests below  cache_affinity_min_blocks  (default 2) score 0. 
 Requests waiting longer than  cache_affinity_max_wait_s  (default 0.2) get a starvation-override slot at the absolute front. 
 Sorts by composite key:
 
 PRIORITY mode:  (priority, -bucketed_score, arrival_time, request_id)  
 FCFS mode:  (-bucketed_score, arrival_time, request_id)  
 
 
 Calls  super().schedule()  against the now-reordered queue. Everything downstream (chunked prefill, allocation, preemption ladder, KV connector) stays unchanged. 
 
 Score bucketing (default edges  (4, 16, 64, 256) ) prevents per-iteration thrash on small score deltas. Sticky-front semantics preserve the V1 invariant that preempted requests are scheduled first in their preemption order. 
 Design details 
 Sort-key composition with priority 
 Cache affinity is a tiebreaker  within  a priority class, never across. A high-priority cache-cold request always beats a low-priority cache-warm request. Tested in unit test  test_priority_overrides_cache . 
 Sticky-front for preempted requests 
  CacheAffinityRequestQueue  maintains two internal deques:  _sticky  (for  prepend_request  calls — preempted requests) and  _sortable  (for  add_request  — new arrivals).  pop_request  drains  _sticky  first. The reorder pass only sorts  _sortable . Preserves the existing invariant that preempted requests retain their preemption order. Composes correctly with the new capacity-triggered preemption path in PR  #40087  (verified — the new path uses the same  prepend_request  mechanism). 
 Anti-starvation 
  cache_affinity_max_wait_s  deadline. Catches the pathological case where a request with no cached prefix is forever deprioritized under bursty cached traffic. 
 Min-blocks threshold 
  cache_affinity_min_blocks  (default 2). Requests with fewer cached blocks score 0. Avoids reordering thrash from one-block hits. 
 What we explicitly do NOT do in v1 
 
  No token-level radix tree.  vLLM is committed to block-level prefix hashing; reproducing sglang's radix tree would require KV-manager surgery and clash with the existing design. Operating at block boundaries captures the bulk of the realistic benefit (system prompts, RAG contexts are typically block-aligned). 
  No request-schema changes.  No new fields on  Request . Config lives entirely on  SchedulerConfig . 
  No thrash-eviction guard.  Ship the metric  vllm:cache_affinity_thrash_evictions_total  to detect thrashing; add a guard in a follow-up PR if benchmarks show it firing. Ship simple, collect evidence, iterate. 
 
 Compatibility 
 
  Mutually exclusive  at engine-load time with EWSJF (PR  #33392 ) — different  --scheduler-cls  values, users pick one. Both are reference policies on the pluggable substrate. Future composite is possible (EWSJF's partition tag as outer key, cache-affinity as inner) but out of scope for v1. 
  Independent of and composable with  the  [1/n]  series under issue         [Performance]: Prefix-caching aware scheduling  #7883   . That series fixes  can_allocate  budget calculation; this RFC reorders the queue. Different layers. 
  Compatible with  priority scheduling ( PR #5958 ,  PR #19057 ) — composes via the sort-key tiebreaker. 
  Compatible with  chunked prefill (chunk-size selection unchanged at  scheduler.py:677-692 ). 
  Compatible with  PR  #40087  (sts07142, capacity-triggered preemption) — verified via 3-way speculative merge: clean, no overlapping changes. 
  No effect  when  --scheduler-cls  points elsewhere (the policy is opt-in plugin-loaded).

 Roadmap (out of scope for v1) 
 Possible follow-up PRs once this lands and the substrate is validated: 
 
  Thrash-eviction guard  — once metric data shows whether it's needed. 
  SLA-tier schema  — revival of  RFC #30256  (closed as not planned, schema designed but never implemented). Cache-affinity sort key naturally extends to SLA-tier as primary key. 
  Goodput-driven adaptive controller  — research-grade extension. Composes with sidikbro's EWSJF (PR       PR Title: [Feature] EWSJF: Adaptive Scheduler for Mixed-Workloads (30-50% Throughput Gain)  #33392   ) — EWSJF's partition tag as outer key, cache-affinity as inner. 
  Cross-instance cache-aware routing hooks  — exposure of cache score for use by external routers (production-stack, llm-d). 
 
 These are not part of this proposal. They are listed only to clarify that v1's small scope is intentional. 
 Alternatives considered 
  Token-level radix tree (sglang's approach).  Rejected: clashes with vLLM's committed block-level cache design. Would require KV manager refactor outside any reasonable PR scope. Block-level captures most of the realistic benefit on production traces (shared prefixes are typically block-aligned). 
  Modify default  Scheduler  directly with a feature flag.  Rejected: violates the pluggable scheduler pattern that PR  #14466  introduced. Plugin form is cleaner, opt-in, and stays out of the default code path. 
  In-engine cross-instance routing.  Rejected: cross-instance routing is the gateway / production-stack layer's responsibility. This RFC is in-engine waiting-queue ordering only. 
  Wait for  RFC #24484  (workload-aware adaptive policy) to land first.  Considered but not blocking. EWSJF (PR  #33392 ) is the reference implementation for that RFC, scoped to throughput optimization on mixed workloads (SJF + Bayesian meta-optimizer). It does not cover cache-affinity reordering. The two contributions are orthogonal in objective and complementary in deployment. 
 Open questions for the community 
 
  Default bucket edges  —  (4, 16, 64, 256)  chosen by intuition. Synthetic sweeps in our benchmark harness can tune these before merge if reviewers want a specific methodology. 
  Thrash detection  — currently shipped as a metric only, with the actual guard deferred to a follow-up. Reviewers who want the guard in v1 can flag it; we'll fold it in if there's appetite. 
  In-tree vs  vllm-contrib   — the implementation is small enough to live in-tree under  vllm/v1/core/sched/ . If maintainers prefer reference policies live elsewhere (analogous to how some adapters live out of tree), happy to relocate.
