🐛 Describe the bug

On both engines the config dump says enable_prefix_caching=True, and both are
genuinely caching — above a threshold. Below it they return exactly zero
cache hits, and nothing anywhere in the startup log, the config dump or
/metrics states what the threshold is.

The threshold is one attention block. On a hybrid checkpoint vLLM raises the
attention block size until the attention page is at least as large as the
recurrent-state page, which produces blocks two to three orders of magnitude
larger than the usual 16:

INFO [interface.py:911] Setting attention block size to 2096 tokens to ensure
                        that attention page size is >= mamba page size.
INFO [interface.py:935] Padding mamba page size by 0.58 % to ensure that mamba
                        page size and attention page size are exactly equal.

INFO [interface.py:911] Setting attention block size to 1920 tokens to ensure
                        that attention page size is >= mamba page size.
INFO [interface.py:935] Padding mamba page size by 1.89 % to ensure that mamba
                        page size and attention page size are exactly equal.

Prefix caching registers whole blocks only, so a shared prefix shorter than
one block is structurally uncacheable. A 1,024-token shared system prompt — a
very ordinary size — gets nothing, on an engine that reports prefix caching as
enabled and that shows a healthy hit rate on longer conversations.

Measurement 1 — zero hits over 2.5M prompt tokens, both models

Concurrency sweep 1..24. Every request is a 1,024-token shared system prompt
plus a per-request user turn (~1.6k-token prompts total), independent seed per
point, prefix cache flushed before each point, 200 output tokens:

engine enable_prefix_caching prompt tokens over the sweep prefix-cache hits
A (Nemotron 3.5 Lightning, block 2096) True 2,533,016 0 (0.0 %)
B (Ling-3.0-flash, block 1920) True 2,555,748 0 (0.0 %)

Not "low" — zero, on both, across five million prompt tokens between them. For
contrast, a plain-GQA checkpoint measured under the identical protocol on the
same rig returns 1.4 % on this shape, and a non-hybrid MoE returns 55 % on a
warm run of it.

Two different hybrid families, two different block sizes, the same shape:
cached_tokens is precisely 0 below one block and precisely one block

(The turn-1 → turn-2 TTFT drop on engine A is not a cache effect — both turns
cache zero tokens. It is first-request-of-a-shape JIT warm-up. Reading it as a
"3.1x cache win" would have been wrong, and cached_tokens is what proves it.)

Measurement 3 — the boundary, directly

The two measurements above are multi-turn traces, where the shared prefix is
whatever the conversation happens to make it. To test the boundary directly I
wrote a probe that controls the shared prefix to the token: build a system
prompt of exactly X tokens (generate prose, tokenize, truncate the id list to X,
decode back, re-tokenize to confirm), send 2 unmeasured warm-up requests to pay
the first-request-of-a-shape JIT cost, POST /reset_prefix_cache, then 4
strictly sequential requests with the same system prompt and a different user
turn each. One request in flight at a time, so nothing co-batches.

Every point also carries a control: one request with a different system
prompt of the same length. If the effect were length-driven rather than
prefix-driven, the control would cache too. It cached exactly 0 on all 33
points.

repeat cached equals floor(X / block) * block on all 25 hybrid points.
Hits first appear at exactly one block — engine A at X=2,096 (2,048 caches
nothing), engine B at X=1,920 (1,900 caches nothing). Blocks then accumulate
normally: 3 measured on A, 4 on B. prefix_cache_hits_total in /metrics
advances by exactly 3x the per-request cached_tokens at every point, so the
per-request number and the engine's own counter agree.

A non-hybrid control engine (plain GQA, default block 16, same probe, same
hardware) caches essentially the whole prefix at every length, including the
1,024 the hybrids cache nothing of:

shared prefix X repeat cached x block TTFT first-seen TTFT repeat
1,024 1,024 64x 0.172 0.057
1,900 1,904 119x 0.250 0.065
2,048 2,048 128x 0.256 0.068
4,096 4,096 256x 0.461 0.086
8,192 8,192 512x 0.914 0.124

That control also calibrates the constant: at X=1,900 it caches 1,904 and at
X=2,200 it caches 2,208 — slightly above X, both exact multiples of 16. So
the shared prefix is not X but X + ~8-19 chat-template tokens, floored to the
block. That is why engine A hits at exactly X=2,096 (common ~2,106 >= 2,096) but
not at X=2,048 (common ~2,058 < 2,096).

The cost of the remainder is not small and it is permanent. At a 4,096-token
shared system prompt, engine A caches 2,096 of it and re-prefills the other
2,000 tokens on every request forever — a 1.36x TTFT saving where the non-hybrid
control gets 5.4x. Rounding the same prompt up to 4,192 tokens makes it
strictly faster on every repeat (2.06x) despite being 96 tokens longer, which is
not a trade-off any operator would think to look for.

What I expected

That an engine reporting enable_prefix_caching=True would, somewhere, state
the smallest prefix it can actually cache — or that the number would be
derivable from something an operator reads at startup without knowing the
hybrid KV internals.

What actually happens

The only surface that exposes it is prompt_tokens_details.cached_tokens on an
individual response, and only if --enable-prompt-tokens-details is on. The
startup log prints Setting attention block size to N tokens, which is the
number — but it is phrased as an internal page-alignment detail, sits far from
anything about caching, and nothing connects the two. /metrics gives
vllm:prefix_cache_queries_total and vllm:prefix_cache_hits_total, which
report the symptom (0 / N) and not the cause; a zero there is indistinguishable
from "this workload has no shared prefixes".

Why this matters operationally

Sizing a shared system prompt at 1-2k tokens is the single most common
enterprise prefix shape there is. On these checkpoints it yields no caching at
all, silently:

  • prefix caching is worth nothing,
  • cache-affinity routing in front of the engine is worth nothing (there is no
    cache to be affine to),
  • capacity planning that assumed a warm prefix is wrong by the full prefill
    cost of the system prompt on every request,

and the only way to find out is to instrument per-request cached_tokens. We
found it by accident. Two of the last five checkpoints we deployed are affected,
and the affected fraction grows as Mamba/GDN/KDA hybrids do.

The earlier generation of this trap was at least visible: on one hybrid we
deployed, vLLM logged enable_prefix_caching=False outright and disabled it.
Here the log says True and the counter says zero, which is worse.

Ask

Either of these would have saved the investigation; both would be better:

  1. A startup log line naming the minimum cacheable prefix, emitted next to
    the prefix-caching config when the effective block size is unusually large —
    e.g. Prefix caching enabled: minimum cacheable prefix is 2096 tokens (attention block size); shared prefixes shorter than this will never hit.
    The value is already computed at that point; this is a logging-only change.
  2. A metric or /v1/models-adjacent field exposing it, e.g. a gauge
    vllm:prefix_cache_block_size_tokens, so a fleet can be audited without
    reading every engine's boot log.

A third, cheaper option: mention the whole-block quantum in the prefix-caching
docs and state explicitly that hybrid checkpoints raise the block size into the
thousands. Right now the docs' 16-token mental model is what most operators are
carrying.

I am happy to send the PR for (1) and/or (2) if maintainers say which shape they
want.
