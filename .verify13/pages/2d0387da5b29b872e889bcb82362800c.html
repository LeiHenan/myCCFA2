Motivation

In multi-turn inference workloads such as agentic workflows and RL rollouts, active sessions accumulate reusable KV prefixes across turns. Under memory pressure, the standard radix cache evicts entries using only the configured cache policy, without considering whether a prefix is still referenced by an active session.

This may evict an active session's prefix while unrelated, unreferenced KV remains cached, causing unnecessary recomputation in later turns and reducing cache hit rate and throughput.

Design

This PR adds session-aware eviction to UnifiedRadixCache. Applications pass a stable top-level session_id with each request. When a request finishes, SGLang registers its reusable KV under that session. When the session ends, the application calls /close_session to release those references.

                    --enable-session-radix-cache
                                 |
              +------------------+------------------+
              |                                     |
       request finished                       session closed
              |                                     |
   register_session_ref(req)          release_radix_session(id)
              |                                     |
              +------------- session refs ----------+
                                 |
                       UnifiedRadixCache
                                 |
              +------------------+------------------+
              |                  |                  |
            FULL                SWA               MAMBA
     reusable prefix path   sliding window   reusable state leaf
              |                  |                  |
              +------------------+------------------+
                                 |
                    device and host eviction
                                 |
                 UNREFERENCED -> REFERENCED

Each UnifiedRadixCache component tracks the KV region reusable by a session:

  • FULL attention tracks the reusable prefix path. Eviction orders nodes by (is_referenced, session_ref_count, base_eviction_priority).
  • SWA tracks the reusable sliding-window tail. Device and host eviction use two LRU passes: unreferenced nodes first, then referenced nodes if more space is required.
  • Mamba tracks the reusable state at the session frontier. It uses the same two-pass unreferenced-first fallback.

Referenced KV is soft-protected, not pinned. If unreferenced KV is insufficient, referenced entries remain evictable. Closing a session removes its references without immediately freeing its KV, allowing the KV to remain reusable until normal eviction reclaims it.

Session generations and bounded closed-session tombstones prevent stale in-flight requests from reattaching references after close or close/reopen.

This feature is implemented only by UnifiedRadixCache. Ordinary RadixCache and HiRadixCache do not maintain session references.

Storage-backed L3 cache is not included in this PR.

Modifications

  • Add SessionUnifiedRadixCacheMixin for session lifecycle and stale-request protection.
  • Add per-component session leaf indexes and compact reference counts for FULL, SWA, and Mamba.
  • Apply session-aware ordering to both device and host eviction.
  • Register reusable KV when requests finish and release references through /close_session.
  • Support top-level session_id without changing or reconstructing request prompts.
  • Preserve the configured base eviction policy without requiring --radix-eviction-policy priority.
  • Remove session tracking and SessionAwareEvictionStrategy integration from ordinary RadixCache and HiRadixCache.
  • Add focused tests for UnifiedRadixCache ownership, registration, release, stale generations, and unreferenced-first eviction.
  • Add documentation for enablement, request lifecycle, and per-component eviction behavior.
  • Enable the feature with --enable-session-radix-cache; UnifiedRadixCache must also be enabled.

Speed Tests and Profiling

We evaluate session radix cache on a SWE-agent agentic workload using GLM-5.2 (UnifiedRadixCache) under different batch sizes. The cache hit rate breakdown between the original HiCache and session radix cache is shown below.

The results show that session-reference-aware radix cache substantially improves both cache hit rate and end-to-end throughput. By preserving KV cache entries that are still referenced by active multi-turn requests, session radix cache reduces unnecessary prefix recomputation and improves cache residency under memory pressure.

However, we also observe that the cache hit rate still drops at larger batch sizes. This suggests that large batches can still cause KV cache thrashing, even with reference-aware eviction. Addressing this issue may require additional mechanisms such as cache-aware admission control, batch throttling, or concurrency control, similar to the approaches explored in ThunderAgent and Concur.

Hey wanted to give some of my thoughts on this PR!

Main correctness issue I found: mixed-priority refs can leak within the same session_id.

Repro shape:

  1. session s1 first registers cached nodes as low priority
  2. the same session later extends/registers a high-priority suffix
  3. release_ref("s1")

After release, the suffix can still have high_ref == 1. The reverse high→low case can similarly leak low_ref.

I think the issue is that register_ref() computes the ref class from the current request priority even for an already-tracked session, while release_ref() decrements all nodes using the session’s original RefInfo.is_high. So one session can end up owning nodes in both ref classes, but release assumes one class.

Possible fixes:

  • Simpler invariant: once a session is tracked, all newly registered suffix nodes use ref_info.is_high, not the current request priority.
  • Or stricter lifecycle: require priority-class changes to go through update_ref() before adding new refs, so the session’s existing refs and future refs stay in one class.
  • Or more flexible accounting: track ref class per (session_id, node) instead of one is_high per session. That is more robust but probably more complexity than needed for this PR.

Bigger-picture thoughts:

I like the direction. Agentic workloads are not well served by plain LRU, because useful prefixes can look temporarily cold while the agent is in a tool call, a branch, or a SWE-bench-style edit loop. Treating session_id as a first-class cache identity is a good primitive.

That said, I think the hard part is lifecycle semantics, not only eviction priority. Long term, this probably wants to behave like a session/trajectory lease:

  • refs are acquired when a trajectory produces reusable KV
  • refs are updated when the session priority changes
  • refs are released when the session/task ends
  • abandoned sessions are bounded by TTL or token budget

Things I’d consider next:

  • unify close_session and release_ref, or at least make the relationship explicit
  • add TTL / max protected-token budgets so leaked or abandoned sessions cannot pin KV forever
  • add priority decay so old high-priority sessions eventually become evictable
  • expose metrics: protected tokens by tier, refs by session, release count, stale refs, evictions by tier
  • test against Mooncake toolagent / SWE-bench-like traces with stable session_id per trajectory
  • think about branch-aware caching for agent search/tree-of-thought workloads, where one task may fan out into multiple related continuations

So my take is: the PR is a promising first step toward agent-aware KV management, and the GPU smoke path works, but I’d fix the mixed-priority accounting and clarify the session/ref lifecycle before landing.

feat: support Session Ref Aware for UnifiedRadixCache
d5cae91 
Track per-session references on UnifiedRadixCache KV so that eviction
consumes unreferenced entries before referenced ones, and closing a
session only dereferences its KV instead of freeing it. Enabled by
--enable-session-radix-cache on top of SGLANG_ENABLE_UNIFIED_RADIX_TREE=1.

Each tree component keeps its own session frontier leaves and per-node
session_ref, over the span it actually owns: Full covers the whole
leaf->root path, SWA one sliding window, Mamba only the leaf. The

priority) instead.

request that finishes after a close/reopen of the same session id cannot
