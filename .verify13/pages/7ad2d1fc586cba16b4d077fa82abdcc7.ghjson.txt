EAGLE/MTP prefix-cache last-block drop causes a 1,648-token recompute per hit on one hybrid Qwen3.8 GDN layout — ~30-40% batch throughput loss on prefix-reusing workloads with speculative decoding
EAGLE/MTP prefix-cache last-block drop causes a 1,648-token recompute per
hit on one hybrid Qwen3.8 GDN layout — ~30-40% batch throughput loss on
prefix-reusing workloads with speculative decoding enabled

## Environment

- vLLM `0.26.1rc1.dev926+gb05ae5dc0`, V1/V2 model runner, async scheduling
- Dual RTX 5090 TP=2, FP8 weights + FP8 KV, prefix caching on
- Model: Qwen3.8-27B (hybrid: GDN/Mamba layers + full attention → 15
  MambaSpec KV groups + full-attention group; scheduler/hash block = 1648
  tokens); other hybrid layouts should be evaluated by their own scheduler
  alignment
- Speculative: dflash (DFlash2, K=7) and mtp — both reproduce; also
  reproduces with an always-K=0 tiered config `[[1,16,0]]` +
  `skip_draft_when_k0: true` (drafter provably never runs at c ≥ 3; without
  `skip_draft_when_k0`, K=0 draft-state sync may still run)

## Summary

With any EAGLE-family `speculative_config` set, multi-round / repeated-prompt
workloads lose ~6-10 points of prefix-cache hit rate versus an identical
no-spec boot (97.5% → 86.9-91.7% in our harness). The cause is the EAGLE
last-block drop (`drop_eagle_block`) in the prefix-cache hit path:

1. `kv_cache_coordinator.py` flags **all** KV groups as eagle when the model
   has no `is_eagle_group` annotation (conservative fallback).
2. The EAGLE-marked dense/full-attention group drops one alignment unit from
   its hit (protecting against (a) draft-layer KV for the last block depending
   on the writer's continuation and (b) prefill-lookahead pollution at chunk
   boundaries); hybrid reconciliation then limits the combined hit to that
   shorter boundary, so the request recomputes one 1,648-token scheduler-
   aligned unit.
3. On dense-attention models that alignment unit is a 16-token block. On this
   hybrid GDN/Mamba layout it is **1,648 tokens**. The same protection
   therefore costs ~100× more cache hit here; other hybrid layouts should be
   evaluated by their own scheduler alignment.

Measured per-request-per-round (32k identical prompt re-sent, cache trace of
`get_computed_blocks`):

| Config | warm lookup hit | tail recompute | c=8 tok/s (vs no-spec 327) |
|---|---|---|---|
| no speculative_config | 31360 (20×1568) | 640 tok | 327 |
| dflash K=7 + tiers | 29664 (18×1648) | 2336 tok | 206 (−37%) |
| dflash + drop disabled (ablation) | 31312 (19×1648) | 688 tok | 322 (−1.6%) |

Disabling the drop recovers essentially the entire warm prefix-reuse gap
(+56% at c=8) on this workload — the last-block rule, not spec-decode step
machinery, accounts for it (a separate cold-prefill drafter cost exists on
unique-prompt traffic; see below) (we profiled the
engine loop: per-step decode time is within 0.6% of no-spec at resolved K=0).

The regression is easy to miss: single-request benchmarks with unique prompts
don't reuse prefixes, and aggregate token/s hides where the time goes. Watch
`vllm:prefix_cache_hits_total` and the re-prefill chunk census instead.

## Why the drop is still needed (and why "just disable it" is not the answer)

The drop is load-bearing for consumers that draft: draft-layer KV in the last
matched block depends on tokens past the matched prefix (the writer's
continuation), and chunked prefill with drafting combines a lookahead token
into boundary KV. Serving such a block to a request that will draft from that
boundary gives it stale/foreign draft KV. Speculative decoding stays
lossless (the target verifies every token), so the damage is acceptance
degradation rather than wrong outputs — but for K>0 consumers the recompute
the drop forces is the correct behavior.

The asymmetry is that a consumer running at **resolved K=0** (dynamic
speculation tiers with `skip_draft_when_k0`, or any K=0 tier) never executes
the drafter at all, so it never reads draft-layer KV: the drop protects a
consumer that does not exist. Our proposed fix makes the drop conditional on
exactly that (reference implementation on our fork — over our open-PR limit
on main right now, will open the PR when a slot frees:
https://github.com/Suppressor72/vllm/tree/feat/eagle-k0-consumer-drop @
dfb6eeae79): skip it when the admission's projected
resolved K is 0 under `skip_draft_when_k0`. Result on the same harness:
c=8 206 → 304 tok/s (no-spec 327, hard-disable ceiling 322), prefix-cache hit
rate 91.7% → 95.4%, zero change at c=1/c=2 where K>0 still drafts.

## Repro

Measured on nightly `0.26.1rc1.dev926+gb05ae5dc0` + local patches (DFlash2
backport #52816, `skip_draft_when_k0` #53420/#53426 lineage, dflash tier
validation) — the cache-path code under discussion is upstream code; config:

```json
{"method": "dflash",
 "model": "<DFlash2 drafter for the target>",
 "num_speculative_tokens": 7,
 "num_speculative_tokens_per_batch_size": [[1, 2, 7], [3, 16, 0]],
 "skip_draft_when_k0": true}
```

The causal comparison stays within one 1,648-token geometry: stock hit
29,664 (18 blocks) → drop-disabled 31,312 (19 blocks), same boot layout. The
no-spec arm (31,360 at a different 1,568-token layout) is context, not the
proof.


1. Any hybrid-GDN target with dflash/mtp/eagle `speculative_config`,
   `enable_prefix_caching=true`.
2. Client: re-send the same ~32k prompt (chat completions), 4 rounds × 8
   concurrent sessions, 256 tokens each.
3. Compare against the same boot without `speculative_config`:
   aggregate tok/s, `vllm:prefix_cache_hits_total`, and (instrumented)
   `KVCacheManager.get_computed_blocks` hit lengths — hits land exactly on
   block-size multiples and are one block shorter under spec.

## Additional observation (separate, not addressed by the PR)

With fully unique prompts (`--salt auto`: no reuse possible) the spec boot
still runs at ~0.59× no-spec on this target (150.7 vs 255.8 tok/s at c=8,
prefill-dominated legs) — a cold-prefill drafter-context cost that is
inherent to running the drafter, distinct from the cache issue above. We have
not yet decomposed it; happy to file separately if maintainers prefer.

<h2 dir="auto">Why the drop is still needed (and why "just disable it" is not the answer)</h2>
<p dir="auto">The drop is load-bearing for consumers that draft: draft-layer KV in the last<br>
matched block depends on tokens past the matched prefix (the writer's<br>
continuation), and chunked prefill with drafting combines a lookahead token<br>
into boundary KV. Serving such a block to a request that will draft from that<br>
boundary gives it stale/foreign draft KV. Speculative decoding stays<br>
lossless (the target verifies every token), so the damage is acceptance<br>
degradation rather than wrong outputs — but for K&gt;0 consumers the recompute<br>
the drop forces is the correct behavior.</p>
<p dir="auto">The asymmetry is that a consumer running at <strong>resolved K=0</strong> (dynamic<br>
speculation tiers with <code class="notranslate">skip_draft_when_k0</code>, or any K=0 tier) never executes<br>
the drafter at all, so it never reads draft-layer KV: the drop protects a<br>
consumer that does not exist. Our proposed fix makes the drop conditional on<br>
exactly that (reference implementation on our fork — over our open-PR limit<br>
on main right now, will open the PR when a slot frees:<br>
<a href="https://github.com/Suppressor72/vllm/tree/feat/eagle-k0-consumer-drop">https://github.com/Suppressor72/vllm/tree/feat/eagle-k0-consumer-drop</a> @<br>
<a class="commit-link" data-hovercard-type="commit" data-hovercard-url="https://github.com/vllm-project/vllm/commit/dfb6eeae7978d0a98dccc132832688986191735c/hovercard" href="https://github.com/vllm-project/vllm/commit/dfb6eeae7978d0a98dccc132832688986191735c"><tt>dfb6eea</tt></a>): skip it when the admission's projected<br>
resolved K is 0 under <code class="notranslate">skip_draft_when_k0</code>. Result on the same harness:<br>
c=8 206 → 304 tok/s (no-spec 327, hard-disable ceiling 322), prefix-cache hit<br>
rate 91.7% → 95.4%, zero change at c=1/c=2 where K&gt;0 still drafts.</p>

equality provides the proof needed to retain the block — which is exactly what

Reproduces on a different model family, which looks like the axis this thread has not covered yet — the two reproductions so far are both Qwen3.8-27B, on different hardware.

**Stack.** Gemma-4-31B-it-qat-FP8 (hybrid attention: sliding + global, `head_dim=256/512`, FA4 for all layers), separate `-assistant` checkpoint that vLLM resolves to `Gemma4MTPModel` and reports as `method='mtp'`. 1× H100 NVL, vLLM 0.27.1, **V1 runner** (`VLLM_USE_V2_MODEL_RUNNER=0`), single GPU, prefix caching on. Schedule pinned to always-K=0 (`[[1, 512, 0]]`); `spec_decode_num_draft_tokens_delta` summed to exactly 0.0 over every measured run, so no drafter rollout occurs in either arm.

Workload is not agentic multi-turn — `vllm bench serve --dataset-name prefix_repetition`, one shared 400-token prefix class, 100 output tokens — and it still shows the drop.

**The deficit is a constant, and that is the part I think is new here.** Sweeping context at fixed low concurrency, three measured runs per cell:

| ctx | conc | queries/run | hits `no_spec` | hits `mtp` K=0 | deficit | hit rate |
|---:|---:|---:|---:|---:|---:|---|
| 400 | 2 | 7 942 | 7 680 | 6 656 | **1 024** | 96.70 % → 83.81 % |
| 4 000 | 26 | 213 004 | 211 456 | 209 792 | 1 664 | 99.27 % → 98.49 % |
| 16 000 | 6 | 257 536 | 257 024 | 256 512 | **512** | 99.80 % → 99.60 % |
| 38 000 | 2 | 609 535 | 609 280 | 608 768 | **512** | 99.96 % → 99.87 % |

The absolute deficit does not grow with the prompt — 512 tokens at both 16k and 38k, a 2.4× context change — so the hit-rate gap collapses from **−12.89 pp to −0.09 pp** across a 95× context range. That is what a fixed alignment-unit drop looks like when you vary the denominator, and it complements @jschmied's turn-count view: same signature, measured along context instead of along turns.

The unit here reads as **512 tokens**, against 1 568 / 1 600 / 1 648 in the two Qwen3.8 reports. Different layout, different unit, same one-unit drop — which supports reading this as "one alignment unit, whatever that unit is for the layout" rather than anything specific to a block size.

**The path is active by construction on this stack**, checked in v0.27.1 source rather than inferred:

- `SpeculativeConfig.use_eagle()` → `self.method in ("eagle", "eagle3", "mtp", "dflash", "dspark")`, and this arm is `method='mtp'`.
- `kv_cache_coordinator.py`: `eagle_group_ids` is built from `g.is_eagle_group`, then *"Conservatively fall back to flag all groups when no group is flagged"* — so on a layout without the annotation, the dense/full-attention group is flagged too.
- The lookup then gets `drop_eagle_block=..., alignment_tokens=self.block_size`.

**Two things I would not claim.** The one high-concurrency cell I have (ctx 400, c 189) loses 24 800 tokens, which is not a clean multiple of the unit, and both arms are already thrashing there (77.72 % → 64.49 %) — I do not attribute that cell to this mechanism. And the 512-token unit is what the counters show; this build does not print its block size, so I have not confirmed the unit *is* the block size.

**One difference from the filing worth recording.** I see the hit-rate loss but not a comparable time cost. In the same runs, per-token latency of the K=0 spec arm against no-spec is +6.56 % at ctx 400 and +6.46 % at ctx 38 000 — flat across the range, while this term's share falls two orders of magnitude over that same range. On a decode-heavy single-prefix workload with a 512-token unit, the recompute is apparently too small to move TPOT, which is consistent with the −27 points / 3× TTFT appearing on multi-turn agentic shapes with ~1.6k units rather than everywhere. That may help bound where the fix matters most.

```python
# vllm/config/speculative.py:1861

        """Whether volatile trailing cache blocks should be discarded."""

```

`use_eagle()` covers `eagle`, `eagle3`, `mtp`, `dflash` and `dspark`, and the result is consumed in `vllm/v1/core/kv_cache_utils.py:2111` along with the offloading scheduler and the Mooncake store worker. So every deployment that does not set the flag still drops the trailing block and still pays the recompute this issue measured — the default path is unchanged by design.

That leaves a question for the maintainers rather than for me: should this stay open against the default, or is an opt-out the intended resolution and the issue should close? I have no stake in which; I would just rather it not sit open by accident, and the three threads linking here would benefit from knowing which it is.

One thing worth keeping separate: #54360 reports prefix-cache hits going to *zero* on hybrid GDN, which is a larger failure than the single trailing block this issue is about. The switch here should not be assumed to cover that one.

<p dir="auto">So the question you put to maintainers is the right one and we would sharpen it only slightly: the<br>
blanket drop has not bought measurable acceptance on either always-drafting layout tested, while costing<br>
one alignment unit of recompute per prefix hit — and the acceptance side may not be measurable at all at<br>
these sample sizes.</p>

 Environment 
 
 vLLM  0.26.1rc1.dev926+gb05ae5dc0 , V1/V2 model runner, async scheduling 
 Dual RTX 5090 TP=2, FP8 weights + FP8 KV, prefix caching on 
 Model: Qwen3.8-27B (hybrid: GDN/Mamba layers + full attention → 15 
MambaSpec KV groups + full-attention group; scheduler/hash block = 1648 
tokens); other hybrid layouts should be evaluated by their own scheduler 
alignment 
 Speculative: dflash (DFlash2, K=7) and mtp — both reproduce; also 
reproduces with an always-K=0 tiered config  [[1,16,0]]  + 
 skip_draft_when_k0: true  (drafter provably never runs at c ≥ 3; without 
 skip_draft_when_k0 , K=0 draft-state sync may still run) 
 
 Summary 
 With any EAGLE-family  speculative_config  set, multi-round / repeated-prompt 
workloads lose ~6-10 points of prefix-cache hit rate versus an identical 
no-spec boot (97.5% → 86.9-91.7% in our harness). The cause is the EAGLE 
last-block drop ( drop_eagle_block ) in the prefix-cache hit path: 
 
  kv_cache_coordinator.py  flags  all  KV groups as eagle when the model 
has no  is_eagle_group  annotation (conservative fallback). 
 The EAGLE-marked dense/full-attention group drops one alignment unit from 
its hit (protecting against (a) draft-layer KV for the last block depending 
on the writer's continuation and (b) prefill-lookahead pollution at chunk 
boundaries); hybrid reconciliation then limits the combined hit to that 
shorter boundary, so the request recomputes one 1,648-token scheduler- 
aligned unit. 
 On dense-attention models that alignment unit is a 16-token block. On this 
hybrid GDN/Mamba layout it is  1,648 tokens . The same protection 
therefore costs ~100× more cache hit here; other hybrid layouts should be 
evaluated by their own scheduler alignment.

 Disabling the drop recovers essentially the entire warm prefix-reuse gap 
(+56% at c=8) on this workload — the last-block rule, not spec-decode step 
machinery, accounts for it (a separate cold-prefill drafter cost exists on 
unique-prompt traffic; see below) (we profiled the 
engine loop: per-step decode time is within 0.6% of no-spec at resolved K=0). 
 The regression is easy to miss: single-request benchmarks with unique prompts 
don't reuse prefixes, and aggregate token/s hides where the time goes. Watch 
 vllm:prefix_cache_hits_total  and the re-prefill chunk census instead. 
 Why the drop is still needed (and why "just disable it" is not the answer) 
 The drop is load-bearing for consumers that draft: draft-layer KV in the last 
matched block depends on tokens past the matched prefix (the writer's 
continuation), and chunked prefill with drafting combines a lookahead token 
into boundary KV. Serving such a block to a request that will draft from that 
boundary gives it stale/foreign draft KV. Speculative decoding stays 
lossless (the target verifies every token), so the damage is acceptance 
degradation rather than wrong outputs — but for K>0 consumers the recompute 
the drop forces is the correct behavior. 
 The asymmetry is that a consumer running at  resolved K=0  (dynamic 
speculation tiers with  skip_draft_when_k0 , or any K=0 tier) never executes 
the drafter at all, so it never reads draft-layer KV: the drop protects a 
consumer that does not exist. Our proposed fix makes the drop conditional on 
exactly that (reference implementation on our fork — over our open-PR limit 
on main right now, will open the PR when a slot frees: 
 https://github.com/Suppressor72/vllm/tree/feat/eagle-k0-consumer-drop  @ 
  dfb6eea  ): skip it when the admission's projected 
resolved K is 0 under  skip_draft_when_k0 . Result on the same harness: 
c=8 206 → 304 tok/s (no-spec 327, hard-disable ceiling 322), prefix-cache hit 
rate 91.7% → 95.4%, zero change at c=1/c=2 where K>0 still drafts. 
 Repro 
 Measured on nightly  0.26.1rc1.dev926+gb05ae5dc0  + local patches (DFlash2 
backport  #52816 ,  skip_draft_when_k0   #53420 / #53426  lineage, dflash tier 
validation) — the cache-path code under discussion is upstream code; config: 
  { "method" :   " dflash "  ,
  "model" :   " <DFlash2 drafter for the target> "  ,
  "num_speculative_tokens" :  7 ,
  "num_speculative_tokens_per_batch_size" : [[ 1 ,  2 ,  7 ], [ 3 ,  16 ,  0 ]],
  "skip_draft_when_k0" :  true }  
 The causal comparison stays within one 1,648-token geometry: stock hit 
29,664 (18 blocks) → drop-disabled 31,312 (19 blocks), same boot layout. The 
no-spec arm (31,360 at a different 1,568-token layout) is context, not the 
proof. 
 
 Any hybrid-GDN target with dflash/mtp/eagle  speculative_config , 
 enable_prefix_caching=true . 
 Client: re-send the same ~32k prompt (chat completions), 4 rounds × 8 
concurrent sessions, 256 tokens each. 
 Compare against the same boot without  speculative_config : 
aggregate tok/s,  vllm:prefix_cache_hits_total , and (instrumented) 
 KVCacheManager.get_computed_blocks  hit lengths — hits land exactly on 
block-size multiples and are one block shorter under spec. 
 
 Additional observation (separate, not addressed by the PR) 
 With fully unique prompts ( --salt auto : no reuse possible) the spec boot 
still runs at ~0.59× no-spec on this target (150.7 vs 255.8 tok/s at c=8, 
prefill-dominated legs) — a cold-prefill drafter-context cost that is 
inherent to running the drafter, distinct from the cache issue above. We have 
not yet decomposed it; happy to file separately if maintainers prefer.
