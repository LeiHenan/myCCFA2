[Bug]: enable_prefix_caching=True but zero hits for any shared prefix shorter than one attention block on hybrid checkpoints (2096 / 1920 tokens), with nothing in the logs or metrics naming the minimum
### Your current environment

<details>

Two independent single-GPU engines, each on one **H200 (SM90)**, TP=1, on 2xH200 nodes.

### 🐛 Describe the bug

On both engines the config dump says `enable_prefix_caching=True`, and both are
genuinely caching — above a threshold. Below it they return **exactly zero**
cache hits, and nothing anywhere in the startup log, the config dump or
`/metrics` states what the threshold is.

The threshold is one attention block. On a hybrid checkpoint vLLM raises the
attention block size until the attention page is at least as large as the
recurrent-state page, which produces blocks **two to three orders of magnitude
larger than the usual 16**:

```
INFO [interface.py:911] Setting attention block size to 2096 tokens to ensure
                        that attention page size is >= mamba page size.
INFO [interface.py:935] Padding mamba page size by 0.58 % to ensure that mamba
                        page size and attention page size are exactly equal.
```

```
INFO [interface.py:911] Setting attention block size to 1920 tokens to ensure
                        that attention page size is >= mamba page size.
INFO [interface.py:935] Padding mamba page size by 1.89 % to ensure that mamba
                        page size and attention page size are exactly equal.
```

Prefix caching registers **whole blocks** only, so a shared prefix shorter than
one block is structurally uncacheable. A 1,024-token shared system prompt — a
very ordinary size — gets nothing, on an engine that reports prefix caching as
enabled and that shows a healthy hit rate on longer conversations.

#### Measurement 1 — zero hits over 2.5M prompt tokens, both models

Concurrency sweep 1..24. Every request is a 1,024-token shared system prompt
plus a per-request user turn (~1.6k-token prompts total), independent seed per
point, prefix cache flushed before each point, 200 output tokens:

| engine | `enable_prefix_caching` | prompt tokens over the sweep | **prefix-cache hits** |
|---|---|---|---|
| A (Nemotron 3.5 Lightning, block 2096) | `True` | 2,533,016 | **0 (0.0 %)** |
| B (Ling-3.0-flash, block 1920) | `True` | 2,555,748 | **0 (0.0 %)** |

Not "low" — zero, on both, across five million prompt tokens between them. For
contrast, a plain-GQA checkpoint measured under the identical protocol on the
same rig returns 1.4 % on this shape, and a non-hybrid MoE returns 55 % on a
warm run of it.

#### Measurement 2 — per-request `cached_tokens`, and the quantum

8 conversations x 6 turns, 1,024-token shared system prompt, reading
`usage.prompt_tokens_details.cached_tokens` per request
(`--enable-prompt-tokens-details`). Median per turn:

**Engine A — block size 2096:**

| turn | prompt tokens p50 | **cached tokens p50** | TTFT p50 s |
|---|---|---|---|
| 1 | 1,692 | **0** | 0.380 |
| 2 | 2,024 | **0** | 0.098 |
| 3 | 2,356 | **0** | 0.145 |
| 4 | 2,687 | **2,096** | 0.153 |
| 5 | 3,020 | **2,096** | 0.124 |
| 6 | 3,352 | **2,096** | 0.121 |

**Engine B — block size 1920:**

| turn | prompt tokens p50 | **cached tokens p50** | TTFT p50 s |
|---|---|---|---|
| 1 | 1,688 | **0** | 0.864 |
| 2 | 2,022 | **0** | 0.262 |

| 5 | 3,025 | **1,920** | 0.238 |
| 6 | 3,357 | **1,920** | 0.210 |

Two different hybrid families, two different block sizes, the same shape:
`cached_tokens` is **precisely 0 below one block** and **precisely one block
above it**. It crosses at exactly the block boundary in both cases.

(The turn-1 → turn-2 TTFT drop on engine A is *not* a cache effect — both turns
cache zero tokens. It is first-request-of-a-shape JIT warm-up. Reading it as a
"3.1x cache win" would have been wrong, and `cached_tokens` is what proves it.)

#### Measurement 3 — the boundary, directly

The two measurements above are multi-turn traces, where the shared prefix is
whatever the conversation happens to make it. To test the boundary directly I
wrote a probe that controls the shared prefix *to the token*: build a system
prompt of exactly X tokens (generate prose, tokenize, truncate the id list to X,
decode back, re-tokenize to confirm), send 2 unmeasured warm-up requests to pay
the first-request-of-a-shape JIT cost, `POST /reset_prefix_cache`, then 4
strictly sequential requests with the same system prompt and a different user
turn each. One request in flight at a time, so nothing co-batches.

Every point also carries a **control**: one request with a *different* system
prompt of the *same* length. If the effect were length-driven rather than
prefix-driven, the control would cache too. **It cached exactly 0 on all 33
points.**

**`repeat cached` equals `floor(X / block) * block` on all 25 hybrid points.**
Hits first appear at exactly one block — engine A at X=2,096 (2,048 caches
nothing), engine B at X=1,920 (1,900 caches nothing). Blocks then accumulate
normally: 3 measured on A, 4 on B. `prefix_cache_hits_total` in `/metrics`
advances by exactly 3x the per-request `cached_tokens` at every point, so the
per-request number and the engine's own counter agree.

**A non-hybrid control engine** (plain GQA, default block 16, same probe, same
hardware) caches essentially the whole prefix at every length, including the
1,024 the hybrids cache nothing of:

| shared prefix X | repeat cached | x block | TTFT first-seen | TTFT repeat |
|---|---|---|---|---|
| 1,024 | 1,024 | 64x | 0.172 | 0.057 |
| 1,900 | 1,904 | 119x | 0.250 | 0.065 |
| 2,048 | 2,048 | 128x | 0.256 | 0.068 |
| 4,096 | 4,096 | 256x | 0.461 | 0.086 |
| 8,192 | 8,192 | 512x | 0.914 | 0.124 |

That control also calibrates the constant: at X=1,900 it caches **1,904** and at
X=2,200 it caches **2,208** — slightly *above* X, both exact multiples of 16. So
the shared prefix is not X but X + ~8-19 chat-template tokens, floored to the
block. That is why engine A hits at exactly X=2,096 (common ~2,106 >= 2,096) but
not at X=2,048 (common ~2,058 < 2,096).

**The cost of the remainder is not small and it is permanent.** At a 4,096-token
shared system prompt, engine A caches 2,096 of it and re-prefills the other
2,000 tokens on every request forever — a 1.36x TTFT saving where the non-hybrid
control gets 5.4x. Rounding the same prompt *up* to 4,192 tokens makes it
strictly faster on every repeat (2.06x) despite being 96 tokens longer, which is
not a trade-off any operator would think to look for.

### What I expected

That an engine reporting `enable_prefix_caching=True` would, somewhere, state
the smallest prefix it can actually cache — or that the number would be
derivable from something an operator reads at startup without knowing the
hybrid KV internals.

### What actually happens

The only surface that exposes it is `prompt_tokens_details.cached_tokens` on an
individual response, and only if `--enable-prompt-tokens-details` is on. The
startup log prints `Setting attention block size to N tokens`, which *is* the
number — but it is phrased as an internal page-alignment detail, sits far from
anything about caching, and nothing connects the two. `/metrics` gives
`vllm:prefix_cache_queries_total` and `vllm:prefix_cache_hits_total`, which
report the symptom (0 / N) and not the cause; a zero there is indistinguishable
from "this workload has no shared prefixes".

### Why this matters operationally

Sizing a shared system prompt at 1-2k tokens is the single most common
enterprise prefix shape there is. On these checkpoints it yields **no caching at
all**, silently:

- prefix caching is worth nothing,
- cache-affinity routing in front of the engine is worth nothing (there is no
  cache to be affine to),
- capacity planning that assumed a warm prefix is wrong by the full prefill
  cost of the system prompt on every request,

and the only way to find out is to instrument per-request `cached_tokens`. We
found it by accident. Two of the last five checkpoints we deployed are affected,
and the affected fraction grows as Mamba/GDN/KDA hybrids do.

The earlier generation of this trap was at least visible: on one hybrid we
deployed, vLLM logged `enable_prefix_caching=False` outright and disabled it.
Here the log says `True` and the counter says zero, which is worse.

### Ask

Either of these would have saved the investigation; both would be better:

1. **A startup log line naming the minimum cacheable prefix**, emitted next to
   the prefix-caching config when the effective block size is unusually large —
   e.g. `Prefix caching enabled: minimum cacheable prefix is 2096 tokens
   (attention block size); shared prefixes shorter than this will never hit.`
   The value is already computed at that point; this is a logging-only change.
2. **A metric or `/v1/models`-adjacent field exposing it**, e.g. a gauge
   `vllm:prefix_cache_block_size_tokens`, so a fleet can be audited without
   reading every engine's boot log.

A third, cheaper option: mention the whole-block quantum in the prefix-caching
docs and state explicitly that hybrid checkpoints raise the block size into the
thousands. Right now the docs' 16-token mental model is what most operators are
carrying.

I am happy to send the PR for (1) and/or (2) if maintainers say which shape they
want.

### 🐛 Describe the bug

On both engines the config dump says `enable_prefix_caching=True`, and both are
genuinely caching — above a threshold. Below it they return **exactly zero**
cache hits, and nothing anywhere in the startup log, the config dump or
`/metrics` states what the threshold is.

The threshold is one attention block. On a hybrid checkpoint vLLM raises the
attention block size until the attention page is at least as large as the
recurrent-state page, which produces blocks **two to three orders of magnitude
larger than the usual 16**:

```
INFO [interface.py:911] Setting attention block size to 2096 tokens to ensure
                        that attention page size is >= mamba page size.
INFO [interface.py:935] Padding mamba page size by 0.58 % to ensure that mamba
                        page size and attention page size are exactly equal.
```

```
INFO [interface.py:911] Setting attention block size to 1920 tokens to ensure
                        that attention page size is >= mamba page size.
INFO [interface.py:935] Padding mamba page size by 1.89 % to ensure that mamba
                        page size and attention page size are exactly equal.
```

Prefix caching registers **whole blocks** only, so a shared prefix shorter than
one block is structurally uncacheable. A 1,024-token shared system prompt — a
very ordinary size — gets nothing, on an engine that reports prefix caching as
enabled and that shows a healthy hit rate on longer conversations.

#### Measurement 1 — zero hits over 2.5M prompt tokens, both models

Concurrency sweep 1..24. Every request is a 1,024-token shared system prompt
plus a per-request user turn (~1.6k-token prompts total), independent seed per
point, prefix cache flushed before each point, 200 output tokens:

| engine | `enable_prefix_caching` | prompt tokens over the sweep | **prefix-cache hits** |
|---|---|---|---|
| A (Nemotron 3.5 Lightning, block 2096) | `True` | 2,533,016 | **0 (0.0 %)** |
| B (Ling-3.0-flash, block 1920) | `True` | 2,555,748 | **0 (0.0 %)** |

Not "low" — zero, on both, across five million prompt tokens between them. For
contrast, a plain-GQA checkpoint measured under the identical protocol on the
same rig returns 1.4 % on this shape, and a non-hybrid MoE returns 55 % on a
warm run of it.

#### Measurement 3 — the boundary, directly

The two measurements above are multi-turn traces, where the shared prefix is
whatever the conversation happens to make it. To test the boundary directly I
wrote a probe that controls the shared prefix *to the token*: build a system
prompt of exactly X tokens (generate prose, tokenize, truncate the id list to X,
decode back, re-tokenize to confirm), send 2 unmeasured warm-up requests to pay
the first-request-of-a-shape JIT cost, `POST /reset_prefix_cache`, then 4
strictly sequential requests with the same system prompt and a different user
turn each. One request in flight at a time, so nothing co-batches.

Every point also carries a **control**: one request with a *different* system
prompt of the *same* length. If the effect were length-driven rather than
prefix-driven, the control would cache too. **It cached exactly 0 on all 33
points.**

**`repeat cached` equals `floor(X / block) * block` on all 25 hybrid points.**
Hits first appear at exactly one block — engine A at X=2,096 (2,048 caches
nothing), engine B at X=1,920 (1,900 caches nothing). Blocks then accumulate
normally: 3 measured on A, 4 on B. `prefix_cache_hits_total` in `/metrics`
advances by exactly 3x the per-request `cached_tokens` at every point, so the
per-request number and the engine's own counter agree.

**A non-hybrid control engine** (plain GQA, default block 16, same probe, same
hardware) caches essentially the whole prefix at every length, including the
1,024 the hybrids cache nothing of:

| shared prefix X | repeat cached | x block | TTFT first-seen | TTFT repeat |
|---|---|---|---|---|
| 1,024 | 1,024 | 64x | 0.172 | 0.057 |
| 1,900 | 1,904 | 119x | 0.250 | 0.065 |
| 2,048 | 2,048 | 128x | 0.256 | 0.068 |
| 4,096 | 4,096 | 256x | 0.461 | 0.086 |
| 8,192 | 8,192 | 512x | 0.914 | 0.124 |

That control also calibrates the constant: at X=1,900 it caches **1,904** and at
X=2,200 it caches **2,208** — slightly *above* X, both exact multiples of 16. So
the shared prefix is not X but X + ~8-19 chat-template tokens, floored to the
block. That is why engine A hits at exactly X=2,096 (common ~2,106 >= 2,096) but
not at X=2,048 (common ~2,058 < 2,096).

**The cost of the remainder is not small and it is permanent.** At a 4,096-token
shared system prompt, engine A caches 2,096 of it and re-prefills the other
2,000 tokens on every request forever — a 1.36x TTFT saving where the non-hybrid
control gets 5.4x. Rounding the same prompt *up* to 4,192 tokens makes it
strictly faster on every repeat (2.06x) despite being 96 tokens longer, which is
not a trade-off any operator would think to look for.

### What I expected

That an engine reporting `enable_prefix_caching=True` would, somewhere, state
the smallest prefix it can actually cache — or that the number would be
derivable from something an operator reads at startup without knowing the
hybrid KV internals.

### What actually happens

The only surface that exposes it is `prompt_tokens_details.cached_tokens` on an
individual response, and only if `--enable-prompt-tokens-details` is on. The
startup log prints `Setting attention block size to N tokens`, which *is* the
number — but it is phrased as an internal page-alignment detail, sits far from
anything about caching, and nothing connects the two. `/metrics` gives
`vllm:prefix_cache_queries_total` and `vllm:prefix_cache_hits_total`, which
report the symptom (0 / N) and not the cause; a zero there is indistinguishable
from "this workload has no shared prefixes".

### Why this matters operationally

Sizing a shared system prompt at 1-2k tokens is the single most common
enterprise prefix shape there is. On these checkpoints it yields **no caching at
all**, silently:

- prefix caching is worth nothing,
- cache-affinity routing in front of the engine is worth nothing (there is no
  cache to be affine to),
- capacity planning that assumed a warm prefix is wrong by the full prefill
  cost of the system prompt on every request,

and the only way to find out is to instrument per-request `cached_tokens`. We
found it by accident. Two of the last five checkpoints we deployed are affected,
and the affected fraction grows as Mamba/GDN/KDA hybrids do.

The earlier generation of this trap was at least visible: on one hybrid we
deployed, vLLM logged `enable_prefix_caching=False` outright and disabled it.
Here the log says `True` and the counter says zero, which is worse.

### Ask

Either of these would have saved the investigation; both would be better:

1. **A startup log line naming the minimum cacheable prefix**, emitted next to
   the prefix-caching config when the effective block size is unusually large —
   e.g. `Prefix caching enabled: minimum cacheable prefix is 2096 tokens
   (attention block size); shared prefixes shorter than this will never hit.`
   The value is already computed at that point; this is a logging-only change.
2. **A metric or `/v1/models`-adjacent field exposing it**, e.g. a gauge
   `vllm:prefix_cache_block_size_tokens`, so a fleet can be audited without
   reading every engine's boot log.

A third, cheaper option: mention the whole-block quantum in the prefix-caching
docs and state explicitly that hybrid checkpoints raise the block size into the
thousands. Right now the docs' 16-token mental model is what most operators are
carrying.

I am happy to send the PR for (1) and/or (2) if maintainers say which shape they
want.

<h4 dir="auto">Measurement 3 — the boundary, directly</h4>
<p dir="auto">The two measurements above are multi-turn traces, where the shared prefix is<br>
whatever the conversation happens to make it. To test the boundary directly I<br>
wrote a probe that controls the shared prefix <em>to the token</em>: build a system<br>
prompt of exactly X tokens (generate prose, tokenize, truncate the id list to X,<br>
decode back, re-tokenize to confirm), send 2 unmeasured warm-up requests to pay<br>
the first-request-of-a-shape JIT cost, <code class="notranslate">POST /reset_prefix_cache</code>, then 4<br>
strictly sequential requests with the same system prompt and a different user<br>
turn each. One request in flight at a time, so nothing co-batches.</p>
<p dir="auto">Every point also carries a <strong>control</strong>: one request with a <em>different</em> system<br>
prompt of the <em>same</em> length. If the effect were length-driven rather than<br>
prefix-driven, the control would cache too. <strong>It cached exactly 0 on all 33<br>
points.</strong></p>

<p dir="auto">That control also calibrates the constant: at X=1,900 it caches <strong>1,904</strong> and at<br>
X=2,200 it caches <strong>2,208</strong> — slightly <em>above</em> X, both exact multiples of 16. So<br>
the shared prefix is not X but X + ~8-19 chat-template tokens, floored to the<br>
block. That is why engine A hits at exactly X=2,096 (common ~2,106 &gt;= 2,096) but<br>
not at X=2,048 (common ~2,058 &lt; 2,096).</p>
<p dir="auto"><strong>The cost of the remainder is not small and it is permanent.</strong> At a 4,096-token<br>
shared system prompt, engine A caches 2,096 of it and re-prefills the other<br>
2,000 tokens on every request forever — a 1.36x TTFT saving where the non-hybrid<br>
control gets 5.4x. Rounding the same prompt <em>up</em> to 4,192 tokens makes it<br>
strictly faster on every repeat (2.06x) despite being 96 tokens longer, which is<br>
not a trade-off any operator would think to look for.</p>
<h3 dir="auto">What I expected</h3>
<p dir="auto">That an engine reporting <code class="notranslate">enable_prefix_caching=True</code> would, somewhere, state<br>
the smallest prefix it can actually cache — or that the number would be<br>
derivable from something an operator reads at startup without knowing the<br>
hybrid KV internals.</p>
<h3 dir="auto">What actually happens</h3>
<p dir="auto">The only surface that exposes it is <code class="notranslate">prompt_tokens_details.cached_tokens</code> on an<br>
individual response, and only if <code class="notranslate">--enable-prompt-tokens-details</code> is on. The<br>
startup log prints <code class="notranslate">Setting attention block size to N tokens</code>, which <em>is</em> the<br>
number — but it is phrased as an internal page-alignment detail, sits far from<br>
anything about caching, and nothing connects the two. <code class="notranslate">/metrics</code> gives<br>
<code class="notranslate">vllm:prefix_cache_queries_total</code> and <code class="notranslate">vllm:prefix_cache_hits_total</code>, which<br>
report the symptom (0 / N) and not the cause; a zero there is indistinguishable<br>
from "this workload has no shared prefixes".</p>
<h3 dir="auto">Why this matters operationally</h3>
<p dir="auto">Sizing a shared system prompt at 1-2k tokens is the single most common<br>
enterprise prefix shape there is. On these checkpoints it yields <strong>no caching at<br>
all</strong>, silently:</p>
<ul dir="auto">
<li>prefix caching is worth nothing,</li>
<li>cache-affinity routing in front of the engine is worth nothing (there is no<br>
cache to be affine to),</li>
<li>capacity planning that assumed a warm prefix is wrong by the full prefill<br>
cost of the system prompt on every request,</li>
</ul>
<p dir="auto">and the only way to find out is to instrument per-request <code class="notranslate">cached_tokens</code>. We<br>
found it by accident. Two of the last five checkpoints we deployed are affected,<br>
and the affected fraction grows as Mamba/GDN/KDA hybrids do.</p>
<p dir="auto">The earlier generation of this trap was at least visible: on one hybrid we<br>
deployed, vLLM logged <code class="notranslate">enable_prefix_caching=False</code> outright and disabled it.<br>
Here the log says <code class="notranslate">True</code> and the counter says zero, which is worse.</p>
<h3 dir="auto">Ask</h3>
<p dir="auto">Either of these would have saved the investigation; both would be better:</p>
<ol dir="auto">
<li><strong>A startup log line naming the minimum cacheable prefix</strong>, emitted next to<br>
the prefix-caching config when the effective block size is unusually large —<br>
e.g. <code class="notranslate">Prefix caching enabled: minimum cacheable prefix is 2096 tokens (attention block size); shared prefixes shorter than this will never hit.</code><br>
The value is already computed at that point; this is a logging-only change.</li>
<li><strong>A metric or <code class="notranslate">/v1/models</code>-adjacent field exposing it</strong>, e.g. a gauge<br>
<code class="notranslate">vllm:prefix_cache_block_size_tokens</code>, so a fleet can be audited without<br>
reading every engine's boot log.</li>
</ol>
<p dir="auto">A third, cheaper option: mention the whole-block quantum in the prefix-caching<br>
docs and state explicitly that hybrid checkpoints raise the block size into the<br>
thousands. Right now the docs' 16-token mental model is what most operators are<br>
carrying.</p>
<p dir="auto">I am happy to send the PR for (1) and/or (2) if maintainers say which shape they<br>
want.</p>

Reproduced your law on `main` @ 8a0a7ee on a third hybrid family: Qwen3.6-35B-A3B W4A16 (GDN + full attention MoE), RTX 6000 Ada, TP=1, `align`, resolved block **1056**. Synthetic prompts, single run. For N=8 requests sharing a `sharedP`-token prefix, hits landed on `(N-1) x floor(sharedP / unit) x unit` in every cell of the five arms without an MTP block drop (five prefix lengths each), once one probe bug of mine is accounted for (two synthetic system prompts shared a token prefix and inflated one cell by one request's worth). A **908-token shared prefix caches 0 tokens permanently** — four sequential requests gave 0/0/0/0 hits and flat TTFT (62.5 / 58.5 / 57.6 / 56.1 ms); at 1308 tokens the first hit appears on the second request.

Two things not in the issue that change what an operator would do:

1. **`--prefix-match-unit` removes the floor without touching the prompt.** An 883-token shared prefix goes 0% → 78% hit fraction over the warm requests at `--prefix-match-unit 352`; a 12-turn conversation on a 512-token system prompt, which never reaches a cacheable boundary by default, goes 0.000 → 0.665. The catch: legal values must divide the resolved block, and every power of two is rejected here (`Invalid prefix_match_unit=64; ... Got group block sizes=[1056, 1056, 1056, 1056]`; 1056 = 2^5·3·11, so 352 works). That makes your ask (1) more valuable — the startup line has to be readable before you can pick a unit.

2. **On this geometry MTP costs the whole cache, and there is an opt-out.** The trailing-block drop is expected (ivanium on #38182), but with a 1056-token block a shared prefix shorter than two blocks has nothing left once one block is dropped. `"disable_eagle_block_drop": true` (#53388) restores the hits at unchanged acceptance — the same opt-out that #53670 measured on a Qwen3.8 GDN layout on 2026-09-04:

| arm (main @ 8a0a7ee) | prefix-cache hits / 72,992 queried tokens | MTP acceptance |
|---|---|---|
| baseline, no spec decode | 22,176 | — |
| + `--prefix-match-unit 352` | 53,152 | — |
| MTP, `num_speculative_tokens=1` | **0** | 59.4% |
| MTP + `disable_eagle_block_drop` | 22,176 | 59.4% |
| MTP + `--prefix-match-unit 352` | 17,600, erratic | 60.5% |
| MTP + both | 53,152 | 59.2% |

Single run per arm; acceptance is over ~1,190 draft tokens per arm, so the differences are noise — the point is that the flag does not visibly cost acceptance. The two 53,152 figures carry the same ~704-token inflation from the probe bug, so they compare like for like.

On your third ask: robertgshaw2-redhat wrote on #54607 (now closed) that a doc on prefix caching for agentic workloads — Marconi caching, prefix-match unit, retention interval, and "prefix-match-unit X spec-dec" — is long overdue. I have a draft page on exactly those four, mechanism read off `main` and the main-specific numbers measured on 8a0a7ee, scoped to mechanism and leaving the startup-log wording to #53759. Happy to open it as a PR if a maintainer wants it, as a new page or a section in `automatic_prefix_caching.md`, once #53945 / #53614 settle the spec-dec part.

 🐛 Describe the bug 
 On both engines the config dump says  enable_prefix_caching=True , and both are 
genuinely caching — above a threshold. Below it they return  exactly zero  
cache hits, and nothing anywhere in the startup log, the config dump or 
 /metrics  states what the threshold is. 
 The threshold is one attention block. On a hybrid checkpoint vLLM raises the 
attention block size until the attention page is at least as large as the 
recurrent-state page, which produces blocks  two to three orders of magnitude 
larger than the usual 16 : 
   INFO [interface.py:911] Setting attention block size to 2096 tokens to ensure
                        that attention page size is >= mamba page size.
INFO [interface.py:935] Padding mamba page size by 0.58 % to ensure that mamba
                        page size and attention page size are exactly equal.
   
   INFO [interface.py:911] Setting attention block size to 1920 tokens to ensure
                        that attention page size is >= mamba page size.
INFO [interface.py:935] Padding mamba page size by 1.89 % to ensure that mamba
                        page size and attention page size are exactly equal.
   
 Prefix caching registers  whole blocks  only, so a shared prefix shorter than 
one block is structurally uncacheable. A 1,024-token shared system prompt — a 
very ordinary size — gets nothing, on an engine that reports prefix caching as 
enabled and that shows a healthy hit rate on longer conversations.

 Measurement 3 — the boundary, directly 
 The two measurements above are multi-turn traces, where the shared prefix is 
whatever the conversation happens to make it. To test the boundary directly I 
wrote a probe that controls the shared prefix  to the token : build a system 
prompt of exactly X tokens (generate prose, tokenize, truncate the id list to X, 
decode back, re-tokenize to confirm), send 2 unmeasured warm-up requests to pay 
the first-request-of-a-shape JIT cost,  POST /reset_prefix_cache , then 4 
strictly sequential requests with the same system prompt and a different user 
turn each. One request in flight at a time, so nothing co-batches. 
 Every point also carries a  control : one request with a  different  system 
prompt of the  same  length. If the effect were length-driven rather than 
prefix-driven, the control would cache too.  It cached exactly 0 on all 33 
points.

 That control also calibrates the constant: at X=1,900 it caches  1,904  and at 
X=2,200 it caches  2,208  — slightly  above  X, both exact multiples of 16. So 
the shared prefix is not X but X + ~8-19 chat-template tokens, floored to the 
block. That is why engine A hits at exactly X=2,096 (common ~2,106 >= 2,096) but 
not at X=2,048 (common ~2,058 < 2,096). 
  The cost of the remainder is not small and it is permanent.  At a 4,096-token 
shared system prompt, engine A caches 2,096 of it and re-prefills the other 
2,000 tokens on every request forever — a 1.36x TTFT saving where the non-hybrid 
control gets 5.4x. Rounding the same prompt  up  to 4,192 tokens makes it 
strictly faster on every repeat (2.06x) despite being 96 tokens longer, which is 
not a trade-off any operator would think to look for. 
 What I expected 
 That an engine reporting  enable_prefix_caching=True  would, somewhere, state 
the smallest prefix it can actually cache — or that the number would be 
derivable from something an operator reads at startup without knowing the 
hybrid KV internals. 
 What actually happens 
 The only surface that exposes it is  prompt_tokens_details.cached_tokens  on an 
individual response, and only if  --enable-prompt-tokens-details  is on. The 
startup log prints  Setting attention block size to N tokens , which  is  the 
number — but it is phrased as an internal page-alignment detail, sits far from 
anything about caching, and nothing connects the two.  /metrics  gives 
 vllm:prefix_cache_queries_total  and  vllm:prefix_cache_hits_total , which 
report the symptom (0 / N) and not the cause; a zero there is indistinguishable 
from "this workload has no shared prefixes". 
 Why this matters operationally 
 Sizing a shared system prompt at 1-2k tokens is the single most common 
enterprise prefix shape there is. On these checkpoints it yields  no caching at 
all , silently: 
 
 prefix caching is worth nothing, 
 cache-affinity routing in front of the engine is worth nothing (there is no 
cache to be affine to), 
 capacity planning that assumed a warm prefix is wrong by the full prefill 
cost of the system prompt on every request, 
 
 and the only way to find out is to instrument per-request  cached_tokens . We 
found it by accident. Two of the last five checkpoints we deployed are affected, 
and the affected fraction grows as Mamba/GDN/KDA hybrids do. 
 The earlier generation of this trap was at least visible: on one hybrid we 
deployed, vLLM logged  enable_prefix_caching=False  outright and disabled it. 
Here the log says  True  and the counter says zero, which is worse. 
 Ask 
 Either of these would have saved the investigation; both would be better: 
 
  A startup log line naming the minimum cacheable prefix , emitted next to 
the prefix-caching config when the effective block size is unusually large — 
e.g.  Prefix caching enabled: minimum cacheable prefix is 2096 tokens (attention block size); shared prefixes shorter than this will never hit.  
The value is already computed at that point; this is a logging-only change. 
  A metric or  /v1/models -adjacent field exposing it , e.g. a gauge 
 vllm:prefix_cache_block_size_tokens , so a fleet can be audited without 
reading every engine's boot log. 
 
 A third, cheaper option: mention the whole-block quantum in the prefix-caching 
docs and state explicitly that hybrid checkpoints raise the block size into the 
thousands. Right now the docs' 16-token mental model is what most operators are 
carrying. 
 I am happy to send the PR for (1) and/or (2) if maintainers say which shape they 
want.
