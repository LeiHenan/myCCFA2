[RFC] Tail-Optimized LRU (T-LRU): Reducing Tail Latency via Conversation-Aware KV Cache Eviction
### Motivation.

## Summary
We propose **Tail-Optimized LRU (T-LRU)**, a lightweight modification to vLLM's existing LRU prefix-cache eviction policy that reduces P95 tail Time-to-First-Token (TTFT) by up to **27.4%** on real conversation workloads, with no overhead during normal (cache-hit) operation and no change to API surface.

The idea and full analysis appear in our paper:
> **Tail-Optimized Caching for LLM Inference**
> Wenxin Zhang, Yueying Li, Ciamac C. Moallemi, Tianyi Peng
> **NeurIPS 2025.** arXiv: https://arxiv.org/abs/2510.15152

## Motivation
vLLM's current eviction policy is LRU. LRU maximizes cache-hit rate but is **conversation-length blind**: it treats a block from a 5-turn, 10 000-token conversation identically to a block from a 1-turn, 100-token conversation. This creates an avoidable source of tail latency.

## Key Insight

T-LRU is **not** “keep everything from long conversations.” It asks a narrower question:

> **How much of this conversation’s prefix do we need to keep so that the next turn still meets the TTFT target?**

Suppose a conversation has `H` cached history blocks, the next turn is estimated to add `Q_hat` blocks, and the TTFT budget is `xi` blocks of uncached prefill work. If `c` history blocks remain cached, the next turn must recompute `(H - c) + Q_hat` blocks. To stay within budget, we need:
`(H - c) + Q_hat <= xi`
which means we should keep at least `B = max(0, H + Q_hat - xi)` cached history blocks. So `B` is the minimum prefix worth protecting:

* the first `B` blocks are TEL-unsafe: evicting them can push the next turn over the TTFT target;
* the remaining `H - B` blocks are TEL-safe: evicting them does not further hurt next-turn tail latency.

For example, if `xi = 16, H = 20`, and `Q_hat = 2`, then `B = 6`. In this case, only the first 6 prefix blocks need to be protected; the remaining 14 blocks can be evicted first without changing whether the next turn meets the TTFT target.
### Proposed Change.

## Algorithm
T-LRU is a **two-queue** extension of LRU. When a request completes and its blocks are freed:
1. Compute B = max(0, H + Q_hat - xi) for the request.
2. 2. The **last H - B blocks** (suffix/tail) are TEL-safe -> append to tel_safe_queue.
3. 3. The **first B blocks** (prefix/head) are TEL-unsafe -> append to the **existing** LRU free queue as before.
When new blocks are needed:
1. **Drain tel_safe_queue first**.
2. 2. **Fall back to the normal LRU queue** for any remaining demand.
`xi` and `Q_hat` are tunable parameters exposed as CLI flags:
```bash
vllm serve <model> --enable-prefix-caching --tlru-xi-tokens 4096 --tlru-qhat-tokens 200
```

## Implementation
All changes are confined to the v1 KV cache stack. No changes to the scheduler, attention kernels, or serving API.
- `vllm/v1/core/kv_cache_utils.py`: Added `is_tel_safe: bool = False` field to `KVCacheBlock`
- - `vllm/v1/core/block_pool.py`: Added `tel_safe_queue`, `free_blocks_tlru()`, modified `get_new_blocks()`
- - - `vllm/v1/core/single_type_kv_cache_manager.py`: `free()` routes to `free_blocks_tlru()` when T-LRU is enabled
- - - - `vllm/v1/core/kv_cache_coordinator.py`: Forwards params to `BlockPool`
- - - - - `tests/v1/core/test_tlru_eviction.py`: 15 unit tests
## Experimental Results (WildChat dataset)
T-LRU reduces P95 TTFT by up to 27.4% vs LRU and closes 25-79% of the gap to the clairvoyant offline optimum. Results on ShareGPT are consistent.

## Design Decisions & Open Questions
1. **Default for Q_hat (tlru-qhat-tokens)**: We default to 200 tokens.
2. 2. **tel_safe_queue vs FreeKVCacheBlockQueue pointer**: The current separate-deque approach is simpler.
3. 3. **Interaction with prefix caching**: TEL-safe blocks are evicted before LRU pool blocks, which is intentional.

 Summary 
 We propose  Tail-Optimized LRU (T-LRU) , a lightweight modification to vLLM's existing LRU prefix-cache eviction policy that reduces P95 tail Time-to-First-Token (TTFT) by up to  27.4%  on real conversation workloads, with no overhead during normal (cache-hit) operation and no change to API surface. 
 The idea and full analysis appear in our paper: 
 
  Tail-Optimized Caching for LLM Inference  
Wenxin Zhang, Yueying Li, Ciamac C. Moallemi, Tianyi Peng 
 NeurIPS 2025.  arXiv:  https://arxiv.org/abs/2510.15152  
 
 Motivation 
 vLLM's current eviction policy is LRU. LRU maximizes cache-hit rate but is  conversation-length blind : it treats a block from a 5-turn, 10 000-token conversation identically to a block from a 1-turn, 100-token conversation. This creates an avoidable source of tail latency. 
 Key Insight 
 T-LRU is  not  “keep everything from long conversations.” It asks a narrower question: 
 
  How much of this conversation’s prefix do we need to keep so that the next turn still meets the TTFT target?  
 
 Suppose a conversation has  H  cached history blocks, the next turn is estimated to add  Q_hat  blocks, and the TTFT budget is  xi  blocks of uncached prefill work. If  c  history blocks remain cached, the next turn must recompute  (H - c) + Q_hat  blocks. To stay within budget, we need: 
 (H - c) + Q_hat <= xi  
which means we should keep at least  B = max(0, H + Q_hat - xi)  cached history blocks. So  B  is the minimum prefix worth protecting: 
 
 the first  B  blocks are TEL-unsafe: evicting them can push the next turn over the TTFT target; 
 the remaining  H - B  blocks are TEL-safe: evicting them does not further hurt next-turn tail latency. 
 
 For example, if  xi = 16, H = 20 , and  Q_hat = 2 , then  B = 6 . In this case, only the first 6 prefix blocks need to be protected; the remaining 14 blocks can be evicted first without changing whether the next turn meets the TTFT target. 
 Proposed Change. 
 Algorithm 
 T-LRU is a  two-queue  extension of LRU. When a request completes and its blocks are freed: 
 
 Compute B = max(0, H + Q_hat - xi) for the request. 
 
 
 The  last H - B blocks  (suffix/tail) are TEL-safe -> append to tel_safe_queue. 
 
 
 
 
 The  first B blocks  (prefix/head) are TEL-unsafe -> append to the  existing  LRU free queue as before. 
When new blocks are needed: 
 
 
  Drain tel_safe_queue first . 
 
 
  Fall back to the normal LRU queue  for any remaining demand. 
 xi  and  Q_hat  are tunable parameters exposed as CLI flags: 
 
 
 
  vllm serve  < model >  --enable-prefix-caching --tlru-xi-tokens 4096 --tlru-qhat-tokens 200  
 Implementation 
 All changes are confined to the v1 KV cache stack. No changes to the scheduler, attention kernels, or serving API. 
 
  vllm/v1/core/kv_cache_utils.py : Added  is_tel_safe: bool = False  field to  KVCacheBlock  
 
 
  vllm/v1/core/block_pool.py : Added  tel_safe_queue ,  free_blocks_tlru() , modified  get_new_blocks()  
 
 
 
 
 
 
  vllm/v1/core/single_type_kv_cache_manager.py :  free()  routes to  free_blocks_tlru()  when T-LRU is enabled 
 
 
 
 
 
 
 
 
 
 
  vllm/v1/core/kv_cache_coordinator.py : Forwards params to  BlockPool  
 
 
 
 
 
 
 
 
 
 
 
 
 
 
  tests/v1/core/test_tlru_eviction.py : 15 unit tests 
 
 
 
 
 
 
 
 
 
 Experimental Results (WildChat dataset) 
 T-LRU reduces P95 TTFT by up to 27.4% vs LRU and closes 25-79% of the gap to the clairvoyant offline optimum. Results on ShareGPT are consistent.

 Any Other Things. 
 Design Decisions & Open Questions 
 
  Default for Q_hat (tlru-qhat-tokens) : We default to 200 tokens. 
 
 
  tel_safe_queue vs FreeKVCacheBlockQueue pointer : The current separate-deque approach is simpler. 
 
 
 
 
  Interaction with prefix caching : TEL-safe blocks are evicted before LRU pool blocks, which is intentional.
