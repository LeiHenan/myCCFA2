[Doc]: --prefix-match-unit and the default match granularity are undocumented
### 📚 The doc issue

Spent longer than I'd like to admit chasing a 0% prefix cache hit rate that turned out to be correct.

I was comparing prefix reuse across a couple of engines. Same hardware, same workload, same run. vLLM 0.27.1 came back with `prefix_cache_hits_total` at exactly 0, and the other engine reported 49.3% on the identical traffic. My first assumption was that I'd misconfigured something.

I hadn't. The shared system prompt in that workload was around 240 tokens, and the model I was running on vLLM resolves to a 784 token KV block. A block only gets cached once it's full, so a shared prefix shorter than one block can't be reused. vLLM had nothing to hit and said so. The other engine's block was small enough that it could.

Both numbers were right. It just took me a while to figure out that the difference was block size and not the traffic, because there's nothing in the metric names, the HELP strings, or the APC docs that mentions a floor exists.

The practical problem is that `queries > 0, hits = 0` looks the same whether your workload has no shared prefix at all, or shares one on every single request that happens to be a bit too short. Those need completely different responses and the metrics don't separate them.

### Suggest a potential alternative/fix

The Limits section of [Automatic Prefix Caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching.html) already lists the cases where APC won't help. This feels like it belongs there. Rough wording:

> APC also works at KV block granularity: a shared prefix shorter than one block cannot be reused, because a block is only cached once it is full. When this happens the prefix cache hit rate correctly reports 0% even though the requests do share a prefix, so a 0% hit rate does not by itself mean the workload has no reuse. If the hit rate is lower than the sharing in your workload would suggest, compare the length of the shared prefix against the block size in use (`--block-size`, which for some model architectures is larger than the default) before concluding that there is nothing to reuse.

Happy to send a PR if that's roughly the right shape, or reword it however you'd prefer. Nothing here is a bug, the number is accurate, it's just hard to read without knowing the floor is there.

Prefix-cache keys are computed every `prefix_match_unit` tokens, and that unit can be set finer than the physical block size as long as every KV cache group's `block_size` divides it, which enables hits at boundaries inside a block.

The default also matters and I had it wrong. For a single KV cache group the unit equals the block size, so the "shorter than one block cannot hit" behaviour I described is real there.                                 [Doc]: --prefix-match-unit and the default match granularity are undocumented     #54607               New issue               Copy link              New issue               Copy link                Closed as not planned                 Closed as not planned      [Doc]: --prefix-match-unit and the default match granularity are undocumented   #54607                  Copy link          Labels       kv-cache-manager                              Description             sanjeevrg89    opened    on Aug 31, 2026                  Issue body actions          📚 The doc issue 
 Spent longer than I'd like to admit chasing a 0% prefix cache hit rate that turned out to be correct. 
 I was comparing prefix reuse across a couple of engines. Same hardware, same workload, same run. vLLM 0.27.1 came back with  prefix_cache_hits_total  at exactly 0, and the other engine reported 49.3% on the identical traffic. My first assumption was that I'd misconfigured something. 
 I hadn't. The shared system prompt in that workload was around 240 tokens, and the model I was running on vLLM resolves to a 784 token KV block. A block only gets cached once it's full, so a shared prefix shorter than one block can't be reused. vLLM had nothing to hit and said so. The other engine's block was small enough that it could. 
 Both numbers were right. It just took me a while to figure out that the difference was block size and not the traffic, because there's nothing in the metric names, the HELP strings, or the APC docs that mentions a floor exists. 
 The practical problem is that  queries > 0, hits = 0  looks the same whether your workload has no shared prefix at all, or shares one on every single request that happens to be a bit too short. Those need completely different responses and the metrics don't separate them. 
 Suggest a potential alternative/fix 
 The Limits section of  Automatic Prefix Caching  already lists the cases where APC won't help. This feels like it belongs there. Rough wording: 
 
 APC also works at KV block granularity: a shared prefix shorter than one block cannot be reused, because a block is only cached once it is full. When this happens the prefix cache hit rate correctly reports 0% even though the requests do share a prefix, so a 0% hit rate does not by itself mean the workload has no reuse. If the hit rate is lower than the sharing in your workload would suggest, compare the length of the shared prefix against the block size in use ( --block-size , which for some model architectures is larger than the default) before concluding that there is nothing to reuse. 
 
 Happy to send a PR if that's roughly the right shape, or reword it however you'd prefer. Nothing here is a bug, the number is accurate, it's just hard to read without knowing the floor is there.
