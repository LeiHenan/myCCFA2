 Problem 
 In long multi-turn agentic conversations, accumulated `role=tool` messages overflow the context window. Left-truncation discards the oldest tokens blindly, often losing the original task description while keeping verbose boilerplate. 
 Solution: ACE (Attention-Weighted Context Eviction) 
 Content-aware compression before chat template rendering. Three scoring modes: 
 Mode 
 Trigger 
 Signal 
 1 — Heuristic 
 fallback 
 Static rules: errors > paths > numbers > boilerplate 
 2 — BM25 
 default 
 Relevance of each line to current conversation 
 3 — Attention 
 conversation_id + prior turns 
 Accumulated attention weights from previous passes 
 Key finding: recency-weighted eviction 
 Flat ratio compression (same for all messages) fails on real agentic sessions — it treats a file read from turn 2 the same as one from turn 8, destroying the agent's investigation thread. 
 ACE uses exponential recency weighting (`recency_blend=0.3` default): 
``` 
age_factor = 0.15 + 0.85 * (msg_recency ^ 0.7) # 0.15 oldest → 1.0 newest 
effective_ratio = target_ratio * age_factor # ~6% oldest, ~40% newest 
``` 
 New API fields 
 ```python 
context_compression: Literal["ace"] | None = None 
context_compression_ratio: float = 0.4 
context_compression_keep_recent: int = 2 
context_compression_recency_blend: float = 0.3 # NEW: 0=pure content, 1=pure recency 
conversation_id: str | None = None 
```

 The heuristic budget_chars = (max_model_len - max_tokens) * 4 is problematic for two reasons: 
 Optimistic Multiplier : A factor of 4 characters per token is an optimistic estimate (common for plain English). For code-heavy tool outputs or non-English text, the ratio is often significantly lower (2.0 - 3.0). Using 4 can result in a budget that is too high, causing the prompt to still exceed the context window after 'compression'. 
 Default for max_tokens : When max_tokens is not specified (defaulting to 0 at line 259), the budget becomes max_model_len * 4 . This effectively disables ACE for most conversations, as the character count will rarely exceed this inflated budget even when the token count is already at the limit. 
 Consider using a more conservative multiplier and ensuring a minimum output buffer is reserved when max_tokens is absent. 
 Suggested change
 budget_chars = ( max_model_len - max_tokens ) * 4 
 budget_chars = int (( max_model_len - ( max_tokens or 1024 )) * 2.5 )

 Update: Phase 2 — Query-relevance scoring (BM25) 
 Following the discussion about what "attention-weighted" should actually mean, the implementation now includes a BM25-based query-relevance scorer as the default mode ( use_query_relevance=True ). 
 The core idea: instead of static keyword heuristics, score each line of old tool results by its BM25 relevance to the current conversation context. This approximates what a transformer's attention mechanism would attend to from the current query position — lines containing terms the model is currently reasoning about score high; unrelated lines score low. 
 Three-phase roadmap: 
 Phase 
 Scoring 
 Status 
 1 
 Heuristics (keyword tiers) 
 ✅ original implementation, still available as fallback 
 2 
 BM25 query-relevance 
 ✅ now default ( use_query_relevance=True ) 
 3 
 Accumulated attention weights from vLLM inference engine 
 🔜 requires hooks in model runner 
 Why Phase 3 matters: vLLM already computes attention during the forward pass. Phase 3 would accumulate per-token attention scores from previous turns (similar to H2O/Scissorhands for KV cache) and use them directly for eviction — replacing the BM25 proxy with exact model-derived importance scores. This is where the "Attention-Weighted" name is fully earned. This requires changes in model_runner.py and is proposed as a follow-up PR.

 Author 
 Phase 3 — Model Runner Wiring (now live) 
 Phase 3 was fully designed but never connected to the inference path. This commit closes the loop. 
 Root cause 
 serving.py called start_capture(session_id) to register an attention tracker, but nothing ever fed it data. The ACEModelHook / ACEAttentionCapture classes existed but were not wired to model_runner.execute_model() . So tracker.has_data was always False and eviction silently fell through to BM25 (Mode 2). 
 What changed (commit b3b583a ) 
 New file: vllm/entrypoints/ace_req_registry.py 
 Thread-safe req_id → session_id registry. This bridges the two layers that could not previously communicate: serving.py (which generates request_id per turn) and model_runner (which only sees req_id during inference). 
 serving.py — after generating request_id , registers it against session_id when context_compression="ace" and conversation_id is set. 
 model_runner.execute_model() — two additions: 
 # Before forward pass
for req_id in input_batch.req_ids:
 session_id = ace_req_registry.get(req_id)
 if session_id:
 install_hook(session_id, self.model, new_token_start=num_computed_tokens[req])
 _ace_sessions.append(session_id)
# After forward pass
for session_id in _ace_sessions:
 flush_hook(session_id) # aggregates layer buffers → tracker
 model_runner.finish_requests() — releases req_id registry entries when requests complete. The AttentionImportanceTracker persists under session_id for the next turn. 
 Limitations (unchanged from design doc) 
 FlashAttention2 and FlashInfer do not return softmax weights from their optimized kernels. On these backends (default GPU path), PyTorch forward hooks receive no attention data and the tracker stays empty → eviction falls back to BM25 automatically via the tracker.has_data guard. 
 Phase 3 is active on CPU and SDPA backends ( --enforce-eager on GPU or any CPU worker). On these backends the full attention-weighted flow now works end-to-end.

 We implemented recency_blend in apply_ace_eviction() : 
 # effective_ratio per message = base_ratio * (min_factor + (1 - min_factor) * msg_recency) 
 # msg_recency: 0.0 = oldest compressible, 1.0 = newest compressible 
 With base=0.3, min_factor=0.15 : 
 Oldest message: keeps 4.5% of lines (near-zero — only errors and paths survive) 
 Newest compressible: keeps 30% of lines (enough for continued reasoning) 
 This matches the intuition: old tool results should be nearly erased; recent ones should be preserved . We could not complete the full organic benchmark with this config due to API budget limits, but directional tests showed correct context growth patterns. 
 Key takeaways for maintainers 
 ACE with fixed ratio is a regression on real agentic usage — the organic benchmark is a clearer signal than synthetic. With real tools and multi-turn sessions, eviction at a flat ratio kills the agent's ability to explore. 
 The recency-weighted path ( recency_blend param) is the right direction — compress old messages aggressively, preserve recent ones. This is what the Phase 3 attention weights would provide automatically: accumulated attention over many turns naturally gives high scores to recently-referenced content. 
 Phase 3 (attention weights) is now wired into model_runner.execute_model() . On FlashAttention backends, it falls back to BM25 gracefully. On CPU/SDPA backends, it accumulates real attention weights. This provides recency-awareness for free — tokens in recent turns receive more cumulative attention and are automatically preserved. 
 recency_blend=0.3 as default is proposed. This requires no attention data and works in all modes. PR is ready to update the default.

 Withdrawing this: I measured it against doing nothing, and it lost 
 Closing this rather than leaving it open, because I no longer believe the design in it. 
 This PR proposes scoring lines with hand-written content rules ( error → high, blank → zero) plus accumulated attention. I finally benchmarked it against the two baselines I should have used from the start — the whole context uncompressed , and blind tail truncation — on a public long-conversation set, 200 questions, a real model answering, every condition on the same token budget:

 tail truncation 
 6.62

 The cause is visible in the arithmetic and I should have seen it: the rules returned 0.1–1.0 on their own, while overlap with the actual question entered multiplied by 0.4 and capped. The rules outweighed the question by more than two to one. Turning them off is worth +3.02 F1 against the same pipeline. 
 Two things I got wrong in how I got here, in case they are useful to anyone reading: 
 Every version was validated against my previous version. Four generations, each an honest win over the last, none of them ever measured against "keep the newest, drop the rest". A benchmark where every entry is something you built is a scoreboard, not a benchmark. 
 The attention signal was the wrong thing to chase. #36311 was closed within hours on the observation that vLLM only evicts blocks with ref_cnt == 0 — blocks no running request is using. The same lesson applies here: at eviction time there is no live query to score against, so relevance is undefined. Any relevance-based policy has to run where a query exists. That is the input layer, not the block manager. 
 I have a replacement — BM25 with IDF computed over the conversation itself, scored against the last user message, at the renderer — and it is not ready to propose either. An adversarial review of it found three separate ways to silently corrupt the prompt on ordinary requests, and a test suite that green-lights an empty prompt. Fixing those first, then opening an RFC per docs/contributing/README.md , before any code.
