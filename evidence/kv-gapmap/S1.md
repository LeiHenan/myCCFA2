# S1: Paged/block KV management and memory allocator: PagedAttention/V1 block manager, SGLang RadixAttention mem pool, block size tuning, hybrid KV cache manager for Mamba/SSM+attention hybrids, KV memory fragmentation, heterogeneous page sizes

Research window: 2025-06 → 2026-09-13 (older work included only where canonical). Target rig: 1× RTX PRO 6000 Blackwell 96GB, sm120, vLLM 0.29.0 / SGLang 0.5.19, Qwen3-4B, single node.

Method note: the local source trees `/tmp/kvsrc/vllm-main` and `/tmp/kvsrc/sglang-main` were grepped directly. `/tmp/kvsrc/sglang-main` is a **partial checkout** (only `3rdparty/ assets/ benchmark/ docker/ docs/ LICENSE README.md`), so SGLang evidence is GitHub-side only. The arXiv Atom API returned HTTP 429 for this host's egress IP for the whole session; all arXiv discovery was done through the `arxiv.org/search/` HTML endpoint instead. The GitHub REST API returned HTTP 403 (rate-limited for the shared IP) for the whole session, so all GitHub evidence was gathered by fetching and parsing the HTML payloads of issue/PR pages, which embed the issue body and comment bodies as JSON.

### CLOSED-1: PagedAttention (canonical fragmentation answer)
- URL: https://arxiv.org/abs/2309.06180
- Evidence: READ BODY
- Detail: The canonical statement that block-paged KV management near-eliminates fragmentation waste. Verbatim from the abstract: "we propose PagedAttention, an attention algorithm inspired by the classical virtual memory and paging techniques in operating systems. On top of it, we build vLLM, an LLM serving system that achieves (1) near-zero waste in KV cache memory and (2) flexible sharing of KV cache within and across requests to further reduce memory usage." Retained as the canonical reference because the "is paging the right primitive" question is still live (see CLOSED-12 / ABANDONED-7).

### CLOSED-12: vAttention — contiguous virtual memory instead of paging
- URL: https://arxiv.org/abs/2405.04437
- Evidence: READ BODY
- Detail: The canonical published counter-position to PagedAttention, still the reference for the "do we need paging" question. Verbatim from the abstract: "in trying to allocate physical memory at runtime, PagedAttention ends up changing the virtual memory layout of the KV cache from contiguous to non-contiguous. Such a design leads to non-trivial programming and performance overheads." and "vAttention is a simpler, portable, and performant alternative to PagedAttention: it supports various attention kernels out-of-the-box and improves LLM serving throughput by up to 1.23x compared to the use of PagedAttention-based kernels of FlashAttention and FlashInfer."

### CLOSED-13: Minima-KV — mixed-format paged attention on the exact target GPU
- URL: https://arxiv.org/abs/2608.23834
- Evidence: READ BODY
- Detail: Published mixed-format paging result evaluated on the target researcher's exact accelerator class. Verbatim from the abstract: "Across separate, configuration-bound Qwen3.6-27B profiles on a single 96-GB NVIDIA RTX PRO 6000 Blackwell GPU, deployment accounting reports 18.3 KiB of attention KV per live token, corresponding to 3.50x compression relative to BF16 and 1.75x relative to FP8." Mechanism verbatim: "Recent and protected Anchor pages remain in FP8, while older non-anchor pages move to packed TQ3; every live-request page remains addressable. Format-specific kernels compute partial attention states and combine them through a globally normalized online-softmax merge, enabling direct heterogeneous decode without a cache-sized dense shadow."

### CLOSED-14: PersistentKV — decode directly over native page tables
- URL: https://arxiv.org/abs/2606.26666
- Evidence: READ BODY
- Detail: Published page-aware scheduling study that executes over native block tables instead of repacking. Verbatim from the abstract: "PersistentKV maps work by KV-head group, executes directly over native page tables, and adds a compact workqueue schedule executing only non-empty row-KV-head-sequence-split tasks." Its own hedges are recorded in ABANDONED-7-adjacent notes; the headline result verbatim: "five held-out seeds improve mean wall decode-token throughput by 1.04x to 1.08x on B8 bimodal, uniform, and Zipf-like workloads, and by 1.40x on a B1 bucketed trace."

### OPEN-1: Per-group (decoupled) page size for Mamba/attention hybrids — fp8 KV cache yields no capacity gain
- WHO is still asking: vLLM issue #55196 (RFC), open
- URL: https://github.com/vllm-project/vllm/issues/55196
- Verbatim quote of the asking: "`--kv-cache-dtype fp8` roughly doubles KV cache capacity on attention-only models (measured 2.00x), but on Mamba/GDN + attention hybrids it gives 1.84x at 32k context and 1.00x (no gain) at short context." and "Root cause is the known hybrid page-pinning behavior (#37121, #40696): the Mamba state is not quantized by `--kv-cache-dtype` and all groups share one uniform page, so the bf16 Mamba page pins bytes-per-block and the fp8 attention page cannot shrink the pool." and "Fix is parity work: quantize the Mamba state too (SGLang already does this at int8) and/or decouple per-group page size (SGLang/TRT-LLM/llama.cpp already use separate pools)."
- What specifically is missing: a per-group page size (or quantized Mamba state) in vLLM. The RFC states the mechanical blocker verbatim: "`get_uniform_page_size` asserts one page across all groups". No merged PR implements per-group pools.

### OPEN-5: Hybrid block sizes can invert the hash/block relationship and crash the offload connector
- WHO is still asking: vLLM issue #56396, open
- URL: https://github.com/vllm-project/vllm/issues/56396
- Verbatim quote of the asking: "Note `block_size (8) < hash_block_size (32)` — the call asks `resolve_block_hashes` to view 32-token-granularity hashes at a *finer* 8-token granularity, but the function only supports the coarsening direction (`block_size >= hash_block_size`, enforced by the divisibility assert). With 8 < 32 the assert `8 % 32 == 0` can never hold, so the crash is deterministic on the first request."
- What specifically is missing: support for a per-group block size smaller than the global `hash_block_size` (the DeepSeek-V4.1-Flash layout has "MLA full-attention group @ block_size 32 + SWA/circular-buffer group @ block_size 8"). An open fix PR exists (#56404) but issue #56396 is open.
- Evidence: READ BODY
