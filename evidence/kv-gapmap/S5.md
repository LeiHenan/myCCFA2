## OPEN

### OPEN-1: Tiered KV offload promotes every waiting request and thrashes the primary DRAM tier
- WHO is still asking: t348575, vLLM issue #49902 (linked forward to #50014)
- URL: https://github.com/vllm-project/vllm/issues/49902
- Verbatim quote of the asking: "Data from the secondary KV offload FS tier appears to blindly be promoted to the DRAM (cpu) tier, which leads to no/little free blocks in this tier. pin dram blocks for promotion -> evict just loaded items -> pin again for promotion cycle (this is an assumption from my data and a rough read of the code). This issue will therefore present itself whenever there are multiple long-context requests waiting to be executed, and there is CPU memory pressure." and "The constant re-promotions are obviously read from disk, so vLLM ends up reading 1+TB of data while it only needed to read a 10th of that."
- What specifically is missing: A promotion/admission policy that only promotes blocks for requests the scheduler will actually run; today the lookup path promotes for every waiting request it walks. The reporter's exact repro is single-GPU and on the target model: `--model Qwen/Qwen3-4B-Instruct-2507 ... "spec_name": "TieringOffloadingSpec", "cpu_bytes_to_use": 68719476736, "eviction_policy": "arc", "block_size": 256, "secondary_tiers": [{"type": "fs_python", ...}]` on "an h100, cuda 13, python 3.12".
- Evidence: READ BODY

### OPEN-2: RFC — back-pressure detection for KV cache offloading tiers
- WHO is still asking: bnellnm, vLLM RFC issue #50031
- URL: https://github.com/vllm-project/vllm/issues/50031
- Verbatim quote of the asking: "vLLM's KV cache offloading framework (CPU DRAM, local NVMe, shared storage) does not detect or respond to bandwidth saturation on secondary tiers. When a tier is saturated — whether from concurrent eviction, excessive store operations, or high IOPS — the system continues dispatching load/store jobs that pile up, further degrading bandwidth for actual serving loads." and "**Saturated-Tier bottleneck: In the case when multiple secondary tiers are specified, all tiers receive the same amount of stores. The CPU blocks are protected from eviction, when the stores are in progress and are released only when the slowest tier has completed the store. Here the slowest tier becomes the bottleneck for the entire system. Further, we observe CPU tier running out of memory, preventing further offloads."
- What specifically is missing: The RFC states its own scope limit verbatim: "The initial implementation adds back-pressure detection to secondary offloading tiers and a single response policy: drop store (write) requests to a tier that is under pressure. No load prioritization, tier rerouting, or load-vs-recompute decision is included in this phase." So load prioritization, tier rerouting, and any load-vs-recompute decision remain unsolved.
- Evidence: READ BODY

### OPEN-3: Unread tiered promotions are evicted by other speculative promotions (open PR, unfixed)
- WHO is still asking: AlejandroParedesLT, vLLM PR #50014 (open, fixes #49902)
- URL: https://github.com/vllm-project/vllm/pull/50014
- Verbatim quote of the asking: "TieringOffloadingManager promotes secondary-tier blocks to the primary CPU tier on every lookup() , including probes for waiting requests the scheduler ends up skipping that step (a request that defers is continue d past, not break ed on, so one schedule() pass can walk the whole waiting queue and issue a promotion per secondary-tier hit). Under many concurrent, disjoint-working-set requests, one promotion's landed-but-not-yet-GPU-read block could be evicted by another promotion before ever being consumed ... The evicted data gets re-promoted (and re-evicted) on a later step, burning secondary-tier I/O on data that never gets used."
- What specifically is missing: The fix (track landed-but-unread promotions and protect them) is proposed but the PR is still open — the shipping tiering manager has no protection for in-flight promotions.
- Evidence: READ BODY

### OPEN-4: SGLang HiCache never consults L3 when a prefix survives only as backuped stubs after host-tier eviction
- WHO is still asking: todayim, SGLang issue #38452
- URL: https://github.com/sgl-project/sglang/issues/38452
