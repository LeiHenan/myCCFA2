Scope: closed-unmerged PRs; issues closed as wontfix / not-planned / by-design / stale; comments saying "won't fix", "not planned", "out of scope", "we decided against", "no longer pursuing", "does not help", "no benefit", "we reverted this"; and papers concluding a popular KV technique does NOT pay off. Engines covered: vLLM, SGLang, TensorRT-LLM, llama.cpp, HuggingFace TGI, LMCache, Dynamo.

Retrieval window prioritised 2025-06 → 2026-09. Today = 2026-09-13.

**Evidence discipline used throughout:** every URL below was actually fetched. "READ BODY" = the page/abstract was retrieved and read (GitHub issue pages embed the full comment timeline in their JSON payload; PR conversation bodies do **not** render, so PR evidence is mostly commit messages from the `.patch` endpoint, which IS retrieved content). "TITLE ONLY" = seen in a search-result list only. Where a closure was performed by an automation (stale bot, linear bot, auto-revert agent) this is stated explicitly and is **not** presented as a maintainer decision.

**Correction applied during verification:** one subagent-supplied candidate (llama.cpp PR #25494) was claimed closed-unmerged; direct retrieval of the PR page and the search API shows `"merged_at": "2026-08-19T15:44:16Z"` — it is **MERGED**. It has been reclassified from ABANDONED to CLOSED and the negative result inside it re-framed accordingly. Two other quotes were byte-checked before use; one arXiv quote required correction because the raw HTML contains `\texttt{}` markup (noted in place).

**Tooling caveat discovered late and worth flagging:** GitHub's `is:unmerged` search qualifier is **not honoured** by the search backend used here. The delegated TensorRT-LLM investigation proved this with a control query — `is:pr is:closed is:unmerged "kv cache"` returned 719 results containing obviously-merged PRs, and overlapped with `is:pr is:closed is:merged`. Consequence: search results **cannot** be used to infer merge status. Every PR cited in this document as "closed unmerged" or "merged revert" had its merge state read individually from the PR page's `mergedTime`/`mergedBy` fields (retrieved for vLLM #50779, #51270, #49574, #55160, #55159, #54386; SGLang #38192, #38163; Dynamo #5406, #13184). Merge statuses asserted here are therefore individually verified, not inferred from the qualifier.

### CLOSED-8: KV-Direct — drop the cache, checkpoint the residual stream

### OPEN-2: vLLM v1 KV cache offloading — the canonical open RFC
- WHO is still asking: `orozery` (author), `njhill`, `josephrocca`; open since 2025-06-19 and labelled `RFC`, `keep-open`
- URL: https://github.com/vllm-project/vllm/issues/19854
- Verbatim quote of the asking: "Currently, in vLLM v1 there is no in-house solution for offloading KV cache data from the GPU memory to other medium (in particular, CPU memory)." The break-even problem is stated by a maintainer in-thread — `njhill`: "Cached CPU blocks would't necessarily have all preceding blocks also in the CPU cache, some prefix might only reside in the GPU cache. For a given cache tier, we may some length threshold below which it's not worth retrieving (and therefore possibly also not worth storing) since it would be faster to recompute." `orozery` concedes the design implication: "I understand this may not be the case, and CPU size could be roughly the same size as the GPU, or larger by a small factor. So you make up a good point."
- What specifically is missing: an eviction-time (not compute-time) GPU→CPU save hook, and a decision on the GPU-block "next-in-line" notification — "since we want this to be async, this will require changes to vllm's core, allowing the connector to be notified on 'soon-to-be-evicted' GPU blocks." The thread ends without resolution.
- Evidence: READ BODY

- URL: https://github.com/sgl-project/sglang/issues/38470
- Verbatim quote of the asking: "The consequence is that the layer-wise pipeline (`LayerDoneCounter` / `wait_until` in the attention layers) almost never overlaps anything: by the time `start_loading` returns and the batch is built and launched, every copy has already landed." … "So the scheduler thread stalls for the full enqueue duration, and the forward that should have hidden the H2D copies only starts once they are essentially complete."
