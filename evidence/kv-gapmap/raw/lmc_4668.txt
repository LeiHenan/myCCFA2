 [CacheBlend] [medium investigation] Cross-pod sibling reuse - does a cold engine reuse a peer's warm blend cache on novel orderings? (measured by timing vs cold)
 Date: 2026-08-20
 Verdict: CONFIRMED - cross-pod reuse works, but it is transient. A cold engine B genuinely reuses engine A's warm blend cache on novel orderings (2.21× vs cold on the first batch), then decays to the cold floor within one batch (same store-flood mechanism as the decay ticket).
 Confidence: High (MEASURED live, two engines sharing one blend server, timing vs a true-cold baseline; CODE-VERIFIED that the store + matcher are shared server-side).
 Severity: Medium (investigation → answered). The capability is real (elastic scale-out can share one warm cache) but inherits the non-prefix decay, so the shared benefit is a burst, not steady-state.

 2. Issue description (plain terms)
 The question: in a fleet where several vLLM engines share one CacheBlend server, can an engine that never warmed a document set still reuse the KV that a different engine warmed - for non-prefix (shuffled/novel-order) RAG queries? If yes, you can warm once on any engine and scale out read replicas that all benefit; if no, each engine must warm its own cache and sharing buys nothing for non-prefix reuse. This matters for elastic scale-out economics.
 3. How verified
 Runtime (MEASURED)
 Two engines A and B pointed at the same blend server. Corpus of 96 docs × 2048 tok built with a unique nonce so it was guaranteed absent from any prior cache. Procedure:
 B-cold baseline (n=3): query engine B with fresh, never-cached docs → true cold on B.
 Warm on A only: send the corpus (2 contiguous passes) to engine A exclusively (populates the shared blend server via A's stores).
 Query B novel: send novel shuffled orderings of the (A-warmed) corpus to engine B , max_tokens=1 , timing vs the B-cold baseline. B never queried these docs itself, so any speedup is reuse of A's warm cache. Batch 0 is the purest cross-pod signal (before B has stored anything of its own).
 Code (CODE-VERIFIED)
 The raw KV store and the fingerprint matcher live in the shared blend server , not per-engine - a sibling engine's lookup probes the same index and loads the same stored chunks ( blend_v3.py matcher/index; the server process serves all connected engines). Salt/model/TP are identical across A and B, so their content hashes coincide.

 5. Root-cause / mechanism
 Why it works: the blend server holds the raw KV + a content-addressed fingerprint index shared across all connected engines. Engine B's lookup finds engine A's stored chunks by content (position-independent), loads them, copies them into B's own GPU, and does the partial-recompute blend. So the warm set is genuinely shared ; the only per-engine cost is the GPU copy (a real but cheap hit).
 Why it's transient: identical to the non-prefix decay defect - the store is unbounded and prefix-chained, so once B starts issuing its own novel queries they flood the shared L1 and evict A's warm chunks. The cross-pod benefit therefore exists as a burst on a freshly-warmed shared cache, not a steady state.
 This also corrects a plausible false-positive: if you warm on B and then re-query B with the same seed, you'd measure B replaying its own stores (prefix reuse), not cross-pod reuse. This test avoids that - B is warmed by A only, and B's test orderings are novel - so the 2.21× is genuinely cross-engine.
 6. Regime (never a flat multiplier)
 Freshly-warmed shared cache, sibling's first novel batch: ~2.2× (measured).
 Sustained sibling novel traffic: decays to ~1.0× (same store-flood decay).
 Net: cross-pod sharing is a real capability for a freshly-warmed or recurrence-heavy shared cache; it does not deliver sustained non-prefix reuse without the store fix.
 7. Caveats & the single cleanest next check
 Measured on gpt-oss-20b, TP=1, 96-doc corpus; the burst magnitude is model/L1-dependent (a larger model / larger shared L1 would show a bigger, longer burst before decay).
 The blend server had ~110 min of prior traffic from an earlier run; I neutralized that by using a unique-nonce corpus (guaranteed cache-absent) and a fresh-nonce cold baseline, so the contamination cannot inflate the result. A blend-server restart before the test would be marginally cleaner but was unnecessary given the nonce isolation.
 Cleanest next check: apply the store save-skip fix (warm A, then serve B read-only) and re-run - expected result: B's batch-0 2.2× holds across all batches instead of decaying, converting cross-pod sharing from a burst into a durable elastic-scale-out property.
