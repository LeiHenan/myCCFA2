 2. Claim restated (hypothesis under test)
 Mechanism claimed: The MP KV connector's store path builds and submits STORE operations for every request unconditionally, with no code path that reads a store-disable signal.
 Component: LMCacheMPConnector and its store-metadata builder ( LMCacheMPRequestMetadata.GetStoreMetadata ).
 Expected symptom: Setting kv_role=kv_consumer , request_configs["lmcache.skip_save"] , or any other store-disable flag has no effect under the MP connector - the engine keeps writing KV to the cache. Warm-then-read-only serving (warm the cache once, then run read-only replicas that never mutate/thrash it) is therefore impossible with the MP connector.
 CONFIRMS the claim: the MP store path takes no kv_role / skip_save / request_configs input and has no early-return keyed on a role/disable signal.
 REFUTES the claim: any per-request or per-engine gate in the MP store path that suppresses STORE ops.
 3. Issue description - why "no store-disable knob" blocks warm-then-read-only serving
 A common production pattern for a shared KV tier is: warm once, then serve read-only. One writer (or an offline warming pass) populates the L1/L2 cache with the working set; a fleet of serving replicas then reads from that cache but must not write back - because each replica's writes (a) thrash a bounded L1 with per-request/per-ordering artifacts, evicting the carefully-warmed hot set, and (b) waste store bandwidth and CPU on data that already exists or will never be reused. The kv_consumer role and lmcache.skip_save exist precisely to express "this engine/request loads but never stores."
 The single-process connector honors all three levers (per-request, per-engine-role, global env). The MP connector honors none of them. Because CacheBlend and the shared-cache/cross-pod topologies run on the MP connector, there is currently no supported way to stand up a read-only serving replica against a warmed cache: every replica keeps storing, so a read-only fleet still mutates and thrashes the shared tier. That is the blocker - it removes an entire deployment topology, not just a tuning knob.
 Aggravating factor: enabling blending forces an additional save-related config ON ( save_unfull_chunk=True , see §5d), so the blend path stores more , not less, and offers no counterbalancing off-switch on the connector it runs on.

 5. Clues / evidence (the decisive absences + the forced-on save)
 5a. Grep: store-disable keys are entirely absent from the MP path
 $ grep -rniE 'kv_role|kv_consumer|skip_save|read_only|load_only|request_config' \
 lmcache/integration/vllm/lmcache_mp_connector.py \
 lmcache/integration/vllm/lmcache_mp_connector_0201.py \
 lmcache/integration/vllm/lmcache_mp_metadata.py \

 <no matches>
 The only occurrence of kv_role anywhere in the MP files is a docstring config example - vllm_multi_process_adapter.py:228 shows '"kv_role":"kv_both",' - i.e. the string is printed as sample YAML, never read.
 5b. Same absence in the vLLM-side MP connector
 $ grep -niE 'kv_role|kv_consumer|kv_producer|skip_save|read_only|load_only|request_config' \
 vllm/distributed/kv_transfer/kv_connector/v1/lmcache_mp_connector.py
 <no matches> (exit 1)
 So the gap is not an artifact of one implementation - both MP connector implementations (the LMCache-shipped adapter and vLLM's self-contained LMCacheMPConnectorUpstream ) lack any store-disable signal.
 5c. kv_role is a vLLM-only field the MP connector never plumbs through
 kv_role does not exist in LMCache's own config ( grep -niE 'kv_role' lmcache/v1/config.py lmcache/v1/multiprocess/ → no matches). In the single-process path it is pulled from vllm_config.kv_transfer_config.kv_role (adapter line 469). The MP connector simply never reads that field, so kv_role=kv_consumer in the --kv-transfer-config is silently inert under the MP connector.
 5d. Forced-on save config when blending is enabled
 lmcache/v1/config.py , lines 709-715 :
 if self . enable_blending :
 if not self . save_unfull_chunk :
 logger . warning (
 "Automatically setting save_unfull_chunk=True because " 
 "enable_blending=True" 
 )
 self . save_unfull_chunk = True 
 Enabling blending forces save_unfull_chunk=True - a save- widening setting - on the very path that runs on the store-disable-less MP connector. Blend therefore stores more aggressively (including partial chunks), with no off-switch on its connector.

 7. Root-cause analysis
 The store-suppression logic lives entirely in the single-process connector's request-tracker construction ( vllm_v1_adapter.py ): kv_role , LMCACHE_FORCE_SKIP_SAVE , and per-request lmcache.skip_save all converge on the skip_save flag threaded into RequestTracker / SaveSpec . When the MP connector was built as a parallel implementation (scheduler/worker split with its own LMCacheMPRequestTracker and GetStoreMetadata metadata builder), that gate was not carried over : the MP metadata builder's contract ( GetStoreMetadata(tracker, tokens_per_chunk, tokens_per_block) ) has no place to express "don't store," and the two scheduler call sites ( _process_new_requests , _process_cached_requests ) invoke it for every scheduled request. The vLLM-side LMCacheMPConnectorUpstream inherited the same omission.
 In short: this is a feature-parity gap introduced by the second (MP) connector implementation , not a bug in a single line. The MP connector never wired kv_transfer_config.kv_role into its store decision, never reads request_configs , and honors no equivalent env switch - so the store path is unconditional by construction.
 8. Caveats & the single cleanest next check
 Caveats 
 CODE-VERIFIED , not MEASURED: I proved the absence of any store-disable input by reading source at the pinned commits; I did not deploy an engine. Nothing about correctness or throughput is claimed here.
 Scope is the store (save) path of the MP connector. The MP retrieve/load path is unaffected - loads still work, which is exactly why "read-only" is the desired-but-unreachable mode.
 The single-process LMCacheConnectorV1 remains a valid workaround for topologies that don't require the MP connector, but it is not an option for CacheBlend / shared-cache / cross-pod, which mandate the MP connector.
 I did not exhaustively audit every alternate MP entry point (e.g. TRT-LLM/SGLang adapters); the finding is specific to the vLLM MP connector named in the ticket.
 Single cleanest next check (positive confirmation, if wanted): deploy one MP-connector engine (TP=1, on a test cluster) with --kv-transfer-config '{"kv_connector":"LMCacheMPConnector","kv_role":"kv_consumer"}' , send one request against an empty cache, and scrape the engine's LMCache metrics - a nonzero store/ num_stored_tokens (or a growing L1) with kv_role=kv_consumer set is the runtime confirmation that the role is ignored. This is optional; the code structure already settles it.
