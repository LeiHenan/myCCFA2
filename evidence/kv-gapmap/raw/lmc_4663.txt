 [CacheBlend] [blocker perf] Non-prefix reuse decays to ~1× under sustained novel RAG - the blend store is prefix-chained and unbounded while the lookup is content-addressed
 Date: 2026-08-20
 Verdict: CONFIRMED - reproduced live and grounded in source.
 Confidence: High (MEASURED decay curve on dev + CODE-VERIFIED mechanism at the pinned commit).
 Severity: blocker (perf) - CacheBlend fails to sustain its value under exactly the workload it exists for (non-prefix RAG recombination); the win is a freshly-warmed burst, not steady state.

 2. Issue description (plain terms)
 CacheBlend's job is to reuse each retrieved document's KV regardless of the document's position in a RAG prompt, so that re-ordered / re-combined documents skip most of prefill. Its lookup does exactly that - it is content-addressed and position-independent. But its store reuses the ordinary prefix-cache write: it persists position-dependent KV keyed by a rolling, prefix-chained hash , unconditionally, on every request. Under sustained novel-ordering RAG traffic (the normal production pattern for RAG: each query retrieves a different combination/order of documents), every request mints a fresh batch of brand-new, un-dedupable keys. Those keys can only ever serve a future contiguous-prefix hit - which never happens on novel RAG - and they are useless to the content-addressed blend matcher, yet they pile into the shared L1 without bound. Once L1 saturates, LRU evicts the warm document chunks (the only thing the matcher can actually reuse), so the speedup decays from a post-warm burst down to the cold baseline within a few dozen queries. Nothing is functionally wrong; the store/lookup asymmetry is the defect. Production impact: any benchmark that re-warms before each measurement reports the burst (e.g. 4–6×) and completely misses that steady-state throughput under real sustained novel traffic falls back to ~1×.
 3. How verified
 Runtime (MEASURED, dev)
 Deployed a CacheBlendEngine blend server + a webhook-injected gpt-oss-20b vLLM engine (config above).
 Built a corpus of 112 docs × 2048 tokens (2048 = 8 × 256, so docs are chunk-aligned - this isolates the decay from any chunk-seam effect). Each query = 14 docs concatenated in a fresh shuffled order that never repeats (never-reset RNG). max_tokens=1 (prefill/TTFT only), concurrency 1.
 Metric = prefill throughput vs a true-COLD baseline (fresh, never-cached documents) - the only trustworthy signal (the built-in hit-counters mislabel blend reuse). Cold baseline measured n=3.
 Ran the full corpus warm pass once, then sustained novel-ordering batches (32 queries/batch), scraping the blend server's store/eviction counters per batch.
 Code (CODE-VERIFIED, commit 9fc6e1af / 436be94e )
 Lookup is content-addressed and offset-tolerant; store is prefix-chained; the MP connector stores unconditionally. Decisive lines quoted in §5.

 5. Decisive code lines (commit 9fc6e1af )
 Lookup is content-addressed + offset-tolerant. lmcache/v1/multiprocess/modules/blend_v3.py , match_sub_sequence :
 rolling = rolling_hash_windows_numba ( arr , self . chunk_size , self . _BASE ) # stride-1 window at EVERY position 
... # direct-address probe over all positions → a chunk matches wherever its content appears 
 The index is populated by on_new_token_hashes via chunk_hash_windows_numba(arr, self.chunk_size, ...) - non-overlapping 256-token chunks keyed by content.
 Store is prefix-chained (position-dependent). lmcache/v1/multiprocess/session.py (~L116-122):
 prefix = self . last_prefix_hash if self . last_prefix_hash is not None else self . hasher . none_hash 
 h = self . hasher . hash_tokens ( chunk , prefix ) # chunk key hashes the chunk PLUS all preceding tokens 
 self . last_prefix_hash = h 
 The MP connector stores every request unconditionally. lmcache/integration/vllm/lmcache_mp_metadata.py - GetStoreMetadata (def ~L176) takes only (tracker, tokens_per_chunk, tokens_per_block) and gates solely on new-chunk count (no dedup, no skip gate); both call sites in the connector ( _process_new_requests , _process_cached_requests ) invoke it and add the STORE op whenever chunks exist. A novel 14-doc ordering therefore mints ~112 brand-new prefix-chained keys/query (×object-groups ×ranks), none of which dedup.
 Consequence: the store set is unbounded (unique per preceding-context → effectively C(112,14)·14! distinct keys), it floods L1, and LRU evicts the warm document chunks the matcher needs.
 6. Root-cause analysis
 One defect: the store key-space and the lookup key-space are asymmetric. 
 Lookup keys are content-only → bounded by corpus size, reusable at any position. Correct.
 Store keys are prefix-chained → unbounded (one new set per novel ordering), and useful only for a contiguous-prefix hit that never occurs in RAG.
 Every novel query writes junk that (a) never serves a future novel query and (b) evicts the genuinely reusable warm chunks. So the reuse the matcher could deliver is continuously destroyed by the store path feeding the same L1. The burst exists only while the warm set is still resident; sustained novel traffic without continuous re-warm drives it to the cold floor. Larger L1 delays the collapse; it does not prevent it (the store set is unbounded).
 7. Regime (never a flat multiplier)
 Post-warm burst: ~2–4.5× (here 4.48× at L1=100 GB, 1.49× at L1=20 GB) - transient.
 Sustained uniform-novel: decays to ~1.0–1.1× (cold floor) within ~1–3 batches (~30–90 queries).
 Sustained with recurrence: partial - batches that happen to re-draw resident docs spike (up to 4.5× here), so skewed/popularity-heavy RAG sustains some reuse; uniform-novel is the worst case.
 Report the regime; do not quote the burst as the headline number.
 8. Caveats & the single cleanest next check
 Model: measured on gpt-oss-20b, not 120b - the decay mechanism is architecture-general (same MP store path), but absolute burst magnitudes differ. INFERRED that 120b shows a larger burst with the same decay shape.
 Docs were chunk-aligned (2048 tok): this deliberately removes any 256-chunk seam effect so the decay reflects only the store flood. Real unpadded RAG would show additional reuse loss on top.
 Cleanest next check: apply a save-skip gate to the MP connector (mirroring the single-process lmcache.skip_save path), warm once, then serve read-only, and re-run this exact driver. Expected pass = store Δ → 0 after warm, eviction Δ flat, and the burst holding across all batches instead of decaying. That both proves the root cause and validates the fix.
