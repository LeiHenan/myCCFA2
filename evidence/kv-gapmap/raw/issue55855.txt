 🚀 The feature, motivation and pitch
 vLLM already supports an object-store secondary tier for KV offloading through the NIXL OBJ backend and OffloadingConnector (RFC for this: #38260 ). The existing JSON shape should remain the same: users configure an OBJ secondary tier with type: "obj" and provide object-store parameters through store_config .
 I would like vLLM to extend this existing OBJ tier so it can use accelerated NIXL OBJ backends that support CPU DRAM registration and RDMA-capable object transfers.
 Existing shape:
 {
 "type" : " obj " ,
 "store_config" : {
 "bucket" : " kv-cache " ,
 "endpoint_override" : " http://object-store.example:9000/ " ,
 "scheme" : " http " 
 },
 "prefix" : " " ,
 "io_threads" : 4 
}
 Proposed extended shape:
 {
 "type" : " obj " ,
 "store_config" : {
 "bucket" : " kv-cache " ,
 "endpoint_override" : " http://object-store.example:9000/ " ,
 "scheme" : " http " ,
 "accelerated" : true ,
 "type" : " <accelerated_backend_type> " ,
 "use_virtual_addressing" : true ,
 "req_checksum" : " supported " ,
 "resp_checksum" : " supported " ,
 "backend_params" : {
 "custom_param" : " custom_value " 
 }
 },
 "prefix" : " " ,
 "io_threads" : 4 ,
 "max_dram_registration_bytes" : 1073741824 
}
 Credentials and region should not be required in the JSON. They should be allowed to come from the AWS SDK default credential/config provider chain, including environment variables, AWS profiles, credential files, IAM roles, or workload identity.
 Explicit access_key, secret_key, session_token, and region fields can remain supported for compatibility, but the expected production path should be environment/profile/workload-identity based configuration.
 The vLLM-side changes should include:
 Pass accelerated, accelerated backend type, checksum options, virtual addressing, and generic backend_params through to NIXL OBJ.
 Preserve the existing OBJ tier behavior and object key layout.
 Register the CPU primary-tier memory with NIXL for accelerated object transfers.
 Support splitting CPU DRAM registration into multiple block-aligned descriptors using max_dram_registration_bytes, because accelerated NIXL OBJ backends may reject descriptors larger than CUOBJ_MAX_MEMORY_REG_SIZE.
 Keep RDMA token handling, backend-specific memory registration, and object PUT/GET implementation inside NIXL.
 This enables RDMA-capable object-store paths for KV chunks moving between vLLM's CPU primary tier and object-store secondary tier, without adding backend-specific transfer logic to vLLM.
 Alternatives
 Continue using the existing non-accelerated NIXL OBJ path. This keeps the current behavior but cannot use RDMA-capable object transfers.
 Add backend-specific RDMA/object-transfer logic directly in vLLM. This is less desirable because memory registration, RDMA token handling, and object transfer mechanics belong in NIXL.
 Additional context
 This should be an extension of the existing OBJ secondary tier, not a new tier type.
 The main implementation caveat is CPU DRAM registration size: vLLM currently has enough context to split the CPU primary-tier pool on KV block boundaries, while NIXL accelerated OBJ backends may enforce CUOBJ_MAX_MEMORY_REG_SIZE per registered descriptor.
