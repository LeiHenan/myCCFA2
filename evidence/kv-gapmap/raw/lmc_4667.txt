 Date: 2026-08-20
 Verdict: CONFIRMED (with one important refinement - see below)
 Confidence: High (code-verified from primary source + deterministic algorithmic reproduction using the real LMCache hashers). Live-serving timing run was skipped (see §8); it is not needed to settle this claim.

 1. Summary
 The CacheBlend fragment store chops each stored token sequence on a fixed chunk_size (256) grid anchored at the start of the concatenated request , with no document-boundary awareness and no inter-document padding . Only complete 256-token chunks are stored/indexed; the trailing partial chunk is dropped. When variable-length (not 256-multiple) RAG documents are concatenated in different orders, each document's offset-mod-256 shifts, so its head fragment, tail remainder, and the seams between documents fall on different token boundaries each time and never become reusable full chunks. Only the grid-aligned interior of each document reuses.
 Because the matcher uses a stride-1 rolling window (full recall), the interior chunks are found wherever the document appears intact, regardless of position - so this is seam/tail loss, not total loss .
 Measured seam tax on a representative RAG working set (12 docs, 1500–2600 tokens): ~11.2% of query tokens lose reuse relative to a chunk-aligned control (100% → 88.75%).

 3. Issue description - why unpadded RAG loses reuse at seams, and why it matters
 CacheBlend's value in RAG is that the same document, retrieved into different prompts in different positions, should reuse its cached KV (non-prefix reuse). That requires the store to key document content in a position-independent way.
 The multiprocess blend store (the path used in the cross-pod / co-located production deploy) does this by fingerprinting fixed 256-token windows of the stored sequence and matching them into new queries with a rolling window. The catch is how the windows are cut on store :
 The grid is anchored at the start of the whole concatenated request ( key.start ), not at each document's boundary. There is no separator handling and no padding inserted between documents.
 A document of length L placed at concatenation offset o is therefore cut at grid lines o + (256 − o mod 256) , ... + 256 , … Its head fragment [o, first_grid_line) shares a 256-window with the previous document's tail (a straddle/seam chunk), and its tail fragment shares a window with the next document's head (or is the dropped trailing partial).
 Change the ordering → o mod 256 changes → the grid cuts the document at different points → different straddle chunks, different fragments. The straddle chunks are adjacency-specific (only reused if that exact document pair recurs adjacently), and the fragments are never captured as standalone chunks.
 Net effect: per document you reliably reuse only the grid-aligned interior (which the offset-tolerant matcher does find anywhere), and you lose up to 2 × (chunk_size − 1) tokens of head+tail per document - on average ≈ one chunk_size per document boundary.
 Why it matters: RAG documents are essentially never exact multiples of 256 tokens. With realistic 1500–2600-token chunks that is ~10–12% of prompt tokens that must be recomputed on every request despite being cached - a standing prefill tax that grows with the number of documents per prompt (more seams) and shrinks with document length (seam amortized over more interior).

 7. Root-cause analysis
 The store fingerprints content on a fixed grid anchored to the concatenated request , not to document boundaries, and inserts no padding to realign each document to the grid. Consequently the stored set of 256-token content windows is a function of each document's arbitrary offset-mod-256 in whatever concatenation warmed it. The rolling matcher recovers only those windows that recur contiguously and identically in a query:
 Interior windows (wholly inside a document) recur wherever the document appears intact → reused (this is why it is not a total loss).
 Head/tail fragments (< 256 tokens, the document's edges relative to the warming grid) are never stored as standalone chunks → permanently lost.
 Straddle/seam chunks (256-window mixing doc-A tail + doc-B head) are adjacency-specific → only reused if that exact pair recurs adjacently, which is the case CacheBlend is meant to avoid depending on.
 There is no code that (a) resets the chunk grid at a document boundary, (b) pads a document up to the next 256 multiple, or (c) stores sub-chunk remainders. The fix space is exactly those three: document-boundary-aware chunking (reset the grid per retrieved document), inter-document padding to a chunk_size multiple, or storing/matching partial tail chunks.
 8. Caveats & the single cleanest next check
 Caveats / what is NOT claimed: 
 This is a perf defect, not correctness - the token-exact verify ( blend_index.py:211 ) guarantees no wrong KV is ever reused.
 The live-serving timing run was skipped. The claim is about which chunks get indexed/matched - pure deterministic geometry - so a serving run would add TTFT numbers but cannot change the verdict, and it would cost a full CacheBlend GPU deploy. Nothing was deployed to any cluster; no teardown needed.
 The ~11.2% figure is workload-specific (12 docs, 1500–2600 tokens). Seam tax scales with docs-per-prompt (more seams) and inversely with document length (seam amortized over more interior). Short docs (< ~2×chunk_size) suffer proportionally far more; a doc shorter than 256 tokens is invisible to the store entirely ( blend_index.py:194 ).
 Applies to the multiprocess / v3 blend path (production cross-pod / co-located). The in-process SegmentTokenDatabase path is separator-aware and not subject to this; confirm which path a given deployment uses before quoting the number.
 Single cleanest next check: Add a document-boundary-aware store variant - reset the chunk grid (and/or right-pad to a chunk_size multiple) at each retrieved-document boundary on store - and re-run the §4b reproduction. Expectation: unaligned reuse rises from ~0.89 toward ~1.0, converting the seam tax directly into recovered prefill. This isolates the fix's ceiling before any serving-timing work.
