 1. Issue in one sentence
 The fs_native L2 disk backend (LMCache GdsBackend ) writes one file per distinct KV chunk unconditionally, with no size cap and no eviction implemented at all , so under CacheBlend novel-ordering traffic (which mints new distinct chunk keys continuously) the on-disk store grows without bound until the L2 filesystem/PVC fills, the node crosses the kubelet DiskPressure threshold, and the serving pods are evicted.

 3. Issue description (plain terms)
 LMCache offers more than one on-disk ("L2") backend. They do not behave the same way with respect to disk safety:
 LocalDiskBackend - the " local_disk " path. It is created only when a positive max_local_disk_size is set, and it enforces that cap with LRU eviction on every write. Bounded by construction. 
 GdsBackend - the " gds_path " path, selected by l2.type: fs_native (GDS/cuFile, or plain O_DIRECT/POSIX on a non-GDS filesystem). It has no size/quota/cap parameter at all , and eviction is explicitly not implemented - the code literally logs "GDS Backend does not support eviction" . Every distinct KV chunk is written as a new file and never reclaimed. Unbounded. 
 Any deployment that selects l2.type: fs_native uses the unbounded GdsBackend , and LMCache exposes no knob to bound it - the backend accepts no size parameter, so there is nothing a config layer could set.
 Why it matters at production level: the L2 tier is a shared node resource (a dedicated NVMe device / PVC). When it fills, the failure is not a graceful cache miss - it is a node-level DiskPressure condition. The kubelet responds by evicting pods on that node. That takes down the serving engines (and can affect co-tenants on the same node), i.e. a self-inflicted availability outage that grows more likely the longer the deployment runs and the more distinct traffic it sees. CacheBlend traffic is the worst case for this: its whole point is non-prefix reuse over many document orderings, and each novel ordering produces new distinct chunk keys → the distinct-key set grows monotonically → the store grows monotonically.

 The store writes ~109 new chunks per novel query and never stops - write_chunks_total is strictly linear in query count (no dedup, no plateau-from-dedup). On the bounded L1 the write rate ≈ the evict rate (10,923 ≈ 11,026): L1 caps residency by evicting the warm set (this is also the decay mechanism of the sibling perf ticket). On the fs_native /GDS L2 GdsBackend , which has no eviction (code evidence above), that identical ~109-chunks/query write stream accumulates on disk without bound → the disk-fill/DiskPressure outcome is the L2 manifestation of exactly this measured write stream. This confirms the mechanism at runtime without ever approaching the disk limit.

 Growth arithmetic (mechanism): distinct chunks written = f(distinct chunk keys served). CacheBlend serves novel document orderings; with chunk_size=256 , each novel ordering that isn't a pure prefix of a prior one produces fresh chunk keys. On-disk size ≈ (number of distinct chunks) × (serialized bytes per chunk). Because reclamation is 0, this is strictly monotonic non-decreasing for the life of the pod - it can only ever go up until the disk is full.

 7. Root-cause analysis
 The GdsBackend was built as a high-throughput GPU-Direct-Storage / O_DIRECT write path and, by the authors' own in-code notes, eviction was never added to it ("Since gds doesn't have eviction now…"). It therefore has neither a capacity parameter nor any reclamation policy: submit_put_task → _async_save_bytes_to_disk writes a file per key and returns. The sibling LocalDiskBackend carries the cap+LRU logic, but it is a different backend selected by a different config ( local_disk + max_local_disk_size>0 ), not the fs_native path.
 Selecting l2.type: fs_native routes to GdsBackend , which exposes no size limit (nor could a config layer add one - the backend accepts none). So a deployment using it has no layer that bounds the L2 store. Combined with CacheBlend's continuously-novel key stream, the store grows until the filesystem fills. On Kubernetes, a full node filesystem is a DiskPressure condition, which the kubelet resolves by evicting pods - hence the "evicts the serving pods" outcome in the title. The mechanism claimed by the ticket is real for the configuration that actually ships.
 8. Caveats & unverified
 Not driven to failure (by design). The DiskPressure/eviction outcome is inferred from the standard kubelet behavior for a full node filesystem, not reproduced - reproducing it would degrade the shared dev node. The store- growth half is code-certain; the eviction half is the well-known kubelet consequence of it.
 Time-to-outage not quantified. Wall-clock time to fill depends on serialized bytes/chunk (model dims, chunk_size=256 , dtype), L2 device capacity, and traffic novelty rate - none measured here. The chart axes are therefore unitless.
 Whether an external backend (RESP/remote) has its own server-side cap is out of scope; this report covers the on-node fs_native /GDS L2 ( GdsBackend ). A resp (Redis-protocol) remote backend's capacity would be governed by that server, not this code.
 use_gds: false (plain O_DIRECT fs_native) uses the same GdsBackend class and the same no-cap/no-evict paths - it does not change the verdict.
 Single cleanest next check (safe, GPU-light, does NOT approach disk-full): deploy one throwaway CacheBlend engine with a small L1 and an fs_native L2 pointed at a small, isolated, bounded scratch dir; drive N successive novel-ordering batches (well short of filling the dir); after each batch record ls "$BASE_PATH" | wc -l and du -sh "$BASE_PATH" . Expect a strictly increasing file count and byte total with zero decreases across batches (no eviction). Fit the slope to bytes-per-distinct-chunk, then divide real L2 capacity by that slope to project time/volume-to-DiskPressure - extrapolate to the outage; never cause it. Tear down the engine and delete the scratch dir afterward.
