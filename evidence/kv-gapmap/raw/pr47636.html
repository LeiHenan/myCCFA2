Purpose

Give the P2P KV-offload secondary tier (type: "p2p" under TieringOffloadingSpec)
the same well-known-port ergonomics the NIXL connector already has, plus per-DP-rank
port binding so data-parallel replicas don't collide.

Two commits:

  1. Well-known default host/port env vars. Add VLLM_P2P_SIDE_CHANNEL_HOST
    (default localhost) and VLLM_P2P_SIDE_CHANNEL_PORT (default 5710), mirroring
    VLLM_NIXL_SIDE_CHANNEL_HOST/VLLM_NIXL_SIDE_CHANNEL_PORT. The P2P manager now
    resolves its control-socket bind address from these env vars instead of the
    hardcoded 0.0.0.0:7777, so operators set the listen host/port at deploy time.
    Explicit host/port keys in the secondary_tiers config still win.

  2. Per-DP-rank control port. Each data-parallel replica runs its own P2P
    secondary-tier manager, so a fixed control port collides across replicas on a
    host. The bound port is now base_port + parallel_config.data_parallel_index
    (mirroring NIXL's side-channel port layout) — one deterministic socket per
    replica. For DP=1 the offset is 0, leaving the well-known default (5710)
    unchanged. The decode leg still receives the target rank's port as remote_port
    in kv_transfer_params; the router/EPP that selects the DP rank computes
    remote_port = base + rank.

Docs (docs/features/kv_offloading_usage.md) are updated to describe both.

Why this is not duplicating an existing PR

Checked vllm-project/vllm open PRs for "P2P side channel port", "VLLM_P2P_SIDE_CHANNEL",
and "kv offload p2p tier". The nearby open PRs address unrelated concerns: #46498 adds
a separate UcclP2pConnector; #47274 adds a TieringManagerReverseAPI protocol;
#47413 adds tier_idx for per-tier metrics; #44865 reshapes the transfer data model.
None touch the P2P tier's control-socket host/port env vars or its bind-port layout.

Manual end-to-end (PD-disaggregated, two hosts, Llama-3.2-1B, UCX/NIXL data plane):
prefiller + decoder deploy with host/port omitted from secondary_tiers; control
sockets bind to the env-derived IP:5710 (DP=1 → offset 0); external prefix-cache hit
rate ~95%.

[KVOffload][P2P] Scope data-transport poll() to the owning peer
30b57c1 
A single NixlTransport is shared across all per-peer P2PSessions of an
engine, but poll() drained and popped completed transfer handles globally.
When one engine serves multiple peers -- e.g. a data-parallel decoder
(dp_size>1) pulling from a single prefiller -- each session's
ServerRole.collect_results() calls the shared poll(), so whichever peer
polled first consumed the other peers' completions and reported them as
"unknown transfer_id". The owning session never observed its own completion
and timed out, a deterministic per-replica hang for dp_index>=1.

Tag each inflight transfer with its peer_id and add an optional owner
filter to poll(); ServerRole now polls only its own peer's transfers. The
shutdown drain keeps the unscoped poll(). Add a regression test and update
the DataTransport test fakes for the new signature.

[KVOffload] Make the CPU offload region data-parallel aware
3948e8c 
The tiering CPU offload region keyed its /dev/shm mmap file on
vllm_config.instance_id, which is shared across all data-parallel replicas
of an engine, and used the physical device index as the intra-row slot rank.
With data_parallel_size>1 every replica mapped the same file and a replica
with a non-zero device index computed a slot offset past the row end,
crashing at startup with "madvise start out of bounds".

(_region_instance_id, mirroring the P2P control socket's base+dp_index
scheme), and fold the device index into the replica-local tensor-parallel
range with % world_size for the slot rank. For DP=1 the index is 0, leaving
behavior unchanged.

Three issues from testing the p2p tier with the llm-d routing sidecar (1P/1D, DP=1, TieringOffloadingSpec + p2p tier, nightly-09663abde):

1. Non-routable host breaks peering with an opaque NIXL error — concrete repro of the localhost concern above. The tier host becomes _local_id = f"{host}:{port}" (manager.py:164), which is also the NIXL agent name, so with host: 0.0.0.0 (and equally the VLLM_P2P_SIDE_CHANNEL_HOST=localhost default) every pod registers the same agent name and NIXL rejects the peer at connect:

nixl_agent.cpp loadRemoteMD: remote agent name same as local agent
P2PSession: error handling 'connect': NIXL_ERR_INVALID_PARAM

This is orthogonal to the base_port + data_parallel_index offset (manager.py:162-163) — that deduplicates the port for replicas on the same host, while this collision is on the host component across different pods, so the offset never comes into play. host: $(POD_IP) fixes it. The seam already exists: ZmqTransport(self._local_id, host, port) (manager.py:179) takes the identity separately from the bind host/port, so _local_id could be derived from an advertised routable address (or fail fast on loopback/0.0.0.0) while the socket binds wherever.

2. First-request transfer fails when the two legs are dispatched concurrently. Our sidecar sends the prefill leg (kv_transfer_params.decode) and the decode leg (kv_transfer_params.prefill) at the same time with the same kv_request_id. On the first request after startup the decoder's fetch races the session bind and the producer's store:

decode   submit_load ... session_ready=False
prefill  server.py fetch RECEIVED kv_request_id=...
prefill  server.py store job timed out          (parked store never joins the fetch)
decode   client.py ... timed out, sending abort

Once the session is warm (session_ready=True) the same flow completes (sent fetch -> sent transfer_done). Sequential orderings (prefill-first or decode-first) serialize the rendezvous, so they don't hit it — concurrent dispatch on a cold session is the repro.

3. kv_load_failure_policy: fail isn't honored when the load fails. Deterministic repro, independent of leg ordering: point the decoder at a permanently unreachable peer (kv_transfer_params.prefill.remote_host=192.0.2.1), policy fail. The load job fails after the 30s load timeout + 10s abort_ack timeout, yet the request returns a normal completion (finish_reason:"length") at exactly 40s — fail has no effect. The mechanism is in v1/kv_offload/tiering/p2p/manager.py: _failed_req_ids — "On load lookup() rejects them so the request falls back to local prefill." A failed load is converted into a lookup miss, so the failed blocks never reach the scheduler and the policy never runs. In P/D the decoder explicitly delegated prefill via kv_transfer_params.prefill, so a failed transfer is a load failure, not a miss.

2 and 3 point at the same seam: failures stay inside the tier instead of reaching the scheduler. Wonder if the abort/timeout path could report failed blocks through get_finished, the way nixl/base_worker.py drains _failed_recv_reqs into done_recving — that routes 3 through the policy (fail errors, recompute keeps today's fallback as a policy decision), and for 2 it would bound the first request to a fast policy-driven recompute instead of a silent 30-60s stall.

Correction on point 2 above (the "concurrent dispatch race") — after more digging it is not a race. Root cause and a real secondary bug below, validated on two clusters; standalone reproducer at the bottom.

Root cause: per-process block hashes. Without PYTHONHASHSEED pinned on both pods, the decoder's demanded hashes never match the prefiller's stored keys, so every fetch/store pairing silently matches 0/N blocks and no KV ever transfers. With PYTHONHASHSEED=0 on both pods, the exact same cold, concurrent, parked-store sequence completes immediately:

parked submit_store job_id=0 blocks=7
fetch RECEIVED blocks=7
NIXL write_blocks CALL local_idxs=7 remote_idxs=7
NIXL write_blocks SUBMITTED transfer_id=0
sent transfer_done                      (decode leg: 0.3s, was 30.2s)
decoder: vllm:kv_offload_load_bytes=1769472

So the park/drain/match machinery is correct — concurrency was a red herring.

Why it looked like a race: ordering only changes fast-fail vs slow-fail of the always-failing match.

  • Fetch-before-store (your sequential modes): the store takes the fast path onto the bound session, and when the prefill request finishes, finish_request reaches the session and _finalize_outbound(success=False) sends TransferDoneMsg — the decoder fails fast and recomputes. Looks like success (sent transfer_done logs regardless of success).
  • Store-parked-before-fetch (concurrent dispatch, cold session): finish_request hits _kv_to_session.pop -> None and returns silently (manager.py:253), so the parked batch never learns the request finished. The fetch's demand never finalizes and the decoder eats the full 30s _LOAD_TIMEOUT_S.

Suggested fixes:

  1. finish_request should also finalize parked entries in _unbound_stores, so an unmatched fetch fast-fails instead of stalling 30s.
  2. A fetch+store pairing that matches 0/N blocks deserves a warning log — the silent mismatch made this expensive to diagnose.
  3. Wonder if the connect handshake could carry a hash-compatibility check the way nixl/base_worker.py exchanges a compatibility hash — a seed mismatch would then fail loudly at connect instead of degrading every transfer.
Two-pod reproducer (stdlib Python, no orchestrator) — flips between the 30s stall and a working transfer purely on PYTHONHASHSEED 
#!/usr/bin/env python3
"""Two-pod reproducer for the P2P offloading tier hash-mismatch failure.

Dispatches the prefill leg (kv_transfer_params.decode) and the decode leg
(kv_transfer_params.prefill) CONCURRENTLY with the same kv_request_id,
mirroring the llm-d routing sidecar.

vLLM block hashes are seeded per process, so the outcome depends on
PYTHONHASHSEED being pinned (same value) on BOTH vLLM pods:

  PYTHONHASHSEED unset  -> the decoder's demanded hashes never match the
    prefiller's stored keys (0/N matched, silently). On a cold session the
    store is parked and finish_request drops it (manager.py: _kv_to_session
    .pop -> None -> return), so nothing finalizes the demand and the decode
    leg stalls the full 30s load timeout:
        prefiller: parked submit_store / fetch RECEIVED / store job timed out
        decoder:   submit_load session_ready=False / timed out, sending abort
    On a warm session the same mismatch fails fast instead
    (TransferDoneMsg success=false) and masquerades as success.

  PYTHONHASHSEED pinned -> the same cold concurrent sequence transfers:
        prefiller: NIXL write_blocks CALL local_idxs=N remote_idxs=N
        decoder:   vllm:kv_offload_load_bytes > 0

Setup: two vLLM instances with OffloadingConnector + TieringOffloadingSpec
+ p2p secondary tier. The tier host must be a ROUTABLE address (pod IP, not
0.0.0.0/localhost — those collide on the NIXL agent name):

  PYTHONHASHSEED=0 vllm serve facebook/opt-125m --port 8000 --enforce-eager \
    --max-model-len 512 --kv-transfer-config \
    '{"kv_connector":"OffloadingConnector","kv_role":"kv_both",
      "kv_connector_extra_config":{"spec_name":"TieringOffloadingSpec",
      "cpu_bytes_to_use":209715200,
      "secondary_tiers":[{"type":"p2p","host":"<THIS_POD_IP>","port":7777}]}}'

Usage:
  python3 repro_p2p_race.py \
    --prefill-url http://<prefill-pod-ip>:8000 \
    --decode-url  http://<decode-pod-ip>:8000 \
    --prefill-host <prefill-pod-ip> --p2p-port 7777

Restart both vLLMs without PYTHONHASHSEED -> first run stalls ~30s.
Restart both with PYTHONHASHSEED=0        -> same first run transfers, <1s.
"""

import argparse
import json
import threading
import time
import urllib.request
import uuid

PROMPT = (
    "In the ancient kingdom beyond the northern mountains where winter lasted "
    "nine months of every year, the royal cartographers maintained detailed "
    "maps of every trade route crossing the frozen passes, and each spring the "
    "merchant caravans would gather in the great stone hall to study those "
    "maps before setting out on their long journeys toward the southern ports, "
    "carrying furs and amber and iron tools to exchange for silk and spices "
    "and books written in languages that few northern scholars could read. "
)


def post(url, body, timeout, out):
    started = time.monotonic()
    req = urllib.request.Request(
        url + "/v1/completions",
        data=json.dumps(body).encode(),
        headers={"Content-Type": "application/json"},
    )
    try:
        with urllib.request.urlopen(req, timeout=timeout) as resp:
            out["status"] = resp.status
            out["body"] = resp.read().decode()[:200]
    except Exception as exc:  # noqa: BLE001 - report anything
        out["error"] = str(exc)
    out["elapsed"] = time.monotonic() - started


def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--prefill-url", required=True)
    ap.add_argument("--decode-url", required=True)
    ap.add_argument("--prefill-host", required=True,
                    help="address the decoder pulls from (prefill pod IP)")
    ap.add_argument("--p2p-port", type=int, default=7777)
    ap.add_argument("--model", default="facebook/opt-125m")
    args = ap.parse_args()

    kv_request_id = str(uuid.uuid4())
    # unique suffix so the engine cannot serve the prompt from its own cache
    prompt = PROMPT + f"Session marker {uuid.uuid4()}."

    prefill_body = {
        "model": args.model,
        "prompt": prompt,
        "max_tokens": 1,           # prefiller returns as soon as KV is stored
        "stream": False,
        "kv_transfer_params": {"decode": {"kv_request_id": kv_request_id}},
    }
    decode_body = {
        "model": args.model,
        "prompt": prompt,
        "max_tokens": 16,
        "kv_transfer_params": {"prefill": {
            "kv_request_id": kv_request_id,
            "remote_host": args.prefill_host,
            "remote_port": args.p2p_port,
        }},
    }

    print(f"kv_request_id: {kv_request_id}")
    prefill_out, decode_out = {}, {}
    threads = [
        threading.Thread(target=post,
                         args=(args.prefill_url, prefill_body, 120, prefill_out)),
        threading.Thread(target=post,
                         args=(args.decode_url, decode_body, 120, decode_out)),
    ]
    # both legs at the same instant, same kv_request_id — the sidecar's dispatch
    for t in threads:
        t.start()
    for t in threads:
        t.join()

    print(f"prefill leg: {prefill_out.get('status', prefill_out.get('error'))} "
          f"in {prefill_out.get('elapsed', 0):.1f}s")
    print(f"decode  leg: {decode_out.get('status', decode_out.get('error'))} "
          f"in {decode_out.get('elapsed', 0):.1f}s")

    if decode_out.get("elapsed", 0) > 25:
        print("=> STALL: hashes did not match (PYTHONHASHSEED differs across "
              "pods) and the parked store was never finalized. Prefiller log: "
              "'store job timed out'; decoder log: "
              f"'{kv_request_id} timed out, sending abort'.")
    else:
        print("=> fast return. Real transfer iff the prefiller logged "

* feat(sidecar): support data parallelism with the offloading P2P tier

vLLM binds DP rank r's P2P tier on <p2p-connector-port>+r and gives each
replica a distinct shared-memory offload region (vllm-project/vllm#47636,
vllm-project/vllm#47987), so ranks in one pod no longer collide and the
startup rejection of --kv-connector=offloading with --data-parallel-size > 1
guards a configuration the engine now supports. Lift it and derive the
injected remote_port from the routed endpoint's port: rank r is served on
<base port>+r, so the matching P2P port is <p2p-connector-port>+r. Ports
outside the rank range fall back to rank 0, so a stale or foreign header
degrades to a lookup miss instead of an error. Assumes pods in the pool
share the sidecar port layout and DP size.

Fixes #2074

Signed-off-by: nilig <nili.ifergan@gmail.com>

* fix(sidecar): bound rank ports and accept scheme-prefixed P2P targets

The injected port is p2p-connector-port plus the target's DP rank, so the
highest rank must stay within 65535 - validate the range, not just the
base. Routed endpoint values may carry a http:// prefix (the proxy trims
it when building handlers); trim it in rank derivation and in extractHost
too, so a scheme-prefixed header yields the correct remote_host and
remote_port instead of a garbage host with a rank-0 port.

Signed-off-by: nilig <nili.ifergan@gmail.com>

* docs(sidecar): scope P2P rank derivation to per-pod DP groups

vLLM binds the tier at p2p-connector-port plus the global
data_parallel_index (tiering/p2p/manager.py), while the endpoint-port
offset yields the pod-local rank. The two agree only when each pod is its
own DP group, so state that boundary: multi-pod DP groups (LWS wide-EP)
need the source's global index supplied per request, and this derivation
is the per-pod fallback.

Signed-off-by: nilig <nili.ifergan@gmail.com>

* chore(sidecar): log P2P rank-derivation fallbacks at debug

The fallbacks in p2pPortFor silently return the base P2P port, so a
misrouted or unparsable target is invisible in the logs; a debug line
per fallback explains which guard fired.

Signed-off-by: nilig <nili.ifergan@gmail.com>

* docs(sidecar): restructure the DP section into plain-language bullets

One paragraph carried seven chained clauses; a lead sentence with one
fact per bullet reads without unpacking.
