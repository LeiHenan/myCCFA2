### CLOSED-1: vLLM Automatic Prefix Caching (hash-based block cache)
- URL: https://docs.vllm.ai/en/latest/design/prefix_caching/
- Evidence: READ BODY
- Detail: The canonical vLLM design doc for prefix KV reuse, retrieved live. It states the value proposition and the implementation choice verbatim: "Since prefix caching is almost a free lunch and won't change model outputs, it has been widely used by many public endpoints (e.g., OpenAI, Anthropic, etc.) and most open source LLM inference frameworks (e.g., SGLang)." And: "While there are many ways to implement prefix caching, vLLM chooses a hash-based approach." The doc specifies the key components and two hard constraints: "We only cache full blocks." And on hashing: "In previous versions, the hash key was not guaranteed to be collision-free. As of v0.11, the default hashing algorithm is `sha256`, which addresses collision risks." Corroborating local tree evidence (not a URL): `/tmp/kvsrc/vllm-main/vllm/config/cache.py:139` reads `enable_prefix_caching: bool = True`, i.e. prefix caching is on by default in the extracted 0.29-era tree, and `prefix_caching_hash_algo: PrefixCachingHashAlgo = "sha256"` at line 141.

### CLOSED-2: Per-request `cache_salt` for prefix-cache isolation, hardened against DoS
- URL: https://docs.vllm.ai/en/latest/design/prefix_caching/ and https://github.com/vllm-project/vllm/pull/54353
- Evidence: READ BODY
- Detail: The design doc documents salting as shipped: "By including a `cache_salt` in the request, this value is injected into the hash of the first block, ensuring that only requests with the same salt can reuse cached KV blocks. This prevents timing-based attacks where an adversary could infer cached content by observing latency differences. This offers protection without compromising performance." The mechanism is an extra hash component: "Extra hashes: Other values required to make this block unique, such as LoRA IDs, multi-modality input hashes (see the example below), and cache salts to isolate caches in multi-tenant environments." The parameter was later hardened by merged PR #54353 ("[Bugfix] Bound cache_salt length to prevent DoS via scheduler CPU exhaustion", merged 2026-08-30), whose body reads verbatim: "Adds `max_length=1024` to the `cache_salt` Pydantic `Field` on all six API protocol models: completions, chat completions, responses, pooling, Anthropic, and scale-out (token-in-token-out)." with the threat being an attacker able to send "arbitrarily large salt strings that are serialized via `pickle.dumps` + `sha256` on the single-threaded EngineCore scheduler, stalling all concurrent requests."

### CLOSED-3: SGLang RadixAttention (canonical reference)
- URL: https://arxiv.org/abs/2312.07104
- Evidence: READ BODY
- Detail: The canonical paper behind SGLang's radix-tree prefix reuse, retrieved from arXiv (submitted 12 Dec 2023, v2 6 Jun 2024). ### CLOSED-4: SGLang radix cache eviction policies (lru / lfu / slru / priority)
- URL: https://docs.sglang.io/docs/advanced_features/radix_eviction_policy.md
- Evidence: READ BODY
- Detail: A shipped, documented eviction-policy surface for the radix cache, retrieved as clean markdown. Verbatim: "Select one with `--radix-eviction-policy`. All of them fall back to least-recently-used order within a tie." Policy semantics are documented per row, e.g. "`lfu` | The prefix with the fewest cache hits, then the least recent." and "`slru` | Prefixes still in the probationary segment, then the least recent within a segment." Two important scoping statements: "A policy only scores. It does not decide how much to free, and it cannot pin KV in memory — a node protected by the policy is still evicted if reclaiming everything else is not enough." and "`fifo`, `mru`, and `filo` also exist in the policy registry but are not offered on the command line. They are reachable only by out-of-tree code that extends the choice list, and exist for experiments rather than serving." The doc also states the tradeoff explicitly: "`lfu` and `slru` help when your traffic has a stable hot set that a recency-only policy keeps flushing; they hurt when prefix popularity shifts over time, because a prefix that earned a high hit count keeps its advantage after it stops being useful."

### CLOSED-5: SGLang session-aware radix cache (soft-pinned KV per session)
- URL: https://docs.sglang.io/docs/advanced_features/session_radix_cache.md
- Evidence: READ BODY
- Detail: Shipped multi-turn/agent KV retention feature. Verbatim: "This feature is implemented only by `UnifiedRadixCache`." Invocation: `SGLANG_ENABLE_UNIFIED_RADIX_TREE=1 ... --enable-session-radix-cache`. Limits are documented up front: "Session references are soft protection, not memory pins. Referenced KV can still be evicted when reclaiming unreferenced KV is insufficient." Eviction order is spelled out per cache component, including hybrid ones: "Full attention | The reusable prefix path from the registered leaf to the root | Unreferenced nodes first, then referenced nodes with fewer session references, then the configured policy such as LRU" and "Mamba | The reusable state on the registered leaf | Two LRU passes: unreferenced nodes first, then referenced nodes if more space is required". Also: "UnifiedRadixCache still applies component cascade rules. Evicting an internal Full node also evicts its SWA and Mamba data; evicting SWA also evicts Mamba data; evicting Mamba affects only Mamba."

### CLOSED-6: SGLang HiCache L3 cross-instance prefix sharing
- URL: https://docs.sglang.io/docs/advanced_features/hicache_design.md
- Evidence: READ BODY
- Detail: This is the shipped answer to "can prefix KV be shared across instances". Verbatim tier statement: "L2 is node-local and instance-private." and "This is the answer to a common question: HiCache cannot pool the host memory of several machines into one larger L2. Growing `--hicache-ratio` or `--hicache-size` only makes each instance's own private L2 larger. Cross-instance reuse is the job of L3, so it needs `--hicache-storage-backend`." On the mechanism: "**Cross-instance Sharing**: When data is written back from L2 to L3, only data not already present in L3 is transferred. KV caches stored in L3 can then be shared across all SGLang instances in the cluster (depending on the L3 backend implementation), significantly improving cache hit rates within the same memory budget." Backends are enumerated verbatim: "Distributed backends such as `mooncake`, `hf3fs`, `nixl` and `aibrix` give cluster-wide scope, but only when every instance is pointed at the same namespace and configuration." The metadata structure is described as "HiRadixTree", extending RadixAttention: "HiRadixTree extends this idea: each node corresponds to the KV cache of a span of consecutive tokens and records where that KV cache is stored—whether in local GPU memory, CPU memory, L3 storage, or multiple of these tiers."

### CLOSED-7: SGLang SMG router cache-aware routing policy

- Evidence: READ BODY

### CLOSED-10: vLLM fallback when a hybrid KV group cannot answer fine-grained lookups
- URL: https://github.com/vllm-project/vllm/pull/51843
- Evidence: READ BODY
- Detail: Merged 2026-08-12. This is the shipped answer to the "fine-grained hits are silently disabled" failure mode. Verbatim summary: "Fine-grained prefix-cache hits are enabled for hybrid models containing Mamba `align` groups. The change list: "Enables fine-grained hits only when every KV cache manager supports the required lookup granularity." / "Falls back to scheduler-block-aligned prefix hits for incompatible layouts." / "Prevents the scheduler from creating partial-tail cache entries after that fallback." / "Logs when fine-grained hits are disabled." ### OPEN-9: HiCache's file backend can report an unrestorable hybrid prefix as a hit
