### CLOSED-1: FP8 e4m3 per-tensor KV cache, calibration-free (scale = 1.0), validated Hopper + Blackwell
- URL: https://vllm.ai/blog/2026-04-22-fp8-kvcache
- Evidence: READ BODY
- Detail: vLLM's flagship FP8 KV-cache validation. The flag quantises both storage *and* the attention matmuls. Verbatim: "vLLM's --kv-cache-dtype fp8 flag quantizes the KV-cache and runs the entire attention computation (the QK and ScoreV matrix multiplications) in FP8 (e4m3 is the format used throughout this post)." On the calibration-free question the blog is explicit that scale=1.0 is the evaluated configuration: "Important: All evaluations use per-tensor uncalibrated quantization scales (i.e., scale = 1.0). This is the simplest possible configuration — no calibration data, no per-head tuning — and represents the worst-case scenario for accuracy." Headline result: "FP8 KV-cache and attention quantization introduces at most 1-2 points of accuracy degradation, with the lowest recovery at 97% (GPQA:Diamond, BF16 model)." Stated exceptions: "The main exceptions are workloads where prefill dominates on head_dim = 256 , hybrid models whose small sliding-window layers should be left in BF16, and models or backends that show persistent uncalibrated accuracy loss, where calibration remains important."

### CLOSED-2: Per-token-head dynamic (calibration-free) INT8 / FP8 / INT4 KV scales shipped in vLLM 0.29.0
- URL: https://raw.githubusercontent.com/vllm-project/vllm/main/vllm/v1/kv_cache_interface.py
- Evidence: READ BODY
- Detail: vLLM's `KVQuantMode` IntEnum enumerates the shipped modes with their scale granularity, verbatim: `INT8_PER_TOKEN_HEAD = 2  # per-token-head dynamic scales for int8`, `FP8_PER_TOKEN_HEAD = 3  # per-token-head dynamic scales for fp8`, `INT4_PER_TOKEN_HEAD = 4  # packed 2×int4/byte, RHT + asymmetric zp`, `NVFP4 = 5  # packed fp4 data + fp8 block scales`, and the four TurboQuant modes `TURBOQUANT_K8V4 = 6`, `TURBOQUANT_4BIT_NC = 7`, `TURBOQUANT_K3V4_NC = 8`, `TURBOQUANT_3BIT_NC = 9` documented as "Hadamard-rotated Lloyd-Max quant, packed K+V per slot." The runtime (not checkpoint) scale computation is logged from `vllm/config/cache.py`: "Dynamic per-token-head scales will be computed at runtime." The same file's non-per-token-head branch states the older caveat verbatim: "Meanwhile, it may cause accuracy drop without a proper scaling factor". This closes the per-token/per-channel-scale question for vLLM: KIVI-style asymmetry is now expressible without calibration.

### CLOSED-5: `--kv-cache-dtype-skip-layers` shipped — per-layer precision escape hatch
- URL: https://github.com/vllm-project/vllm/pull/33695
- Evidence: READ BODY
- Detail: Merged; the flag is also documented in the vLLM FP8 KV-cache blog, verbatim: "We added --kv-cache-dtype-skip-layers ( vllm#33695 ) to allow for hybrid settings." The blog states the rationale verbatim: "Models like GPT-OSS use some layers with sliding window attention, where tokens attend to a fixed window size, for example 128 tokens. Here FP8 overheads cannot be amortized. Therefore, keeping those layers in BF16 is actually faster than quantizing them... Furthermore, if some layers are particularly sensitive to quantization, this feature allows skipping those layers." It is present in vLLM 0.29.0 source (`vllm/config/cache.py: kv_cache_dtype_skip_layers: list[str] = field(default_factory=list)`) and documented at https://docs.vllm.ai/en/v0.28.0/features/quantization/quantized_kvcache/ as accepting "either layer indices or layer-type names".

### CLOSED-6: fp8_e5m2 KV cache unblocked for weight-only-quantised checkpoints
- URL: https://github.com/vllm-project/vllm/pull/45040
- Evidence: READ BODY
- Detail: Merged by yewentao256 Jun 18, 2026. Body verbatim: "_init_kv_cache_quant rejects --kv-cache-dtype fp8_e5m2 for every quantized checkpoint with \"fp8_e5m2 kv-cache is not supported with fp8 checkpoints\". But weight-only checkpoints (INT4/INT8 compressed-tensors, AWQ, GPTQ) carry no fp8 KV scales and are not fp8. On Ampere, where fp8_e5m2 is the only fp8 KV cache dtype that runs at all ( fp8_e4m3 is unsupported by the hardware), this makes fp8 KV cache unreachable for every weight-quantized model." This is the clearest shipped statement of the e4m3-vs-e5m2 hardware split: e5m2 is the Ampere-compatible format, e4m3 is not.

### CLOSED-7: KIVI — per-channel K, per-token V, tuning-free 2-bit KV cache
- URL: https://arxiv.org/abs/2402.02750
- Evidence: READ BODY
- Detail: The canonical answer to the per-channel/per-token scale question. Abstract verbatim: "Our findings indicate that the key cache should be quantized per-channel, i.e., group elements along the channel dimension and quantize them together. In contrast, the value cache should be quantized per-token. From this analysis, we developed a tuning-free 2bit KV cache quantization algorithm named KIVI." Also: "KIVI can enable Llama, Falcon, and Mistral models to maintain almost the same quality while using 2.6× less peak memory (including model weight)." Submission history shows v1 5 Feb 2024, v2 25 Jul 2024 (no 2025-2026 revision).

### CLOSED-8: KVQuant — per-channel key quant, pre-RoPE key quant, non-uniform datatypes, per-vector dense-and-sparse outliers
- URL: https://arxiv.org/abs/2401.18079
- Evidence: READ BODY
- Detail: The canonical reference for outlier handling in KV quantisation and the source of the "dense-and-sparse" idea. Abstract verbatim: "(i) Per-Channel Key Quantization, where we adjust the dimension along which we quantize the Key activations to better match the distribution; (ii) Pre-RoPE Key Quantization, where we quantize Key activations before the rotary positional embedding to mitigate its impact on quantization; (iii) Non-Uniform KV Cache Quantization, where we derive per-layer sensitivity-weighted non-uniform datatypes that better represent the distributions; and (iv) Per-Vector Dense-and-Sparse Quantization, where we isolate outliers separately for each vector to minimize skews in quantization ranges." Result verbatim: "we achieve < 0.1 perplexity degradation with 3-bit quantization on both Wikitext-2 and C4". Submission history runs to v6 on 28 May 2025.

### CLOSED-9: TurboQuant — data-oblivious rotation + per-coordinate Lloyd-Max quantiser, near-optimal distortion
- URL: https://arxiv.org/abs/2504.19874
- Evidence: READ BODY
- Detail: The theoretical paper underlying vLLM's shipped turboquant_* dtypes. Abstract verbatim: "TurboQuant achieves this by randomly rotating input vectors, inducing a concentrated Beta distribution on coordinates, and leveraging the near-independence property of distinct coordinates in high dimensions to simply apply optimal scalar quantizers per each coordinate." And: "Experimental results validate our theoretical findings, showing that for KV cache quantization, we achieve absolute quality neutrality with 3.5 bits per channel and marginal quality degradation with 2.5 bits per channel." The full HTML explains that the non-integer bit rates come from outlier splitting, verbatim: "These non-integer bit precisions result from our strategy of splitting channels into outlier and non-outlier sets, and applying two independent instances of TurboQuant to each, allocating higher bit precision to outliers." and "in our 2.5-bit setup, 32 outlier channels are quantized at 3 bits, while the remaining 96 channels use 2 bits, leading to an effective bit precision of ( 32 × 3 + 96 × 2 ) / 128 = 2.5". Note the paper's own setup is modest: "All experiments are performed using a single NVIDIA A100 GPU."

### CLOSED-10: KVarN — calibration-free variance-normalised KV quantiser that targets autoregressive error accumulation
- URL: https://arxiv.org/abs/2606.03458
- Evidence: READ BODY
- Detail: The most recent (Jun 2026) published answer to the "quantized-KV attention error" sub-question. Abstract verbatim: "KV-cache quantization can help improve this, but current methods are evaluated under prefill-like settings and errors behave differently under autoregressive decoding. We show that in the latter regime, quantization errors accumulate across timesteps, driven primarily by incorrect token scales. We introduce KVarN, a calibration-free KV-cache quantizer that applies a Hadamard rotation followed by a dual-scaling variance normalization across both axes of the K and V matrices." Claim verbatim: "KVarN establishes a new state-of-theart for KV-cache quantization on generative benchmarks, including MATH500, AIME24 and HumanEval, at 2-bit precision." A vLLM implementation is claimed available in the abstract.

### CLOSED-11: QAQ — keys and values have distinct quantisation sensitivity; dedicated outlier handling
- URL: https://arxiv.org/abs/2403.04643
- Evidence: READ BODY
- Detail: Abstract verbatim: "We theoretically demonstrate that key cache and value cache exhibit distinct sensitivities to quantization, leading to the formulation of separate quantization strategies for their non-uniform quantization. Through the integration of dedicated outlier handling, as well as an improved attention-aware approach, QAQ achieves up to 10x the compression ratio of the KV cache size with a neglectable impact on model performance." QAQ is notable for being absent from both engine trees (see OPEN-12).

### CLOSED-12: FP8 long-context accuracy collapse traced to Tensor-Core accumulation precision, and fixed (two-level accumulation)
- URL: https://vllm.ai/blog/2026-04-22-fp8-kvcache
- Evidence: READ BODY
- Detail: This is the strongest published entry on "quantized-KV attention error" as a *kernel numerics* problem rather than a storage-format problem. Verbatim: "Hopper's FP8 Tensor Cores are documented as accumulating into FP32 registers, but in practice the intermediate accumulation loses precision when the contraction dimension is large... When the contraction dimension reaches 100K or more, this imprecise accumulation causes drastic numerical errors. Concretely, in long context inference, during the Softmax(AttnScore) * V matmul, the contraction dimension corresponds to the context lengths. Empirically, we found that this can lead to accuracy regressions from 91% (BF16) to 13% (FP8) on a long-context needle-in-a-haystack task." The fix verbatim: "we added a two-level accumulation strategy (see SageAttention2 ) that writes the partially accumulated results into an actual FP32 register ( flash-attention#104 ), which brought the FP8 accuracy back to 89%." Residual cost verbatim: "On the downside, this two-level accumulation increases the register pressure and causes slowdowns during prefill... however, for head dimensions larger than 128, the prefill performance remains behind BF16."
