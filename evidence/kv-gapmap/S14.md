### CLOSED-1: vLLM prefix-cache hash algorithm selection (collision resistance)
- URL: https://docs.vllm.ai/en/latest/design/prefix_caching/
- Evidence: READ BODY
- Detail: The vLLM APC design doc now documents a selectable hash algorithm and states the historical collision weakness was removed. Verbatim from the retrieved page: "In previous versions, the hash key was not guaranteed to be collision-free. As of v0.11, the default hashing algorithm is `sha256`, which addresses collision risks." On `xxhash` the page warns verbatim: "IMPORTANT: Use of a hashing algorithm that is not considered cryptographically secure theoretically increases the risk of hash collisions, which can cause undefined behavior or even leak private information in multi-tenant environments." The doc also names `sha256_cbor` as "recommended for deterministic caching across environments". Confirmed in the local vLLM source tree: `vllm/config/cache.py:145` — "default, as SHA256 is the most secure choice to avoid potential hash collisions", and `tests/v1/engine/test_engine_args.py:34` asserts `vllm_config.cache_config.prefix_caching_hash_algo == "sha256"`.

### CLOSED-4: vLLM prefix-cache hit-rate counters and their design rationale
- URL: https://docs.vllm.ai/en/latest/design/metrics/
- Evidence: READ BODY
- Detail: The Metrics design doc lists verbatim: "`vllm:prefix_cache_queries` (Counter) - Number of prefix cache queries." and "`vllm:prefix_cache_hits` (Counter) - Number of prefix cache hits." ### CLOSED-9: SGLang deterministic inference and its radix-cache compatibility matrix

- Evidence: READ BODY
- Detail: Documents `--enable-deterministic-inference` (flag; default: disabled). The page states the root cause verbatim: "The main source is varying batch sizes. ### CLOSED-14: Eviction error certificates via randomized eviction design

### CLOSED-17: SSD-resident KV without the kernel filesystem

- Evidence: READ BODY
- Detail: Title "Unified KV Pooling to Accelerate Long-Context LLM Serving", submitted 2026-06-10.
