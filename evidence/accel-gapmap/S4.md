# S4 — Batching & scheduling (single-GPU, vLLM 0.29.0 / SGLang 0.5.19)

Target rig: RTX PRO 6000 Blackwell, 96 GB, sm120, single GPU, no NVLink/IB; vLLM 0.29.0; SGLang 0.5.19; Qwen3-4B dense full-attention.
Scope: continuous batching, chunked prefill, `max_num_batched_tokens`, scheduling policy/priority,
preemption mode (scheduling aspects), prefill–decode interference, CPU-side/host-bound scheduling
overhead, batch-level tuning observability. NOT KV-cache policy, NOT speculative decoding.

All quotes below are verbatim from the retrieved page/file named in `URL:`. Where a quote is taken
from a raw-markdown file, the source's own inline code backticks are preserved inside the quotation
marks. Nothing inside quotation marks has been edited.

QUOTE: "In V1, **chunked prefill is enabled by default whenever possible**. With chunked prefill enabled, the scheduling policy prioritizes decode requests. ### A.4.10 | CLOSED

Separately, the successor design (#53277, still open) narrowed the target to cache-warm continuation under long-context contention.

### C.4.6 | ABANDONED   (vLLM "only schedule prefill chunks when the entire context fits" — PR closed unmerged; the idea later shipped by another route)
WHO: jmkuebler (PR author); vLLM maintainers closed PR #21809 unmerged
ARTIFACT: vLLM PR #21809 "[Bugfix] Scheduler: only schedule prefill chunks when entire context fits" (state token `CLOSED`; not merged)
URL: https://github.com/vllm-project/vllm/pull/21809
STATED REASON (verbatim from the PR body): "I observed that v1 behaves weirdly when preempting long context requests when prefix caching is disabled and chunked prefill is enabled, see #18115 . SECOND QUOTE (same body, verbatim, the generalised rule): "More generally, unless we do prefix caching, we should not schedule prefill chunks unless the full context will be able to fit. EVIDENCE: READ BODY
S3B: SOLVED (shipped in v0.29.0 by a different route — the `scheduler_reserve_full_isl` config field, whose v0.29.0 docstring is verbatim: "If True, the scheduler checks whether the full input sequence length fits in the KV cache before admitting a new request, rather than only checking the first chunk. Prevents over-admission and KV cache thrashing with chunked prefill." It defaults to `True`. Query used: `is:issue "cache affinity scheduler"` and the v0.29.0 source read of `vllm/config/scheduler.py`, which was searched independently of PR #21809's own citations.)
REASON-MAY-HAVE-EXPIRED: The reason has expired. PR #21809 was written against a V1 scheduler that admitted a chunk without checking whether the request's whole context would fit; vLLM v0.29.0 ships exactly that check as `scheduler_reserve_full_isl: bool = True`, default on. The thrash cycle described in the PR body is guarded against by default in the rig's version.
