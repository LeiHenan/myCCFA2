# S2 — Compilation & CUDA graphs (vLLM 0.29.0 / SGLang 0.5.19 on sm120)

Researcher: S2. Scope: `torch.compile` / TorchInductor, `CompilationConfig`, compile cache,
`cudagraph_mode` / `CUDAGraphMode`, piecewise-vs-full graphs, attention-backend CG gating,
capture sizes, SGLang per-phase CUDA-graph backends, sm120/Blackwell compile/graph behaviour,
and measurement/observability gaps. KV-cache management and speculative decoding are **not** row
subjects (cited only as adjacent context where the trigger lives there).

Rig: 1× RTX PRO 6000 Blackwell 96 GB, sm120, driver 580, 208 CPU cores, no NVLink/IB/cluster;
vLLM 0.29.0, SGLang 0.5.19; Qwen3-4B dense (full attention, not MoE/Mamba/MLA).

Section C (ATTEMPTED-AND-ABANDONED) is the highest-value section per the scope update; every C
row carries `REASON-MAY-HAVE-EXPIRED:` where the stated reason is tied to a changed constraint.
Every B and C row carries an `S3B:` occupancy verdict derived from searches run independently of
the row's own citations.

URL: https://raw.githubusercontent.com/vllm-project/vllm/v0.29.0/docs/design/cuda_graphs.md

### C.1 | ABANDONED  (piecewise CUDA graphs for DeepEP high-throughput + DP)
WHO: yewentao256 (author) and ProExpertProg (maintainer) on vllm-project/vllm; later re-attempted by yewentao256 and re-reverted by LucasWilkinson
ARTIFACT: PR #25093 "[Bug] Fix torch Compilation Cache Hit Error" (merged), PR #29558 "[Perf] Enable cuda graph for deepepHT, 5.3% throughput improvement, 4.4% TTFT improvement" (merged), PR #30910 "[BugFix] Partial revert of #29558 (DeepEP HT + PIECEWISE CG support)" (merged)
URL: https://github.com/vllm-project/vllm/pull/25093 ; https://github.com/vllm-project/vllm/pull/29558 ; https://github.com/vllm-project/vllm/pull/30910
STATED REASON: "The root cause of this issue is from (runtime_shape, graph_index, backend_name) is not a strong enough cache key for compiled cuda graph. And in complicated situation like DeepEP HT, we split the piecewise graph moe_forward and moe_forward_shared and make the wrong cache hit. I am not sure if it is a good idea to refactor the cache key system throughly just for the support of piecewise graph for HT (Perhaps not worth enough), so simply cancel the support for HT graph now. If we encounter other scenarios where the cache key proves insufficient, we should revisit and redesign the cache system."
SECOND REASON (revert of the re-enable, by LucasWilkinson): "Partially revert #29558 as this broke H200 tests"
THIRD REASON (maintainer alternative offered in review, by ProExpertProg): "This seems fine, but if we want more performance we could also just disable inductor compile caching (increases startup time but would give the best performance)."
EVIDENCE: READ BODY
REASON-MAY-HAVE-EXPIRED: YES — the reason is bound to (a) the `(runtime_shape, graph_index, backend_name)` cache-key design as it existed in 2025 and (b) `deepep_high_throughput` with `data_parallel_size > 1`, which the target rig (1 GPU) cannot exercise at all. The cache-key mechanism has since been re-partitioned (`use_inductor_graph_partition`) and the code comment marking the debt is still present in main.
S3B: OCCUPIED (open PR #55319 "[Bugfix][DeepEP] Synchronize EP ranks before CUDA graph capture" — adjacent EP/capture work; the re-enable itself is reverts-on-reverts, not a live PR)
