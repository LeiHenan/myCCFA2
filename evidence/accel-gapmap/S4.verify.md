### The two known-thin claims called out for attack — both CONFIRMED verbatim

**1. `max_num_batched_tokens` defaults to 8192 for a 96 GB card (OpenAI-server usage context).**
The quoted ladder re-locates as one continuous run (`verify.py quote` → `MATCH`, ratio 1.0) at
`raw.githubusercontent.com/vllm-project/vllm/v0.29.0/vllm/engine/arg_utils.py`:

> `elif device_memory >= 70 * GiB_bytes and "a100" not in device_name:` … `UsageContext.LLM_CLASS: 16384,` / `UsageContext.OPENAI_API_SERVER: 8192,`

A 96 GB RTX PRO 6000 Blackwell satisfies `device_memory >= 70 GiB` and its device name contains no
`a100`, so it lands in exactly that branch; `vllm serve` uses `UsageContext.OPENAI_API_SERVER`. I also
read the neighbouring branches to rule out a later override: the `>= 160 GiB` branch (B200/B300 only),
the final `else` (8192 / 2048), and the TPU special-cases are the complete set — there is no
Blackwell/sm120-specific adjustment anywhere else in the file. **The default really is 8192 here.**

**2. The docs recommend `> 8192`.**
`raw.githubusercontent.com/vllm-project/vllm/v0.29.0/docs/configuration/optimization.md`,
§"Performance Tuning with Chunked Prefill" (`MATCH`, ratio 1.0), all three bullets quoted exactly:

> `- Smaller values (e.g., 2048) achieve better ITL because there are fewer prefills slowing down decodes.`
> `- Higher values achieve better time to first token (TTFT) as you can process more prefill tokens in a batch.`
> `- For optimal throughput, we recommend setting \`max_num_batched_tokens > 8192\` especially for smaller models on large GPUs.`

Both sides are exact. The row's inference — a ≥70 GiB non-A100 card under the OpenAI server context
defaults to a value **one token below** the documented throughput recommendation — is arithmetically
correct and is not overstated anywhere in A.4.2/A.4.4.
