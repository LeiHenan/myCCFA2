### 🐛 Describe the bug

Two ModelOpt-produced NVFP4 conversions of GLM-5.3-Flash emit **invalid UTF-8 byte-token
sequences** during generation on SM120. A compressed-tensors NVFP4 conversion of the *same*
model, served from the same image with the same kernel, KV layout, parallelism and sampling
settings, is clean. Only the checkpoint changes between these rows.

The failure is quiet: the server returns HTTP 200, throughput looks normal, English text is
mostly fine, and short prompts read correctly. It shows up as U+FFFD inside multi-byte
(here: Korean) text, which is easy to mistake for a rendering or client problem.

#### Result

Six generations per row — 3 at `temperature=0.0`, 3 at `0.7`, identical Korean prompt,
`max_tokens=4096`. The count is U+FFFD characters across `content` + `reasoning`.

| checkpoint | quant format | U+FFFD / 6 runs | degenerate loops |
|---|---|---:|---:|
| `LibertAIDAI/GLM-5.3-Flash-NVFP4` | modelopt NVFP4 | **86** | 0/6 |
| `LibertAIDAI/...` @ rev `cf5434c00b` (43-entry ignore list) | modelopt NVFP4 | **62** | 1/6 |
| `dealignai/GLM-5.3-Flash-UNCENSORED-NVFP4` | modelopt NVFP4 | **94** | 0/6 |
| `RedHatAI/GLM-5.3-Flash-NVFP4` | compressed-tensors NVFP4 | **0** | 0/6 |

Sample from a `temperature=0` generation on the LibertAI checkpoint — `퍼셉트론`
(“perceptron”) loses its middle syllable:

```
프랭크 로젠블랫(Frank Rosenblatt)의 퍼<?>트론(Perceptron, 1957)
```

#### This is not a detokenizer artifact

Requesting `return_token_ids: true` and decoding the returned ids offline with the
checkpoint's own tokenizer reproduces the same U+FFFD count as the API text (5 and 5 on the
sampled request), so the emitted token ids themselves do not form valid UTF-8. Byte-token
continuations are near-deterministic, so producing an invalid continuation under greedy
decoding points at the logits rather than at decoding.

#### Ruled out

Each of these was varied independently with everything else held fixed:

- **Context length** — a Korean prompt answered correctly at 62, 25 772, 103 040, 412 112 and
  1 030 162 prompt tokens, with both Korean and English filler. Corruption appears at
  **zero context** too, so it is not the sparse-MLA/long-context path.
- **Sampling** — present at `temperature=0.0`.
- **MTP** — `num_speculative_tokens` 5 and 0 behave the same.
- **PDL** — patching `CudaPlatformBase.is_arch_support_pdl` to exclude SM12x changes nothing.
- **Abliteration** — the guardrail-removed `dealignai` build and its un-abliterated
  `LibertAIDAI` sibling score the same (94 vs 86).
- **`quantization_config.ignore` completeness** — our LibertAI copy predated commit
  `cf5434c00b`, which grew the ignore list from 32 to 43 entries (fused attention
  projections, `q/k/v/qkv_conv1d`, `o_norm`, `visual.*`). Updating `config.json` to that
  revision — weights untouched — left corruption in place (86 → 62, within the run-to-run
  spread of 7–22 per generation).

#### Open question

The two checkpoint families differ in **loader path**, not only in file format: modelopt vs
compressed-tensors. So this data cannot distinguish

- (A) the two ModelOpt conversions carry damaged weights, from
- (B) vLLM's ModelOpt NVFP4 path is wrong here while the compressed-tensors NVFP4 path is
  correct.

If (B), every ModelOpt NVFP4 checkpoint is affected, not just this model. Someone able to
compare the two loaders' dequantized weights for the same tensor would settle it quickly;
we do not have a reference to diff against.

#### Side observation: NvFp4 MoE backend availability on SM120

While isolating the above, with the checkpoint held fixed:

| `moe_backend` | result on SM120 |
|---|---|
| `flashinfer_trtllm` | rejected — `kernel does not support current device cuda` |
| `flashinfer_cutedsl` | rejected — same |
| `flashinfer_cutlass` | **6/6 runs collapse into a repeated single token** (`locklocklock…`) |
| `cutlass` (VLLM_CUTLASS) | **6/6 collapse**, no `content` produced at all |
| `emulation` | collapses — 49 129 chars of `</arg_value>` repeats, 0 % Hangul |
| `marlin` | the only usable path |

The two CUTLASS failures line up with sgl-project/sglang#18954 (“NVFP4 models produce NaN
outputs on RTX PRO 6000 Blackwell (SM120)”), which was closed on the FlashInfer side; this is
the same symptom reached through vLLM, and it reproduces on vLLM's own CUTLASS path as well.
That `emulation` also collapses is the part we cannot explain — a dequantizing reference path
should be the safe fallback.

Swapping `/model` to `RedHatAI/GLM-5.3-Flash-NVFP4` with everything else identical returns 0.

--- COMMENT 4 ---
**Root cause found, with numeric proof and a validated fix — answering the open question above: it is (B), vLLM's ModelOpt NVFP4 path.** Reproduced and root-caused on 2× GB10 DGX Spark (SM121), image `radixark/vllm-glm53-flash:sm121-v8`, same vLLM commit `0.1.dev20051+g487ecf187`. Independent of the reporter's SM120 setup.

## Root cause: single-gscale assumption in the NVFP4 fused-MoE marlin repack

`vllm/model_executor/layers/quantization/modelopt.py`,
`ModelOptNvFP4FusedMoE.process_weights_after_loading` (~line 1527):

```python
w13_weight_scale_2 = layer.w13_weight_scale_2[:, 0]
```

The fused `[gate; up]` marlin GEMM gets **one** global scale — gate's (w1). A
`warning_once` fires when the scales differ ("w1_weight_scale_2 must match
w3_weight_scale_2. Accuracy may be affected."), but the repack proceeds, and the
up (w3) half is dequantized with gate's global scale. The up-proj output is then
systematically mis-scaled by `ws2_gate / ws2_up` per expert.

This is exact only when gate and up share one global scale. Whether they do is a
property of the **checkpoint**, not the code:

| checkpoint | producer | gate/up expert pairs | pairs with gate scale == up scale |
|---|---|---|---|
| Murai-P3 (ours) | ModelOpt 0.45.0, per-tensor amax, W4A16 | 12,384 (43 layers incl. MTP 45) | **30.9%** — mismatch on 69.1%; ratio max/min mean 1.1454, median 1.077, p90 1.286, max 10.0 |
| RedHatAI/GLM-5.3-Flash-NVFP4 | llm-compressor (compressed-tensors, W4A4, group-16) | 12,096 (42 layers, no MTP) | **100.0%** — shared by construction |

(Measured with a plain-python safetensors header reader over the checkpoints;
no GPU involved.)

So: **any ModelOpt NVFP4 checkpoint quantized with separate gate/up projections
and per-tensor amax scaling hits this** — including the LibertAI checkpoint and
ours. Compressed-tensors checkpoints that fuse the scale are immune. Note the
compressed-tensors NVFP4 MoE scheme (`compressed_tensors_moe_w4a4_nvfp4.py`,
lines ~203–210) has the same `[:, 0]` single-gscale pattern — it just happens to
be exact for checkpoints llm-compressor produces.

## Numeric proof (local, BF16 master + ModelOpt dequant, no serving)

Layer 10, expert 0 (gate/up scale ratio 1.23), up-proj round-trip rel_l2:

- correct dequant: **0.0929**
- single-gscale repack: **0.2549**
- single-gscale + compensation (below): **0.0929** (restored exactly)

Controls: expert 2 (ratio 0.93): 0.1124 → 0.0924 compensated; expert 1
(ratio 1.0): unaffected, as expected.

## Runtime proof (serving, same checkpoint, only repack numerics changed)

Probe: temp 0, non-streaming, 3 passes each of a Korean tool-call prompt and an
English code+JSON prompt, counting U+FFFD (probe method from the reporter of
this issue; corruption is silent server-side — nothing in the logs).

| | unpatched | patched |
|---|---|---|
| Korean ×3 | 1 / 3 / 4 | 0 / 0 / 0 |
| English ×3 | 0 / 0 / 0 | 0 / 0 / 0 |
| **total** | **8 / 6 passes** | **0 / 6 passes** |

Post-fix outputs verified non-vacuous (1,331 chars of structured Korean, 0
U+FFFD). A behavioral spot-check battery on the patched build was
behavior-neutral (within temp-1.0 sampling noise). A larger battery then ran
46 passes / ~90k tokens on the patched build — the original Korean and
English probes at 10 passes each, eight additional script families
(Japanese, Chinese, Tamil, Arabic, Russian, Hindi, emoji-heavy,
code-switching) at 3 passes each, and two 8,000-token Korean long-form
generations: **0 U+FFFD events, 0 lone surrogates, 0 control characters, 0
repetition loops — clean across the board.**

## The fix (~20 lines, validated as a runtime bind-mount, no image rebuild)

Before the repack, rescale the up half's FP8 block scales by
`ws2_up / ws2_gate`, clamped to the FP8-E4M3 max (448):

```python
if self.moe.is_act_and_mul:
    ratio = layer.w13_weight_scale_2[:, 1].float() / layer.w13_weight_scale_2[:, 0].float()
    ratio = ratio.view(-1, *([1] * (layer.w13_weight_scale.dim() - 1)))  # (E,1,..,1) broadcast
    nh = layer.w13_weight_scale.shape[1] // 2                            # TP-sharded fused dim
    s = layer.w13_weight_scale.float()
    s[:, nh:] = (s[:, nh:] * ratio).clamp(max=448.0)
    layer.w13_weight_scale = torch.nn.Parameter(s.to(torch.float8_e4m3fn), requires_grad=False)
w13_weight_scale_2 = layer.w13_weight_scale_2[:, 0].contiguous()  # unchanged line
```

Boot-time stats on our checkpoint: ratio mean ~1.0 / max 2.0 per layer, FP8
clamps ≈ 0.03% of up-half scales (negligible). The pre-existing warning still
fires once — the check is upstream of the compensation; cosmetic.

Two implementation notes if this becomes a PR: (1) `w13_weight_scale` is 3-D
`(E, 2·intermediate/tp, blocks)` per rank under TP — the half-split and the
broadcast must be rank-aware (our v1 failed on exactly this); (2) an alternative
is requantizing both halves to `max(ws2_gate, ws2_up)`, mirroring
`process_fp8_weight_tensor_strategy_moe` — we did not test that variant.

## Affected lineage

All separate-gate/up ModelOpt NVFP4 MoE checkpoints whose gate/up per-tensor
amax global scales differ. Confirmed on two independent GLM-5.3-Flash NVFP4
checkpoints (ours and, per this issue's reporter, the LibertAI one); the
reporter's control (compressed-tensors, RedHatAI) showed 0/0/0, which we
independently replicated (0/6 on the same probe, same stack). This is not
GB10-specific in mechanism — the mis-scaling happens at repack, before any
kernel runs — but Blackwell marlin NVFP4 MoE is where this code path executes.
