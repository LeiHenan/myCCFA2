### 🐛 Describe the bug

**Symptom.** Under sustained load the EngineCore dies with `torch.AcceleratorError: CUDA error: an illegal memory access was encountered` (raised from `vllm/v1/worker/gpu/async_utils.py:168` in `get_output` → `self.copy_event.synchronize()`, i.e. the asynchronous error surfaces at the next sync). At the same second the kernel log shows an **Xid 13**:

```
NVRM: Xid (PCI:0000:11:00): 13, Graphics SM Warp Exception on (GPC 0, TPC 0, SM 0): Out Of Range Address
NVRM: Xid (PCI:0000:11:00): 13, Graphics SM Global Exception on (GPC 0, TPC 0, SM 0): Multiple Warp Errors
NVRM: Xid (PCI:0000:11:00): 13, Graphics Exception: ESR 0x505730=0xf05000e 0x505734=0x4 0x505728=0x1c81fb60 0x50572c=0x1174
```

Every event produces exactly 289 kernel lines, always starting at GPC 0 / TPC 0 / SM 0 and spreading over all GPCs, and always with the **same ESR values** (`0x505728=0x1c81fb60 0x50572c=0x1174`) — regardless of the attention backend (see experiments). `nvidia-smi -q -d ROW_REMAPPER` shows 0 correctable / 0 uncorrectable errors; the GPU is otherwise healthy. The container exits (`terminate called after throwing an instance of 'c10::AcceleratorError'`), Docker restarts it, and it serves again after ~25 s.

**Frequency.** 4 events in roughly 2,500 chat completions over two days, all under load, none when idle:

**Workload.** A RAG service (own .NET client against `/v1/chat/completions`): 2–3 completions per user question, tools with `tool_choice=auto` (Mistral tool parser → structured outputs, backend `guidance`, the grammar is visible in the dump's `SamplingParams`), prompts 10k–29k tokens, `temperature=0.0`, `seed=42`, `max_tokens=2048`. The intersection is **`FlashInferFP8ScaledMMLinearKernel` inside piecewise CUDA graphs on SM120**, for small mixed batches (≈400–480 new tokens after a large prefix-cache hit, padded to a capture size). On this GPU vLLM picks `FlashInferFP8ScaledMMLinearKernel` ahead of CUTLASS (`_POSSIBLE_FP8_KERNELS` order: Marlin, FlashInfer, CUTLASS, B12x, Torch); the v0.28.0 release notes mention new B12X dense linear backends for this architecture (#52016), so the FP8 GEMM path on SM120 is fresh territory in this release.

Things ruled out: the torch.compile cache (deleted between event 1 and events 2–4), the attention backend, GPU memory errors (row remapper clean), thermal/power (card at its 300 W power cap, 89–90 °C, no thermal slowdown). The first event happened on 2026-09-04 after ~14 days of uptime without any Xid; all four events are under sustained load only.

**Expected behaviour.** No illegal memory access; the FlashInfer FP8 scaled-MM kernel should behave like CUTLASS inside CUDA graph replay.

**Related.** This looks like the mechanism described in #52553 / flashinfer-ai/flashinfer#4553 (the shared cuDNN GEMM workspace in FlashInfer is moved with `resize_()` when a plan asks for more than 32 MiB; graphs captured earlier keep the old address, so every later replay is a use-after-free — the PR author mentions an FP8 plan asking for 256 bytes more than the default). #52540 (ModelOpt NVFP4 on RTX PRO 6000) and #52225 (Xid 13 on SM120 under multi-hour load) report the same symptom with NVFP4 checkpoints; this report is an FP8 checkpoint on an RTX PRO 5000 where the FP8 scaled-MM kernel alone makes the difference, so it may serve as an independent confirmation from a different quantization path. I did not find an FP8 report for `FlashInferFP8ScaledMMLinearKernel` yet, hence the separate issue — happy to have it merged if it is a duplicate.

**Workaround** we run now: `VLLM_DISABLED_KERNELS=FlashInferFP8ScaledMMLinearKernel` (CUTLASS is ~10 % slower in single-stream latency, no measurable difference under concurrency). `--enforce-eager` also works but costs ~20 % under load and ~50 % single-stream.

At your versions, the path you isolated can hit the #52553 / flashinfer#4553 workspace bug, but only if the captured runner is cuDNN. This is from reading the source, not from a reproduction.

In v0.28.0, `FlashInferFP8ScaledMMLinearKernel.apply_scaled_mm` -> `vllm.utils.flashinfer.flashinfer_scaled_fp8_mm` -> `flashinfer.bmm_fp8(..., backend="auto")`. In flashinfer 0.6.16.post3, `bmm_fp8` with `auto` builds its runner list from `_heuristic_func_bmm_fp8`, which on SM120 is `[cutlass_sm12x, cublas, cudnn]` (cuDNN only if `import cudnn` succeeds), allocates the shared `bmm_fp8_workspace` (32 MiB via `_get_cache_buf`) and calls `fp8_gemm_sm100` -> `tuner.choose_one("fp8_gemm", ...)`. Only the cuDNN runner (`CudnnFp8GemmRunner` -> `execute_cudnn_gemm_fp8_graph`) grows that workspace with `workspace.resize_()` when a plan wants more than it has; the CUTLASS and cuBLAS runners never resize it. The resize happens on a non-captured execution, and every graph captured earlier keeps the old pointer, which is the #4553 use-after-free.

Without tuning data the autotuner returns `runners[0]`, i.e. CUTLASS sm12x, and cuDNN is never touched. But vLLM's kernel warmup runs FlashInfer autotune on any GPU with capability >= 9.0 (`kernel_warmup.py`: `has_device_capability(90)`), SM120 included, unless `enable_flashinfer_autotune` is explicitly False. It does one dummy run at `max_num_batched_tokens` (8192 in your config) and the tuner generates a profile per token bucket up to it; your 405 to 482 new-token prefills map to the 512 bucket (`map_to_hybrid_bucket_uncapped`, 256-token steps above 256), so those shapes hit tuned entries. If cuDNN won `fp8_gemm` for that bucket, your captured graphs replay the cuDNN runner and the first plan that needs a larger workspace moves it under them. Eager passing doesn't narrow it; any graph-lifetime bug does that. CUTLASS passing with graphs on does.

Two things you can check without a long soak:

1. `--no-enable-flashinfer-autotune` keeps `FlashInferFP8ScaledMMLinearKernel` but forces FlashInfer's fallback runner (CUTLASS sm12x) inside `bmm_fp8`, and skips loading any autotune cache. If the Xid stops, that points at the cuDNN runner; the cache file below shows whether it was picked at all. `VLLM_FLASHINFER_AUTOTUNE_SKIP_OPS=fp8_gemm` is weaker: it skips tuning that op, but a cache file persisted from an earlier run is still loaded, so point `VLLM_FLASHINFER_AUTOTUNE_CACHE_DIR` at an empty directory if you use it.
2. vLLM logs `Using FlashInfer autotune cache file: <path>` at startup. The keys look like `('fp8_gemm', 'CudnnFp8GemmRunner', ...)`; that runner name in there means the cuDNN runner was live.

A patched wheel from flashinfer#4553 would test whether the workspace-resize fix alone prevents the crash. Both #4553 and vLLM #52553 are open and unmerged as of today, and `flashinfer/gemm/gemm_base.py` at v0.6.18.post1 (the newest release; vLLM main's Dockerfile pins 0.6.18) still has the `resize_()` sites. So upgrading FlashInfer alone won't help.

--- COMMENT 4 ---
We encountered this exact same failure mode (`Xid 13: Out Of Range Address` on SM 0, surfacing asynchronously at `copy_event.synchronize()` / `torch.cuda.synchronize()` regardless of attention backend) on an RTX 4090 under vLLM v1.

In our case, we isolated the root cause to an out-of-bounds gather in the v1 sampling pipeline:
1. In `vllm/v1/worker/gpu/sample/prompt_logprob.py` (`_prompt_logprobs_token_ids_kernel`), `target_pos = num_computed_tokens + 1 + block` attempts to read index $L$ on prompt prefill of length $L$.
2. This loads uninitialized memory / garbage values into `token_ids`.
3. Downstream `torch.gather` or Triton kernels attempt to gather using those invalid token IDs, triggering the CUDA MMU `Xid 13` fault which then halts the stream and surfaces at the next synchronization event.

**Question for the OP:** Does your sustained load workload issue requests with `logprobs` or `prompt_logprobs`?
- If yes: Defensive clamping of token IDs (`clamped_ids = logprob_token_ids.clamp(0, vocab_size - 1)`) and fixing the boundary condition in `_prompt_logprobs_token_ids_kernel` immediately resolved this.
- If no: It strongly suggests a sibling out-of-bounds indexing vulnerability in v1's KV block table mapping or dynamic batch queueing.
