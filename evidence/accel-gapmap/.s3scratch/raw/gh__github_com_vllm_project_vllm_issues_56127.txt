TITLE: RFC: per-M, per-shape kernel dispatch for blockwise-FP8 linear layers (W8A16 at decode, FP8xFP8 at prefill) · Issue #56127 · vllm-project/vllm · GitHub
CREATED_AT: 2026-09-09T17:56:38Z | 2026-09-09T19:17:24Z | 2026-09-09T19:17:33Z
STATE_REASON: COMPLETED

--- COMMENT 1 ---
> **Scope caveat.** All measurements below come from a **single machine**: 4× RTX PRO 6000 Blackwell Server Edition (GB202, sm_120), PCIe peer-to-peer, **no NVLink**, driver 580.126.09, CUDA 13.0, vLLM `0.28.1rc1.dev500+g51da0ca66`, model Qwen3.6-27B-FP8 at TP=4. The *enablement* work is general; the *conclusions about where a change pays* are specific to a latency-bound interconnect and should be re-measured on NVLink before being trusted there. Numbers were produced by a harness that enforces CUDA-graph-captured timing, two working-set regimes (this GPU has 134 MB of L2), clearing both the vLLM and torch-inductor caches between A/B configs, node-level trace assertions for any wiring claim, and an output-equivalence gate.

**Status: draft, not filed.** Measured on 4× RTX PRO 6000 Blackwell (GB202, sm120, PCIe).

## The claim

At decode batch sizes a blockwise-FP8 GEMM is **pure weight streaming**: it reads N×K weight
bytes regardless of how many tokens it serves, and the activation traffic (T×K) is two orders
of magnitude smaller. MMA throughput is therefore irrelevant there, so quantising activations
to FP8 buys nothing and costs a launch plus ~7× the numerical error. At prefill sizes the
tensor cores do bind and FP8×FP8 is the right kernel.

So the choice is a **regime** choice, and the regime boundary is per shape.

## Evidence

DRAM-resident (≥3× L2 rotating working set — the model's actual condition, since each weight
is touched once per step against ~6.75 GB/rank). Ratio is W8A16 ÷ (FP8×FP8 + activation quant):

| shape (per rank, TP=4) | T=1 | T=4 | T=32 | T=64 | T=128 |
|---|---|---|---|---|---|
| `in_proj_z` 1536×5120 | **1.21×** | **1.22×** | 1.05× | 0.73× | 1.21× |
| `in_proj_qkv` 2560×5120 | 1.12× | 1.13× | 1.01× | 0.78× | 1.07× |
| `linear_attn.out_proj` 5120×1536 | 1.08× | 1.09× | 1.00× | 0.83× | 0.66× |
| `gate_up` 8704×5120 | 1.04× | 1.05× | 1.02× | 0.94× | 0.67× |
| `down_proj` 5120×4352 | 1.04× | 1.04× | 0.98× | 0.85× | 0.74× |
| **T=256 / T=1024** (down_proj) | — | — | — | — | 0.58× / **0.54×** |

Accuracy is the unambiguous part: **2.3e-03…4.5e-03 vs 2.3e-02…3.4e-02** against an fp32
reference, ~7× better, because activations never leave bf16.

End-to-end, decode isolated, equivalence PASS at every point:

| batch | FP8×FP8 | W8A16 | delta |
|---|---|---|---|
| 1 | 112.0 | **117.9** | **+5.3%** |
| 8 | 654.0 | **700.6** | **+7.1%** |
| 32 | 1983.5 | 2014.3 | +1.6% (noise) |
| 128 | 4144.3 | 3878.3 | **−6.4%** |

And W8A16 removes the activation-quant stage outright: **234 standalone quant kernel launches
per step → 0** (`per_token_group_quant_8bit` 127.4/step, `silu_and_mul_per_block_quant` 42.5,
three others), confirmed by node-level trace assertion.

## What this asks for

`linear_backend` is currently selected once, globally. The proposal is to let a layer hold both
prepared weights and pick per call by M, with the threshold **per shape** rather than one
global constant — `down_proj` turns over by T=32 while `in_proj_z` is still winning 1.05×
there.

The honest cost: no FP8-weight kernel in vLLM streams with bf16 activations from the CUTLASS
layout. Marlin needs `gptq_marlin_repack`; Machete needs `machete_prepack_B`; `torch._scaled_mm`
rejects bf16×fp8 outright. So per-M dispatch means **both formats resident**, and since the
Marlin repack is int32 and the same size as the fp8 original, that is **≈ +6.75 GB/rank** at
TP=4 for this model — real KV-cache budget. A kernel that streams FP8 weights against bf16
activations *without* a repack would remove that cost entirely and is the more valuable change.

## GB202 note

Two things specific to this part that are worth recording for anyone tuning sm120:

1. **The N tile is pinned by the quantisation block size.** CUTLASS asserts
   `Scale Granularity M must evenly divide the tile shape M`, and in the sm120 `swap_ab` decode
   path the tile's M dimension *is* the original N, with `ScaleGranularityM = 128` because the
   weight's block scales are 128 wide. So `ceil(N/128)` CTAs is implied by
   `weight_block_size=[128,128]`, not chosen — a 64-wide N tile will not compile. Adding CTAs
   via a stream-K/split-K scheduler instead measures **0.80–0.93×** the default scheduler at
   DRAM-resident working sets.

2. **Measurement traps that produce wrong tuning decisions on this SKU.** L2 is 134 MB, so a
   benchmark looping over one 22–45 MB weight is L2-fed and can read *above* the 1792 GB/s DRAM
   peak — that regime reports W8A16 at 1.81× where the DRAM-resident number is 1.04×. And
   per-call timing charges CPU dispatch to the kernel (23.94 µs vs 14.45 µs back-to-back for
   the same GEMM), which also makes two GEMMs on two streams look like they serialise when
   under CUDA graphs they overlap. Byte-weighted, these GEMMs run at 1000 GB/s in microbench
   and 1125 GB/s in-model — 56% and 63% of peak — so the remaining headroom is ~1.6×, not the
   2–3× the narrow shapes alone suggest.

---

### Corrections history

This work published several wrong numbers before the harness caught them. They are listed
because they change how the remaining numbers should be read, and because two of them are
traps specific to this GPU that anyone repeating the measurements will hit.

| claim | corrected to | cause |
|---|---|---|
| W8A16 is 1.81× at T=1 | **1.04–1.22×** DRAM-resident | 1.81× was L2-fed; this GPU has 134 MB of L2, so a loop over one 22–45 MB weight reads above the 1792 GB/s DRAM peak |
| GEMM launches serialise, so split-K is dead | GEMMs **overlap** under CUDA graphs | per-call timing charges CPU dispatch to the kernel (23.94 µs vs 14.45 back-to-back) |
| micro-batching costs +18–28 µs/GEMM | **+1.2–3.9 µs** | measured eager, and never measured the shared-weight L2 case that the second micro-batch actually sees |
| 381 standalone quant launches/step | **234** | trace window included prefill |
| GEMMs run at 27–48% of roofline | **56–63%** byte-weighted | the 27–48% shapes carry 18% of the bytes |
| the 256 KB two-shot threshold is too high | it is **2.5× too low** (crossover 640 KB) | fitted `comm(T) = F + B·T` rather than assumed |
| stream priority gives ~0 protection | **1.83×** with a real prefill background | the original probe used a wall-clock spin kernel, which measures queuing, not contention |

Two further results are negative and worth stating so others do not repeat them: collapsing the
second barrier of a two-shot into per-peer flag waits changes F by 0.7% (the cost is PCIe flag
propagation, not wait-for-slowest), and a grid-wide doorbell that cuts F by 30% in isolation
measures **−24.7% end-to-end**, because a grid-wide flag is a full grid barrier and waits for
the slowest-*scheduled* block once other work is resident.
