TITLE: [Bug] --moe-runner-backend deep_gemm accepted for DSV4.1 MXFP4 experts, then fails in CUDA graph capture (layout.hpp:108, sm_121) · Issue #39226 · sgl-project/sglang · GitHub
CREATED_AT: 2026-09-12T17:00:08Z

--- COMMENT 1 ---
## Describe the bug

`--moe-runner-backend deep_gemm` is an accepted value, passes argument validation, loads 75 GB of weights for four minutes, and only then fails — during CUDA graph capture — on a DeepGEMM scale-layout assertion. On a 4× DGX Spark (GB10, **sm_121**, TP4/EP2) serving DeepSeek-V4.1-Flash, whose routed experts are **MXFP4**:

```
File "sglang/srt/layers/moe/moe_runner/deep_gemm.py", line 368, in _run_contiguous_gemm
    deep_gemm_wrapper.grouped_gemm_nt_f8f8bf16_contig(
File "sglang/srt/layers/deep_gemm_wrapper/entrypoint.py", line 157, in grouped_gemm_nt_f8f8bf16_contig
    deep_gemm.m_grouped_fp8_gemm_nt_contiguous(
File "deep_gemm/__init__.py", line 174, in m_grouped_fp8_fp4_gemm_nt_contiguous
RuntimeError: Assertion error (deep_gemm/.../utils/layout.hpp:108):
  sf.size(-1) == ceil_div(k, gran_k * (sf_dtype == torch::...))

Exception: Capture cuda graph failed: Assertion error (... layout.hpp:108) ...
RuntimeError: Server failed to become healthy; inspect container logs
```

DeepGEMM expects a scale-factor tensor whose last dimension matches its packing convention; DSV4.1's MXFP4 expert scales do not carry that shape. The combination is simply unsupported.

## Why this is worth a guard rather than a doc note

The same codebase already rejects incompatible combinations **at argument resolution**, with a message that says what to do — for example FlashInfer allreduce fusion raises `ValueError: FlashInfer allreduce fusion requires SM90 or SM10X NVIDIA GPUs.` before anything loads.

Here the cost of finding out is a full weight load plus graph capture, and the error surfaces as a device-side assertion several frames below the flag that caused it. A reader of the traceback has no reason to connect `layout.hpp:108` to `--moe-runner-backend`.

A check at resolution time — "backend `deep_gemm` does not support this model's MXFP4 expert scale layout" — would turn eight minutes and an opaque assertion into an immediate, actionable message.

## Related, and why this is not a duplicate

- **#39063 / #39065** are the closest existing work: `should_deepgemm_weight_requant_ue8m0` returns False for all SM120 weights, so **blockwise FP8** MoE scales are never UE8M0-requantized and DeepGEMM asserts. That path runs through `Fp8MoEMethod.process_weights_after_loading`. **DSV4.1's experts are MXFP4 and go through `quantization/mxfp4.py` instead**, so that fix does not reach this case — I checked before filing.
- **#35388** reports the same DeepGEMM entry point failing on GB300/sm_103, but on the *format* assertion (`smxx_layout.cuh:131`, the power-of-two check) rather than this *shape* one.
- **#39193** (mine) is the same family again: non-power-of-two scales reaching `fp8_einsum`, silently truncated rather than rejected.

Four separate reports now cluster around DeepGEMM scale-factor handling on Blackwell. A shared front-end check for "does this backend accept this model's scale layout" would cover all of them.

## Environment

- 4× NVIDIA DGX Spark (GB10, compute capability 12.1), TP4 / EP2, 200G RoCE
- DeepSeek-V4.1-Flash, MXFP4 routed experts (384 + 1 shared, top-6), DSpark speculative decoding
- The working configuration is `--moe-runner-backend flashinfer_mxfp4`; the boot log shows the live path as "Preparing DSv4 MXFP4 experts for FlashInfer SM120 CUTLASS W4A8"

## Reproduction

Serve DeepSeek-V4.1-Flash on an sm_120/sm_121 fleet with `--moe-runner-backend deep_gemm` added. The boot reaches weight loading and fails in CUDA graph capture with the assertion above. Removing the flag boots normally.
