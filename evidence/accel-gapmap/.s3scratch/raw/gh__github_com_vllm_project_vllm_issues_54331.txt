Note: `flashinfer-cubin` has to be uninstalled here. Since flashinfer 0.6.14 the cubin package
enforces strict version equality with `flashinfer-python`, and cubin is only published up to 0.6.13,
so `vllm==0.28.0` (which pins `flashinfer-python==0.6.16.post3`) refuses to start with it present.

### 🐛 Describe the bug

## Summary

On a single RTX PRO 6000 Blackwell (**sm_120**), a Qwen3.5-MoE-family **hybrid GDN (linear-attention)
NVFP4** model reliably dies after ~7–8 minutes of sustained, high-concurrency offline inference —
**as long as CUDA graphs are enabled**. Turning CUDA graphs off is the only thing I have found that
prevents it.

I ran a five-arm dissection today on vLLM 0.28.0, same box, same corpus, same command, one engine per
run. Three candidate mechanisms are **refuted**:

| arm | `cudagraph_mode` | attention backend | outcome |
|---|---|---|---|
| stock | `FULL_AND_PIECEWISE` | FlashInfer (+ `xqa` decode) | **CRASH** — SIGSEGV in `CUDAGraph::replay`, 7m45s, 1252 windows |
| `PIECEWISE` only | `PIECEWISE` | FlashInfer (+ `xqa` decode) | **CRASH** — same SIGSEGV, 7m16s, 1170 windows |
| `TRITON_ATTN` | `FULL_AND_PIECEWISE` | `TRITON_ATTN` (no FlashInfer, no `xqa`) | **CRASH** — `illegal instruction` at `async_copy_ready_event.synchronize()` |
| `expandable_segments` | `FULL_AND_PIECEWISE` | FlashInfer (+ `xqa` decode) | **CRASH** — same SIGSEGV, 7m00s, 1179 windows |
| **`enforce_eager`** | **off** | FlashInfer (+ `xqa` decode) | **SURVIVES** — 2/2 rounds complete, clean |

So: **FULL decode graphs are not necessary, FlashInfer/`xqa` is not necessary, and allocator
fragmentation is not the cause** (see below). The only invariant across the four deaths is
*CUDA graphs on + a hybrid-GDN model under saturation*.

**vLLM 0.24.0 is clean** on the identical box, model, corpus and command — I re-ran that control today
specifically to rule out the machine. The fault first appears in **0.26.0** and survives 0.26.0 →
0.27.0 → 0.27.1 → 0.28.0, with a byte-identical stack, across **two different checkpoints** in the
same family.

## Primary signature

```
!!!!!!! Segfault encountered !!!!!!!
  File "<unknown>", line 0, in cuGraphLaunch
  File "<unknown>", line 0, in cudaGraphLaunch
  File "<unknown>", line 0, in at::cuda::CUDAGraph::replay()
  File "<unknown>", line 0, in torch::detail::wrap_pybind_function_impl_<void (at::cuda::CUDAGraph::*)(), 0ul, true>(...)
  File "<unknown>", line 0, in pybind11::cpp_function::dispatcher(_object*, _object* const*, unsigned long, _object*)
```

The EngineCore process dies outright; all in-flight requests then raise `EngineDeadError`.

**The same fault presents with at least three different surfaces**, which is worth knowing if you are
trying to match reports:

1. host SIGSEGV in `cuGraphLaunch → cudaGraphLaunch → at::cuda::CUDAGraph::replay()` (stock, and the `PIECEWISE` arm)
2. `torch.AcceleratorError: CUDA error: an illegal instruction was encountered`, reported at
   `gpu_model_runner.py … self.async_copy_ready_event.synchronize()` (the `TRITON_ATTN` arm; also seen on 0.27.0 via a different driver script)
3. `CUDA error: unspecified launch failure` (0.26.0, second run)

Surfaces 2 and 3 are asynchronous reports at a sync point, so the reported location is not the
faulting kernel.

## Configuration

- **GPU:** 1× RTX PRO 6000 Blackwell Workstation Edition, 96 GB, **sm_120**, driver 610.43.02, TP=1.
- **Model:** `ornith-ai/Ornith-1.5-35B-A3B-NVFP4` — arch `qwen3_5_moe`, hybrid GDN linear attention
  (30 of 40 layers are `linear_attention`). Also reproduced on `nvidia/Qwen3.6-35B-A3B-NVFP4`.
- **Quantization:** `quantization=modelopt_mixed` — FP8 W8A8 on the attention path
  (`linear_attn` in_proj_qkv/z/out_proj, `self_attn` q/k/v/o) and **NVFP4 W4A4 group-size 16** on
  `lm_head` + MoE experts + shared_expert.
- **KV cache:** `kv_cache_dtype=fp8_e4m3` (auto-promoted from the checkpoint's `kv_cache_scheme`).
- **Kernels selected at boot:** `MarlinNvFp4LinearKernel`, `'MARLIN' NvFp4 MoE backend`,
  `Triton/FLA GDN prefill kernel (requested=auto, head_k_dim=128)`, `GDN decode kernel: cuda`,
  and `FlashInfer resolved query dtypes: prefill=bf16, decode=bf16, decode_backend=xqa,
  kv_cache_dtype=float8_e4m3fn, arch=sm120`.
- `enable_prefix_caching=True`, `enable_chunked_prefill=True`, `gpu_memory_utilization=0.90`,
  `max_model_len=32768`, `max_cudagraph_capture_size=512`. Attention block size forced to 2096 so the
  attention page size ≥ the mamba page size.
- **No speculative decoding, no MTP, no async scheduling.**
- **Workload:** offline batch video inference, up to 70 concurrent requests, multi-turn per video over
  a shared system+video KV prefix; 1358 windows per round, one engine for the whole run.

Note on sm_120 specifically: `_resolve_gdn_prefill_backend` only enables the flashinfer/cutedsl GDN
prefill paths for SM90 and cc-family-10.x, so **cc 12.0 always falls through to Triton**. Passing
`--gdn-prefill-backend flashinfer|cutedsl` is inert here. There is no GDN backend escape hatch on this
card.

## Discriminator matrix

Today, on **0.28.0** (`Ornith-1.5-35B-A3B-NVFP4`, 2 rounds each):

| configuration | crashes |
|---|---|
| stock defaults | **1 / 1** @ 7m45s, 1252 windows |
| `cudagraph_mode=PIECEWISE` | **1 / 1** @ 7m16s, 1170 windows |
| `attention_backend=TRITON_ATTN` | **1 / 1**, different surface (illegal instruction) |
| `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` | **1 / 1** @ 7m00s, 1179 windows |
| **`enforce_eager=True`** | **0 / 1** — 2/2 rounds, `events_total` 244 both, `parse_failures` 0 |

Earlier, on **0.27.0** (`Qwen3.6-35B-A3B-NVFP4`, 4 rounds each):

| configuration | crashes |
|---|---|
| stock defaults, one engine | **1 / 1** @ +5m50s |
| `max_num_seqs=128` (halves the FULL capture ceiling to 256) | **1 / 1** @ +4m49s — **refuted as a fix** |
| **`enforce_eager`**, one engine | **0 / 1** — 4 rounds clean, but **+23.6 % time/round** (495.6 s vs 401.1 s) |
| fresh engine per round (`--rounds 1` × 4) | **0 / 4** |
| **Gemma4-26B-A4B-NVFP4** (MoE, *not* hybrid-GDN), one engine | **0 / 1** |
| a 100-min production-pacing soak, 70 streams, GPU util ~65 % | **0 / 1** |
| 0.24.0 control, 5 rounds | **0 / 1** |

Reading:

1. **CUDA graphs on + one long-lived engine + sustained ~100 % saturation** is the trigger. Graphs
   off, or a fresh engine per round, is clean.
2. A 100-minute soak at ~65 % utilization never reproduced it — the trigger looks like sustained
   saturation, not elapsed time. That is why benchmark/eval drivers hit it and a latency-bound
   deployment may not.
3. **Hybrid-GDN specific.** Gemma4-26B (MoE, no GDN linear attention) is clean on the same box, same
   release, same driver, same harness.
4. Capping `max_num_seqs` is **not** a workaround.

## Notable: the `TRITON_ATTN` workaround from #54225 does NOT work here

[#54225](https://github.com/vllm-project/vllm/issues/54225) reports a superficially similar crash on
the same card class and reports `--attention-backend TRITON_ATTN` as sufficient to stop it (0/2 runs
over 413 requests). **On my configuration `TRITON_ATTN` does not help** — the engine still dies, only
the surface changes from a host SIGSEGV to an asynchronous `illegal instruction`. I take that as
evidence these are different bugs rather than one, and it is part of why I filed separately.

## What I believe is ruled out

- **Hardware / driver.** 0.24.0 is clean on the same box; I re-ran that control today for exactly this
  reason. 5/5 rounds, `events_total` 244 every round, `parse_failures` 0, zero faults, ECC clean, no Xid.
  A colleague independently ran a second 5-round 0.24.0 control on the same machine today with
  `nvidia/Qwen3.6-35B-A3B-NVFP4` — the checkpoint #37431 reports against — also 5/5 valid,
  `events_total` 244 every round, `parse_failures` 0, zero crash signatures. Two different hybrid-GDN
  checkpoints, two operators, same silicon, 0.24.0 clean both times.
- **FULL decode CUDA graphs** — `PIECEWISE` still crashes.
- **FlashInfer / `xqa` decode** — `TRITON_ATTN` still crashes.
- **`max_num_seqs` / capture-size ceiling** — halving it still crashed (0.27.0).
- **Allocator fragmentation** — `expandable_segments:True` removes the warnings, not the crash; and
  warning counts anti-correlate with crashing (see below).
- **transformers version confound** — transformers is 5.14.1 on both the 0.24.0 and 0.28.0 envs.
- **Total VRAM exhaustion** — 53.88 GiB KV pool, ~5.6 GiB peak activation, on a 96 GiB card.
- **An accuracy regression in 0.28.0** — the `enforce_eager` arm scores normally (event F1 0.8463 /
  0.8408 over 2 rounds, vs 0.8343 ± 0.0042 for the 0.24.0 5-round control). 0.28.0's problem is
  stability, not quality.

## Allocator fragmentation: investigated and RULED OUT

The stock run logs a handful of **non-fatal** allocator OOM warnings before it dies, which looked like
a promising lead:

```
[rank0]:[W CUDACachingAllocator.cpp:3933] memory allocation failed with OOM on device 0
  while trying to allocate 1595932672 bytes (free: 783220736, total: 102014189568).
```

(The card is nowhere near exhausted — 53.88 GiB KV pool, ~5.6 GiB peak activation, 96 GiB card.)

I tested it and **it is not the cause**, on two independent grounds:

1. **`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` removes the warnings and does not remove the
   crash.** Stock config otherwise unchanged, graphs still captured (`PIECEWISE=51`, `FULL=35`).
   Warning count dropped 6 → 1; the run still died with the identical `CUDAGraph::replay` SIGSEGV at
   7m00s / 1179 windows — squarely inside the 7m00s–7m45s band of the other deaths.
2. **The warnings do not track the crash.** Warning counts per arm: stock 6 (crashed), PIECEWISE 3
   (crashed), **`TRITON_ATTN` 0 (crashed)**, expandable_segments 1 (crashed), **`enforce_eager` 4
   (survived)**. An arm with zero warnings died; the arm with four warnings is the one that lived.

So the warnings are a co-symptom of saturation, not the mechanism. I am including this because it is
the first thing I would have asked, and it is now closed.

(For anyone worried the flag itself perturbs graph capture — a known interaction, since
`expandable_segments` and CUDA graph capture both want to own memory pools — capture proceeded
normally here, and a separate 10-round run on 0.24.0 with `expandable_segments:True` +
`FULL_AND_PIECEWISE` + `enforce_eager=False` was clean across two checkpoints. The flag is not
breaking capture.)

## Caution for anyone reproducing: crashed runs look like clean accuracy regressions

Both crashed arms **exited 0** and wrote a result file whose first round reported a perfectly
plausible score (event F1 0.7806 and 0.7851). They were truncated: `events_total` was 132 and 113
instead of 244, and round 2 was empty. If you gate on the exit code or the headline metric you will
record this crash as a ~0.05 accuracy regression that does not exist. Gate on the number of scored
items per round.

## Related, but I believe distinct

- [#54225](https://github.com/vllm-project/vllm/issues/54225) — same card class/quant/KV dtype, but a
  device-side illegal access, deterministic on a 16-token request, and its `TRITON_ATTN` workaround
  does not work for me (above).
- [#52540](https://github.com/vllm-project/vllm/issues/52540) — sm_120 ModelOpt NVFP4 hybrid GDN under
  sustained load with CUDA graphs. Closest in shape; IMA rather than a host segfault.
- [#37431](https://github.com/vllm-project/vllm/issues/37431) — the GDN/Mamba cudagraph tracker, but
  overwhelmingly **sm_121 / GB10**. Its refuted-mitigation ledger (including PIECEWISE) is sm_121-specific;
  my PIECEWISE arm is, as far as I know, the first test of that knob on sm_120 — and it also fails, for
  whatever that is worth. That thread also contains a useful independent control: a reporter running
  **Gemma-4-26B-A4B-NVFP4 for 24 days clean on the same GB10 box** that fails with GDN models, which
  matches the Gemma-clean / GDN-crashes split I measured on sm_120. (He notes his own partition is not
  airtight — he saw one Xid 13 on `gpt-oss-120b`, a pure-attention model, at the same fault address.)
- [#52225](https://github.com/vllm-project/vllm/issues/52225), [#53726](https://github.com/vllm-project/vllm/issues/53726) —
  Xid 13 / spec-decode-race families; I run no MTP and no async scheduling.
- [#49926](https://github.com/vllm-project/vllm/issues/49926) — same model + quant, names a "CUDA graph
  replay" family, but GB10 sm_121, and `--enforce-eager` does *not* clear it there whereas it does here.
- [#35293](https://github.com/vllm-project/vllm/issues/35293) — **byte-identical stack** on GLM-5-FP8 /
  8×H200 / vLLM 0.16.0rc2, with the same `--enforce-eager` workaround. Closed in a day with no root
  cause. Cited as precedent for the signature, not as a duplicate.

## One note on v0.28.0 specifically

`v0.28.0` looks to be cut from ~2026-08-17 `main` plus a small number of cherry-picks, so it does not
contain [#50729](https://github.com/vllm-project/vllm/pull/50729) ("[Bugfix][Mamba] Fix overlapping
state copy race", merged 2026-08-17) or [#53077](https://github.com/vllm-project/vllm/pull/53077). I
checked #50729's absence in the source: `vllm/v1/worker/mamba_utils.py` at `v0.28.0` has no
`memmove`/overlap handling, while `v0.28.1rc0` has
`is_left_overlap = dst_ptr < src_ptr and dst_ptr + size > src_ptr`. I have **not** tested 0.28.1rc0 —
if that fix is expected to address this, I am happy to run the same four arms against it.

 Reading:

 CUDA graphs on + one long-lived engine + sustained ~100 % saturation is the trigger. Graphs

off, or a fresh engine per round, is clean.

 A 100-minute soak at ~65 % utilization never reproduced it — the trigger looks like sustained

saturation, not elapsed time. That is why benchmark/eval drivers hit it and a latency-bound

deployment may not.

 Hybrid-GDN specific. Gemma4-26B (MoE, no GDN linear attention) is clean on the same box, same

release, same driver, same harness.

 Capping max_num_seqs is not a workaround.

 Notable: the TRITON_ATTN workaround from #54225 does NOT work here

 #54225 reports a superficially similar crash on

the same card class and reports --attention-backend TRITON_ATTN as sufficient to stop it (0/2 runs

over 413 requests). On my configuration TRITON_ATTN does not help — the engine still dies, only

the surface changes from a host SIGSEGV to an asynchronous illegal instruction . I take that as

evidence these are different bugs rather than one, and it is part of why I filed separately.

 What I believe is ruled out

 Hardware / driver. 0.24.0 is clean on the same box; I re-ran that control today for exactly this

reason. 5/5 rounds, events_total 244 every round, parse_failures 0, zero faults, ECC clean, no Xid.

A colleague independently ran a second 5-round 0.24.0 control on the same machine today with

 nvidia/Qwen3.6-35B-A3B-NVFP4 — the checkpoint Mamba-2 Triton kernels crash with illegal instruction on SM121 (DGX Spark) without CUDA_LAUNCH_BLOCKING=1 #37431 reports against — also 5/5 valid,

 events_total 244 every round, parse_failures 0, zero crash signatures. Two different hybrid-GDN

checkpoints, two operators, same silicon, 0.24.0 clean both times.

 FULL decode CUDA graphs — PIECEWISE still crashes.

 FlashInfer / xqa decode — TRITON_ATTN still crashes.

 max_num_seqs / capture-size ceiling — halving it still crashed (0.27.0).

 Allocator fragmentation — expandable_segments:True removes the warnings, not the crash; and

warning counts anti-correlate with crashing (see below).

 transformers version confound — transformers is 5.14.1 on both the 0.24.0 and 0.28.0 envs.

 Total VRAM exhaustion — 53.88 GiB KV pool, ~5.6 GiB peak activation, on a 96 GiB card.

 An accuracy regression in 0.28.0 — the enforce_eager arm scores normally (event F1 0.8463 /

0.8408 over 2 rounds, vs 0.8343 ± 0.0042 for the 0.24.0 5-round control). 0.28.0's problem is

stability, not quality.

 Allocator fragmentation: investigated and RULED OUT

 The stock run logs a handful of non-fatal allocator OOM warnings before it dies, which looked like

a promising lead:

 [rank0]:[W CUDACachingAllocator.cpp:3933] memory allocation failed with OOM on device 0
 while trying to allocate 1595932672 bytes (free: 783220736, total: 102014189568).

 (The card is nowhere near exhausted — 53.88 GiB KV pool, ~5.6 GiB peak activation, 96 GiB card.)

 I tested it and it is not the cause , on two independent grounds:

 PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True removes the warnings and does not remove the

crash. Stock config otherwise unchanged, graphs still captured ( PIECEWISE=51 , FULL=35 ).

Warning count dropped 6 → 1; the run still died with the identical CUDAGraph::replay SIGSEGV at

7m00s / 1179 windows — squarely inside the 7m00s–7m45s band of the other deaths.

 The warnings do not track the crash. Warning counts per arm: stock 6 (crashed), PIECEWISE 3

(crashed), TRITON_ATTN 0 (crashed) , expandable_segments 1 (crashed), enforce_eager 4

(survived) . An arm with zero warnings died; the arm with four warnings is the one that lived.

 So the warnings are a co-symptom of saturation, not the mechanism. I am including this because it is

the first thing I would have asked, and it is now closed.

 (For anyone worried the flag itself perturbs graph capture — a known interaction, since

 expandable_segments and CUDA graph capture both want to own memory pools — capture proceeded

normally here, and a separate 10-round run on 0.24.0 with expandable_segments:True +

 FULL_AND_PIECEWISE + enforce_eager=False was clean across two checkpoints. The flag is not

breaking capture.)

 Caution for anyone reproducing: crashed runs look like clean accuracy regressions

 Both crashed arms exited 0 and wrote a result file whose first round reported a perfectly

plausible score (event F1 0.7806 and 0.7851). They were truncated: events_total was 132 and 113

instead of 244, and round 2 was empty. If you gate on the exit code or the headline metric you will

record this crash as a ~0.05 accuracy regression that does not exist. Gate on the number of scored

items per round.
