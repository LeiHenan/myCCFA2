### 🚀 The feature, motivation and pitch

vLLM main already contains the optional direct **B12X** NVFP4 linear *and* MoE backend merged in #52018. Its support predicate explicitly covers **SM120 and SM121**, NVFP4 W4A16, supported shapes, tensor-parallel constraints and package availability.

However, the automatic NVFP4 MoE selector in `vllm/model_executor/layers/fused_moe/oracle/nvfp4.py` never considers `NvFp4MoeBackend.B12X`. On an SM121 (GB10 / DGX Spark) deployment the preference list walks past the FlashInfer/CUTLASS entries and lands directly on **Marlin**, so the merged B12X MoE kernel is only reachable via an explicit `--moe-backend b12x`. This is the fallback behaviour reported in #50925, and Marlin NVFP4 on this class of device is the common factor in #49926, #50934, #52225 and #49070.

**The proposal:** insert `NvFp4MoeBackend.B12X` immediately before `MARLIN` in the automatic preference list. No model, server or device special case is encoded — the existing B12X support predicate stays the authority, so an absent package, an unsupported GPU, quantization scheme, shape or parallel configuration falls through to the current Marlin path unchanged.

#### What was measured

On a GB10 (SM121) running a hybrid Mamba NVFP4 MoE model at `max_model_len=131072`, FP8 KV cache, prefix caching on, full CUDA graphs:

| run | backend | outcome |
| --- | --- | --- |
| A | Marlin (auto) | `EngineDeadError`, illegal memory access surfacing at output-copy sync |
| B | Marlin (auto), `VLLM_MARLIN_USE_ATOMIC_ADD=0` | same fault class — disabling atomic accumulation was **not** sufficient |
| C | `--moe-backend b12x` explicit | ~26 min, 18,499,772 prompt tokens, 106,838 generated, 18,530,470 prefix-cache queries / 17,082,400 hits, peak engine concurrency 3, **no CUDA traceback or illegal-memory-access line** |

Run C exercised substantially more prompt traffic than either crashing Marlin run at the same observed peak request concurrency.

With the one-line selector change and **no** explicit backend flag (`moe_backend='auto'` in the emitted serve config), the engine boots as:

```text
Using 'B12X' NvFp4 MoE backend out of potential backends: [..., 'VLLM_CUTLASS', 'B12X', 'MARLIN', ...].
```

It completed piecewise and full CUDA-graph capture, warmed the B12X MoE signature, returned HTTP 200 from `/health` and advertised the model at `max_model_len=131072` with no traceback.

**Honest limits:** this does not prove which Marlin instruction caused the asynchronous fault, and a single ~26-minute stress sample does not establish multi-day stability. What it does show is that a supported, already-merged backend is being hidden from users who never pass an explicit flag.

### Alternatives

- **#47577** — the existing open PR auto-selects a *FlashInfer* B12X implementation on **exact SM120** and deliberately leaves SM121 on Marlin. This proposal does not duplicate that kernel work; it exposes the newer *direct* B12X backend from #52018, whose merged support predicate and measured coverage include SM121. I found no open PR that adds the direct backend to the automatic NVFP4 selector.
- **#48624** (gated-intermediate padding) does not apply — the model's `moe_intermediate_size=512` at TP=1 is already aligned to the relevant tile boundaries.
- **#48929** (MiniMax correctness) plumbs model-specific SwiGLU-OAI and sparse-index layouts and explicitly changes no low-level Marlin kernel; the model here uses ordinary SiLU.
- **Explicit `--moe-backend b12x`** works today, but requires every SM12x operator to independently discover that the default is unsafe for them.
- **Eager execution** also survived the stress, at a significant throughput cost.

### Additional context

Patch below, based on `main` at `22df3a34e`. Pre-commit passes for all three changed files (Ruff, formatting, typos, markdownlint, SPDX, mypy). The focused GPU suite passed **39/39 on SM121**, covering selector behaviour, W4A16 correctness and CUDA-graph replay. The added parametrized test proves both the supported selection and the unsupported fall-through ordering.

Happy to open this as a pull request if maintainers would prefer that — I filed it as an issue first so the SM121 evidence and the relationship to #47577 could be discussed before the code review.
