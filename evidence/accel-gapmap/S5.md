# S5: Per-step non-GEMM overheads — sampling, logits processing, tokenizer/detokenizer, structured output/grammars, async output processing

Scope note: researcher S5. Target rig = ONE RTX PRO 6000 Blackwell (96 GB, sm120), 208 host cores,
vLLM 0.29.0, SGLang 0.5.19, Qwen3-4B dense + EAGLE3/dflash2 drafters. Because a dense 4B on this card
is frequently host-bound, the rows below concentrate on CPU-side per-step work (sampler selection,
full-vocab logits handling, grammar compilation and bitmask staging, tokenizer/detokenizer, output
processing overlap) and on which of those stages are instrumented at all. KV-cache management and
speculative decoding are adjacent context only (e.g. where a drafter changes which logits-processor /
grammar paths are reachable); they are never a row's subject.

`vllm/v1/sample/`, `vllm/v1/structured_output/`, `vllm/v1/metrics/`, `docs/features/`, `docs/design/`,

### A5.9 | CLOSED
QUESTION: How expensive is the per-decode-step structured-output bitmask on the host, and was the resulting regression fixed?
WHO: vLLM (reporter romancomplexio; root-caused and fixed by njhill in #49919)
ARTIFACT: issue #49013 ("[Perf] ~2x decode throughput regression for structured outputs since #45424") + PR #49919 ("[Core] Explicitly manage torch CPU threads in workers")
URL: https://github.com/vllm-project/vllm/pull/49919 ; https://github.com/vllm-project/vllm/issues/49013
STATUS: merged (#49919, commit 7635a9002ba); issue #49013 closed COMPLETED
EVIDENCE: READ BODY
QUOTE: "torch defaults its intra-op thread pool to the host core count, ignoring process affinity, cgroup CPU quotas, and co-located worker processes. Any torch CPU op above the parallel_for grain size (32k elements) fans out across that pool, and the OpenMP workers then spin-wait after every parallel region - stealing cycles from the engine loop's serial code and, in containers, burning the CFS quota so that the entire process is throttled for the rest of the quota period. This is the root cause of the 2-6x structured-output decode throughput regression reported in #49013 (per-step pinning/fill of the ~12.6MB grammar bitmask on the hot path)."
RESIDUAL (reporter, verbatim, after the fix): "unfortunately, this hasn't fixed the performance regression. In my understanding the problem for us has been the added allocation of a 12MB tensor per every structured decode step."
NOTE: the merged fix addressed thread oversubscription, not the per-step allocation; the two PRs that targeted the allocation directly (#49150, #49780) were closed unmerged with no stated reason (see NEGATIVE FINDINGS). This is the single largest measured per-step non-GEMM cost in this file, and it is CPU-side, not GPU-architecture-specific.

### B5.3 | OPEN
WHO IS STILL ASKING: anencore94 (issue author and PR author); vLLM issue #49460 with open fix PR #49461
URL: https://github.com/vllm-project/vllm/issues/49460 ; https://github.com/vllm-project/vllm/pull/49461
ASKING QUOTE: "StructuredOutputManager sizes its grammar-compile ThreadPoolExecutor as max(1, (multiprocessing.cpu_count() + 1) // 2) with no upper bound. multiprocessing.cpu_count() is not cgroup-aware, so inside a container with a CFS quota (e.g. a Kubernetes pod with cpu limit 6 scheduled on a 172-core host) the pool is created with 86 workers. A burst of guided-JSON requests fans CPU-bound compiles out over the quota, sustains CFS throttling (ratio ≈ 1.00 for minutes in our production incident), and stalls the engine loop: inter-token latency collapsed from 7–9 ms to 68–93 ms with the GPU at 7–12% SM active, until requests hit the ingress deadline (intermittent 502s)."
