# S2 伪问题筛查（Pseudo-problem screen） — 草案语料生命周期：跨会话/跨副本的冷启动罚金

**候选**：`sglang-draft-corpus` ｜ **成本上限**：0 GPU·h
**目标**：把『没人做过』『听起来优雅』『指标能动』这类立项理由剔除掉。

## 七形态逐条判定

> 逐个形态判定，命中即写出命中理由（不允许"整体看起来不像"式结论）。

| 形态 | 是否命中 | 判定依据 |
|---|---|---|
| **① 算术量级型**（量级来自"理论上能省 X%"，零实测） | **不命中** | 量级来自**自有实测 160 格**：首通 accept **1.8365** vs 饱和 **7.7827**（4.24×）、32 请求 wall **25.22 s → 8.67 s**；原始数据在仓库外 `/root/ccfa_results/2026-09-13/p12_smoke/smoke.jsonl`，探针可 `--selftest` 离线复跑。**不是推算**。 |
| **② 已被 shipped 覆盖型**（以为没人做，其实引擎已默认实现） | **部分命中（已处置）** | 命中点：**上游已 ship `POST /add_external_corpus`**（`http_server.py:998`）+ 多 SAM + 动态配额 PR 栈。**处置**：不再把"预置语料"当创新点（用户硬约束 #5），主张收窄到引擎**明确未覆盖**的 **跨会话/跨重启的语料恢复与生命周期**（`external_corpus_manager.py:23-111` 无 save/snapshot/restore），并在 S3 给出结构性理由。 |
| **③ 基线反证型**（现象存在，但基线已把它消掉） | **不命中（但已设防线）** | 最危险的朴素基线是**前缀缓存**（radix cache）——它同样能让"第 2 遍变快"。本设计**全网格 `--disable-radix-cache`**，并在 C1 判据里强制 `cached_tokens == 0`；冒烟 160/160 实测 `cached_tokens = 0` ⇒ 收益**不可能**由前缀缓存解释。第二个基线是**引擎自带的会话内累积**，它正是 C 臂（稳态），已纳入判据。 |
| **④ 度量口径型**（指标定义错了，量出来的是结构性假象） | **不命中（已对源码核）** | `spec_accept_length = completion_tokens / spec_verify_ct`（`tokenizer_manager.py:2811-2814`），**上界 = `speculative_num_draft_tokens = 8`**；冒烟实测 max = 8.0000、min = 1.2308，**无一越界**（C1 判据会逐请求查）。另：`mean_itl_ms` 的"每流式 chunk"更正（decision #82）已吸收——本候选**不使用** `itl` 语义做任何主张。 |
| **⑤ 不可行域型**（只在拿不到的资源上成立） | **不命中** | 单卡 96 GB（实测 `97887 MiB`，当前占用 0 MiB）、单机、无需多副本、无需专有 trace；语料是**纯 CPU 结构**（`srt/speculative/cpp_ngram/`）。全部资源**本机已有并实测可用**。 |
| **⑥ 被更一般机制吸收型**（特例已被更一般的方法覆盖） | **不命中** | 最接近的"更一般机制"是**前缀缓存 / KV 复用**（跨会话复用 *KV*）与 **HiCache**（KV 的层级存储，`--enable-hierarchical-cache`）。差异轴是结构性的：**NGRAM 语料不是 KV**（无 per-token 状态、不占显存、可在副本间纯拷贝），且**即使前缀缓存全程开启，NGRAM 的语料命中仍然独立**（我们的实验把 radix cache 关掉后接受长度仍从 1.84 涨到 7.78 ⇒ 两条机制**可分离**）。S3 会补读 HiCache 正文划边界。 |
| **⑦ 方法找问题型**（从一个想用的技术出发，反推一个"问题"） | **不命中（自检过）** | 立项顺序是**痛点→方案**：先测出 P1 的冷窗口（4.24×/2.91×），**再**问"能不能闭合它"，最后才发现引擎已 ship 的 `add_external_corpus` 正好是可用的干预原语。**若这个 API 不存在**，冷窗口这个痛点在**短会话/serverless/弹性扩缩**场景下**依然存在**（只是要自己改引擎）⇒ 符合"如果这个技术不存在，这个问题还值得做吗"的检验。 |

## 自检十问

| # | 问题 | 答 | 一句依据 |
|---|---|---|---|
| 1 | 能一句话说出**谁**在**什么负载**上**损失了什么**？ | **是** | "**短会话/弹性扩缩的 NGRAM 服务**"在"**每个新实例的第一段流量**"上损失了 **2.91× 的 wall**（接受长度 1.84 vs 7.78）。 |
| 2 | 这个损失有**真机数字**，不是"理论上"？ | **是** | 160 格逐请求实测（`p12_smoke/smoke.jsonl`），含 3 条采集路径。 |
| 3 | 读过**现有机制的实现**，并指出它**结构上**做不到？ | **是** | `external_corpus_manager.py:23-111` 只有 add/remove/list，**无持久化路径**；第 86 行是作者自认的 UB。 |
| 4 | 跑过**至少两个朴素基线**，确认它们消不掉这个损失？ | **是** | ① 前缀缓存基线：`--disable-radix-cache` 下罚金**依然存在**（且 `cached_tokens=0`）；② 引擎自带会话内累积基线：第 2 遍才生效 ⇒ **首通仍然慢**。 |
| 5 | 量级**不是**由一个说不清口径的指标算出来的？ | **是** | `spec_accept_length = completion_tokens / spec_verify_ct`，出处给到 `tokenizer_manager.py:2811-2814`，上界 8 实测无越界。 |
| 6 | 所需资源**确实拿得到**？ | **是** | 单卡 96 GB / 单机 / 0 MiB 占用 / 磁盘余 80 G；成本上界 ≤8 GPU·h（用户已授权）。 |
| 7 | 能指出**最近邻 3 篇**并逐条说明差异轴？ | **是** | 见 `30_occupancy.md`：上游 roadmap #21052（同对象、**已做完外置语料本身**，我们做**恢复生命周期**）、PR #22538/#22569（同对象、**关闭未 merge**，我们不做动态配额）、agentic-kv-cache / Continuum（**KV** 生命周期，我们做**语料**生命周期，且 KV 不能跨副本纯拷贝）。 |
| 8 | 动机写成"痛点→方案"，**不是**"方案→痛点"？ | **是** | 见形态⑦ 的判定：先有 160 格冷窗口数据，后有"用现成 API 试闭合"的实验。 |
| 9 | 如果实验结果是**阴性**，这个阴性本身有信息量吗？ | **是** | 阴性能写成"**引擎已 ship 的语料预置 API 不足以闭合冷窗口**"这一结构性结论（附 3 进程重复 + k=3 可分辨性），并指出缺口在配额/合并策略而非 API 有无；对上游有直接价值。 |
| 10 | 能给出**≤2 周内可测**的判据与 kill 条件？ | **是** | 判据 C0–C4 与杀判据已冻结在 `50_prereg.md`（**采数前**，commit `207de66`），实验一轮 ≈0.15 GPU·h。 |

**结论：十问全部为"是"** ⇒ 无条目因十问被否。
