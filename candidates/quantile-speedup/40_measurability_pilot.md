# 新方向（B）可行性证据：加速技术**重新分配**延迟，而均值掩盖了这一点

**日期**：2026-09-14 ｜ **平台**：<SSH_HOST>（RTX 4080 SUPER，vLLM 0.29.0）｜ **成本**：≈0.1 GPU·h
**状态**：**首次探测即出现强信号** —— 这是五轮以来第一个"均值与尾部分歧"的量化证据

---

## 1. 一句话

> **投机解码把平均延迟降了 19.7%，却让 p99 一点没降（0.997×）、变异系数翻了 4 倍（0.078 → 0.320），
> 并且把加速比在请求之间拉开了 3.2 倍（0.81× 到 2.59×）。**
> **SLO 是按分位数签的，而所有加速论文只报均值。**

---

## 2. 实测数据

**设置**：Qwen3-4B，24 个不同 prompt（各 512 token，仅尾 8 token 不同），
`max_tokens=32 + ignore_eos`（**输出长度钉死，两臂解码成本对齐**），
加速技术用 **prompt-lookup / n-gram 投机**（**无需 draft 模型**，故本机即可跑）。

```
arm              mean_ms    p50_ms    p95_ms    p99_ms       CV
---------------------------------------------------------------
baseline           930.2     897.5    1079.6    1081.9   0.0779
ngram_spec         776.9     924.0    1084.6    1085.2   0.3195

mean_speedup        : 1.197      ← 均值上"快了 19.7%"
p99_speedup         : 0.997      ← 尾部**一点没快**
mean_vs_p99_gap     : 1.201      ← 均值与尾部差 20%
CV: 0.0779 → 0.3195              ← 方差放大 4.1×
```

**逐请求加速比分布**（同一 prompt 配对比较，24 对）：

```
min 0.809×   p50 1.112×   max 2.593×   spread 3.21×
```

⇒ 加速**不是**"每个请求都快 20%"：
- **中位数只快 11.2%**（远低于均值 19.7%）；
- **最快的请求快 2.59×，最慢的反而慢 19%**（0.809 < 1，即**被拖慢了**）；
- 均值之所以是 19.7%，是被少数高加速请求**拉起来**的。

---

## 3. 为什么这是一个**真问题**（而不是又一次"均值 vs 尾部"的老生常谈）

1. **它换的是问题，不是格子。**
   现有加速文献报的是 **"平均加速比"**；SLO 常用 **p95/p99 TTFT 或 TPOT**。
   二者的差不是"精度问题"，而是**同一个技术对分布做了重分配**——
   **一个可以写进合同的数字（p99）在加速后没有改善，而基准数字（均值）改善了 20%。**
2. **结构性无人做**（需再核，见 §4）：
   *Speculative Decoding: Performance or Illusion?*（MLSys'26 **oral**）打的是
   **高 batch 下收益缩水**这一**均值趋势**；它**没有**给出"逐请求加速比分布"这一对象，
   也**没有**把结论落到"按分位数签订的 SLO 会不会被破坏"。
3. **有直接的工程后果**：运维按均值调参（"开投机更快"）会把 p99 留在原地甚至变差；
   而**是否开启一项加速技术**在真实系统里正是按分位数决策的。
4. **可测且便宜**：单卡、无 draft 模型、输出长度钉死即可做到公平对照。

## 4. 最近邻核查结果（**已做，结论收紧**）

我读了 [*Speculative Decoding: Performance or Illusion?*](https://arxiv.org/abs/2601.11580)
（arXiv 2601.11580，MLSys'26，**UC Berkeley / Ion Stoica 组**）的**摘要全文**：

> "…**acceptance length varies markedly across output token positions, requests, and datasets.**
> Comparing measured performance with theoretical bounds reveals substantial gaps … we leverage
> this observation to **highlight new research opportunities that our study opens up**."

**⇒ 这显著收紧了我的新颖性主张，必须诚实记录：**

| 我的原主张 | 核查后的修正 |
|---|---|
| "无人报逐请求差异" | ❌ **过强**。该文摘要**已经**说 acceptance length 在 **requests** 之间差异显著 |
| "无人把结论落到分位数 SLO" | ✅ **仍然成立**（摘要中无 SLO / percentile / tail 字样；但**我只读了摘要，未读正文**） |

**因此差异轴必须收窄成**：
> 该文报的是**接受长度**在请求间的变异，落点是**均值加速比与理论上界的差距**；
> 本文报的是**端到端逐请求加速比分布**，落点是**按分位数签订的 SLO 是否被破坏**。
> **当 SLO 以 p95/p99 表述、且加速比在请求间高度异质时**，二者结论不同。

**⚠️ 竞争风险（必须写进方案）**：这是一个**强组正在活跃的方向**，且该文明确说它
"opens up new research opportunities"。**继续做必须假定他们会跟进**，
因此差异轴必须足够硬——否则这就是在别人的 roadmap 上抢跑。

**未完成的核查**：该文**正文**（HTML v2 可读）必须读，确认它**没有**已经给出
逐请求加速比分布或分位数结论。**在读正文之前，本方向不立项。**

## 4b. 判据（修订版，先写后做）

1. **0 GPU**：读 arXiv 2601.11580 **正文**，逐节确认无 "per-request speedup distribution / p95 / p99" 结论；
2. **补设计缺陷**（见 §5）：n≥200、**同实例交错**、每个配置重复 5 次报 p50/p95；
3. **立项判据**：`p95_speedup / mean_speedup < 0.7`，**且**该比值在噪声预算内稳定（重复间极差 < 15%）；
4. **杀判据**：若正文已有同靶子结论，或补测后该比值回到 1.0 附近 ⇒ **归档**。

## 5. 诚实边界（这条必须先说清楚）

- **n=24 个 prompt × 1 次**，且是**单请求串行**（无并发）。
  **CV 与分位数在 n=24 下极不稳定**；当前数字只能当**可行性信号**，**不能当结论**。
- 我**没有**做噪声预算（同配置重复 ≥5 次报 p50/p95）——这正是 workspace 判据 §4.1 要求的，
  **必须补**，否则这条和被我杀掉的 8 个候选没有区别。
- `p99_speedup = 0.997` 在 n=24 下几乎是"同一个排序统计量的抖动"，**不应过度解读**。
- 两臂是**两个独立引擎实例**（先 baseline 后 spec），存在**实例间系统差异**的混淆；
  更强设计是**交错运行**或**同实例切换**。
- 只在 **1 个模型 / 1 种加速技术（ngram 投机）/ 无并发** 上测过。
