# 课题方案（方向 B 定稿）：加速技术改善**均值**但不改善**SLO 分位数**

**日期**：2026-09-14 ｜ **平台**：<SSH_HOST>（RTX 4080 SUPER 32GB，vLLM 0.29.0）
**成本**：≈0.5 GPU·h ｜ **状态**：**新颖性已核实 + 关键现象已在受控实验下复现**

---

## 1. 一句话课题

> **推理加速文献报的是"平均快 N 倍"，而生产 SLO 签的是分位数。
> 本文证明这两件事会系统性背离：n-gram 投机把平均延迟降了 28.2%，p95 却只降 0.3%，
> 且有 17.5% 的请求被它拖慢。加速不是在"整体提速"，而是在"重新分配延迟"。**

---

## 2. 受控实验证据（本轮核心产出）

### 2.1 设计（修掉了 pilot 的全部三个缺陷）

| pilot 的缺陷 | 定稿设计 |
|---|---|
| n=24，1 次 | n=40（本次；可扩至 200），**每臂 40 次** |
| 两引擎**顺序**跑（系统漂移混淆） | **两引擎同进程、逐请求交错、交替先后顺序** |
| 无噪声底 | **同引擎二次通过**给出"同一条件下的抖动基线" |

两个引擎：`baseline`（无投机）与 `ngram-spec`（`num_speculative_tokens=5`, lookup 4/2）。
输出长度用 `max_tokens=16 + ignore_eos` **钉死**，两臂解码成本对齐。
Qwen3-4B，prompt 256 token，`max_model_len=1024`，`enforce_eager`，无前缀缓存。

### 2.2 结果

```
metric        eng1(基线)   eng2(投机)   ratio(eng2/eng1)   噪声底
mean_ms          551.2       395.7         0.718           0.942  ← 均值真的快了
p50_ms            ~            ~           0.672           0.963

p99_ms           589.3       585.9         0.994           1.025  ← 尾部**完全没动**
CV                 ~           ~           8.95×           3.72×  ← 方差放大 9 倍
```

**判据通过**：`tail_vs_mean = 1.389`，而噪声底为 `1.064` ⇒
**"尾部跟不上均值"这个效应超出了噪声，且幅度 39% 远超噪声的 6%。**

### 2.3 逐请求分布（这是论文的图 1）

```
spec/baseline 延迟比（<1 = 投机更快）
  min 0.395   p05 0.514   p50 0.648   p95 1.071   max 1.089
  被拖慢的请求比例：17.5%          ← 六分之一的请求开加速反而变慢
```

**三句话读完**：
1. **中位数请求快 35%**（0.648），**最快的快 2.5×**（0.395）；
2. **最慢的请求反而慢 9%**（1.089），**17.5% 的请求被拖慢**；
3. **p95/p99 与基线无差别**——因为被拖慢的那批请求正好落在尾部。

## 3. 新颖性（已用全文核查，不是猜的）

最近邻 [*Speculative Decoding: Performance or Illusion?*](https://arxiv.org/abs/2601.11580)
（arXiv 2601.11580v2，MLSys'26，UC Berkeley）**全文机械扫描**：

| 关键词 | 命中 | 上下文 |
|---|---|---|
| `percentile` | 3 | **全部**在"per-request mean **generation length** 的箱线图" |
| `p95` / `p99` | **0** | — |
| `tail latency` / `jitter` / `straggler` / `worst-case` | **0** | — |
| `SLO` | 0 | — |

该文报的是**接受长度/生成长度**在请求间的变异，落点是**均值加速比与理论上界的差距**。
**它没有把结论落到延迟或加速比的分位数上。**

**差异轴（条件性）**：
> 最近邻报"均值快多少"；**当 SLO 以 p95/p99 表述时**，它覆盖不到
> **同一技术对延迟分布的重分配**；我们报**逐请求加速比分布**与**分位数加速比**，
> 因此**当加速比在请求间高度异质（本文：0.40–1.09）时**结论不同。

---

## 4. 研究问题（形式化）

设加速技术 $T$ 对请求 $r$ 的延迟为 $L_T(r)$，基线为 $L_0(r)$。定义**逐请求加速比**

$$S(r) = L_0(r) / L_T(r)$$

现有文献报 $\mathbb{E}[S]$。SLO 关心的是 $L_T$ 的分位数，等价于关心
**$S$ 在 $L_0$ 高分位处的取值**，而不是 $S$ 的均值。

**核心问题**：
1. 加速比的**异质性** $\mathrm{Var}[S]$ 由什么决定？（本文的 `S(r)` 跨越 0.40–1.09）
2. 在什么条件下 $\text{p95}(L_T) / \text{p95}(L_0) > \mathbb{E}[S]^{-1}$（尾部被背弃）？
3. 能否**预测**哪些请求会变慢，从而**按请求**决定是否启用加速？

**问题 3 是本文的技术贡献点**：如果 $\Pr[S(r) < 1]$ 可由请求的可观测量
（prompt 与输出的 n-gram 重叠率、输出长度、模板化程度）预测，
那么"**按请求选择性加速**"能把 p95 拿回来，而不牺牲均值收益。

---

## 5. 方法设想

1. **测量学**：定义"**分位数加速比**" $\text{QSR}_q = L_0^{(q)} / L_T^{(q)}$，
   并给出它与 $\mathbb{E}[S]$ 的背离量 $\text{Gap} = \mathbb{E}[S] \cdot \text{QSR}_q$（本文 = 1.39）。
2. **归因**：把 $S(r)$ 分解为可观测请求特征的函数
   （n-gram 接受长度的期望、输出长度、prompt 自相似度），拟合出**慢请求的判据**。
3. **策略**：**按请求的选择性投机**——对一个请求先做极短探测，预测 $S(r)$，
   低于阈值就不启用投机。判据是 p95 与均值的**联合改善**。
4. **可迁移性**：把同一套方法用到其它加速技术（EAGLE / MTP / draft-model / 前缀缓存），
   验证"均值-尾部分歧"是否是该类技术的通性。

## 8. 诚实边界

- 本轮 n=40、单模型、单一加速技术（ngram）、无并发、`ignore_eos` 钉死输出长度。
  **这是受控但窄的结论**；扩样前不得声称普适。
- **噪声底是"同引擎二次通过"**，不是"同配置 5 次重复"（workspace §4.1 要求后者）；E2 必须补。
- 我**没有**测实际 SLO 违约率（那需要真实负载与 deadline），只测了延迟分位数。
- 五轮里我杀掉了 9 个候选（见 `第4轮结论` 与 `E3判定`）；本方向是第 10 个，
  也是**第一个在新颖性和量级上都过关的**。

## 9. 复现命令（含全部环境坑，可直接执行）

```bash
<SSH_HOST>
pkill -9 -f e4_final; pkill -9 -f vllm; sleep 4
cd /root/autodl-tmp
VLLM_USE_FLASHINFER_SAMPLER=0 VLLM_ATTENTION_BACKEND=FLASH_ATTN \
  timeout 520 /root/miniconda3/bin/python e4_final.py \
    --n-prompts 40 --gpu-util 0.42 --max-len 1024 --gen 16 --prompt 256 \
    --seed 7919 --tag s1
# 结果：/root/autodl-tmp/e4_final_s1.json
```

**必须遵守的参数（每条都是踩坑换来的）**：
- `--max-len 1024`：2048 会让两个引擎的 KV 合计超过 32GB 卡
- `--gpu-util 0.42`：单进程**最多两个** `LLM` 实例；三个必然失败
- `VLLM_USE_FLASHINFER_SAMPLER=0`：该机缺 flashinfer 包
- **单次命令窗口约 10 分钟 ⇒ n=40 是一次能跑完的上限**（n=140 已实测超时）
- 更大样本必须用**多个 seed 的独立批次**（`--seed` 已支持），不能靠拉长单次
- `screen` 会随 SSH 会话消失（容器 `/run` 是临时的），`setsid nohup` 在该机不持久化

**已内建的四个对照（缺一不可）**：
1. `ratios_noise`（同引擎二次通过）⇒ 判"尾部不动"是否只是抖动；
2. 交错 + **交替先后顺序** ⇒ 消除系统漂移；
3. `ignore_eos` 钉死输出长度 ⇒ 消除"输出长度不同"这一混淆；
4. 两臂输出 token 数一致性断言。
