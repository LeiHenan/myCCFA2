# C-1d 判定：装置分歧已解决；**hybrid 的投机代价与接受率无关**（统一装置，单次实验内同时测得）

**日期**：2026-09-14 ｜ **平台**：RTX 4080 SUPER 32GB，vLLM 0.29.0，ngram K=3，实时文本 48 请求

---

## 0. 三句话

1. **装置分歧解决了**：先前"离线 1192 / server 61 tok/s"的矛盾，根因是 **server 装置串行发 48 次 HTTP、无批处理**；统一装置复现了离线值。
2. **hybrid 的投机代价与接受率无关**：hybrid **接受率更高**（0.687 vs 0.573）、**平均接受长度更长**（3.06 vs 2.72），**投机代价却是 dense 的 2.1 倍**（2.79× vs 1.32×）。
   （总计 4.93× 中只有 2.79× 是投机的锅，另 2.34× 是模型本身更慢——见 §5b 的分解。）
3. ⇒ 我先前"C-1b 的代价来自低接受率"的假设**被彻底证伪**；代价在**每步执行路径**上。

## 1. 统一装置的实测（**同一实验内同时得到吞吐与接受率**）

`probes/c1d_unified.py`：离线 `LLM` API（与 C-1b 同批形，48 请求一次批量提交），
并用 `per_request_spec_decode_metrics="detailed"` 从引擎的 per-request 累加器
（`RequestSpecDecodeMetrics`：`histogram[j]` + `num_draft_tokens`）**精确算出**接受指标。

| 单元 | tok/s | 输出长度 | **accept_rate** | **mean_accept_len** | 提交的 draft tokens |
|---|---|---|---|---|---|
| dense Qwen3-4B, K=3 | **1209.5** | 32.0 | **0.5725** | **2.7174** | 1104 |
| **hybrid** Qwen3.5-4B, K=3 | **208.4** | 32.0 | **0.7226** | **3.1677** | 930 |

- **吞吐比 dense/hybrid = 5.80×**
- **接受率比 hybrid/dense = 1.26×（hybrid 更好）**
- **平均接受长度 hybrid/dense = 1.17×（hybrid 更长）**
- 输出长度两臂都精确 32 ⇒ **长度混淆已排除**
- 48/48 请求都带上了 metrics ⇒ 覆盖完整

## 2. 装置分歧的根因（已定位）

| 装置 | dense K=3 | hybrid K=3 | 提交方式 |
|---|---|---|---|
| 离线 `LLM`（C-1b） | 1192.5 | 222.6 | **48 请求一次批量 `generate()`** |
| **统一装置（本轮）** | **1209.5** | **208.4** | 同上（复现 ✅） |
| OpenAI server（C-1c） | 60.94 | 68.25 | **48 次串行 HTTP** |

**⇒ server 装置是坏的那个**（串行 HTTP 完全放弃 continuous batching）。
**C-1b 的吞吐数字是对的**；C-1c 的吞吐数字**不可用**。

**但 C-1c 的接受率数字也不可直接采用**：它用的是引擎的 **Prometheus 计数器**
（`Δaccepted/Δdraft_tokens`），给出 dense 0.5725（与统一装置**完全一致** ✅）
但 hybrid 0.9044（统一装置为 **0.7226** ❌）。
⇒ 两个"接受率"口径不同，**hybrid 上不一致**。**统一装置的 per-request 累加器口径更可信**
（它同时给出 histogram 与 num_draft_tokens，可自校验：632/1104 与 672/930）。

## 3. 这一条现在**可以**作为立项候选的核（但仍不够）

**可主张的**（同一装置、同一实验、48 请求、两臂输出长度相同）：

> **在 hybrid（线性注意力 + 全注意力）目标上启用 ngram 投机，接受率反而更高
> （0.72 vs 0.57）、平均接受长度更长（3.17 vs 2.72），但吞吐只有 dense 的 1/5.8。**
> **⇒ 投机的代价不在"草稿被拒"，而在每步执行路径本身。**

**为什么这有意思**：整个投机解码文献的默认因果模型是"**接受率 → 加速比**"
（`arXiv 2601.11580` 也是这么分解的）。本条给出一个**接受率与加速比反向**的实例，
且限定在 hybrid 架构上——而 hybrid 正是 2026 年主流新模型的默认形态。

## 5. 必须排除的替代解释（下一步）

| # | 解释 | 如何排除 |
|---|---|---|
| A1 | hybrid 的**无投机**基线本身就慢（628 vs 1468），5.8× 里有一部分是**模型本身**的差异，不是投机的 | 报**相对各自 K=0 的比值**（C-1b 已测：dense 1.23×，hybrid 2.82×）——**这条其实已有数据，只是没和接受率放在一次实验里** |
| A2 | ngram 的**草稿上下文构建**在 hybrid 上特别贵（每步重建 attention metadata、Mamba 对齐） | 用 profile / 拆步计时；或换一个非 ngram 的 drafter |
| A3 | hybrid 的 KV/状态布局使**验证步的批形**退化 | 读 scheduler 的 batch 组成，对比两臂实际 batch size |

**A1 是最关键的**：如果 5.8× 主要来自模型本身（628 vs 1468 = 2.34×），
那么**投机额外贡献的**是 5.80 / 2.34 = **2.48×**——与 C-1b 的 2.82× 量级一致。
⇒ **下一步必须报"相对各自 K=0 的比值 + 接受率"三者并列**，否则会把模型差异算成投机代价。

## 5b. 补做：把 5.8× 拆开（A1 已排除）

同一统一装置跑满 2×2 网格（本轮补测 K=0 基线）：

| 单元 | tok/s | **accept_rate** | **mean_accept_len** |
|---|---|---|---|
| dense, K=0 | 1452.1 | — | — |
| dense, K=3 | 1098.9 | **0.5725** | 2.7174 |
| hybrid, K=0 | 622.0 | — | — |
| hybrid, K=3 | **223.0** | **0.6869** | 3.0608 |

**正确分解**（这是 §5 A1 要的）：

| 效应 | 倍数 | 含义 |
|---|---|---|
| dense→hybrid，**无投机**（模型本身） | 1452.1/622.0 = **2.34×** | **不是投机的锅** |
| dense，投机代价 | 1452.1/1098.9 = **1.32×** | |
| **hybrid，投机代价** | 622.0/223.0 = **2.79×** | **← 投机本身的锅** |
| 合计（dense K3 vs hybrid K3） | 1098.9/223.0 = **4.93×** | |

⇒ **先前写的"5.80×"包含了 2.34× 的模型差异，不能全记在投机账上。**
**投机本身的代价是 hybrid 2.79× vs dense 1.32×（差 2.1×）**，与 C-1b 独立测得的
2.82× vs 1.23× 一致（跨运行复现 ✅）。

**而与此同时接受率仍然是 hybrid 更高**（0.687 vs 0.573，接受长度 3.06 vs 2.72）。
⇒ **接受率更高、投机代价反而大 2.1 倍** —— 这是本轮最硬的一条。

## 6. 诚实边界

- 单模型、单 K=3、单 drafter（ngram）、并发 1（批量提交）、`enforce_eager`、前缀缓存开。
- `mean_accept_len` 的算法：`1 + accepted/steps`（每次 verify 步含 1 个 bonus token），
  与引擎文档口径一致，但**我未与引擎自报值交叉验证**（引擎未暴露 drafts 计数器）。
- **本轮结论是"接受率不是 hybrid 变慢的原因"，不是"hybrid 变慢的原因是 X"。** 后者尚无证据。
- 复现：`/root/autodl-tmp/c1d_unified.py --ks 3 --targets dense,hybrid`；
  原始数据 `results/C1d-unified/`。
