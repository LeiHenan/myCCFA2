# S1 痛点发现（Pain discovery） — 前缀复用的生效时延（重复前缀第 2 次仍零命中）

**候选**：`prefix-reuse-lag` ｜ **成本上限**：0 GPU·h（可用 ≤1 GPU·h 做量级取证）
**目标**：只收集**真痛点**：有人真的疼、有量级、有可复现证据。此阶段禁止提方案。

## 候选痛点清单

### P1（主）同一 serve 会话中，**完全相同的重复前缀在第 2 次出现时仍然零命中**

- **现象**：32 条 prompt（`--disable-shuffle`，同顺序）连续跑 3 次；`prefix_cache_hits_total` 的**增量**为
  **r1 = 0 / 131328**、**r2 = 0 / 131328**、**r3 = 130560 / 131328** —— 第 2 次发出**完全相同**的前缀却**一个块都没命中**。
- **后果（已实测）**：第 3 次的吞吐是前两次的 **2.10×（d3）/ 2.59×（d5）**。
- **谁在疼**：多轮 / agentic / RAG / few-shot 负载 —— 它们的提示前缀**反复出现**；若复用要等到第 3 次，则**每次前缀重现都白付一遍完整 prefill**（TTFT 与吞吐双输）。
- **量级**：**L2（自有实测，可复算）**：662/670/**1390** 与 750/758/**1942** tok/s（`A3_util95`），极差 **2.10× / 2.59×**。
- **证据（可复现）**：`results/p06-frontier/2026-09-13/A3_util95/bs32/*.metrics` 的增量（命令见 §逐条证据）。
- **反证（必须排除）**：① 不是抢占（`num_preemptions_total` 全为 0）；② 不是接受率（accept 1.732/1.727/1.713 稳定）；
  ③ 不是显存不足（池 497,673 tokens ≫ 需求 131k）；④ **不是"池太小留不住"** —— 那正是对照组 `A3_tight`（util 0.30，池 114,675）的表现：
  它三次**全零命中且吞吐平坦（1.01–1.02×）**，说明 0.95 组的第 3 次命中是真实发生的复用，而 0.30 组从未复用。

### P2 复用是否生效**取决于显存预算**，而预算通常按"最大吞吐"而非"复用能否生效"来设

- **现象**：同样负载，util 0.95 会出现复用（第 3 次），util 0.30 永不出现 ⇒ 同一份代码、同一负载，**只改一个内存参数就决定了前缀缓存有没有用**。
- **量级**：L2（同上数据）。
- **证据**：`A3_tight`（util 0.30）三次全零命中且平坦 595/602/603；`A3_util95`（util 0.95）第 3 次命中 130,560 tokens。
- **反证**：这是「池子太小」的显然结果，可能不构成新问题 ⇒ 需在 S4 判定它是否只是常识。

### P3 源码层面**看不出**为什么第 2 次不命中

- **现象**：`cache_full_blocks` 由 `single_type_kv_cache_manager.py:472` 在 **prefill 填充过程中**调用（不是等请求结束），
  且 full-attention 的 `block_mask = None`（默认缓存每个非空块），`enable_prefix_caching=True` 已确认 —— 按代码推断第 2 次就该命中。
- **谁在疼**：所有依赖前缀缓存的部署（无法预测收益何时出现）。
- **量级**：**L0/L1**（机制未知 ⇒ 无法量化"可回收多少"）。
- **证据**：`v1/core/single_type_kv_cache_manager.py:472` 的 `cache_full_blocks` 调用点 + `block_pool.py:225` 的入池条件 + serve log 的 `enable_prefix_caching=True`。
- **反证**：也许只是**指标口径**（`prefix_cache_hits_total` 只统计某种路径），而实际已复用 ⇒ **必须用 TTFT 交叉验证**（命中的 TTFT 应显著下降）。

## 不疼的反证

1. **可能是"最后一块永不入池"的正常结果**：命中数 130,560 = 8192−32 块（每 prompt 少 1 块），与"部分块不缓存"一致 ⇒ 大部分前缀其实**能**被复用，问题只在**时机**。
2. **可能只是 benchmark 假象**：guidellm issue #460 把"重复请求导致 100% 命中"直接当 bug 上报 ⇒ 说明"重复请求会命中"在别处是**预期**行为，
   那么本工作区看到的"第 2 次零命中"很可能是**特定并发/池配置**下的现象，而非普遍规律 ⇒ **必须做并发与池大小的扫描**。
3. **可能已有等价工作**（占位不再否决，但影响创新陈述）：PrefixWall（前缀缓存侧信道）、边缘调度协同、Zenodo 成本模型、
   agentic-kv-cache（淘汰策略复现）—— 都不是"复用生效时延"，但相关。
