# C-1c 判定：接受率拿到了，**但它与 C-1b 的吞吐结论相矛盾** ⇒ 必须先解决仪器分歧

**日期**：2026-09-14 ｜ **平台**：RTX 4080 SUPER 32GB，vLLM 0.29.0，ngram K=3
**目的**：补上 C-1b 缺的**接受率**证据（离线 `LLM` API 四次尝试全失败 ⇒ 改用 OpenAI server + `/metrics`）
**结果**：**拿到了**，但**它推翻了我对机制的假设**，而且**这套装置与 C-1b 的装置给出的吞吐差了一个数量级**。

---

## 1. 实测（server + `/metrics` 计数器，每格 3 遍，真实文本 48 请求）

| target | prefix cache | **accept_rate** | tok/s |
|---|---|---|---|
| dense Qwen3-4B | on | **0.5725** | 60.94 |
| dense Qwen3-4B | off | **0.5788** | 52.83 |
| **hybrid** Qwen3.5-4B | on | **0.9044** | 68.25 |
| **hybrid** Qwen3.5-4B | off | **0.8852** | 63.09 |

（`accept_rate` 由引擎自己的计数器算出：`Δaccepted / Δdraft_tokens`，3 遍的样本一致）

## 2. 发现一：**hybrid 的接受率比 dense 更高**（0.90 vs 0.57）—— 推翻我的机制假设

C-1b 我推测 hybrid 变慢是因为草稿被拒。**数据说反了**：

- **hybrid 接受率 0.885–0.904，dense 只有 0.573–0.579**；
- 即 hybrid **更"好猜"**（它的输出更模板化/更重复），草稿命中率更高。

⇒ **C-1b 里"代价来自低接受率"的假设被证伪。**
若接受率不是原因，hybrid 的额外开销只能在**草稿/验证路径本身**（每步固定开销、
Mamba 状态回滚、graph 重捕获等）——**但这只是剩下的可能性，我没有证据**。

## 3. 发现二（**必须先解决**）：两套装置的吞吐差一个数量级

| 装置 | hybrid K=0 | hybrid K=3 | dense K=0 | dense K=3 |
|---|---|---|---|---|
| **离线 `LLM` API**（C-1b） | 628.7 | 222.6 | 1468.2 | 1192.5 |
| **OpenAI server**（本文件） | — | **68.25** | — | **60.94** |

**同一台机器、同一模型、同一 K、同一语料，吞吐差 3–20×。**

**这意味着我目前无法把两套结果放在一起比较**，因此：

- C-1b 的"**hybrid 比 dense 慢 2.4–2.8×**"是在**离线装置**上测的，**未在 server 装置上复现**；
- 本文件的"**hybrid 比 dense 略快**"是在**server 装置**上测的；
- **两者不能同时为真** ⇒ 至少有一套装置有系统性偏差。

**候选原因（均未验证）**：
1. server 装置里 `ignore_eos` / `max_tokens` 未被遵守，实际输出长度远超 32 ⇒ 吞吐被严重稀释；
2. server 装置每请求 `seed=0` + 请求级调度引入了不同批形；
3. 离线装置的 `llm.generate(flat)` 是**一次批量提交 48 个请求**，server 是**串行 48 次 HTTP** ⇒ 前者吃满了 continuous batching，后者几乎无批处理；
4. tokenizer 不同（server 用 `--model` 的，客户端用 `--tokenizer` 的）。

**我倾向原因 3**（批量 vs 串行 HTTP），但**没有验证**。

## 4. 因此本轮的结论只能是**有限度的**

| 主张 | 状态 |
|---|---|
| hybrid 接受率高于 dense（0.90 vs 0.57，同装置内 3 遍一致） | ✅ **成立**（装置内自洽，计数器直读） |
| C-1b 的"低接受率"机制解释 | ❌ **被证伪** |
| hybrid 上投机是净损失 | ⚠️ **仅离线装置**；server 装置**未复现** |
| hybrid 比 dense 慢 2.4–2.8× | ⚠️ **同上，不可跨装置引用** |

## 5. 下一步（**先解决仪器分歧，再做任何机制主张**）

**统一装置实验**（这是唯一能继续的路）：在同一套 server 装置里同时测 dense/hybrid × K∈{0,3}，
并且**用批量提交**（一次 POST 多请求 / 用 `vllm bench serve` 的并发模式）对齐离线装置的批形，
同时记录**每请求实际输出长度**以排除原因 1。
**判据**：
- 若统一装置下 hybrid 仍慢 ⇒ C-1b 成立，且**接受率更高却更慢**是真发现（机制在草稿路径）；
- 若统一装置下 hybrid 不慢 ⇒ **C-1b 是装置伪影 ⇒ 归档 C-1**。

**在跑完这个之前，我不会写任何机制主张。**

## 6. 诚实边界

- `mean_accept_len` 始终为 **null**：引擎未暴露 `vllm:spec_decode_num_drafts` 计数器，
  所以只能算接受率，算不出平均接受长度。
- `accept_rate` 是**装置内**量（Δcounter），**不能与离线装置的接受率对比**（离线根本没测到）。
- 每格只有 3 遍 × 48 请求；server 装置的三遍数值稳定（如 dense off: 52.8/55.1/52.8），
  但**稳定不等于正确**——上面的数量级分歧正说明装置本身可能是错的。
- 复现：`bash /root/autodl-tmp/c1c_run.sh`（K=3），原始 JSON 在 `results/C1c-acceptance/`。
