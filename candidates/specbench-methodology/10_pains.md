## 候选痛点清单

量级：**L2** = 有数字 + 可复现；**L1** = 有数字声明（他人）；**L0** = 尚无数字。

### P1 暖机爬升随配置变化 ⇒「N 次重复取均值」系统性偏置赢家

- **现象**：同一格的前几次重复存在冷启动爬升，**且爬升幅度取决于配置**（深度/batch），因此"跑 N 次取均值"会**朝特定方向**偏置结论，而不是只增加噪声。
- **谁在疼**：所有做投机解码/服务对比的人（含审稿人复核时算不出同样的数）；做部署选型的人。
- **量级**：**L2** —— A1 网格 120 格逐次数据实测：`bs=1` 时深 drafter（d5）爬 **11–13%**，浅的（d1/d3）只爬 **6–7%**；`bs≥8` <4%。改用稳态口径（后一半重复）后，d5 相对优势从 **25.6–32.6%** 变为 **26.3–31.8%**。
- **证据**（可复现，零 GPU）：`python probes/p06-frontier/analyze_bs_grid.py --dir results/p06-frontier/2026-09-13/A1_4k --stat mean`（旧口径）对 `--stat steady`（正确口径）；逐次数列见 `results/…/A1_4k/bs_grid.csv` 的 `ramp_top_pct` 列。
- **反证**：若爬升只影响绝对值、不影响**排序**，则价值有限 ⇒ 必须实测"排序是否被扭曲"（列为 S4 判定项）。
- **🔻 2026-09-13 零卡复算（S4）：本条【被自己的数据削弱，已降级】** —— 在 120 格 A1 数据上三种口径（`rep1`/`mean`/`steady`）下 `argmax_depth` **8/8 格都没变**；差距偏差最大仅 **2.31 pp** 且**符号不一致**（bs=1/32 为负、bs=8/16 的 γ=7 为正）⇒ **不足 8% 闸门，不得写成论文主张**。原始结论保留在此并标注被削弱（不许静默改写）。证据：`results/p08-specbench/2026-09-13/artifacts.md`。

### P2 数据集选择让接受率恒为 1.00 —— 投机解码"看起来免费"

- **现象**：`vllm bench serve --dataset-name random` 用随机 token 当输入 ⇒ 草稿 token **必然被接受**，接受长度 ≈ γ+1，于是测出的是**理论上界**而非真实负载表现。
- **谁在疼**：任何用默认 bench 参数做投机解码对比的人；用随机数据集做的"加速比"结论。
- **量级**：**L2（本工作区实测）** —— `#6` T0 期间实测 `--dataset-name random` 下**接受率 ≡ 1.00**；改用真实文本后接受长度 **1.30→2.83**（随深度）⇒ 同一配置的接受长度相差 **≈2.2–3.9×**。
- **证据**：`probes/p06-frontier/run_t1.sh` 第 11 行注释（"必须 `DATASET=custom`（真实文本）：`--dataset-name random` 会让接受率恒为 1.00"）+ `results/p06-frontier/2026-09-12/T0/summary.md`。
- **反证**：若没人真的用随机数据集下结论，则这是"纸上风险" ⇒ 取证任务 2（抽查公开评测脚本）。

### P3 `mean_itl_ms` 是「每步」而非「每 token」⇒ 每步代价被误算 accept_len 倍（尾延迟同理）

- **现象**：投机解码下 ITL 是**每个 verify 步**的延迟（一步吐 `accept_len` 个 token），不是每 token。当成"每 token 延迟"用，每步代价就错 `accept_len` 倍；`p99 ITL` 被当成"用户体验的 p99 每 token 延迟"同样错。
- **谁在疼**：做"深度/长度权衡"这类**每步代价**分析的人（本工作区就写错过一次，靠自测抓到）；报尾延迟的人。
- **量级**：**L2** —— 18/18 格实测 `tpot ≈ itl / accept_len`（误差 <1%）；A1 `bs=32/γ=7` 实测 `mean_itl=34.9 ms`、`accept_len=2.83`、`tpot=12.3 ms` ⇒ **2.83×**；`p99_itl=48.5 ms` vs `mean_tpot=12.45 ms` ⇒ **3.9×**。
- **证据（可复现）**：`python probes/p06-frontier/analyze_mechanism.py --dir results/p06-frontier/2026-09-13/A1_4k`（脚本 docstring 记录了恒等式与"初版写错、被自测抓到"的过程）。
- **反证**：若各引擎文档已写清且无人误用 ⇒ 价值下降。**反证存在**：vLLM 需专门发文档 PR **[#55283](https://app.semanticdiff.com/gh/vllm-project/vllm/pull/55283/overview)**「Clarify ITL vs TPOT Prometheus metrics」⇒ 混淆是官方承认的普遍问题。
- **🔺 2026-09-13 新增直接证据（比"文档混淆"强得多）**：vLLM issue **[#19776](https://github.com/vllm-project/vllm/issues/19776)**「**[Bug][Spec Decode]: TPOT in prometheus is ITL in vllm serve**」—— **引擎自己在 `/metrics` 里导出的 TPOT，在投机解码下实际是 ITL**，即恰好等于我们的恒等式 I1（`tpot ≈ itl / accept_len`）被**在公开指标里违反**；官方目前的处置是一份**文档 PR #55283**。
  ⇒ 这把本方向从"可能有人会用错"升级为"**引擎的公开指标在投机解码下就是错的**"，且**修法只是改文档**（自检器本可自动发现这类不一致）。
  另两条配套证据：vLLM PR **[#31739](https://github.com/vllm-project/vllm/pull/31739)**「[Spec Decode][UX] **Add acceptance stats to `vllm bench serve` report**」（接受率统计是**后加的**，说明此前报告里没有）＋ vLLM 文档新增「[Per-Request Acceptance Metrics](https://docs.vllm.ai/en/latest/features/speculative_decoding/acceptance_metrics/)」页。

### P4 基准客户端单进程 ⇒ 高并发下 TTFT/TPOT 被系统性抬高

- **现象**：主流 bench 工具用单进程 asyncio 客户端，在 GIL 下形成客户端排队瓶颈，随请求率上升**抬高 TTFT/TPOT**，把客户端瓶颈误读成引擎瓶颈。
- **谁在疼**：所有做高并发服务评测的人。
- **量级**：**L1（他人）** —— 该论文用 M/G/1 建模 + 实测证明，并提出多进程客户端与 NTPOT 指标。
- **证据**：arXiv **[2605.24217](https://arxiv.org/abs/2605.24217)**《Identifying and Mitigating Systemic Measurement Bias in Production LLM Inference Benchmarks》（2026-05，v2）。
- **反证**：**这篇论文本身就是反证** —— 该靶子已被占 ⇒ 我们不重复打。
- **占位快扫**：✅ 已读摘要级正文，确认靶子是**客户端**，不是引擎控制回路。

### P5 从业者没有公认测法；关键量在可观测性上分散/缺失

- **现象**：开启 MTP/投机解码后**"该怎么测"没有公认答案**；接受率这类核心量在某些服务端**根本不导出**。
- **谁在疼**：一线部署与运维（论坛提问者）。
- **量级**：**L1**（多处独立证据，均非本工作区）。
- **证据**：vLLM 论坛《[vLLM 的 MTP 的标准测试方法是什么？](https://discuss.vllm.ai/t/vllm-mtp/2715)》、《[服务开启 MTP，如何评估指定维度的真实吞吐](https://discuss.vllm.ai/t/vllm-mtp/2658)》；vllm.cpp issue **[#2770](https://github.com/mudler/vllm.cpp/issues/2770)**「the OpenAI server exports no speculative-decoding acceptance metric」；vLLM PR **[#55283](https://app.semanticdiff.com/gh/vllm-project/vllm/pull/55283/overview)**。
- **⚠️ 必须如实记录的更正**：我们**自己**在 vLLM 0.29 的 `/metrics` 里**确实读到** `vllm:spec_decode_num_accepted_tokens_total` / `_per_pos_total`（见 `results/…/A1_4k/*.metrics`）⇒ **"服务端不导出接受率"在 vLLM 上不成立**，只对 vllm.cpp / 部分 OpenAI 兼容服务端成立。本条**收窄为**："关键量**分散且命名不统一**（部分引擎有、部分没有；ITL/TPOT 需专门发文澄清）"。
- **反证**：若上游已把标准测法写进文档 ⇒ 本条消失。目前没有（所以才有人在论坛问）。

### P6 观察到的"模型行为"可能是推理后端的副作用

- **现象**：同一模型在不同推理后端/批处理下给出不同结果 ⇒ 以"模型能力"名义报告的东西可能是**后端伪影**。
- **谁在疼**：做评测与模型对比的人（与我们的 A1/A4 同源）。
- **量级**：**L1（他人）**。
- **证据**：arXiv **[2608.04714](https://arxiv.org/abs/2608.04714)**《What We Observe as LLM Behavior Can Be a Side-effect of Inference Backend》。
- **反证**：靶子是**行为/正确性**，不是**性能度量** ⇒ 与本方向相邻但不重叠（作 S3 的边界材料）。
