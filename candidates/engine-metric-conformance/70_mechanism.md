## 效应分解：`mean_itl_ms` 到底是什么

**源码证据（vLLM 0.29.0，逐字）**：

| 量 | 计算处 | 定义 |
|---|---|---|
| `output.itl` | `benchmarks/lib/endpoint_request_func.py:241` | `output.itl.append(timestamp - most_recent_timestamp)`，**位于 `if choices := data.get("choices"):` 内** ⇒ **每收到一个"含内容的流式 chunk"记一次**（不是每 token，也不是每步） |
| `mean_itl_ms` | `benchmarks/serve.py:620` | `itls += outputs[i].itl` 后取均值 ⇒ **每个 chunk 的平均间隔** |
| `mean_tpot_ms` | `benchmarks/serve.py:616` | `tpot = (latency - ttft) / (output_len - 1)` ⇒ **每 token** |

⇒ **恒等式（本次建立）**：

```
mean_itl_ms / mean_tpot_ms  ≈  每个 chunk 平均携带的 token 数
```

**这个比值不是常数，它取决于引擎的「流式/chunk 策略」** —— 而策略随**引擎**与**投机方法**变化。

## 对 C2 反常的解释（两次实验的差值由此闭合）

| 实验 | 投机方法 | itl (ms) | tpot (ms) | 比值 | accept_len | chunk 平均携带 |
|---|---|---|---|---|---|---|
| **p08** ground truth（24 格） | dflash2 drafter | ≈16 | ≈5.6 | **2.85** | 2.85 | **≈accept_len**（一步的接受结果打包成一个 chunk） |
| **p09** 跨引擎实测 | **NGRAM** | 12.3 | 11.4 | **1.07** | 1.50 | **≈1**（几乎每 token 一个 chunk） |

⇒ **同一个引擎、同一个客户端、同一个模型、同一个 γ，仅换投机方法，`mean_itl_ms` 的语义就变了。**

## ⚠️ 就地更正（不许静默改写历史）

**本工作区此前把 `mean_itl_ms` 表述为「每步延迟（step_ms = itl）」**（decision #67/#76、
`probes/p06-frontier/analyze_mechanism.py` 的 docstring、`analyze_bs_grid.py` 的注释）。

**准确表述应为**：`mean_itl_ms` 是**每个流式 chunk** 的间隔；在 **dflash2** 下 chunk 恰好携带该步接受的
`accept_len` 个 token，所以它**数值上** ≈ 每步延迟 —— 该表述在那组数据上**结论仍然成立**
（`tpot ≈ itl/accept_len` 在 18/18 格误差 <1%），但**它不是一个通用定义**：
换到 NGRAM 就退化为 ≈每 token。

**影响范围**：所有引用"ITL 是每步"的地方（`analyze_mechanism.py` docstring、decision #67/#76）——
已就地标注更正；**结论数字不改**（它们来自 dflash2 数据，前提在那种情况下成立），**但表述必须加限定**。

## 为什么这**加强**了本候选（而不是杀死它）

本候选的主张是"**同名指标的语义随环境漂移，跨引擎/跨方法比较因此不可比**"。
本次拿到的正是一个**源码级、双边实测**的实例：

1. 指标名相同（`itl`）、客户端相同、模型相同；
2. **仅换投机方法**，`itl/tpot` 从 **2.85** 变成 **1.07**；
3. 机制清楚：**chunk 策略不同**（源码行给出）；
4. **后果可量化**：把 `itl` 当"每 token 延迟"用，误差 = chunk 平均携带 token 数（实测最高 **2.85×**，远超 8%）。

⇒ 这比原先设想的"跨引擎名称映射不足"更具体：**连"同一个引擎内、同名指标"都可能不可比。**

## 替代解释与排除证据

| 替代解释 | 排除证据 |
|---|---|
| **显存挤占**导致延迟异常 | vLLM 侧 `num_preemptions_total` 全程为 0（计数器，非 gauge）；SGLang 侧 `num_retracted_reqs` = 0 |
| **排队**（并发不足/客户端瓶颈） | 两次实验用**同一个客户端**、同一并发档；且 C1 显示 token 计数完全一致 ⇒ 负载相同 |
| **顺序/前缀缓存**造成 chunk 结构差异 | 两次都用 `--disable-shuffle` + 同一 prompt 文件；前缀缓存只影响 prefill，不改 decode 的 chunk 组装 |
| **冷启动/暖机** | 只比较**同一次 serve 会话内**的 rep；且该效应在 p08 已量化（bs=1 约 11–13%）⇒ 不足以解释 2.85 vs 1.07 的**语义级**差异 |
| **跨机器差异** | 两次实验在**同一台机器、同一张卡**上完成 |
| **数值巧合**（2.85 恰好等于 accept_len） | 18/18 格全部吻合（p08），且**源码行给出机制**（chunk 携带多 token）⇒ 非巧合 |
| **客户端版本差异** | 两次都用 vLLM 0.29.0 的同一个 `vllm bench serve` |

**结论**：唯一能解释两次差值的是**机制本身** —— chunk 策略（源码行 + 双边数值 + 18/18 吻合）。

## 适用范围（诚实边界）

1. **只验证了 vLLM 0.29.0 的客户端**（`vllm bench serve`）；SGLang 侧的 `itl` 语义**未测**（其 NGRAM 在 sm120 起不来）；
2. `accept_len` 与 chunk 携带数**在 dflash2 下数值相等**是**观测事实**，不是引擎契约 ⇒ 换版本可能变；
3. **未测**：其他流式协议（非 OpenAI completions）、`stream_options` 差异、多 token 的 usage 汇总路径；
4. C3（两引擎接受长度定义）**仍未判定**。

## 上界复核

S4 预估"已知分量 2.45–2.88×"——**本次源码级确认成立**（2.85× 的实测 + 机制解释），
且新增一条**更普遍**的上界：**chunk 策略造成的语义漂移没有上界保证**（取决于引擎实现，
本次观测到 1.07–2.85 的两端）。
