# S1 痛点发现（Pain discovery） — 跨引擎指标定义一致性（投机解码/服务度量）

**候选**：`engine-metric-conformance` ｜ **成本上限**：0 GPU·h（可用 ≤1 GPU·h 做量级取证）
**目标**：只收集**真痛点**：有人真的疼、有量级、有可复现证据。此阶段禁止提方案。
**策略前提（用户已选 ②）**：本方向**不声称"没人做过"**，而是承认有邻居，**把差异轴写清楚做强**。

## 候选痛点清单

量级：**L2** = 有数字 + 可复现；**L1** = 有数字声明（他人）；**L0** = 尚无数字。

### P1 跨引擎比较被普遍依赖，但**指标定义没有任何一致性保证**

- **现象**：论文/博客/厂商材料大量做"引擎 A 比引擎 B 快 X%"的比较，但**没有任何机制保证 A 的 `acceptance length` / `ITL` / `TPOT` 与 B 是同一个量**；各家自行实现、自行命名。
- **谁在疼**：所有做跨引擎选型与对比的人；审稿人要复核跨引擎结论时无从下手。
- **量级**：**L1（他人侧证据强）** —— NVIDIA **Dynamo 专门写了 `docs/observability/metrics-comparison.md`**（PR **#8055**「docs(observability): **add cross-engine metrics comparison**」）来说明不同引擎指标如何对应 ⇒ **厂商自己承认需要人工对照表**。
- **证据**：[Dynamo PR #8055](https://github.com/ai-dynamo/dynamo/pull/8055) 与 [metrics-comparison.md](https://github.com/ai-dynamo/dynamo/blob/2553addc8f9a6f80732ccacc2a2e402216afa5a9/docs/observability/metrics-comparison.md)。
- **反证**：若该文档已经把所有定义差异写全且被广泛采纳 ⇒ 痛点只剩"没人读文档"⇒ 价值下降。**必须实测文档未覆盖的差异**（S4）。

### P2 厂商已经开始"为了可比性而人为控制接受长度"，说明混淆是行业级共识

- **现象**：接受长度是投机解码性能的**混淆变量**（它同时取决于模型、数据、γ），跨引擎比较必须控制它；AMD 直接提供了**强制接受长度**的能力。
- **谁在疼**：做硬件/引擎横评的人。
- **量级**：**L1**。
- **证据**：AMD ROCm 文档 **[Forced acceptance length](https://rocm.docs.amd.com/projects/atom/en/latest/forced_acceptance_length.html)**（`atom` 项目）。
- **反证**：这是**厂商测试工具**，不是定义规范 ⇒ 恰好说明**缺的是规范**（对我们有利），但也要承认"控制手段已存在"。

### P3 单引擎内部是**自洽**的 ⇒ 问题定位在"跨引擎定义"而不是"引擎有 bug"

- **现象**：我们已经在 vLLM 0.29 上验证：五条度量恒等式在 **24/24** 格成立（I1 误差 ≤1.72%、两条独立路径 I3 一致、无 I2/I4 违规）。⇒ 引擎内部没问题，**差异只可能出现在引擎之间**。
- **谁在疼**：同 P1。
- **量级**：**L2（自有实测）**。
- **证据**：`results/p08-specbench/2026-09-13/consistency.md`（24 格）、`candidates/specbench-methodology/60_decision.md`（decision #76）。
- **反证**：单引擎自洽**不必然**意味着跨引擎不自洽 ⇒ **这正是 S4 必须实测的第一件事**；若实测发现各引擎定义其实等价，本方向**自我判死**。

### P4 同一份"指标"在不同引擎里的**语义不同**已经有确凿实例

- **现象**：vLLM 的 Prometheus **TPOT 在投机解码下数值等于 ITL**（即每步延迟而非每 token），需要专门发文档 PR 澄清。
- **谁在疼**：直接读 `/metrics` 做监控与告警的人 —— 会把"每步"当成"每 token"，**数值差 `accept_len` 倍**（我们实测 2.45–2.88×）。
- **量级**：**L2（自有实测 + 官方 issue）**。
- **证据**：vLLM issue **[#19776](https://github.com/vllm-project/vllm/issues/19776)**「[Bug][Spec Decode]: TPOT in prometheus is ITL in vllm serve」＋ 文档 PR **[#55283](https://app.semanticdiff.com/gh/vllm-project/vllm/pull/55283/overview)**；我们自己的放大倍数实测见 decision #76。
- **反证**：这是**命名**问题而非数值问题（数值上引擎是自洽的，decision #76）⇒ 它证明的是"**语义/命名层缺规范**"，不是"数值算错"。必须如实区分。

### P5 社区需要"公式参照"，但只以**单篇论文附录**的形式存在

- **现象**：指标定义散落在各论文附录与各引擎文档里；有人不得不在论文里专门用一节列出"exact formulas for reference"。
- **谁在疼**：想复现或对比的读者。
- **量级**：**L1**。
- **证据**：**InferenceBench**（arXiv [2607.20468](https://arxiv.org/html/2607.20468v1)）§3.2「a condensed version of these definitions appears in Section 3.2; this subsection collects the exact formulas for reference」。
- **反证**：若学界已形成事实标准（大家都照同一套公式）⇒ 差异可能很小 ⇒ 同样由 S4 实测裁决。

### P6 "口径陷阱"在实践里真的会绊倒人（我们自己就是样本）

- **现象**：写自检器时，我们自己两次因口径错误产生**假的不一致**：(a) 把**累计计数器**与**单次运行值**直接相比 ⇒ 造出 8–16% 假差异；(b) 分组键漏掉"同一 serve 会话内先跑 bs=1 再跑 bs=32" ⇒ 再次假报警。
- **谁在疼**：任何跨引擎/跨工具对比的人都会踩 —— 这类错误会让**正确的引擎看起来不一致**。
- **量级**：**L2（自有实测）**。
- **证据**：decision #76；修正前后 4/24 → **0/24**。
- **反证**：这是"我们的 bug"，不是别人的疼 ⇒ 只能作为**方法论动机**（说明"口径一致性"是真实工程问题），不能作为"别人在疼"的证据。

## 逐条证据

P1/P2/P4/P5 为**他人侧**证据（厂商 PR、厂商文档、官方 issue、论文附录）；P3/P6 为**自有实测**（24 格数据、两次仪器 bug）。
**六条里 4 条来自他人**，满足 S1 的"≥2 条来自别人"要求。

## 不疼的反证

1. **P1 的反证最强**：Dynamo 已经写了跨引擎指标对照文档 ⇒ 可能"已经被治"（只是没人读）。**S3 必须读该文档正文**判断它覆盖到什么程度。
2. **P3 的反证**：单引擎自洽不蕴含跨引擎不自洽 ⇒ **若实测各引擎定义等价，本方向当场判死**（这是本方向最可能的死法）。
3. **P4 的反证**：那是命名问题，数值自洽 ⇒ 不能夸大成"引擎算错"。
4. **P6 的反证**：自己的 bug 不是别人的疼。
5. **方法学前车之鉴**：`specbench` 的核心假设（random 数据集抬高接受率）被自己的 ground truth 否证（decision #76）⇒ **本方向的一切"定义差异"主张，都必须先在两个引擎上实测**，禁止只凭文档推断。

## 取证任务（≤1 GPU·h，全部可复现）

1. **读 Dynamo 的 `metrics-comparison.md` 正文**（0 GPU·h）：逐条记录它声明了哪些对应关系、**没有**覆盖哪些指标（尤其接受长度与 ITL/TPOT 在投机解码下的语义）。
2. **装第二个引擎**（SGLang，独立 venv，数据盘，~30 min）：与 vLLM 在同一张卡、同一模型、同一负载上跑。
3. **定义一致性实测**（≤1 GPU·h）：同一负载下取两引擎的 `accept_len` / ITL / TPOT / 吞吐，**逐项判定是否同一个量**（用 P08 的五条恒等式做参照系）。
