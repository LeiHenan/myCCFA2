# 案例研究：把《从实践现场提炼研究课题》用到尽 —— 4 轮、0 存活

**日期**：2026-09-15 ｜ **机器**：单卡 RTX PRO 6000 96 GB / sm120 / vLLM 0.29.0
**成本**：≈4 GPU·h + 8 个子代理（其中 4 个做文献）
**结论**：**4 个候选全部 KILL，0 存活。** 但**方法论本身经受住了检验**——它给出的每一条判据都能杀，且杀得可复核。
**用途**：本文是 [`PRACTICE_TO_TOPIC_METHODOLOGY.md`](PRACTICE_TO_TOPIC_METHODOLOGY.md) 的**实证附录**，也是它**边界**的证据。规则可追溯、可反驳。

## 1. 一句话

> 我按这份方法论走完了完整循环：**4 个候选，每个都先冻结判据、再做最便宜的证伪实验**，结果 **4 个全杀**（2 个被实测自证伪、2 个被已发表工作占位）。**方法论没有失灵**——它每一次都用小时级成本拦住了一个周级的错误。**真正的问题是分母**：在第 5 节列的约束下，"可推导的机制"集合已被 2024–2026 的出版物基本抽干。

## 2. 四个候选与判决（全部先冻结判据）

| # | 候选（机制主张） | 判决 | 决定性证据 | 死因类别 |
|---|---|---|---|---|
| A | vLLM 默认调度把 token 预算切太小 ⇒ 一个"最大化 fresh-tokens-per-pass"的策略能赢 | **KILL** | dense 仅 **+2.83%** < 5% 门槛；**关掉 prefix cache 后 MoE 增益反而更大**（+26.18%→+28.61%）⇒ 收益 100% 来自"chunk 变大" | **被实测自证伪** |

| C | KV 压缩/稀疏这一族的收益是 **batch 的函数**，故低并发下不适用 | **KILL** | 五篇独立影响（见 §3），其中 [2503.24000](https://arxiv.org/abs/2503.24000) 是 **MLSys 2025 正刊**且把"哪些 batch×prompt 范围有利"做成了决策工具 | **已发表占位** |

## 3. 占位核查的五篇（全部逐字取证，定串复核）

| 占位者 | 级别 | 它逐字说了什么 |
|---|---|---|
| [2503.24000](https://arxiv.org/abs/2503.24000) | **MLSys 2025** | *"a throughput analysis tool to decide **under which ranges of batch sizes and prompt lengths** KV cache compression can present advantageous performance"* |
| [2504.17768](https://arxiv.org/abs/2504.17768) | venue UNVERIFIED | *"At batch size 1, weight loading dominates: KV cache represents only **7%** at 16K tokens… At batch size 8 … **35–80%**"* + *"**At batch size 1, sparse attention provides minimal benefit**"* |
| [2402.05099](https://arxiv.org/abs/2402.05099)（Hydragen） | — | *"with small batch sizes or short sequence lengths, decoding speed is often bottlenecked not by attention, but by **reading the parameters of the model from GPU memory**"* |
| [2604.19157](https://arxiv.org/abs/2604.19157)（SAW-INT4） | — | *"**neutral at low concurrency** and increasingly advantageous at higher concurrency"* |
| [2608.23962](https://arxiv.org/abs/2608.23962) | — | *"The decision … turns on which side of this wall a deployment sits on; **context length and batch size do not decide it**"* ← **这一条是反证，不是占位** |

**外加引擎侧两处**：vLLM `--performance-mode`（PR #34936，**已发货**）的 docstring 按 batch 分模式；SGLang issue #30815 有按 batch×ctx 的 FP8-KV 症状表（`Small batch (1-8) → 10-30% slower`）。

**⇒ 方法论 §5.5 的警告被实证**：检索**系统性高估"已被占"**。我这里遇到的是反方向——我一直在**系统性高估"还没被占"**（4 个候选里 2 个我判断是空格，实测发现是已有常识）。

## 5. 我在本案例里犯的 5 个错（这是本文最有价值的部分）

技术判断错了可以改，**口径错了会让结论反向**（§7.2 的警告）。我 5 个错里有 3 个是口径类：

| # | 错误 | 类别 | 后果 |
|---|---|---|---|
| 1 | 单位错误：把 `N/throughput` 当作 per-pass 时间（应为 `C/throughput`） | **代理量** | 拟合出负值，一度以为模型不成立 |
| 2 | 误判 MoE 的 HIT/MISS 臂"被混淆"（声称两臂输出 token 数不同） | 未核原始字段 | **读回原始 JSON 后确认两臂 `max_tokens` 都是 1，判断是错的**——我凭派生指标推断 |
| 3 | 指定的"打乱前缀"对照**无效** | **对照组未验证其未生效** | shuffled 臂命中率 8,137 ≈ agentic 的 8,111（真 miss 应为 512）；子代理自行补跑真对照才拿到决定性数字 |
| 4 | 报"KV 占单步 100%"时**分子分母口径不同**（Δ整步增量 ÷ 预测 KV 项） | **代理量** | 高估；正确说法只是"B≥8 时增量与 KV 字节成正比（0.82）" |
| 5 | 在子代理简报里把 `B*` 方向**推反**（写"MoE 的 a 更大 ⇒ 翻转批次更低"，实际 `B* ∝ a` ⇒ 更高） | **参数相关的结论** | 子代理独立复核代数后指出；我采纳，**不主张任何方向的 MoE/B\* 比较** |

**⇒ 5 个错里 4 个是"没读原始字段 / 没核分母口径 / 没验对照"**，即 §7.1"任何数字都要能追溯到采集方式与口径"与 §9.2"跳过度量审计"的直接实例。
**并且 4 个错全部由"事前冻结的判据 + 读回原始数据"抓出**，没有一次是我事后自省发现的。

## 6. 对方法论的 4 条修订建议（全部来自本案例的失败）

### 6.1 §3 的"变量是否在手"需要一个**前置检查：分母是否成立**

本案例最贵的错误：我把"agentic 负载（长输入短输出）"当作我的分母，围绕它做了 4 轮。**直到第 3 轮才算清：在那个分母里 prefill 只占端到端 0.42–1.18%**（图 D≫P 时 decode 主导）。
⇒ **加一条**：*在问"变量在不在手"之前，先算清"我瞄准的那个成本项占目标量的比例"；占比 <10% 的，直接归档，不要进入抽象阶段。*
**代价**：这一条若早用，能省掉候选 A 的全部 GPU 预算。

### 6.2 §2 的"四类原料"要加一个**交叉判据**：原料必须与"目标成本项"同轴

我记下了真实的**反常**（prefill 占比高、KV 占比低），但那两个数**属于不同的量纲**，拼不成一条可检验陈述。⇒ **加一条**：*每条记录必须标注它属于哪条成本轴（延迟/吞吐/容量/带宽/能耗）；跨轴的观察不能直接抽象成一条陈述。*

### 6.3 §5 要**明写"检索的偏置方向"**

§5.5 说了检索**高估"已被占"**。本案例证明**反向偏置同样致命**：我 4 个候选里 2 个自认是空格，实测都是已有常识（Hydragen 逐字写过、2504.17768 附录测过）。
⇒ **加一条**：*检索既高估"已被占"（只看已发表），也让人高估"还没被占"（因为**自己的第一个想法通常不是第一个想法**）。因此"框架未被占"**只能由实验确认**，不能由"我没搜到"确认。*

### 6.4 §10 的边界要加第 5 条：**它无法更换分母**

§10.1 说"寄生在实践上"、§10.3 说"无法产生由新能力驱动的课题"。本案例给出更精确的形态：
> **当约束（单卡 / 无生产轨迹 / 无多卡 / 无引擎内部权限）固定时，可从第一性原理推导的机制集合会先于耐心耗尽。** 本案例 4 个候选全部落在同一约束内 ⇒ 命中率 0/4。
⇒ **加一条**：*当连续 N≥3 个候选都死于同一约束时，问题不在候选，在分母。此时唯一有产出率的方向是**改变分母**（换硬件档 / 换并行度 / 引入他人无法复制的真实负载），而不是继续在约束内推导。*
