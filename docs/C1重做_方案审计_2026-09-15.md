## 1. 致命错误：使原 P1/P2/P3 三个判定**都不能成立**

### 1.1 【结构性】主判据 P3 测的量，几乎完全由"是否发生跨请求前缀复用"支配

预登记 §1（`prereg:28-30`）：P3 = "(P/C 开 vs 关) 的差值在 dflash2 上显著大于在 eagle3/ngram 上"，且是**唯一立项判据**（`prereg:32`）。

复算 `repo2/results/C1-spec-prefix/2026-09-14/c1_full.json` + `c1_dflash.json`：

| drafter | PC on (tok/s) | PC off (tok/s) | off/on | 换算成"PC 收益" |
|---|---|---|---|---|
| 无投机 | 1196.92 | 230.52 | 0.1926 | 5.19× |
| ngram | 1231.92 | 253.14 | **0.2055** | 4.87× |
| eagle3 | 1431.34 | 259.09 | **0.1810** | 5.53× |
| dflash2 | 1461.59 | 270.02 | **0.1847** | 5.41× |

**四档的 PC 收益都是 4.9–5.5×；待检验的"类别差异"是 0.1810 vs 0.1847 = 2%。**

原因不是噪声，是**构造**：那 48 个请求共享同一个 1024-token system prefix（`c1_spec_prefix.py:56-64`，8 个对话用同一个填充串）。PC off 时这 48×1024 个 token 全部重算，PC on 时全部复用。于是 `off/on` 这个比值测的是**"预填充复用开关"**，而投机解码只作用于**解码**阶段、且只占墙钟的极小部分（每请求 prompt≈1024–1400 token，输出钉死 32 token，`c1_spec_prefix.py:104`）。

⇒ **用一个 5× 的共同效应做分母，去分辨 2% 的类别差异，是设计层面的不可辨识。** 判定文自己把这个共同效应写出来了（`C1判定…:64`：「无投机时 PC 给 5.19×；有投机时 4.9–5.5×。四档全部同向、量级一致」）——这句话本身就是"P3 无法区分 drafter"的证据，却被当作正面结论。

### 1.2 【致命】假设的核心对象 `dflash2`，在正式运行中**根本没跑起来**

复算 `c1_full.json`（该文件 `config.drafters = "none,dflash2,eagle3,ngram"`，即预登记的完整网格）：

```
dflash2|pc=off   ERROR: ValidationError: 1 validation error for SpeculativeConfig ...
dflash2|pc=on    ERROR: ValidationError: 1 validation error for SpeculativeConfig ...
eagle3|pc=on     tps_p1=1431.34     ngram|pc=on   tps_p1=1231.92     none|pc=on  tps_p1=1196.92
```

发表表格里的 dflash2 行（1461.59 / 270.02）来自**另一次独立脚本调用**：
`c1_dflash.json`，其 `config.drafters="dflash2"`、独立进程、独立 GPU 状态、独立时间窗。

⇒ **P1（dflash2 的机制预测）从来没有被测过；P3（dflash2 vs eagle3/ngram）的两侧不在同一次运行中，无法配对。** 而 `C1判定…:16` 的表头写的是「4 drafter × PC 开/关，每格 3 遍，48 请求/遍」——把两次运行合成了一张表。

**根因**（可从错误串直接读出）：预登记 §2 网格与探针 CLI 都写 `dflash2`，但 vLLM 的合法 method 名是 `dflash`（`dflash2` 只是 **checkpoint 的文件名**）。预登记本身写的是一个不可执行的轴取值。探针 `spec_cfg()`（`c1_spec_prefix.py:112-117`）虽然注释里写明了这一点，但第一轮运行用的仍是未修正的调用路径。

### 1.3 【致命】P1 的预测**不是**从 §0 自述的机制推出来的

预登记 §0（`prereg:12-13`）自述的上游机制是：
> dflash 需要 target 辅助隐藏状态建 context KV，而**前缀缓存恢复的 token 从不经过 target** ⇒ 读到未初始化 KV。

预登记 §1 的 P1（`prereg:28`）却是：
> `dflash2` 在第 2 遍时 **cached_tokens ≈ 0**（prompt 全量重算）。

**这两件事没有因果关系。** 前缀缓存的命中计数统计的是 **target 的 KV 块复用**；drafter 的辅助 KV 是另一条通路。上游机制若为真，可观测后果是**草稿上下文损坏**（接受率塌陷 / 输出与 PC-off 不一致），**而不是 cached_tokens 归零**。P1 选错了仪器。

⇒ 即使当时真的读到了 `cached_tokens`，**P1 也不具备证伪该机制的能力**。

### 1.4 【致命】唯一的机制仪器是一个空桩

预登记 §2（`prereg:45`）把 `cached_tokens` 列为**必报量**；探针 docstring（`c1_spec_prefix.py:18`）宣称 "report per-pass cached_tokens so P1/P2 are read directly, not inferred"。

实际代码（`c1_spec_prefix.py:148-153`）：

```python
cached = None
try:  # per-request cached tokens if the engine exposes them
    det = [getattr(o, "prompt_token_ids", None) for o in outs]
    cached = None if det is None else None
except Exception:
    cached = None
```

**三个分支恒为 `None`**，且 `cached` 从未写入 `results`（落盘只有 `passes` / `tps_p1` / `tps_first`，见 `:158-160`）。

⇒ P1/P2 的判定（`C1判定…:31-32`）**全部靠"第 2/3 遍是否变快"间接推断**。判定文 §5 自己承认了（`C1判定…:106`：「**没有直接读 `cached_tokens`**……**我没做到**」）。

## 2. 判据与统计缺陷

### 2.1 「1.15×」是拍出来的，而实测跨遍波动是 1.14–3.00×

预登记 §4（`prereg:58`）与 §5（`prereg:66`）两次使用 1.15×（"一个能写进论文的量级"），但**没有任何噪声模型**：没有 seed 间波动的定义、没有最小可检测效应（MDE）、没有功效计算。

同批数据的真实波动（`c1_full.json` 逐遍 tok/s）：

| 格 | pass0 | pass1 | pass2 | 跨遍极差 |
|---|---|---|---|---|
| none \| PC on | 1049.69 | 1170.05 | 1196.92 | 1.14× |
| ngram \| PC on | 410.62 | 1173.01 | 1231.92 | **3.00×** |
| eagle3 \| PC on | 1342.29 | 1400.33 | 1431.34 | 1.07× |

⇒ **阈值 1.15× 落在单格自身的跨遍波动之内。** 在一个波动可达 3× 的量上，用 1.15× 做杀判据，判据本身没有分辨力。

### 2.2 「第 2/3 遍变快 ⇒ 缓存命中」被**同一批数据**证伪

`C1判定…:31` 的推断是：「dflash2 PC-on 三遍 728 → 1172 → 1462 tok/s，第 2/3 遍显著快于第 1 遍 ⇒ **缓存确实在命中**」。

但 `c1_full.json` 里 **PC 关闭**的臂：

| 格 | pass0 | pass1 | pass2 | 首遍/稳态 |
|---|---|---|---|---|
| **ngram \| PC off** | **181.94** | 252.51 | 253.14 | **1.39×** |
| none \| PC off | 231.56 | 230.55 | 230.52 | 1.00× |
| eagle3 \| PC off | 260.88 | 261.26 | 259.09 | 1.00× |
| dflash2 \| PC off | 270.37 | 269.91 | 270.02 | 1.00× |

`ngram|PC off` 在**完全没有缓存可命中**的条件下，首遍同样慢 1.39×。⇒ **"首遍慢"至少部分是引擎预热（模块加载 / 分配器 / 首次 plan）的属性，不是缓存命中的证据。**

需要说清楚的是：PC-on 各臂**跨遍持续上升**（none 1049→1170→1197）确实与"缓存逐步填充"相容；但**该数据没有任何对照能把这一个解释与"预热 + 批内调度顺序"分开**。这正是重做必须**直读 `cached_tokens`** 的理由——不是因为它更精确，而是因为**原数据在原理上无法判定**。

### 2.3 P3 的两半条件实现不一致，且把零点对照排除在外

预登记 §4（`prereg:57-60`）写了两条并列条件：(a) 吞吐差 **≤ 1.15×** ⇒ 杀；(b) 该差**不大于** eagle3/ngram ⇒ 杀。

代码 `c1_spec_prefix.py:180-185`：
```python
print(f"    dflash2 worse than both? {p_d > max(p_e, p_n) * 1.15}")
print(f"    P3 gate (>=1.15x)?      {p_d >= 1.15}")
```
- (a) 被套到 `off/on` **比值**上，而预登记写的是"吞吐**差**"——口径在采数后被自行解释；
- (b) 从"不大于"改写成"需大于 115%"，语义被替换；
- 这个 `if` 只在 `dflash2/eagle3/ngram` 三者齐全时执行（`:179`），**把 `none`（预登记 §2 明确写的"零点"）排除在主判据之外**。

### 2.4 drafter 类别与草稿深度 K 完全绑定

`c1_spec_prefix.py:106-121`：`ngram → K=5`、`dflash2 → K=7`、`eagle3 → K=3`。

预登记 §2 的网格里**没有 K 这个轴**（`prereg:39-40` 只有 drafter 与前缀缓存）。⇒ "drafter 类别效应"与"草稿深度效应"在设计中不可分离；而 C-1m 之后的所有结论（每步耗时随 K 平坦）恰恰说明 K 是敏感参数。

### 2.5 每格有效样本 n=1

- **无 seed 轴**：`build_conversations` 有 `seed` 形参（`:48`），调用处写死 `0`（`:99`），CLI 无 `--seed`。预登记 §2 承诺的"5 个独立 prompt 集"与 §3 对照 2（"同 drafter 换 seed"给出类别内波动）**从未存在**——而 P3 的表述恰恰要求"差异 > seed 间波动"。
- **无重复**：`--passes` 默认 3（`:90`），且三遍是**冷/热/再热**（不同缓存状态），不是重复。预登记 §2（`prereg:46`）承诺"每个配置重复 5 次，报中位与极差"。
- **判据只用最后一遍**：`tps_p1 = passes[-1]["tok_per_s"]`（`:159`、`:171`）。中位数与极差都没有进入 P3。

⇒ 主判据建立在**每格一次观测**上，且没有任何误差估计。

## 4. 装置性错误（已逐条复核）

### 4.1 hybrid 臂用了 **dense 模型的分词器**

`c1c_client.py:79`：`--tokenizer` 默认 `/root/autodl-tmp/models/Qwen3-4B`。
`c1c_run.sh` 的调用行**没有传 `--tokenizer`**：

```bash
"$PY" /root/autodl-tmp/c1c_client.py --url "http://127.0.0.1:${PORT}" \
    --model m --out "$OUT/${CELL}.json"
```

而该脚本的 `MODELS` 循环同时跑 `Qwen3-4B` 与 `Qwen3.5-4B`。⇒ **hybrid 臂的 prompt 是用 Qwen3-4B 的分词器编码后喂给 Qwen3.5-4B 的**（词表规模不同，C-1b 记为 151936 vs 248320）。因此 `C1c判定…` 的"hybrid 接受率 0.9044 / 0.8852"**不是目标工作负载上的接受率**。这是判定文自己列出的 4 条"未验证原因"之一，而它其实是**已实现的**。

### 4.2 C-1m 的"与厂商计数器交叉验证"是空的

`C1_final_verdict…:44-47` 主张"给引擎循环打桩，并**证明该计数与厂商自己的计数器一致**"。复算 `repo2/results/C1m-step-cost/2026-09-15/c1m_step_cost.json`：

```
dense|K=0   steps_file=99.0  steps_iter=0.0  total_out=96
dense|K=2   steps_file=88.0  steps_iter=0.0  total_out=96
...
distinct steps_iter = {0.0}          ← 全 8 格恒为 0
```

⇒ 交叉验证**从未生效**（`disable_log_stats` 默认 True，Prometheus 计数器读 0）。同时 `dense|K=0` 的 `steps_file=99` 而 `total_out=96`：这 99 是**引擎迭代数（含 prefill）**，不是解码步数——列名"真实步数 / ms/步"因此也不准确。

### 4.3 每格独立起停引擎，且 on/off 顺序固定 ⇒ 顺序效应无对照

`c1_spec_prefix.py:124-164` 的外层循环是 `for drafter: for pc in (True, False): LLM(...); 3 passes; del llm; empty_cache(); sleep(3)`。

- 顺序**固定为 PC on → PC off**（`:125`），从未交叉或随机化；
- 每格都包含一次冷启动，而首遍系统性最慢（§2.2）；
- 在**共享的云 GPU** 上，任何与时间相关的漂移（邻居负载、热节流、碎片）都会**系统性地**落在先跑的臂上。

P3 的两臂**必然**一先一后，却没有 A/B/A 交叉。

## 7. 对重做的直接约束

由 §1–§4 直接推出，重做方案必须满足（详见 `prereg_C1_v2_2026-09-15.md`）：

1. **主量必须与预填充解耦**：报 decode 期 tok/s（或 output tokens / 解码步）与 TTFT 两个量，另报"预填充占比"以证明它不再支配结论。
2. **所有对比臂必须在同一次运行、同一进程、同一批形内配对**；网格值必须先验证合法（`dflash` 而非 `dflash2`）。
3. **机制仪器必须直读**：`cached_tokens` / `prefix_cache_hits_total` / 接受率 / 草稿步数，且**阳性对照必须断言命中 > 0**，否则该次运行作废。
4. **正确性不变量作为新判据**：PC on/off 在贪心解码下**必须产出完全相同的 token**（缓存本应语义透明）。任何分歧都是 bug，且能直接承载 §0 自述的"读到未初始化 KV"机制——这是 P1 的正确仪器。
5. **K 固定或作为显式因子**；不得与 drafter 绑定。
