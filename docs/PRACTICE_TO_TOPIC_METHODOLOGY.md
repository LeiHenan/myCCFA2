# 从实践现场提炼研究课题：纯方法论

> **v3（2026-09-15）**：v2 的三条修订来自案例研究 #2；v3 的两条来自
> [`PRACTICE_TO_TOPIC_CASESTUDY3_2026-09-15.md`](PRACTICE_TO_TOPIC_CASESTUDY3_2026-09-15.md)
> （挖 `myCCFA2` 全现场）——§5 新增"占位要看上游是否在修"，§8 新增"封存前核验被引用资产是否存在"。
> 修订记录见文末。

## 一、总原则

1. 选题的原料来自你自己的实践现场；文献检索只承担**证伪**职能。
2. 依据：可检索者即已发表，中间存在数月到一年的滞后；而决定一个方向是否仍然空着的，是尚未公开的在途工作，检索工具看不到。
3. 推论：检索是**杀伤性工具**（判断"我要做的这个具体点是否已被做"），不是**探照灯**（"替我找一个没人做的方向"）。
4. 成本不对称：检索以小时计，误判以周计。整个循环的设计目标就是"用小时换周"。

## 二、原料：实践问题的五类

1. **失效**——流程实际跑不通、报错、崩溃。
2. **反常**——结果与预期、或与前人报告相反。
3. **度量不可靠**——测量方式本身可疑：口径、环境依赖。
4. **代理量失明**——被当作某量之代理的那个量，与目标量**无关**。
   - 它与第 3 类的区别：第 3 类是"口径写错了"，改口径即可；**失明是口径再规范也测不到**。
   - 判定方式：在**一个已知的真缺陷**上同时测代理量与目标量。若目标量变化巨大而代理量变化可忽略，即判失明。
   - 实例：MTP + 前缀缓存的状态损坏使贪心输出分歧从 `0/320` 升到 `243/320`（`p=9.0e-32`），
     而同一批次的**接受率只动 `−0.25%`**。⇒ 接受率作为正确性代理是**失明**，不是口径问题。
5. **不可测**——想回答的问题所需的变量根本没有被记录。

每条必须落成**一句带数字的记录**；印象与感觉不算原料。
每条还必须标注**配置点**（见 §7.3）——"在哪个配置上取到的"与数字本身同等重要。

## 三、过滤：三道闸

1. **它改变谁的结论**——只改自己的（是缺陷，修掉即可）；改同行的默认假设（候选）；改整个领域的评价口径（最好的原料）。
2. **变量是否在手**——问"回答问题所需的量是否已存在于现有数据中"，而不是"能不能再采一次"。
3. **效应量是否够**——差异必须大到能被独立复现、并足以改变他人的判断。

三条中任一条不过，即归档为负结果，不再投入。

## 四、抽象：把散点收敛成一条带基线的陈述

1. 单个异常不是课题；成组异常背后的**不变量**才是。
2. 每条量化陈述必须自带参照系（随机水平、前人结果、对照组），否则无法判断量级。
3. 抽象后的陈述必须能推出一个可检验的设计含义，否则它只是描述。
4. **参照系本身可能是自变量的函数**——把参照系写进判据之前，先做一次
   "**它对哪些自变量敏感**"的扫描。未扫描前，不得把参照系当常数用。
   - 实例：同实例冷/暖的 nospec 分歧基线**随生成长度漂移**，`8.4%`（`gen=64`）→ `26.9%`（`gen=256`）。
     因此任何"分歧率 < X%"的闸门**不声明 `gen` 就不可比**。
   - 同理，跨配置基线与同实例基线是**两个不同的量**，不可互相替代（见 §7.2）。

## 五、占位核查：三通道、限时

1. **引用图谱**——找最接近那项工作的引用者队列（后续工作）。
2. **预印本检索**——用精确短语 + 按提交日期限定窗口，找同期尚未互相引用的撞车。
3. **在审稿件库**——找尚无论文可引的在途工作。
4. 每个候选限时（约一小时），产出只允许两种结论：**框架已被占 / 框架未被占**。
5. 关键区分：框架是否被占可由检索判定；**具体主张是否被占只能由实验判定**。检索只在已发表范围内搜索，因此系统性高估"已被占"，不可据此直接放弃——必须抽出自己的具体增量单独检验。
   反向同样成立：**框架被占不等于你的具体主张被占**，不得因为"这个方向已经有人做了"而丢掉一个可检验的具体增量。
6. **占位还要看"上游是否正在修"**——"已被报为 bug"与"正在被修"是两种不同的占位。
   后者意味着**即使你现在做出来，发表时也已过期**。凡判"框架被占"的，都要再看一眼
   上游 issue 的 linked PR 与最近提交；修复在途的，直接归档，不要投入。
   - 实例：一条"引擎配置静默失效"的候选，在检索到上游 issue 之后又查到
     **一个已合并的"启动时打印 fully resolved config"PR** ⇒ 修复在发货，课题保质期已尽。

## 六、先证伪，后建设

1. 对每个候选，先设计**能杀死它的最便宜实验**，并预先写死继续/停止的判据。
2. 实验预算设上限（一天量级）；超限说明问题尚未收敛。
3. 优先选择可离线完成、不消耗新资源的检验方式。
4. 结论为"停止"时，产出物是一条可发表的负结果与一份归档说明，不是失败。
5. **第 0 步永远是溯源审计**（零成本，见 §7.1/§7.4）：确认候选所依赖的每个数字**确实能从已归档的数据里复算出来**。
   复算不出来的数字，其证据效力为零——**先补溯源，再花任何算力**。

## 七、数字的溯源纪律

1. 任何将写入结论的数字，都必须能追溯到采集方式、口径与环境条件。
2. 重点提防四类隐性口径问题：
   **代理量**（以 A 代替 B 计量，且未验证 A 与 B 相关）、
   **参照系混用**（把跨配置量与同实例量互相替代）、
   **样本不足的测量**（测在过短的窗口/过小的样本上）、
   **参数相关的结论**（换一个未报告的参数结果就变）。
3. 结论必须标注它是在**哪个配置点**上取得的；配置点不等于方法的普遍性质。
4. **否定性结论必须附取证（可执行阻断）**——凡结论中含
   "某能力**不存在** / **不可测** / **已被修** / **从未发生**"的，
   必须附一条**可复现的取证命令及其原始输出**（`config.json` 的字段、registry 的条目、启动日志的行、上游 commit 的 sha…）。
   只凭记忆或推断写下的否定性结论，**不得进入报告**。
   - 理由：这是唯一一类**没有任何下游机制能拦住**的错误——它不会被数据推翻（因为你根本没去采那个数），
     也不会被同行推翻（因为看起来像是"边界声明"）。它只会被**取证**推翻。
   - 实例：报告里写"未测 MTP（该模型无 MTP drafter）"，而 `config.json` 里
     `mtp_num_hidden_layers = 1`、shard index 含 15 个 `mtp.*` 张量、引擎 registry 已注册对应架构。
     ⇒ 把"我没试"写成了"不可测"，并据此下了一个错误的总结论。

## 八、停止规则：数据的问题容量

一份数据能支撑的主张类型，由其变量结构决定。出现以下任一情况即封存：

1. 下一次分析不会改变任何决定；
2. 要回答的新问题需要数据中不存在的变量；
3. 还能得到的只是同一结论的更细版本。

封存时把数据整理为可公开的产物，并写明"它能回答什么、不能回答什么"——这比再多几张图更有价值。

**封存前的最后一步：资产核查（与 §7.4 同构，对象从"数字"换成"文件"）。**
凡在交付物里被**具名引用**的产物（文件、清单、表格、脚本），都要附一条**可复现的存在性取证**
（`git ls-files <pattern>` 或 `ls` 的原始输出），并对"仅被引用、从未入库"的项**显式标注为缺失**。

- 理由：交付物里一句"本案例留下 X、Y、Z"会被读成"X、Y、Z 可复核"。只要没人去 `git ls-files`，
  缺失就能无限期潜伏——**它不会被数据推翻，只会被取证推翻**，与 §7.4 完全同构。
- 实例：一份案例研究把"13 格瓶颈清单（4 格标未知）"列为头号可复核资产，
  而 `git log --all --diff-filter=A -- '*BOTTLENECK*'` 只命中**加入这条引用的那个提交本身** ⇒
  该文件**从未存在过**；后续还有一条决策把"收口条件"建立在这份不存在的清单上。

## 九、常见失误

1. 用摘要下强判断（框架可以用摘要否掉，主张不行）。
2. 跳过度量审计——口径错误往往比想法错误更致命。
3. 把一次配置下的观测当作普遍性质。
4. 沉没成本——已投入的工作不构成继续投入的理由。
5. 丢弃负结果——它既防止他人重走，也可能独立成文。
6. **把"我没测"写成"不可测"**——见 §7.4。它同时污染边界声明与总结论，且自查抓不到。
7. **用一个便宜的代理量替掉昂贵的真值，却从未验证过两者相关**——见 §2.4。

## 十、方法的边界

1. 它**寄生在实践上**：没有一手实验就没有原料。
2. 它**偏好小而可测的问题**，可能系统性错过需要大投入的方向。
3. 它**无法产生由新能力驱动的课题**（新硬件、新范式）——那类课题来自"最早接触新事物"。
4. 它可能**积累大量负结果却拼不成一篇论文**。
5. 它**无法更换分母**：当约束固定时，可从现场推出的候选集合会先于耐心耗尽。连续 N≥3 个候选死于**同一约束**时，问题不在候选，在分母。

## 附：循环清单

```
[记录] 每次实验后 5 分钟
  □ 失效 / 反常 / 度量不可靠 / 代理量失明 / 不可测，各写一句带数字的记录
  □ 每条标注配置点

[过滤] 每个候选 10 分钟
  □ 改变谁的结论？   □ 变量在不在手？   □ 效应量够不够？

[抽象] 半天
  □ 把散点收敛成一条带基线的量化陈述，并推出可检验含义
  □ 参照系扫描：它对哪些自变量敏感？（未扫描不得当常数用）

[核查] 每个候选 1 小时
  □ 引用图谱 → 预印本按日期 → 在审库
  □ 产出只允许是"框架被占 / 未被占"
  □ 框架被占 ≠ 主张被占

[证伪] ≤ 1 天
  □ 第 0 步：溯源审计（零成本）——结论依赖的数字都能从归档数据复算吗？
  □ 判据先写死   □ 能用离线就不用新资源   □ 停止即归档负结果

[停止] 每月一次
  □ 下一次分析会改变决定吗？不会就封存并发布数据
  □ 连续 3 个候选死于同一约束？→ 换分母，不是换候选
  □ 资产核查：交付物里具名引用的每个产物，都能用 git ls-files 取证到吗？
```
