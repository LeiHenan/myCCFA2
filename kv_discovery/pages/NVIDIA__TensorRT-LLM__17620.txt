Description

The B200 L0 test

disaggregated/test_disaggregated.py::test_disaggregated_ctxpp4_gentp4[TinyLlama-1.1B-Chat-v1.0]

times out on its first requests when using the KV cache manager V2 C++ backend with the Python/NIXL transceiver. In this PP4 context to TP4 generation configuration, peer connections are established lazily after the server reports ready. Creating all required connections can exceed the 60-second KV transfer request timeout, even though the transfer path itself is functioning correctly.

This PR moves connection establishment ahead of server readiness:

- Collects and publishes transfer rank information for every rank in an instance.

- Stages discovered workers before making them available to the router.

- Establishes connections for every context-generation instance pair and waits for acknowledgements.

- Reports the initial disaggregated service as ready only after connection establishment has been attempted for a stable discovered topology.

- Applies the same ordering to dynamically added workers and multi-instance topologies.

- Keeps peer registration idempotent and removes stale pair bookkeeping when workers are deleted.

- Falls back to the existing lazy connection path when proactive connection establishment fails or Python/NIXL metadata is unavailable.

This changes when connections are established, without changing request routing or KV cache transfer behavior after the server becomes ready.

🩺 Stability & Availability | 🟠 Major | 🏗️ Heavy lift

Await or re-verify the cancelled onboarding task before you finish DELETE cleanup.

The DELETE branch cancels the onboarding task and then continues without awaiting it. Cancellation is delivered only at the task's next suspension point. _onboard_worker can already be inside router.add_server(worker_addr) past its last _worker_is_current check. Router.add_server appends to self._servers under an uncontended asyncio.Lock, so it can complete without yielding. In that interleaving add_server appends the address after remove_server has already run, and a deleted worker stays routable. Requests then go to a worker that discovery removed.

Await the cancelled task before you remove the server, or re-run the removal after the task settles.
