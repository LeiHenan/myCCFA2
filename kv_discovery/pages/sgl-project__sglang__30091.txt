Motivation

Follow-up promised in #30050. That PR ran gpt-oss sliding-window layers by

storing full KV history and applying the window at read time (banded mask

at prefill, trailing-window truncation at decode). Numerically exact, but

sliding layers paid full-context memory.

This PR makes sliding-window layers keep only the trailing window tokens on

the per-request KV path (--disable-radix-cache, the configuration the

gpt-oss e2e tests run) via a new WindowedAttentionKVCache. Measured

per-request KV for gpt-oss-20b geometry (24 layers, 12 sliding, window=128,

8 KV heads x 64 head_dim, bf16):

(Numbers are decode steady state. While a prefill chunk is in flight a

windowed layer's transient buffer is window + max(chunk, window) — the kept

prefix plus the chunk — so with the default 4096-token chunked prefill the

per-layer peak is ~4224 slots regardless of prompt length: no saving while

prefilling a <= 4k prompt, roughly half from the second chunk onwards, and

the buffer shrinks to 2*window on the first decode step.)

Modifications

- WindowedAttentionKVCache (attention_kv_cache.py): fixed-size,

temporal-order buffer. Decode appends in place into a 2*window buffer and

compacts the trailing window into a fresh buffer when full (amortised O(1)

per token); prefill chunks normalise the kept prefix to

min(local, window) on every update_and_fetch, so the returned length is

deterministic. offset stays absolute (RoPE positions, decode

bookkeeping); make_mask clamps the mask offset to the kept prefix,

mirroring mlx_lm RotatingKVCache.make_mask, so mask width always equals

returned key length. Oversized prefill-chunk buffers shrink back to

2*window on the first decode step. Requesting a full-context mask after

history has been dropped raises.

- MlxModelRunner: _new_native_cache builds windowed caches for layers in

get_layer_window_sizes(model) only when disable_radix_cache is set;

the pool/radix path keeps [MLX] Support gpt-oss: sliding-window attention, attention sinks, sm_scale #30050's full-history semantics because (a)

_sync_new_kv_to_pool / _sync_decode_kv_to_pool slice per-request caches

at absolute offsets, and (b) radix prefix reuse at match point P needs

sliding KV for [P-window, P), which windowed storage no longer has.

Pool-side memory work is tracked separately.

- _acquire_cache resets reused caches via a new reset() (both cache

classes) instead of poking offset.

- MLXAttentionWrapper._batched_decode is unchanged: its trailing-window

slice and locally rebuilt padding mask are already correct for both cache

kinds (the windowed buffer is temporal, holds >= min(offset, window)

tokens, and reports absolute offsets). Docstring updated.

Test

- New test/registered/unit/hardware_backend/mlx/test_windowed_kv_cache.py

(15 tests): bit-exact equivalence of windowed storage vs the trailing slice

of full-history storage across chunk patterns and compaction boundaries

(including chunk > 2window and buffer shrink after oversized chunks); mask

width == returned key length on every chunk; clamped mask == trailing

columns of the full banded mask; tiny-gpt-oss chunked prefill and 2window

greedy decode produce identical tokens windowed vs full-history; wrapper

batched decode over windowed caches matches the full-KV banded reference at

1e-5 for 12 consecutive steps across the compaction boundary; runner wiring

(windowed only on the per-request path, all-contiguous otherwise, reset on

reuse).

- Existing MLX suites stay green: test_sliding_window_attention (24),

[RENDERED BLOCK author=LarrySimingDeng date=2026-07-05T07:38:31Z]
Planned, yes. Leaning toward mirroring the CUDA path rather than inventing: SWAKVPool already splits full and SWA layers into separate pools, and SWARadixCache drives the SWA side.

So it's really both of the mechanisms you named, sitting on top of that split, not either/or:

- full-attention layers stay on the existing pool with full prefix sharing,

- SWA layers get a separate window-bounded pool with the match/hit length clamped to the window,

- out-of-window SWA slots reclaimed window-aware (_evict_swa / swa_evict_floor in chunk_cache.py).

For the MLX follow-up I'd stage it: first the pool split so sliding layers drop the NotImplementedError and get window-bounded radix storage (the pool-backed form of this PR's WindowedAttentionKVCache), then cross-request SWA sharing plus window-aware eviction only if MLX concurrency makes the reuse worth the extra liveness complexity. Low-concurrency local serving probably does not need the full SWARadixCache machinery on day one.

Also pushed the missing if __name__ fix, thanks for the catch.

Adding a diagram of where the ~48% per-request KV reduction comes from.

gpt-oss-20B has 24 layers and 12 of them are sliding-window (window=128). Windowing those caps their KV at 128 tokens while the 12 full-attention layers still store all L, so the saving is 1/2 - 64/L: it approaches a 50% ceiling and lands around 48% at a few-thousand-token context.
