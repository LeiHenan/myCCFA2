Motivation

DSA Prefill context parallelism requires every CP rank to consume the complete Main KV and Indexer history. Upstream main supports a layer-sharded path through #29421, using NCCL and remaining applicable across NVLink domains. This PR adds another option for same-host deployments within one peer-accessible NVLink domain: CP ranks share one CUDA VMM view and directly read peer-owned HBM pages. The two paths cover different topology and communication trade-offs.

Like layer sharding, the shared layout stores one aggregate Main-K/Indexer cache instead of eight replicated copies, providing up to 8x logical cache capacity over Base CP8 for the same KV memory budget. The difference is the access model: instead of materializing each owner layer on every rank through a collective, attention kernels directly read peer-owned pages through the shared VMM view. On full GLM-5.2-FP8 / H20-3e, Shared KV stays within 1.86% of Base CP8 warmed mean Prefill latency through 256K. Base CP8 fits about 380K tokens in the tested configuration; Shared KV is intentionally capped at 1.2M tokens for the benchmark and successfully serves a 1M input. The tested 100K L2 host-cache restore reduces latency by 92.67%.

Modifications

- Add --enable-dsa-shared-kv-cache for same-host DSA L1/L2 sharing.

- Store Main KV and Indexer once per CP group with owner-sharded CUDA VMM pages; kernels read the group-wide cache directly without per-layer KV broadcast.

- Preserve the same ownership in page-first HiCache and Mooncake Prefill transfer, with mandatory CP synchronization before peer data is consumed.

Design

Logical page p is owned by CP rank p % cp_size, and each rank allocates only its owner pages. CUDA VMM exposes the physical allocations as one group-wide tensor view. Main KV uses the canonical view; Indexer adds a rank-local alias over the same physical allocation for the paged DeepGEMM path, without duplicating HBM. A mandatory CP write fence runs before any rank reads peer-owned pages.

Page-first L2 keeps the same logical IDs and ownership. Each rank allocates pinned DRAM only for its owner pages and transfers only between local DRAM and local HBM. CPU failure agreement and a device fence complete each group-wide backup or restore. Mooncake Prefill transfer uses bounded registered staging buffers rather than a second HBM cache.

The current scope is one host, one peer-accessible NVLink domain, GLM-5.2 DSA, FP8 KV, tp=attn_cp, interleaved Prefill CP, pp=1, page-first L1/L2, and Mooncake Prefill transfer. HiSparse, speculative decoding, and L3 storage are not enabled with this path.

In the current upstream implementation, the layer-sharded path has not yet optimized its communication to fetch only active/sparse KV. Under the matched setup used here, Shared KV reduces warmed mean Prefill latency by 49.01% at 4K (798.09 vs. 406.91 ms), 16.26% at 128K (14,877.29 vs. 12,457.69 ms), and 7.87% at 1M (179,701.77 vs. 165,565.18 ms). These results describe the current implementations rather than an inherent limit of layer sharding; the comparison should be repeated after its sparse-fetch communication path is optimized.

Code Review

This pull request introduces a page-sharded DSA (DeepSeek Sparse Attention) GPU KV and indexer cache sharing mechanism across context-parallel (CP) ranks using CUDA Virtual Memory Management (VMM). Key changes include updating Triton kernels to use 64-bit address arithmetic, implementing VMM-based cross-rank memory sharing, adding host-side L2 cache support, and introducing configuration options and tests. The code review identified critical distributed execution issues: a potential deadlock in the VMM mapping phase if an exception occurs before synchronization, and multiple runtime TypeErrors in dsa_shared_host.py caused by passing a GroupCoordinator instead of a raw ProcessGroup to PyTorch distributed APIs. Actionable suggestions were provided to wrap the VMM setup in a single try-except block and extract the underlying cpu_group from the coordinator.

@yiminghub2024 Thanks for your interest:

- Cache hierarchy: L1 is the shared HBM KV/indexer cache implemented with CUDA VMM. L2 uses SGLang HiCache in pinned host DRAM. Mooncake is used only as the PD transfer backend, not as the L2 cache. L3 storage is not supported yet, but the owner-sharded page design can be extended to L3 in future work.

- Feature flags: --enable-dsa-cache-layer-split and --enable-dsa-shared-kv-cache are alternative cache layouts and cannot be enabled together. Please select one of them.

- Purpose: Both approaches reduce KV/indexer replication across Prefill CP ranks, allowing the same HBM capacity to hold more cache tokens, longer contexts, or more concurrent requests. They do not change the logical KV content. The lower TTFT is an additional performance benefit observed with the shared-VMM path in our workloads.

- Speculative decoding: This PR does not currently support speculative decoding, including EAGLE and MTP. These paths require separate correctness and performance work.
