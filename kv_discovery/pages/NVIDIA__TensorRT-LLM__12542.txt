Reproduction

Problem description

In disaggregated serving with enable_block_reuse, the async CacheSender thread transfers KV cache blocks to the decode via UCX in the background after prefill completes. However, between the request completion and the async send, the

executor loop can evict the KV cache block from the reuse tree for a new request. When CacheSender::sendSync calls BlockRange::fromReuseTree, the block is gone, triggering

TLLM_CHECK_WITH_INFO(lastBlock, "Couldn't find the requested block in the reuse tree") at kvCacheUtils.h:84. The exception is caught and logged, but the UCX send never happens. The decode blocks forever in checkGenTransferStatus →

std::future::get waiting for data that will never arrive, deadlocking the entire pipeline.

Reproduction:

Run a load test with several steps, changing the concurrency. For example, with LLMPerf run concurrency:4, then 8 and then again 4. ISL:1k, OSL:200. Esp. Step 3 run for longer data set like 4k requests. Set the engine backend to pytorch, "enable_block_reuse": true, and "cache_transceiver_config.backend": "UCX". Send requests which will have the same prefix to simulate that the same KV cache blocks are reused.

'cache_transceiver_config': {
 'backend': 'UCX',
 'kv_transfer_timeout_ms': 180000,
 'max_tokens_in_buffer': 16384
}

Expected behavior

- KV cache blocks referenced by pending async CacheSender transfers should not be evicted from the reuse tree. The CacheSender should hold a reference (or pin) on the blocks until the UCX transfer completes, preventing the

"Couldn't find the requested block in the reuse tree" assertion at kvCacheUtils.h:84. The source code acknowledges this case with // TODO: handle the case where the last block is not found but does not handle it.

- If a KV cache transfer fails for any reason, the decode should not block indefinitely. checkGenTransferStatus calls std::future::get() without a timeout, ignoring the configured kv_transfer_timeout_ms=180000 (180s). It should use

std::future::wait_for() with the configured timeout and fail the affected request gracefully instead of deadlocking the entire pipeline.

actual behavior

- The prefill completes the request and returns success to the processor. The async CacheSender thread then attempts to send the KV cache blocks via UCX, but the executor loop has already evicted the block from the reuse tree.

BlockRange::fromReuseTree fails with an assertion, the exception is caught and logged by sendAndRemoveResponse, but the UCX send never happens. The prefill process continues running normally — the Python executor loop is unaware of the failure.

- The decode calls checkGenTransferStatus → std::future::get() which blocks forever waiting for KV cache data that will never arrive. The configured kv_transfer_timeout_ms=180000 is not applied to this wait. The decode executor loop is

permanently frozen, no further requests are processed, and all processors hang waiting for decode responses. The entire serving pipeline is silently deadlocked with no health check failure or error propagation to the application level.

additional notes

I caught this exception while running py-spy on processes, but I've seen the same symptoms with runs when py-spy wasn't attached
