Motivation

test/registered/attention/test_verify_shared_kv.py::test_qwen3_5_fp8_kv_cache has never passed on stage-b-1-gpu-small-amd-mi35x since it was added (#34517); it fails inside the Triton AMD backend, not in sglang code (latest instance):

python3: llvm/ADT/SmallVector.h:292: Assertion `idx < size()' failed.
extend_attention.py:305:0: error: Failures have been detected while processing an MLIR pass pipeline
extend_attention.py:305:0: note: Pipeline failed while executing [`ConvertTritonAMDGPUToLLVM` ...]
RuntimeError: PassManager::run failed

Only the fp8 variant fails; the bf16 variants of the same test pass. The crash is not test-specific — it is in the shared prefill kernel, so a model served on MI35x with --kv-cache-dtype fp8_e4m3 through the Triton attention backend hits it, in decode as well as prefill. (Backends that do not route through these kernels, and the two ROCm Triton kernels that cannot take an fp8 pool at all, are out of scope; see Modifications.)

Scope: the ROCm 7.0 image only — 7.2 was never affected. The dividing line is the Triton wheel, not ROCm. On the pre-fix ROCm 7.2 MI35x lane (job 95705686213, Aug 18, before any commit here) test_verify_shared_kv.py reported "passed": true with no PassManager::run failed or idx < size() in the log; that lane's only red was the unrelated test_quark_mxfp4.py near-miss. The 7.0 log carries aiter's require triton>=3.6.0, found 3.4.0, while 7.2 emits no such warning, so its Triton clears 3.6.0 (docker/rocm.Dockerfile installs aiter's pin over the base ROCm Torch triton==3.5.1 when BUILD_TRITON=1).

Root cause

Every Triton attention kernel that reads a KV pool casts the wide operand down to the pool dtype before the dot (tl.dot(q.to(k.dtype), k), tl.dot(p.to(v.dtype), v)), so an fp8 pool also feeds the fp8 matrix core. On gfx950 AccelerateAMDMatmul promotes an fp8 x fp8 tl.dot to the scaled V_MFMA_*_F8F6F4 family, which is 16x16x128 under the matrix_instr_nonkdim=16 launch hint all of these kernels pass.

A dot whose reduction is narrower than 128 does not tile that instruction: AMDMfmaEncodingAttr::getRepForOperand clamps the resulting zero K-repetitions up to one, and ScaledDotOpMFMAConversionHelper then reads kBase = 32 elements per lane from a register range that only holds K / 4. That is the out-of-bounds SmallVector access.

P @ V reduces BLOCK_N, which is 64 (extend, verify) or 32 (decode, split-KV verify) — never 128 — so the fp8 path never compiles on gfx950. Q @ Kpe reduces BLOCK_DPE (32/64) and Q @ K reduces BLOCK_DMODEL, which is also below 128 at head_dim <= 64.

Triton rejects the intrinsic instead of miscompiling it as of triton-lang/triton#8278, which dropped the enforcedNonKDim == 0 && escape hatch that had let an explicit matrix_instr_nonkdim skip Triton's own "K is not a multiple of the intrinsic's kDim" check. That fix missed 3.5 and landed in 3.6:

Triton branch
guard in chooseMfmaInstruction
narrow fp8 dot

release/3.4.x, release/3.5.x

enforcedNonKDim == 0 && inputKSize % kDim != 0

promoted, then aborts

release/3.6.x and later

if (inputKSize % kDim != 0)

rejected, falls back to non-scaled fp8 MFMA

So anything on 3.4 or 3.5 with matrix_instr_nonkdim set — which is every kernel here — crashes, and the ROCm 7.0 image ships 3.4.0.

The guard therefore carries a triton.__version__ < 3.6 term, so it is inert on 7.2. Without it the guard also fired on 7.2, where Triton already falls back to the non-scaled V_MFMA_F32_16X16X32_FP8_FP8 and the narrow dot works — the same pre-fix job ran test_qwen3_5_fp8_kv_cache green. That would have substituted a bf16 dot for a working fp8 one on the lane that gates PRs, trading unquantized P (more accurate) against fp8→bf16 converts and a 2-byte V tile in LDS, for a rate difference nobody has measured. Not a trade worth making on the primary lane.

With the version term:

- 7.0 / Triton 3.4 — guard active, replaces a hard compile abort.

- 7.2 / Triton ≥3.6 — guard inert, codegen byte-identical to today.

- When ROCm 7.0 is dropped the guard is permanently inert and the whole module can be deleted, so this does not become long-lived debt.

extend_attention.py already gates gfx950 tile choices on _is_triton_ge_37, so a Triton-version term is an established idiom in this file rather than a new mechanism. A version string that will not parse keeps the guard on, which is the safe direction.

Modifications

- New python/sglang/kernels/ops/attention/fp8_dot_support.py with dot_in_kv_dtype(kv_dtype, reduction_width): True for every non-fp8 pool and every arch other than gfx950, and on gfx950 only for reduction widths that tile the scaled MFMA instruction.

- Each dot that casts an operand down to the tile it reads gets its own constexpr verdict (QK_DOT_IN_KV_DTYPE, QK_PE_DOT_IN_KV_DTYPE, PV_DOT_IN_KV_DTYPE, PV_EXTEND_DOT_IN_V_DTYPE). When it is False the KV tile is upcast to the query dtype instead of the query tile being cast down. This covers _fwd_kernel and _fwd_kernel_unified (extend), _fwd_grouped_kernel_stage1 (decode), _verify_mla_prefix_stage1, and _verify_prefix_stage1 — including _fwd_kernel's extend-stage P @ V, whose V is the caller's current-chunk tensor rather than the pool.

Every flag is True on non-gfx950 hardware and for bf16/fp16 pools, so those paths generate the same code as before. matrix_instr_nonkdim, tile sizes, warp counts, and the #mma layout are all untouched.
