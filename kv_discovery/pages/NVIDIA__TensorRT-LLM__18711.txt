Description

KVCacheManagerV2 stopped committing after prefill, so generation KV produced by decode was not retained in the reusable block index. For a multi-turn disaggregated request, the decode worker could reuse the original prompt but had to receive the previous turn's output KV again.

This change keeps ALL_REUSABLE V2 caches open after prefill and commits only the stable generation prefix after sampling state is applied and before response handling can remove the request. The newest sampled token is excluded because its KV is not materialized until the next forward pass. Accepted speculative KV relocation and history resize complete before commit. Generation commit remains disabled for draft caches and compression that manages physical history, preserving prompt-only reuse for TriAttention. Token collection uses a zero-copy view and materializes only the newly committed slice, avoiding an O(sequence length) Python-list conversion on every decode step.

The generic resource-manager update skips only the target V2 KV manager to avoid updating it twice while preserving draft KV and KV compression manager updates. This change does not modify the transfer-side prefix trimming algorithm or any public API.

Test Coverage

- Focused unit tests cover context/decode commit boundaries, terminal commit, speculative-KV relocation, Python token slicing, target-only resource-manager skipping, and the TriAttention generation-commit guard.

- B200 1P1D with Llama-3.1-8B-Instruct, NIXL, 32-token blocks, and both scheduler modes: the matched second-turn transfer decreased from 3 blocks to 1 block, initial/forced-miss transfers remained 5/7 blocks, and outputs were token-identical to baseline.

- B200 1P1D with one-model EAGLE3, using both linear and dynamic-tree decoding: transfers changed from 5/3/7 to 5/1/7 blocks and all outputs matched baseline.
