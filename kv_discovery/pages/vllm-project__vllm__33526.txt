[GRAPHQL COMMENT by orozery assoc=COLLABORATOR at 2026-02-02T07:46:06Z]
Thank you for proposing this clear and detailed RFC!
In theory this could be indeed helpful in the situation you described.
It does come with a tradeoff of implementation complexity.
In particular, to pull it off you would need to somehow propagate batch-level completions of onload operations.
This is currently not cleanly possible with the current connector API, though PR #31964 may enable it.
Even with #31964 merged, it is still not enough and you would need more changes to the vLLM core.
Specifically, you would need some new API that will allow the connector to cache the GPU blocks of the completed onloaded batch in the GPU prefix cache.

The reason request B is blocked in the first place is the optimization I've added in #29087, while trying to avoid changes to the vLLM core.
I'm actually not sure this optimization has any real-life benefits, but it was relatively easy to implement.
My motivation behind it was actually not saving time, but actually reducing the GPU KV cache usage (by avoiding duplicating KV data across requests with the same prefix).
The penalty for the use-case you're describing is a delay of request B, up to the time it takes to onload request A.
In practice, this delay should be upto ~1s, but more commonly (assuming A does not take up the entire KV cache) it will be upto a few 10s of ms.
I think this is less of an issue, and in particular because it is currently not linked to any real-life use-case.

[RENDERED BLOCK author=pougetat date=Feb 1, 2026]
Motivation.

KV Cache CPU offloading is a new native vLLM feature introduced with RFC #19854. It enables offloading of KV cache blocks to CPU memory from GPU memory which is especially useful when not enough GPU memory is available for storage.

The current design onloads KV cache blocks for entire requests at once and prevents concurrent onloading operations for the same KV cache blocks.

This can introduce a head of line blocking bottleneck where a larger request sharing the same prefix as a smaller request prevents the smaller request from being scheduled due to the larger request’s blocks being onloaded. The smaller request needs to wait for all of the blocks relevant to the larger request to be onloaded before it can be scheduled, even if it only requires a small portion of the blocks for itself.

Already discussed as a desired feature, this RFC outlines support for more progressive onloading of KV cache blocks such that the head of line blocking issue is reduced.

Proposed Change.

A quick recap of the existing design

The following diagram taken from RFC #19854 illustrates the current design of CPU offloading.

Batched Progressive Loading

Instead of a single block transfer request per inference request, we can split up our transfers into multiple, each covering a subset of the required blocks.

Core changes:

- We introduce a new BatchTransferSpec representing a dictionary of BatchIds to TransferSpecs. The worker process will be able to operate on these batches and build KVConnectorMetadata from it specific to those batches. We no longer operate on individual requests for load operations.

- For the OffloadingConnectorScheduler, we will need to maintain a mapping of BatchIds to BlockHashes similar to how we currently maintain a mapping of ReqIds to BlockHashes.

- The Worker Process currently tracks a map of JobIds to RequestIds, used when building KVConnectorMetadata to signal which requests have had their blocks loaded from CPU memory. This will be updated to map JobIds to BatchTransferSpec since we no longer load all blocks for a request at once.

- The CPU->GPU worker process performs swap_block operations on each list of blocks defined in a BatchTransferSpec.

- When ModelRunnerOutput is relayed back to the scheduler, the list of BatchIds will be relayed instead of ReqIds. Important note: This does not actually require an API change given that KVConnectorMetadata currently accepts a []string as input so BatchIds can be used as a replacement for RequestIds.

Notes:

- We keep the store path completely unchanged for now, with the potential to introduce batching for it as well in the future.

- The OffloadingConnectorScheduler will be responsible for dictating batching parameters. We discuss the actual batching sizes and how they’re chosen in the next section.

Variable Batch Sizing

We propose a “smart batching” strategy meant to:

- Lower processing start time for short requests sharing blocks with a longer request.

- Avoid introducing too much overhead with too aggressive batching, especially when it comes to longer requests.

Our batching strategy tries to solve this problem by:

- Batching more aggressively for the start of a request: The first 100 blockIds are split into batches of 10 blocks.

- Batching less aggressively for the later portions of a request: The blockIds > 100 are split into batches of 100 blocks.

We could take this further and increase batch size dynamically past the first 100 blocks based on request side, this first iteration of the RFC tries to keep things simple.

We also will need to discuss what makes sense for the threshold of the first section of more aggressively batched block requests, currently defined as 100.
