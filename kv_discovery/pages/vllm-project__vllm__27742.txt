The challenge is how to support the layout with minimal code changes.

For layers with different page sizes I currently don't see an easy way.

Looking at `get_kv_cache_groups` I see 4 cases:
1. is_kv_cache_type_attention_free
2. is_kv_cache_spec_uniform
3. UniformTypeKVCacheSpecs
4. is_kv_cache_page_size_uniform

(1) is not interesting.
(2) is the case we're currently targeting.
(4) seems feasible (I guess this is what you meant)

But in (3) you could have different page sizes per layers.

[GRAPHQL COMMENT by heheda12345 assoc=COLLABORATOR at 2025-10-30T06:51:36Z]
BTW deepseek v3.2 has two types of kv cache with different hidden size. For a model with different hidden size $h1$, $h2$, ..., $h_n$, we can do something like:
```
total = h1 + h2 + ... + h_n
buffer = torch.empty(shape=((num_blocks + 1) * total,))
kv_cache_2 = buffer[h1: h1 + num_blocks * total].view(num_blocks, total)
# the kv cache of layer 2 page p can be accessed via:
kv_cache_2[p, :h2]
```

Motivation.

High-level goal: optimize the transfer time of KV data from/to the vllm KV cache by reducing per-transfer fragmentation at the vllm KV cache side.

The 2 main use-cases we're considering are:

- NixlConnector

- OffloadingConnector

So our goal is to try and optimize the time each of these connectors spend for a single transfer (GPU->CPU of the offloading connector, and GPU->host_buffer/other agent for NixlConnector).

The transfer unit is a block of KV-data corresponding to some aligned (default)16-tokens out of some request.

We consider the case of simple models where all layers have the same layout (i.e. not using the Hybrid Memory Allocator), although this can be explored in the future.

For this case, the current layout for the vllm KV cache is (roughly) this:

As you can see, the KV data that needs to be transferred is breaked down to num_layers non-contiguous segments.

This does not take into account the k_or_v and num_kv_heads dimensions which may further cause extra fragmentation.

In this RFC, we propose a new KV cache layout that for each block, will place all KV data for all layers contiguously:

This will reduce the number of fragments to copy by a factor of num_layers.

We have tested this with both the NixlConnector and the OffloadingConnector and saw that the transfer time is improved by a factor of X4 (tested on Llama-3.1-8B-Instruct).

Furthermore, we tested plain model execution and saw no noticeable degradation in performance.

Proposed Change.

We propose to change the KV tensor allocation in gpu_model_runner.py to support this new layout, allocating a single tensor for all layers (instead of 1 per layer as it is today).

This new layout will only be selected if:

- The model has a simple uniform layout (not HMA)

- A KV connector is configured and, the KV connector class explicitly prefers (via a new classmethod) to use the new layout.
