# p37 —— 候选 A（并发搜索式推理的 KV 准入/复用）**证伪**

**机器**：RTX PRO 6000 Blackwell 95.6 GB / sm120 / vLLM 0.29.0 ｜ **成本** ≈0.1 GPU·h
**脚本**：`probes/p37-beam-prefill/{beamprefill.py,discriminate.py}`

## 1. 源码事实（vLLM 0.29.0，第一手）
`entrypoints/generate/beam_search/{online.py(222),offline.py(457),utils.py(162)}`，**不在 `v1/core/`**；
两条路径同一设计：外层 `for _ in range(max_tokens)`，内层**每个 beam 一个独立 `generate()` 请求**，
`SamplingParams(max_tokens=1)`，且每步 `beam.get_prompt()` **重发完整上下文**（`online.py:60-95`）。
零卡算术：B=4/T=32/L=313 时，无 APC 的 prefill 量为 B(T·L+T²/2)=42112，理想 345 ⇒ **122×**。

## 2. 实验一（三臂）
| 臂 | 墙钟 |
|---|---|
| 贪心（APC 开） | 0.245 s |
| beam（APC 开） | **0.768 s = 3.1×** |
| 贪心（APC 关） | 0.236 s |
| beam（APC 关） | **1.395 s = 5.9×** |
⇒ 关掉 APC 使 beam 再差 1.8×，证明共享前缀确实被反复 prefill；APC 兜住了一部分。

## 3. 实验二（判别：结构性 vs 包装层）——决定性
| 臂 | 墙钟 | 相对贪心 |
|---|---|---|
| 贪心 n=1 | 0.233 s | 1.00× |
| **原生 n=4（单请求，4 条共享前缀序列）** | 0.246 s | **1.06×** |
| **4 个独立请求** | 0.245 s | **1.05×** |
| `beam_search` 包装层 | 0.641 s | **2.75×** |

⇒ **引擎能廉价批处理共享前缀的多序列（连独立请求都只要 1.05×）；2.6× 的额外开销全部在 `beam_search` 包装层。**

## 4. 判决：**杀**（不是效应不存在，而是归类错误）
现象真实且量级大（2.6×），但它是**引擎 API 实现缺陷**，不是**机制缺口**：
上游只要把 beam 保活、用持久/流式请求替代"每步重发上下文"，就能拿回这 2.6×。
⇒ 触犯本目标规则 6（**凡新颖性建立在"引擎还没做 X / 做得差"上的题，保质期约一个 release**）。
