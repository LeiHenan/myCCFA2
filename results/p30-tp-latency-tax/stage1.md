# p30 stage-1：**探针无效** —— 阴性对照失败，本表不能作为任何发现的依据

**日期**：2026-09-15 ｜ **成本**：≈0.05 GPU·h（空闲卡 2,3）｜ **脚本**：`probes/p30-tp-overlap/overlap_probe.py`

## 实测（36 层 = 一个 token 的 TP 通信/计算量；5 臂同进程交错轮转，60 rep）

| 臂 | M=1 (msg 5 KB) | M=64 (msg 320 KB) |
|---|---|---|
| `comm_only` 36×all_reduce | 0.944 ms（极差 88.7%） | 1.837 ms（极差 136.2%） |
| `comp_only` 36×GEMM(105 MiB) | 4.469 ms（4.3%） | 4.818 ms（150.9%） |
| `serial` all_reduce→GEMM | 4.880 ms（20.2%） | 6.699 ms（137.5%） |
| `dep_streams`（**阴性对照**） | **4.627 ms**（8.3%） | **5.529 ms**（109.3%） |
| `indep_streams`（上界） | **4.606 ms**（44.5%） | **5.354 ms**（131.2%） |

## 判决：**无效**，不是 +5.6% / +20.1%

**阴性对照 `dep_streams` 与 `indep_streams` 只差 0.5%（M=1）/ 3.2%（M=64），而格内极差是 8–44% / 109–136%。**
两臂本应相差整个通信量（≈1–2 ms），实际却在同一格内无法区分
⇒ **我显式插入的 `s_comp.wait_stream(s_comm)` 并没有起到串行化作用 ⇒ 两臂测的是同一件事。**
按本项目纪律（"两臂其实完全相同"已被抓到过两次），**这张表只能作为探针失败的证据，不能当作重叠存在的证据。**

## 为什么失败（根因，已用于设计 stage-2）

**我把 dataflow 建错了。** 真实 TP 的依赖链是

```
x → gemm_i → all_reduce_i → gemm_{i+1} → …
```

`comm_i` 依赖 `gemm_i`，而 `gemm_{i+1}` 依赖 `comm_i` —— **严格串行链**。
而 stage-1 的 `dep`/`indep` 两臂里 `comm_{i+1}` **不依赖** `gemm_i`，于是 36 次通信可以自己排成一条流水线，
两条流之间的那个 `wait_stream` 只是把 GEMM 往后排了一点、并没有制造出"通信被计算挡住"的形态。
⇒ 由此得到一条**独立于本次目标的一般教训**：*重叠实验的阴性对照必须是"依赖关系相同、只改并发"*；
只换流而不动依赖，测不到串行化。

## 本次失败仍然产出的两个**可用**事实（这两个有独立证据，不受上述缺陷影响）

1. **背靠背排队的集合通信会被摊销**：`comm_only` = 0.944 ms / 36 = **0.0262 ms/次**，
   而 p27 单发测得的 1 KB all-reduce 是 **0.0548 ms/次**（2.1×）。
   ⇒ 同一个集合通信，"有依赖、必须等" 与 "无依赖、可排队" 相差 2 倍。
   **推论（重要）**：p27 的 0.0548 ms 正是**串行链上的暴露延迟**，用它算出的 3.95 ms/token 税是**对的**；
   任何用背靠背基准（0.026 ms）去估 decode 通信代价的做法都会**低估 2 倍**。
2. **`comp_only` 的极差在 M=1 只有 4.3%，而所有含通信的臂都是 8–137%**：
   在这台 load≈337 的共享机上，**纯计算的短核是稳的，集合通信是不稳的**。
   ⇒ stage-2 必须用**配对**设计（每 rep 内相对基线取比值），不能用跨格中位数比较。
