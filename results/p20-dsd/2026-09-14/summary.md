## 0. 这一轮真正的产出排序（先说重要的）

1. **⛔ S3b：本格的"K=0 档有代价"这一现象已被上游占位并正在修**（§4）⇒ **不立项**。这是本轮最重要的结论。
2. **✅ P1a 否证了原来的主假设 H1** —— 用**K 匹配**的对照（唯一变量是有没有表）测得**表的存在本身零代价**（−0.51%，噪声 3.63%）。这是本项目里少见的**干净否证**。
3. **✅ P3/P5 通过** —— 对照有效：全 K=0 表确实产生 **0** 草稿；跳变表在并发 8 下确实落到 bs≥4 档（31 草稿 vs 4954）。
4. **📏 一组可引用的暖态数字**（并发 8 + 前缀缓存开启，上游 benchmark 未覆盖的条件）：K=3 投机 **+48.5%**、K=1 **+11.2%**、全 K=0 表 **−31.7%**（相对不投机）。
5. **🔧 机制线索（我的，不是引文）**：K=0 档的**每 token 延迟 ≈ 真投机档**（ITL 17.4 ms vs 18.0 ms）而**远差于不投机**（11.9 ms）⇒ K=0 **没有回到普通解码路径**，而是**照付投机路径的每步代价、却每步只吐 1 个 token**。

## 1. 设计（最终版）

**固定**：vLLM 0.29.0 / Qwen3-4B / sm120 / `--max-model-len 8192 --max-num-seqs 32 --gpu-memory-utilization 0.55 --enforce-eager` /

**每臂独立 serve**，每臂先跑 **1 趟预热并丢弃**，再测 **3 次重复**。

## 3. 预登记判据逐条

| 判据 | 结果 | 判定 |
|---|---|---|
| **P1a**（K 匹配：`thr(A6) − thr(A2)`，唯一变量 = 有没有表） | **−0.51%**（噪声 3.63%） | **H1 否证**：表的**存在本身不花钱**。效应也 <3× 噪声 ⇒ 与 0 不可分辨。**这是本轮最干净的一次否证**——因为 A2 与 A6 的 K 完全相同、指令完全相同，只有"表"这一项不同。 |

## 4. ⛔ S3b 判定：**已被上游占位并正在修复 ⇒ 不立项**

在把上面第 4 条（K=0 档的代价）写成候选**之前**做 S3b 检索，直接命中：

| artifact | 状态 | 关键内容 |
|---|---|---|
| **vLLM PR #53426** | **OPEN** | 标题即机制：*"[Core][Spec Decode] **Opt-in skip of the K=0 draft sync forward** (MTP + DFlash, default off)"* ⇒ 上游已认定 **K=0 档仍会跑一次 draft 同步前向**，并已有开关化的修法。**这与我实测的 ITL 特征（17.4 ms ≈ 真投机的 18.0 ms，而非不投机的 11.9 ms）完全吻合。** |
| **vLLM issue #49548** | **OPEN** | *"catastrophic aggregate-throughput collapse under concurrency at the batch-size threshold"*；正文：`[[1,4,2],[5,512,0]]` 使 8 并发从 ~232 tok/s 掉到 **24–157**，且 *"the collapse is specific to concurrency"*；报告者自建仪器 **`VLLM_DSD_K0_DIAG=1`** 逐步记录解析出的 K 与批大小。 |
| **vLLM issue #48494** | OPEN | *"[DSD] incur[s] a **12–25% throughput penalty** vs no-spec … even with an all-K=0 table producing nearly zero draft tokens"* + *"**The presence of the batch-size table is the trigger**; K=0 tiers are not required."* |
| **vLLM PR #47737** | **OPEN** | *"Fix ZeroDivisionError when Dynamic SD schedule includes K=0 for DSpark draft cudagraph capture"* —— K=0 路径本身还有独立缺陷在修。 |

**⇒ S3b 三问**：② **有未关闭的同类性能报告**（#49548、#48494 均 OPEN）✔；③ **上游正在修**（#53426 OPEN，且**已经把机制定位到 "K=0 draft sync forward"**）✔ ⇒ **记 🔴，不立项**。

**⚠️ 一个方法论上值得记下来的细节（本轮最大的意外）**：#48494 的措辞是 *"**The presence of the batch-size table is the trigger**; K=0 tiers are not required."*
—— 它把因果归给**"表的存在"**。而我的 **P1a**（K 匹配）显示**表的存在本身是零代价**（−0.51%），
真正花钱的是 **K=0 这一档**（P1b：−31.7%）。
⇒ **上游那句因果表述与 K 匹配对照的实测不符**；更准确的表述是 *"把 K 设成 0 仍要付投机路径的每步代价"*（也就是 #53426 自己的标题）。
我**不据此主张新课题**（现象与机制都已被占位），但这条"**用 K 匹配对照纠正上游因果措辞**"的做法本身是可复用的。

**我这组数字的独立价值（记录，不立项）**：上游 benchmark（PR #45953）是 **BS1 且关闭前缀缓存**、只报 TPOT；
#49548 用的是 **Qwen3.5-122B MTP / PIECEWISE cudagraph / 静态对比**。
我的是 **并发 8 + 前缀缓存开启 + `--enforce-eager` + dense Qwen3-4B + DFlash2**，并给出**K 匹配对照**与**ITL 分解** ⇒ 属"**在同一现象上补一个上游没覆盖的条件与一个更干净的对照**"。

## 5. 仪器事故与自我更正（三轮网格才拿到可用数据，全部记下）

1. **v1/v2 全轮零产出（18 份 bench 日志 0 字节、0 份结果 JSON）** 的根因：运行器调用
   `python -m vllm.benchmarks.serve`，而该模块在 0.29.0 里**没有 `if __name__ == "__main__":` 块**
   ⇒ **import 后静默退出、退出码 0** ⇒ `|| echo "bench 失败"` **永不触发**。
   正确入口 `python -m vllm.entrypoints.cli.main bench serve`。**教训：断言产物，不要断言退出码**（详见 decision #123）。
2. **连带更正**：我此前记录"`--result-filename` 不存在"**是错的** —— 该结论由同一个静默退出推出。实测该参数存在（`--help=all` 第 185 行），现已启用。
3. **v2 的"热 p50"是伪比较**：p21 实测表明 **dflash 系投机的前缀缓存第 2 遍仍 0 命中、第 3 遍才命中**
   （`request_prefill_kv_computed` 第 2 遍仍 4096/4096、第 3 遍降到 32/4096）。
   故 v2 里 A1 第 2 遍已暖而 A2–A6 到第 3 遍才暖 ⇒ **冷热状态不匹配**（这也是 v2 噪声高达 34–77% 的唯一原因）。
4. **v3 的预热趟修掉了它**：噪声降到 0.36–3.63%。**并且 v3 又独立确认了一次该结构** ——
   即使加了 **1 趟**预热，dflash 臂的 **rep1 仍是冷的**（A2 rep1 = 546 tok/s / TTFT 318 ms，rep2 才 969 / 76 ms）
   ⇒ **需要 2 趟预热**。这是同一现象在第三个实验里的复现。
5. **孤儿进程**：v2 结束后发现一个 **PPID=1 的 `VLLM::EngineCore`（31.8 GB，来自另一个 venv `spec-c6/venv` 0.28.0）**，
   已手工清理；v3 的运行器已加"回收后轮询显存到 ~0 才进下一臂"。
6. **一个本可省掉的混淆**：投机臂的 **KV 容量少 23%**（246,794 vs 不投机的 319,328 token，因 draft 模型占用显存）。
   它不解释 P1a（A2/A6 容量相同），也可能不解释 P1b（24×4096 的工作集在两个容量下都放得下），
   但**凡涉及 A1 vs 投机臂的比较都应记住这一点**。
