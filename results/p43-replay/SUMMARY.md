# p43 —— 真实轨迹在真机上的回放：仪器建成 + 一个推翻我自己 §0.6 的实测

机器：RTX PRO 6000 Blackwell 95.6 GB / vLLM 0.29.0 / Qwen3-4B ｜ 轨迹：Alibaba `qwen_traceB`（真实生产）

## 1. 仪器与噪声地板（这是本轮最有价值的产出）
| 回放 | 到达率 | TTFT p50 | TTFT p95 | e2e p50 | 完成 | **同格噪声** |
|---|---|---|---|---|---|---|
| 基线（1500 条，scale 7，conc 64）×2 | 3.65 req/s | 28.5 / 28.6 ms | 35.8 / 35.7 ms | 399.5 / 399.9 ms | 1500/1500 | **0.4%** |
| **结构忠实**（同上）×2 | 3.65 req/s | 31.63 / 31.23 ms | 65.7 / 63.8 ms | 420.5 / 417.9 ms | 1500/1500 | **1.3%** |

⇒ **专卡噪声地板 0.4–1.3%**（对比 schoolserver 共享机的 132%）⇒ **>4% 的效应即可判定**（3× 噪声）。

## 2. 方法学：**结构忠实的轨迹回放**（本轮必须自己发明的东西）
首版回放用固定文本造 prompt ⇒ **所有请求前缀相同** ⇒ 完全没复现轨迹的前缀共享结构，
而结构正是本实验的全部意义（于是 TTFT 恰好等于"完全未命中"的 prefill，毫无信息）。
**修法**：按 `hash_ids` 逐块构造——块 id 确定性展开为 16 个 token，prompt = 各块顺序拼接，
以 token id 列表直接发送。**轨迹里共享的块在 prompt 里也共享。**
实测：1500 条、平均 851 token（53 块）、共享块 37,481/79,863 = **53%**（与仿真一致）。

## 3. 配置回读（断言产物真的生效）
`/metrics` 的 `cache_config_info`：`block_size=16`、`enable_prefix_caching=True`、
**`num_gpu_blocks=34207`**、`kv_cache_size_tokens=547312`、`kv_cache_max_concurrency=66.8`。
**`prefix_cache_queries=4,937,949` tokens、`hits=3,720,192` ⇒ 命中率 75.3%。**

## 4. ⚠️ 推翻我自己 §0.6 的实测
我此前用 **prefill 代价 = token 数 × 32.6 µs** 估"缓存能省多少"，据此算 traceB 的缺口值 4.8–9.1%。
**但真机实测**：命中率 75.3% ⇒ 真正的 prefill 计算只剩 851×0.247 ≈ **210 token ≈ 6.8 ms**，
**而 TTFT p50 = 31.4 ms**。⇒ **TTFT 有一个约 24 ms 的非 prefill 地板**（与小批下每步 ~5 ms 的
调度/起步延迟一致），**缓存省下的 prefill 在这条负载上根本不是 TTFT 的主要成分。**

⇒ **缓存/驱逐这条轴现在三重出局**：
① 可达性：简单在线策略补 0–35% 缺口、会话感知为负（p41/p42）；
② 占位：可达部分由 KVLearn（SYSTOR '26）声称解决；
③ **服务器实测：end-to-end 不由 prefill 决定**（本轮）。

## 5. 仪器已知限制（下一轮必须修）
`/metrics` 是**累计值**，而本轮跑了两条不同配置的回放 ⇒ 无法拆出每臂的命中率。
**修法**：每臂前后读取计数器取差，或每臂重启引擎。这是任何干预对照的前置条件。

## 6. 服务端记录
`setsid nohup … < /dev/null > log 2>&1 &` 是让 ssh 会话立即返回的可行模式（直接 `nohup … &` 会因继承 stdout 而挂住会话）。
